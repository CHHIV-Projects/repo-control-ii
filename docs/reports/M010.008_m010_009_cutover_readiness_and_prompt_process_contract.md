## Future approved-prompt process contract

This is a future acceptance requirement, not a current Coder permission or a
change to installed bootstrap behavior.

1. A Product Owner explicitly approves and selects one exact prompt revision
   for one repository/milestone. The binding is the canonical repository ID,
   registry key/root, milestone ID, prompt document/revision IDs, content
   SHA-256, current selection revision, and live lifecycle approval.
2. The approved prompt **need not have a separate Git commit** before the
   Coder starts. Under DB authority, the prompt is read as the immutable,
   versioned database revision; a Git file is neither a prerequisite nor an
   alternate source of authority.
3. Coder preflight must compare its expected verified binding to the active
   Repo Control selection. It accepts only the expected approved revision and
   exact hash, with an explicit live lifecycle authorization. A stale
   approval, changed hash, wrong revision, repository, or milestone fails
   closed.
4. If the future implementation still materializes the prompt in the
   worktree, the only prompt-related dirty entry it may allow is that exact
   selected canonical path with bytes matching the approved revision/hash.
   Any unrelated staged, unstaged, untracked, or conflicted path must still be
   rejected or escalated under the approved policy. Do not globally relax
   Git cleanliness checks.
5. Tests must cover uncommitted expected prompt + clean remainder (accept),
   changed bytes/hash, wrong selection/revision, stale or absent lifecycle
   approval, wrong repository/milestone, and each form of unrelated dirty
   worktree (reject). If DB authority is not active, current filesystem,
   Git, and lifecycle semantics remain unchanged.

  grant a clean-tree exception for prompts.
- [`src/repoctl/workflow/milestones.py`](../../src/repoctl/workflow/milestones.py)
  currently validates the selected prompt as a contained file under the
  configured milestone root and rediscovers it from filesystem candidates.
  Selection resolution must become DB-revision-aware only in the approved
  authority transition.
- [`src/repoctl/workflow/coder_interface.py`](../../src/repoctl/workflow/coder_interface.py)
  resolves the registry selection and `get_coder_context` reads prompt bytes
  from the worktree. A future adapter must instead resolve the exact approved
  database revision and expose its source/hash without path fallback.
- [`src/repoctl/workflow/context_verification.py`](../../src/repoctl/workflow/context_verification.py)
  currently hashes the selected filesystem prompt and records the observed
  Git dirty-entry snapshot. A future verification record must bind the DB
  revision/hash and distinguish only the exact expected prompt artifact from
  unrelated dirty state.
- Existing ordinary Git mutation safeguards remain separate:
  [`src/repoctl/workflow/commit_plan.py`](../../src/repoctl/workflow/commit_plan.py)
  and [`src/repoctl/workflow/commit_execution.py`](../../src/repoctl/workflow/commit_execution.py)
  reject unstaged/untracked changes for their commit contract; Git Review
  also retains its explicit path selection and confirmation flow. These are
  not to be weakened to implement the prompt requirement.

The inspected `coder_interface` path validates that the selected repository
is a managed Git worktree; it does not itself impose a blanket clean-working-
tree requirement. The current bootstrap asks the Coder to inspect and
classify dirty paths, while context verification records them. The future
change is therefore a narrowly bound source-resolution/expected-prompt
exception, not removal of a current universal clean-tree gate.
