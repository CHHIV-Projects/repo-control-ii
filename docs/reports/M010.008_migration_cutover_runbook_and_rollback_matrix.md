   revision/hash, and live lifecycle authorization through Repo Control.
2. Record SHA-256 of `ops/repositories.toml`, the selected prompt, its
   workflow source, each available closeout, the current selection pointer,
   the dispatch ledger, and every other source in the approved inventory.
   Record missing sources as absent; do not synthesize approvals, event-time
   hashes, links, or decision history.
3. Use the exact service/CLI interpreter that will run Repo Control. Require
   SQLite `>= 3.51.3` or a separately documented and verified fixed backport.
   The observed interpreter here is Python 3.12.3 at
   `/home/chuck/projects/repo-control-ii/.venv/bin/python`, linked to SQLite
   3.45.1 (`NOT PRODUCTION ELIGIBLE`). Stop rather than weakening the gate or
   upgrading the environment without separate operator approval.
4. Product Owner/operator defines the absolute database path, parent
   directory, service UID/GID, restrictive file/directory permissions,
   backup location, restore procedure, schema ID/version, and startup/runtime
   gate. Confirm there is no existing file, symlink, conflicting database, or
   second writer at the target.
5. Inventory all writers and readers to be quiesced or switched together:
   browser routes, CLI commands, Architect proposal/dispatch handlers, Coder
   context/verification, milestone selection, workflow/sidecar recording,
   background jobs, and any running service process. A partial client switch
   or dual write is a NO-GO.
6. Confirm the existing Git Review process remains the only Git mutation
   path. The closeout publisher may hand an exact materialized revision to
   Git Review but may not stage or commit it.

## Operator sequence

### A. Quiesce and snapshot

1. Announce a maintenance window and stop accepting new workflow mutations.
   Quiesce every identified writer using the approved operator procedure;
   verify no writer is active. Do not stop or restart a live service as part
   of this M010.008 rehearsal.
2. Preserve legacy files and external state in place. Capture a read-only
   inventory with exact paths, byte counts, SHA-256 hashes, repository
   identity, milestone ID, source owner, and provenance. Do not relocate or
   rewrite source files.
3. If an authoritative DB already exists in the separately approved future
   operation, take its backup through SQLite's supported online backup API.
   Record the source database identity, schema/application IDs, backup time,
   and operator. Verify the backup copy using `PRAGMA integrity_check`,
   expected schema/version, repository/milestone identity, and a read-only
   reopen. Do not copy a live WAL database with an ad-hoc file copy.
4. Test restore to a separate disposable path before cutover. Compare schema,
   integrity, source hashes, ordered event IDs/JSON, reducer projection, and
   exact document revision hashes. Record snapshot age and the maximum
   activity that a restore could lose. A successful backup without a
   verified restore is NO-GO.

### B. Import and parity gate

1. Re-resolve the registry entry and live selected milestone; bind every
   import to repository ID/key/root and the exact prompt path/revision/hash.
2. Import only validated, read-only source copies. Keep `central_operational`
   dispatch bytes separate from `git_owned` prompts, closeouts, workflow
   sidecars, and project context. Legacy numeric IDs remain text/history;
   never coerce them into the canonical M/R InformationStore identity.
3. Require an exact source manifest and deterministic receipt. Verify prompt
   and closeout bytes/hash, event JSON/hash/order/IDs, the existing lifecycle
   reducer result, and dispatch status snapshots. A reported actor or current
   dispatch status is not proof of Product Owner identity or historical
   decision. Add links/approval records only where the source contains
   evidence that supports them.
4. Re-run the exact import to verify idempotency. Refuse changed bytes,
   malformed or ambiguous identities, duplicate/conflicting sources,
   cross-repository paths, or any mismatch. Report every absent, unreadable,
   unparseable, or unsupported source; never call a partial inventory
   complete.
5. While all writers remain quiesced, run read-only integration probes for
   the browser, Coder, Architect, search/paging/export, lifecycle, dispatch,
   and publication handoff. Require exact revision/hash parity and complete
   continuation flags. Review the intended reader/writer adapter map and
   verify no legacy writer remains enabled for a DB-owned record.

### C. Single-authority decision and verification

1. Stop before the first DB-authoritative write for a final Product Owner
   GO/NO-GO decision. Confirm runtime eligibility, verified backup/restore,
   source inventory and import parity, selected identity, access permissions,
   reader probes, recovery owner, and explicit acknowledgement of possible
   post-backup activity loss.
2. On GO, switch the approved readers and writers as one bounded operation.
   Use one authoritative DB for DB-owned prompts, workflow events,
   approvals/links, closeout revisions, and dispatches. Retain legacy files
   as read-only historical evidence; do not dual-write or automatically fall
   back to stale sidecars. Keep Git-owned governing/project context and
   procedures under their existing Git owner unless a later approved
   architecture explicitly changes that boundary.
3. Before reopening writes, verify the live repository/milestone binding,
   selected approved prompt revision/hash, lifecycle projection and
   authorization, dispatch source status, exact document reads, and source
   ownership labels through every enabled interface. Run a read-only Git
   status check and confirm that no procedure, registry, branch, remote, or
   Git authority changed.
4. Product Owner records GO and accepts the observed post-cutover state.
   Otherwise keep writers quiesced and follow the matrix below. Do not let a
   timeout, ambiguous response, or unavailable reader silently select an old
   source.

## Rollback / recovery decision matrix

| State when a fault is found | Required action | Forbidden shortcut |
|---|---|---|
| Before any DB-authoritative write; legacy sources untouched | Abort the attempt. Leave DB unused, re-enable the existing legacy workflow only after confirming the old selection and sources are unchanged. Record the failure and retry only after correction and a new PO GO. | Do not edit or “repair” legacy sources as a cutover side effect. |
| Import or parity fails while writers are quiesced | Stop before the authority flip. Preserve the failed disposable DB and mismatch report for diagnosis; continue only after corrected source evidence and a full parity rerun. | Do not waive missing events, hashes, identities, or approvals. |
| DB authority has been enabled but no DB-authoritative activity was accepted | Quiesce all writers again. Product Owner may authorize return to untouched legacy authority only after proving the DB accepted no authoritative write and all legacy sources remain unchanged. | Do not infer “no writes” from a UI timeout; inspect durable receipts and events. |
| At least one DB-authoritative write may have been accepted | Keep the DB authoritative or enter a PO-approved recovery state. Preserve a read-only copy of the current DB and logs; inspect receipts/events; use a verified consistent backup only with explicit Product Owner acknowledgement of activity/data loss and a bounded reconciliation plan. | Never silently switch back to stale sidecars, replay old events as current, or overwrite newer DB state. |
| Runtime, permissions, backup, or restore check fails after cutover | Quiesce new writes, preserve the current DB and evidence, and have the PO/operator choose repair on the eligible runtime or a verified restore with the loss window recorded. | Do not weaken the SQLite version gate, copy live WAL files ad hoc, or fall back automatically. |
| Git publication acknowledgement is ambiguous | Use existing Git Review's read-only status, blob, and commit-tree checks for the exact path/revision/hash. Resume only after PO review of the evidence. | Do not auto-stage/recommit or associate a commit without exact blob verification. |

Every restore decision records source snapshot identity/time, current DB
identity, lost/replayable activity window, operator, PO acknowledgement, and
verification outcome. No custom WAL-recovery or replication mechanism is
introduced.

## M010.008 limitations carried forward

- No live DB, service or host runtime was changed; no database-authoritative
  write or authority flip was performed.
- Current SQLite 3.45.1 is below the 3.51.3 production floor. Any runtime
  upgrade must be a narrow, operator-mediated, separately approved change to
  the exact venv/service interpreter, followed by runtime and regression
  checks; do not install packages as part of this rehearsal.
- A disposable backup/restore test does not establish production restore
  time, recovery-point objective, service permissions, or supported-runtime
  behavior.
- Historical committed Git objects, inaccessible repositories, and
  unsupported document types are outside the current provider inventory and
  must remain explicitly NOT VERIFIED.
