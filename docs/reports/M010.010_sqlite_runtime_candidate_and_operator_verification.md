## Operator sequence — only after separate approval

1. Keep the active service and `.venv` untouched. After approval, use a
   disposable source/build directory and the versioned prefixes below:

   ```bash
   BUILD_ROOT="$HOME/.cache/repoctl-sqlite-3.51.3"
   SQLITE_PREFIX="$HOME/.local/opt/sqlite-3.51.3"
   PYTHON_PREFIX="$HOME/.local/opt/python-3.12.16-sqlite-3.51.3"
   CANDIDATE_VENV="$HOME/.venvs/repo-control-python-3.12.16-sqlite-3.51.3"
   mkdir -p "$BUILD_ROOT" "$SQLITE_PREFIX" "$PYTHON_PREFIX"
   cd "$BUILD_ROOT"
   curl -fSLO https://www.python.org/ftp/python/3.12.16/Python-3.12.16.tar.xz
   printf '%s  %s\n' \
     b5796915dc45ff745cfb4e990a7e7c93d6f546328a102ce31448d69ebc37575c \
     Python-3.12.16.tar.xz | sha256sum -c -
   curl -fSLO https://sqlite.org/2026/sqlite-autoconf-3510300.tar.gz
   printf '%s  %s\n' \
     81f5be397049b0cae1b167f2225af7646fc0f82e4a9b3c48c9ea3a533e21d77a \
     sqlite-autoconf-3510300.tar.gz | sha256sum -c -
   tar -xzf sqlite-autoconf-3510300.tar.gz
   python3 -c 'import hashlib,pathlib,sys; p=pathlib.Path(sys.argv[1]); print(hashlib.sha3_256(p.read_bytes()).hexdigest()); assert hashlib.sha3_256(p.read_bytes()).hexdigest() == "32d5424f97e0a7fc5ed2f6335afbb58be4e0298bd7117a34e39d345ff13d859e"' \
     sqlite-autoconf-3510300/sqlite3.c
   ```

   Stop if either source verification fails. `python3` above is only a
   verification utility; the candidate build itself must use the pinned
   CPython source.
2. Build SQLite, then CPython against that exact prefix:

   ```bash
   cd "$BUILD_ROOT/sqlite-autoconf-3510300"
   ./configure --prefix="$SQLITE_PREFIX" --disable-static
   make -j2
   make install
   PKG_CONFIG_PATH="$SQLITE_PREFIX/lib/pkgconfig" pkg-config --modversion sqlite3
   tar -xf "$BUILD_ROOT/Python-3.12.16.tar.xz" -C "$BUILD_ROOT"
   cd "$BUILD_ROOT/Python-3.12.16"
   CPPFLAGS="-I$SQLITE_PREFIX/include" \
   LDFLAGS="-L$SQLITE_PREFIX/lib -Wl,-rpath,$SQLITE_PREFIX/lib" \
   PKG_CONFIG_PATH="$SQLITE_PREFIX/lib/pkgconfig" \
     ./configure --prefix="$PYTHON_PREFIX" --enable-optimizations
   make -j2
   make install
   ```

   Require `pkg-config --modversion sqlite3` to print `3.51.3`. Do not copy
   libraries into `/usr`, edit the active venv, or change systemd.
3. Create a sibling venv, install the project from its approved manifest, and
   run the exact probe and focused tests:

   ```bash
   "$PYTHON_PREFIX/bin/python3.12" -m venv "$CANDIDATE_VENV"
   "$CANDIDATE_VENV/bin/python" -m pip install -e /home/chuck/projects/repo-control-ii
   "$CANDIDATE_VENV/bin/python" \
     /home/chuck/projects/repo-control-ii/ops/verify_sqlite_runtime.py
   SQLITE_EXTENSION="$("$CANDIDATE_VENV/bin/python" -c 'import _sqlite3; print(_sqlite3.__file__)')"
   ldd "$SQLITE_EXTENSION"
   cd /home/chuck/projects/repo-control-ii
   PYTHONPATH=src:. "$CANDIDATE_VENV/bin/python" -m unittest -q \
     tests.test_information_store tests.test_information_store_fixture \
     tests.test_approved_prompt_preflight tests.test_migration_rehearsal \
     tests.test_store_authority tests.test_architect_mcp
   ```

   Require exit 0, `production_eligible: true`, SQLite >= 3.51.3, the
   expected SQLite source ID, and a `loaded_sqlite_libraries` path under the
   pinned SQLite prefix. Also inspect `ldd` for the candidate `_sqlite3`
   extension and run the focused InformationStore and application regression
   tests under this exact interpreter. `pyproject.toml` currently specifies a
   Flask version range, not a fully locked dependency set; dependency
   reproducibility remains an operator prerequisite. Record actual output;
   the runtime probe alone is not regression evidence.
4. If any build, link, version, or test check fails, stop and leave the
   existing service and venv unchanged. A future service switch requires
   separate PO approval, a planned sibling venv path, exact systemd diff,
   backup/restore readiness, and an operator-controlled restart/rollback.

## Separately authorized cutover and recovery checklist

These are Product Owner/operator actions, not instructions to activate now.
Use the eligible candidate interpreter consistently for every command, and
consult `repoctl store-authority <action> --help` for exact arguments.

1. Confirm all registered roots, identities and selections; review source
   exclusions and the two qualified historical mappings. Obtain the eligible
   runtime and verified service/CLI deployment, completed procedure release,
   Git Review probe, DB/backup locations and permissions, restore owner, and
   an agreed recovery-point/loss window. Back up the legacy source and state
   images, including selection pointers. Quiesce **all** old and new browser,
   CLI, MCP, background and service writers; old processes cannot be trusted to
   enforce a newly installed authority guard.
2. With the canonical registry and external state root, run
   `store-authority prepare --registry <registry> --state-root <state-root>
   --destination <empty-outside-repositories-directory> --writers-quiesced`.
   Review its complete inventory, source/event/dispatch parity, refusals,
   exclusions and prepared database path. Preserve the exact report. The
   command requires an exact v1 selection for every registered repository.
3. For each exact `prepared_selection_bindings` object from that report, run
   `store-authority bind-selection --registry <registry> --state-root
   <state-root> --database <prepared-db> --binding-json '<exact-object>'
   --po-confirm`. This deliberately extends each external selection pointer;
   preserve the original pointer bytes and keep writers stopped.
4. Choose an explicit 32-character lowercase hexadecimal generation and run
   `store-authority preview --registry <registry> --state-root <state-root>
   --database <prepared-db> --generation <generation>`. Review its exact
   registry, database, selection, inventory and `plan_sha256` bindings. On an
   explicit PO GO, run `store-authority activate` with those same arguments,
   `--expected-plan-sha256 <reviewed-hash> --po-confirm --writers-quiesced
   --source-parity-confirmed`. An interrupted/partial switch must remain
   stopped until its guard, marker and plan are reconciled; never fall back
   merely because activation returned an error.
5. Before reopening writes, restart/deploy every consumer under the approved
   eligible runtime and verify each service and client reports the same
   database, generation, registry, repository, selection and exact prompt
   binding. Imported prompt approvals and approved guidance are unverified
   historical claims: the PO must explicitly confirm each exact current
   revision/guidance as needed. Those confirmations are managed writes.
6. Make SQLite-consistent backups through the online backup API, verify
   `integrity_check`, `foreign_key_check`, schema, identity, events and
   revision hashes, and rehearse a restore in a separate location. Quiesce
   consumers and account for WAL and database identity during any real restore;
   the fixture restored a latest consistent backup to the same database, not
   damaged-WAL recovery or a production recovery-point guarantee.
7. Before any managed write, a reviewed `store-authority abort` with the same
   generation and plan hash, `--po-confirm --writers-quiesced`, may return to
   legacy authority only after source parity and no-write checks pass. After a
   write or a conservatively marked selection-switch attempt, **do not** use
   stale sidecars as authority; preserve evidence and recover the SQLite
   authority or pursue a separately approved audited reverse export. For an
   interrupted selection switch, use `preview-selection-recovery`, review the
   exact plan, then `recover-selection --expected-plan-sha256 <hash>
   --po-confirm`; both are restricted to the matching registered repository.
