## Persistence and Bounds

Dispatches are stored as repository-scoped operational JSON outside the repository at:

`<state_root>/<repository_id>/architect_dispatches.json`

This reuses Repo Control's external state root and `STATE_ARTIFACT_LOCK`; ledger updates use same-directory temporary files, `fsync`, and atomic replacement. No database or new service was introduced. Pending records are retained rather than silently pruned.

Explicit limits:

- body: 64 KiB UTF-8;
- title: 200 characters;
- retained records: 50 per repository;
- `repo_dispatches` list results: at most 5, with lookup by durable dispatch ID for a single result;
- ledger: 8 MiB.

## Architect MCP Interface

The ten existing evidence tools retain their GET-only semantics. Four separate tools were added:

- `architect_submit_prompt_draft` → `POST /api/architect/v1/dispatches/prompt`;
- `architect_submit_instruction_draft` → `POST /api/architect/v1/dispatches/instruction`;
- `architect_submit_response_draft` → `POST /api/architect/v1/dispatches/response`;
- `repo_dispatches` → bounded `GET /api/architect/v1/dispatches`.

Submission calls require repository-key and registry-generation preconditions. INSTRUCTION and RESPONSE proposals must target the selected, non-closed milestone. A RESPONSE event reference, when supplied, must belong to that active milestone. Submission creates only a PENDING proposal; the adapter exposes no approval, arbitrary path, shell, Git, or lifecycle-event operation.

Readback returns repository-scoped dispatch metadata and complete bounded content, including PENDING / APPROVED / REJECTED status. Results can be filtered by milestone or status, capped to five entries, or retrieved by dispatch ID.

## Product Owner Approval and PROMPT Boundary

The `/architect-dispatches` Repo Control page displays the complete proposed body and metadata. Its CSRF-protected browser actions are `Approve & Send` / `Approve & Save Prompt` and `Reject`; stale repository submissions are rejected. Approval is not exposed through Architect MCP.

PROMPT approval derives a canonical `.md` filename from validated milestone ID and title under the configured milestone root. The destination is shown before approval. Creation uses a same-directory temporary file, `fsync`, and atomic no-overwrite hard-link creation; symlink escapes and existing milestone-ID collisions are rejected. Approval does not select the milestone, record `prompt_approved`, start lifecycle work, or change Git.

INSTRUCTION / RESPONSE approval only changes dispatch state. It does not record lifecycle events. Repeated approval is safe; rejected proposals cannot later be approved or materialized.

## Coder Consumption

`repoctl coder-context` adds a separate **APPROVED ARCHITECT DISPATCHES** section. It includes only approved INSTRUCTION / RESPONSE records whose approved milestone matches the active selection, with deterministic milestone-local aliases (`A1`, `A2`, …). Pending, rejected, prompt, other-repository, and other-milestone records are excluded. Coder status and lifecycle semantics remain unchanged.
