## 4. Architecture / Integration Notes

### Host and discovery evidence

The current local repository evidence shows:

- Both worktrees contain `.agents/skills/<skill-name>/SKILL.md`.
- Neither worktree contains root `AGENTS.md`, `.github/copilot-instructions.md`,
  `.github/instructions/`, or `.vscode/` workspace settings.
- The `coding_agent_rules.md` documents live under `docs/context/`; those paths
  are not one of the documented standard workspace instruction locations
  found in the official VS Code material consulted.
- Vocab bootstrap/workflow link to the same local `.agents/skills` copies.
  Repo Control II bootstrap says to load the applicable Skill explicitly.

The official [VS Code Agent Skills documentation](https://code.visualstudio.com/docs/agent-customization/agent-skills)
lists `.agents/skills/` and `.github/skills/` as supported project Skill
locations and `~/.agents/skills/` / `~/.copilot/skills/` as user-level
locations. It says discovery makes Skills available but does not guarantee
their invocation. It does not establish a supported symlink contract.

The official [VS Code custom-instructions documentation](https://code.visualstudio.com/docs/agent-customization/custom-instructions)
describes `.github/copilot-instructions.md`, `AGENTS.md`, and
`.github/instructions/**/*.instructions.md`, with activation depending on the
selected harness and, for some Local-harness paths, settings. The
[GitHub Copilot support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support)
also distinguishes supported customization types by environment. The
deprecated `chat.agentSkillsLocations` setting is not a durable common
mechanism across current Copilot harnesses.

The selected VS Code harness, effective user/profile instructions, parent
workspace customizations, and actual loaded instruction set were not
inspectable from these repository files. Therefore:

- deterministic repository evidence establishes a missing repository-local
  standard bootstrap entrypoint in both checkouts and identical project Skills;
- the fresh Repo Control II PASS and Vocab FAIL are Product Owner-reported
  observations, not independently reproduced in this session;
- no causal link between those observations and a particular file difference
  is established;
- symlink traversal by the coding host and automatic discovery of an external
  shared directory remain unsupported/unverified assumptions and should not
  be acceptance dependencies.

### Generic shared core versus local overlay

Recommend a focused shared Repo Control procedure bundle, not wholesale
centralization of either current workflow document.

**Centrally governed generic core:**

- minimal-handoff semantics and mandatory fresh context retrieval;
- canonical managed-repository CLI invocation and identity verification;
- lifecycle/authorization and approved-dispatch interpretation;
- read-only Git preflight and absolute no-Git-mutation rule;
- authority ordering, pre-work feedback, stop/escalation rules;
- generic Skill routing and loading expectations;
- evidence, validation, closeout, review, and correction boundaries.

**Repository-specific overlays:**

- repository identity and project-specific worktree/context references;
- production data/runtime/service boundaries;
- project-specific architecture constraints, model/data authority, and
  prohibitions;
- test commands and validation prerequisites;
- temporary migration constraints only while demonstrably active.

`project_context.md` and `project_architecture.md` remain project-local.
`canonical_parking_lot.md` remains project-local planning authority. The
Repo Control II `project_workflow.md` should remain a comprehensive
human-readable description of Repo Control II's own implementation and
operational model; a managed project's workflow should be a small overlay with
a verifiable reference to shared generic procedure, not a copy of all 1,566
lines. `coding_agent_rules.md` should remain the repository-specific bootstrap
overlay/source for project constraints, while a host-recognized bootstrap
entrypoint supplies the always-on generic instructions. `.agents/skills/**`
should be generated/materialized from canonical generic Skill sources.

### Governance models considered

| Model | Benefits | Risks / evidence | Disposition |
|---|---|---|---|
| Host/user-level shared directory or central absolute-path references, with no repository materialization | One physical copy; low per-repository file count | Depends on per-host/profile setup and path access; not self-contained or naturally reviewable in each repo; user-level policy can leak across repo boundaries; host does not automatically load arbitrary central docs; local instruction-location settings vary or are deprecated | Do not use as sole source-delivery mechanism. Could be an operator convenience only after tested host configuration. |
| Symlink each repository's supported Skill/instruction path to central files | Avoids content copies and preserves apparent local locations | Official documentation consulted does not guarantee symlink handling; targets depend on a shared host path, break in clones/other hosts, complicate isolation and Git review, and do not solve host bootstrap discovery by themselves | Reject as a required mechanism unless a later explicit host compatibility test proves it reliable. |
| One versioned canonical bundle plus PO-reviewed generated/materialized workspace copies and a separate local overlay | Host-supported local paths; self-contained worktrees; deterministic content comparison; normal Git diff/review; new and existing repos use the same release | Generated copies still exist and require explicit upgrade/reconciliation; a hash detects but does not prevent model non-compliance | **Recommend.** This best balances host discovery, repository portability, deterministic drift detection, and PO review. |

The recommended source is one versioned procedure bundle maintained in Repo
Control II, containing only generic bootstrap/workflow modules and the three
Skills. Managed repositories receive:

1. a short generated host-recognized always-on instruction/bootstrap file
   (target `.github/copilot-instructions.md` for the current Copilot-in-VS-Code
   deployment, subject to explicit setting/harness verification);
2. physical generated `.agents/skills/<name>/SKILL.md` files from the same
   release, because they are a documented workspace Skill location and
   symlink support is not established;
3. an independently maintained project overlay and minimal project workflow,
   never included in the generic source hash and never overwritten by generic
   reconciliation.

Keep a small per-repository manifest/lock recording the canonical release,
manifest schema, each generated generic file's SHA-256, overlay schema/version,
and the expected host entrypoint. The project-specific overlay must not
override lifecycle, Product Owner, Git, or central-state authority. The
materializer should produce a proposed diff; it must not silently write
managed repositories.
