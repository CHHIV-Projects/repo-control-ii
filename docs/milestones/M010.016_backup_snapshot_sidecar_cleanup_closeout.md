## 2. Resulting Behavior

- **Root cause reproduced on the pinned runtime.** Python 3.12.16 / SQLite 3.51.3 read-only validation of WAL-mode temporary databases created a zero-byte `-wal` and a 32 KiB `-shm`. Backup cleanup removed only the database partial itself. After the remote partial was renamed, its partial-named sidecars remained. Restore verification similarly left sidecars beside the published backup and temporary restore database.
- Cleanup now tracks the exact SQLite sidecar paths for each operation-owned snapshot, partial, or restore temporary. It removes only newly appearing regular sidecars after their SQLite connections have closed, and only when any WAL file is empty. Unexpected pre-existing sidecars and non-empty WAL files are preserved and fail closed; no wildcard cleanup is used.
- Restore validation holds a nonblocking exclusive lock on its manifest for the duration of the operation, so another Repo Control restore cannot remove sidecars while the first restore is using the same backup.
- The source database was verified to remain in WAL mode with both committed workflow events intact. The backup and restore continue to pass identity, integrity, foreign-key, selection, workflow, and document-hash validation.

## 4. Architecture / Integration Notes

- The backup still uses SQLite's Online Backup API and preserves the source journal mode; cleanup applies only to exact sidecar names derived from operation-owned temporary copies.
- Finalized backup validation refuses sidecars that existed before that validation. Restore operations serialize on the manifest and remove only sidecars created during the locked operation.
- The monitor path was not changed; it checks manifests and database bytes without opening SQLite connections.
