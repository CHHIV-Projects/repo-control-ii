## 2. Resulting Behavior

- The Git Review form renders the authoritative stage and action bounds rather than duplicated literals.

- The JavaScript URL includes a SHA-256 content version so changed assets use a new URL.
- When commit preparation is available, the file list shows the staged count and links to the existing commit review and message form. When unavailable, the exact `can_commit` reason is shown beside the list, without a dead link.
- Confirming a stage action returns to the changed-file heading. Staging does not start commit preparation or bypass the existing confirmation flow.

## 4. Architecture / Integration Notes

- The reproduced `NaN` condition was a served-template/current-script mismatch: the live Git Review HTML had `data-max-paths="256"` and no `data-max-path-bytes`, while the served JavaScript read `dataset.maxPathBytes`. Converting the absent value produced `NaN`. The current source template had the byte attribute, and the running service predated the current template; this supports stale process/template deployment skew. Browser caching alone was not established as the cause.
- Read-only inspection of the live Git Review page showed the existing commit availability reason: “There are no explicitly staged changes to commit.” A staged worktree was not manufactured because Coder Git mutations are prohibited.
- **Repository Intelligence: NOT USED** — the route, template, JavaScript, and authoritative limit constants were directly traceable, and focused mocked-route/browser checks supplied the needed evidence. `coder-intelligence stats` reported `STALE` with reason `supported_source_inputs_changed`; the graph was built at `2026-11-12T05:11:04.660390+00:00` against the pre-change source. Refresh was considered but not attempted because the change is localized and direct evidence was sufficient. No structural query or refresh receipt informed the implementation.
