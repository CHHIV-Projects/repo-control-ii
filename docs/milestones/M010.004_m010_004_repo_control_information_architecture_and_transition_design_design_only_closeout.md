### Document revision and lifecycle contract

Use repository-qualified stable `document_id` and immutable `revision_id` values. A document record identifies repository ID, logical document key/type, optional milestone ID, source/origin path, and current draft/approved revision pointers. Each UTF-8 Markdown revision stores its full content, SHA-256, parent revision, creation time, reported author/source, provenance, and optional source commit/blob or migrated source hash. Saving an edit creates a new revision; never overwrite approved content. Approval/review is a separate append-only decision/link record that identifies the exact revision and actor-attribution/PO-confirmation evidence. Actor labels remain reports, not authenticated identity.

The minimum logical tables are: `repository` and `milestone` identity; `document` and immutable `document_revision`; versioned `workflow_event` rows plus revision/projection state; `workflow_document_link` from lifecycle event IDs to prompt/closeout revision IDs and hashes; `architect_dispatch` plus append-only status decisions; idempotent `transaction_receipt`; and a small `document_publication` record. Keep indexes for repository/milestone/type/status/revision/time and event sequence. Store complete event JSON and exact source IDs/timestamps/order/attribution/binding fields. Use schema/application IDs and explicit migration versions; reject unknown/newer schemas and stale prompt/revision identities.

Links from events do not rewrite old payloads. New prompt approval links the selected prompt revision; closeout submission and acceptance each link the exact closeout revision; dispatch decisions link any related document/event revision. For imported v1 records, retain exact event JSON and add only links justified by available path/hash evidence. Record the source sidecar/file hash; do not invent event-time prompt hashes or historical draft transactions that the source never stored. Preserve all 21 event types and six lifecycle phases through the existing reducer.

An application-owned facade should provide:

```text
list_documents(repository, filters, cursor)
get_revision(document_id, revision_id)
read_revision_page(document_id, revision_id, byte_offset, content_hash)
compare_revisions(document_id, left_revision_id, right_revision_id)
create_draft(document_id, base_revision_id, markdown, request_id)
submit_revision(document_id, revision_id, expected_store_revision, request_id)
approve_revision(document_id, revision_id, explicit_po_confirmation, request_id)
append_workflow(identity, expected_revision, request_id, events, document_links)
page_workflow(identity, snapshot_revision, cursor, limit)
search_documents(repository_ids, milestone/type/status filters, query, cursor)
export_revisions(revision_ids)  # read-only Markdown download
```

Full-content responses include repository/milestone/document/revision IDs, source path or origin, SHA-256, authority class, approved/draft state, observed/current version, and next byte offset. Bound page size and result counts; bind continuation to exact revision/hash so a changed or stale page fails explicitly. Search is scoped and paged over authoritative text; any full-text index is rebuildable derivative data. Bulk Markdown export is a read-only snapshot with a manifest of IDs/hashes and clear central-vs-Git authority labels. No DB filename/path or arbitrary filesystem path is exposed to clients.

Within SQLite, document revision links, lifecycle event append, receipt, and projection update commit atomically. Use `BEGIN IMMEDIATE`, expected revision and stable request ID/hash; exact retry returns its original receipt and reused ID with different content fails. The lifecycle reducer owns semantics, not SQL. Preserve explicit PO confirmation, binding rules, waiting/question/bug/escalation resolution, acceptance/closure/reopen, and current dispatch-vs-closeout guard. The SQLite runtime gate is an explicit startup/preflight check against `sqlite3.sqlite_version_info`: require at least 3.51.3 or a specifically documented fixed backport. The observed environment is SQLite 3.45.1 and does not meet the conservative gate. M010.004 makes no upgrade/install.

The browser gains a repository-aware Document Library: browse/filter by repository, milestone, type, status, and revision; view exact Markdown; compare revisions; search; download one or a bounded selection. Architect keeps bounded read-only search/get/version tools, with full content through stable IDs and range paging. Coder keeps live `coder-context` authority and gets bounded `coder-read-document` access for selected exact versions, rather than receiving broad pasted documents. The MCP and CLI responses identify draft, approved, historical, Git-sourced, or generated-cache authority explicitly. Role-limited editing/approval remains PO-controlled; read access does not confer write authority.

### Accepted closeout → optional Git publication

Keep acceptance and publication as two different, visible decisions:

1. Coder submits a closeout revision to Repo Control. The submission records the exact `revision_id` and SHA-256 and moves lifecycle to REVIEW through the existing transition.
2. The Product Owner reviews and accepts/closes that exact revision. Acceptance is not a Git action and does not imply publication.
3. If desired, the Product Owner separately selects **Publish accepted closeout to Git**. Repo Control shows the target repository/path, source revision/hash, current branch and HEAD, whether this is an existing published version, and the complete deterministic Markdown diff. It identifies an optional related code/reconnaissance commit context but does not choose or create a commit.
4. On explicit confirmation, Repo Control materializes the exact accepted Markdown revision at the canonical milestone path as an untracked or modified working-tree file. It does **not** stage or commit. The Product Owner may combine it with relevant code changes or publish it alone after reconnaissance.
5. The ordinary Git Review stage/commit prepare-confirm flow remains authoritative. Before staging, verify the working-tree bytes; before commit, verify the staged blob; after commit, verify the chosen commit contains the exact path/blob SHA. Record the publication ID, revision/hash, status, and resulting commit SHA in the publication record. Git and SQLite are not one atomic transaction.
6. User-visible statuses distinguish `accepted_not_published`, `preview_ready`, `materialized_unstaged`, `staged`, `committed`, `failed`, and `drifted`. A materialization or stage is not reported as published; only a verified commit is `committed`.

Use an idempotency key over repository, accepted revision/hash, and canonical path. Exact-revision retry reuses the publication record and is a no-op if the worktree/index/commit already contains that exact bytes/hash. If the path exists with different content, if its Git index changes, or if the target/branch/HEAD changed since review, stop for a fresh preview; never overwrite or adopt a drifted file silently. If commit acknowledgment is ambiguous, inspect Git read-only for a commit containing the expected blob before retrying. Any failure remains visible; do not claim atomicity with the DB. Do not add a second editable Git copy or any Coder Git authority.

### Context, bootstrap, graph, runtime, and product boundary

The five registry-mapped project context documents stay in Git as the source in the initial transition. Repo Control serves exact document revisions by Git commit/blob hash and reports uncommitted worktree content as such. Later, the Product Owner may select individual governed documents for DB authoring; their Git copies then become generated/pinned snapshots with revision/hash lock metadata, not concurrent editing surfaces. No sweeping relocation or mandatory SQLite storage for every project file.

Canonical shared procedure and Skills remain source-controlled under `shared/procedure`, versioned by manifest and verified by hashes. Per-repository `AGENTS.md`, Copilot entrypoint, workflow core, Skills, and lock remain generated installation products, pinned and physically present. Local overlays remain project-specific Git files. If Repo Control is down, a cold Coder still has its bootstrap and installed Skills; it cannot establish live prompt/lifecycle authority, so it must stop rather than trust stale local authority. This avoids a bootstrap/document-service circular dependency.

Graphs/indexes remain external, rebuildable products tied to Git/source snapshot hashes, graph schema/provider, and build provenance. They can support bounded retrieval/impact, but never replace exact source documents. Retain service design as `systemd + the pinned project Python environment + embedded SQLite` on the existing Linux host. The service and Coder CLI already share the same venv and have direct access to registered repositories and host Git; no separate DB server is needed. Containerizing would add volume/root mapping, UID/permission, Git/key access, and host tool/runtime coordination with no current container deployment to reuse. A container would not turn SQLite into a database-server service. Test the actual linked SQLite library under the exact service/CLI interpreter before any future write; this milestone does not upgrade the host.

Keep this in Repo Control II. Current code has filesystem-specific coupling, but already separates registry, lifecycle reducer, Coder interface, Architect contract/adapter, dispatches, Git actions, procedure governance, and Intelligence provider. A repository-owned `InformationStore` facade plus bounded adapters can evolve these seams incrementally. There is no evidence that the present application cannot support the model or that a Repo Control III split would reduce risk; a new repo would duplicate auth, installation, service, and Git coordination. No new repository is initiated.

### Risks and mitigations

1. **Split authority or stale exports.** Keep per-class authority and revision labels explicit; one backend accepts writes at a time; hash every materialized snapshot; fail closed on stale identity.
2. **Migration loses identity or cross-links.** Import read-only copies first, preserve exact payloads/source hashes, and compare reducer state, document links, approvals, and dispatch status before any cutover.
3. **SQLite/runtime/backup risk.** Gate actual linked version, use local owner-protected storage and SQLite-aware verified snapshots; preserve the M010.002 WAL-corruption FAIL/B1 without claiming a self-consistency audit proves completeness. A restore with possible post-snapshot loss is explicit PO action.
4. **Git publication drift or ambiguous completion.** Revision/hash-bound preview and idempotency; normal PO Git controls; read-only reconciliation after ambiguous outcomes; collisions block instead of overwrite.
5. **Bootstrap/document-service availability.** Keep pinned physical entrypoints, Skills, overlays, and procedure lock in Git; live authority checks still fail closed when service/state is unavailable.
