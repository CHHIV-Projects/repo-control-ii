# M005.003 — Coding Agent Rules Decomposition and Skill-Based Context Proof of Concept

## Objective

Complete the next substantive step of the M005 Agent Procedure arc by testing whether the current large `coding_agent_rules.md` can be safely decomposed into:

```text
small always-loaded authority/bootstrap policy
+
task-appropriate Agent Skills
+
active milestone prompt / approved correction / approved instruction
+
deterministic Repo Control state and evidence
```

The target Product Owner experience is intentionally minimal:

```text
"Prompt ready."
"Correction ready."
"Instruction ready."
```

Those short notifications should be sufficient. The Product Owner should not need to restate preflight, Git restrictions, blocker handling, lifecycle procedure, validation procedure, closeout procedure, or other standing operational boilerplate in chat.

This milestone is a proof of concept and controlled restructuring exercise. It must preserve all existing authority and safety boundaries while determining how much procedural content can move from `coding_agent_rules.md` into reusable Skills.

## Critical Product Requirement

The normal Coder start-of-work contract must incorporate this behavior as standing procedure:

> Before coding, apply the standing pre-work feedback rule:
> - raise only genuine blockers, ambiguities, conflicts, risks, or materially useful implementation insights;
> - if none exist, state that briefly and proceed.
>
> Do not perform any Git mutations.
>
> If you encounter a genuine blocking question, use the bounded Repo Control `coder-question` path rather than only asking in chat.

This must not depend on the Product Owner retyping those instructions for each milestone.

## Product intent

Agent Skills are intended to carry reusable procedural detail so that the Coder does not require a long repeated manual for every task.

However, Skills must not become the sole carrier of critical authority or safety rules.

Use this separation:

```text
Always-loaded Coder bootstrap
= authority, instruction priority, lifecycle authorization, no-Git rule, core stop/safety rules, how to retrieve current work

Agent Skills
= detailed reusable procedure for a specific mode/phase/task

Active milestone prompt / correction / approved Architect instruction
= current task delta, acceptance criteria, bounded decision

Repo Control
= selected milestone, lifecycle, authorization, durable events, bounded Coder submissions

Git / tests / Graphify
= deterministic evidence
```

Do not preserve duplicated prose merely because it already exists. Do not remove critical always-loaded rules merely to reduce bytes.

## Phase 1 — Classify the current Coding Agent Rules

Classify every substantive section of `docs/context/coding_agent_rules.md` into one primary destination:

```text
A. ALWAYS-LOADED AUTHORITY / BOOTSTRAP
B. SKILL PROCEDURE
C. MILESTONE-SPECIFIC / PROMPT-OWNED
D. DETERMINISTICALLY ENFORCED / SHOULD BE REFERENCED, NOT EXPLAINED AT LENGTH
E. REFERENCE-ONLY / LOW-FREQUENCY
F. DUPLICATE / REDUNDANT / CANDIDATE FOR REMOVAL
```

Create the classification in the M005.003 closeout or a compact milestone-local analysis section; do not create a new permanent planning artifact unless necessary.

For each current section, record:
- section number/title;
- destination classification;
- rationale;
- whether content is safety/authority-critical;
- proposed Skill if applicable;
- whether any content must remain duplicated intentionally.

The purpose is not to maximize movement into Skills. The purpose is to create the smallest safe always-loaded core.

## Phase 2 — Define the minimal always-loaded Coder bootstrap

Design a candidate compact `coding_agent_rules.md` that contains only durable rules that must always be available before any optional Skill is loaded.

At minimum it must retain clearly and explicitly:
- instruction/rule priority;
- Product Owner authority;
- active milestone prompt and approved binding lock-in authority;
- requirement to retrieve active context from Repo Control;
- lifecycle authorization requirement;
- the standing pre-work feedback rule;
- absolute Coder prohibition on Git mutation;
- use of bounded `coder-question` for genuine blocking questions during authorized implementation;
- project/repository isolation;
- secrets/security boundary;
- deterministic-evidence principle;
- stop/escalate on material conflict, scope expansion, authority uncertainty, wrong repository/branch, or unauthorized phase;
- Skills confer procedure, not authority;
- if a Skill is unavailable, the Coder must still behave safely from the bootstrap + prompt + Repo Control evidence.

Normal Product Owner notification should require only:

```text
Prompt ready.
Correction ready.
Instruction ready.
```

The Coder should then pull current authoritative context rather than asking the Product Owner to repeat standing procedure.

Do not encode task-specific acceptance criteria in the bootstrap.

## Phase 3 — Skill decomposition

Evaluate and create only the Skills that materially reduce procedural bulk while remaining cohesive and reusable.

Existing accepted Skills:
- `repo-control-validation-closeout`
- `repo-control-blocker-bug-escalation`

Strong candidate additional Skills to evaluate:
- `repo-control-preflight`
- `repo-control-reconnaissance`
- `repo-control-implementation`
- `repo-control-documentation`
- `repo-control-repository-intelligence`
- `repo-control-tool-evaluation`
- `repo-control-review-correction`

These names are candidates, not mandatory output.

Prefer a smaller number of cohesive Skills over many tiny fragments.

Create a Skill only when:
- its procedure is stable and reused across milestones;
- it can be invoked at a recognizable boundary;
- it does not become the sole carrier of critical authority;
- it materially replaces procedural bulk from `coding_agent_rules.md`;
- it remains instruction-only unless separately approved;
- it has clear canonical references where needed;
- it does not duplicate another Skill without benefit.

Do not create a Skill merely because a section can technically be moved.

## Phase 4 — Explicit invocation and automatic behavior

Define how the Coder knows what to load after a minimal Product Owner notification.

Preferred model:

```text
PO: "Prompt ready."
  -> Coder retrieves coder-context
  -> verifies repository / branch / lifecycle / authorization
  -> applies standing pre-work feedback rule
  -> loads applicable procedural Skill(s) for the milestone mode
  -> proceeds if no genuine blocker exists

PO: "Correction ready."
  -> Coder retrieves coder-context
  -> confirms IN_PROGRESS correction mode and correction scope
  -> loads review/correction procedure if applicable
  -> performs only the bounded correction

PO: "Instruction ready."
  -> Coder retrieves coder-context
  -> identifies approved applicable Architect instruction
  -> verifies it does not override higher authority
  -> loads relevant procedural Skill(s)
  -> proceeds within existing milestone scope
```

Explicit Skill invocation remains preferred where reliability matters.

Do not require the Product Owner to name Skills manually in normal operation.

The Coder/standing bootstrap may direct itself to load the applicable Skill based on milestone mode/phase/procedure boundary. This is procedural routing, not authority inference.

Do not rely solely on host implicit Skill matching for a mandatory safety gate.

## Phase 5 — Controlled context-reduction POC

Produce and test a candidate reduced `coding_agent_rules.md` plus the applicable Skill set.

Do not merely estimate usefulness from file sizes. Test whether the reduced bootstrap still produces correct behavior.

Use a bounded set of representative scenarios derived from real Repo Control workflow:

1. new implementation prompt with no blocker;
2. genuine blocking architectural question;
3. unrelated/pre-existing bug discovery;
4. documentation-only milestone;
5. reconnaissance/tool-evaluation milestone;
6. validation/closeout transition;
7. bounded REVIEW correction;
8. instruction-ready case with an approved Architect instruction;
9. wrong branch or unauthorized lifecycle state;
10. explicit request by user/Coder context that would otherwise tempt a Git mutation.

These may be simulation-based where real lifecycle mutation would be disruptive. Do not manufacture destructive production states.

For each scenario, verify:
- correct authoritative context retrieval;
- correct applicable Skill selection/invocation;
- pre-work feedback rule behavior;
- correct proceed/stop decision;
- correct use of bounded `coder-question` where genuinely blocking;
- no unauthorized Git mutation;
- no lost authority rule;
- no dependence on Product Owner repeating procedural boilerplate;
- reasonable clarity when Skills are unavailable.
