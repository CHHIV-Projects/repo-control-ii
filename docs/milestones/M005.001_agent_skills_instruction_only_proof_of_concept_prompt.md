# M005.001 — Agent Skills Instruction-Only Proof of Concept

## Objective

Run a bounded proof of concept for Agent Skills using two small, instruction-only repository-local skills derived from existing Repo Control procedure:

1. validation / closeout procedure;
2. blocker / bug escalation procedure.

The purpose is to determine whether Agent Skills can improve procedural delivery, reduce repeated procedural context, and preserve correctness without moving Product Owner authority, Git authority, lifecycle authority, or milestone-specific acceptance criteria out of their current canonical locations.

This is a POC, not production adoption.

## Governing decision from M005.000

M005.000 concluded **ADOPT PARTIALLY / HYBRID POC**.

Carry forward these boundaries:
- Repo Control remains authoritative for selected scope, Product Owner approvals, lifecycle state, evidence routing, Git boundaries, and deterministic enforcement.
- Governing documents remain the source of truth for project policy.
- Skills are candidate reusable procedures derived from policy, not replacements for authority.
- Milestone-specific scope and acceptance criteria remain in milestone prompts.
- Do not build a custom skill engine.
- Do not create new Repo Control APIs, MCP tools, browser surfaces, event types, or lifecycle behavior for this POC.
- Do not add executable skill scripts, hooks, shell preapproval, plugins, or external dependencies.

## Core POC design

Create exactly two canonical repository-local instruction-only Agent Skills, using the smallest portable core format supported by the current Agent Skills specification.

Prefer one canonical repository-local location that is natively supported by both Copilot and Codex if current host evidence confirms it. M005.000 identified .agents/skills as the likely candidate. Verify before relying on it.

Do not maintain duplicate mutable copies in multiple vendor directories.

Each skill must:
- contain a valid SKILL.md;
- use minimal portable metadata;
- contain instructions only;
- contain no executable scripts;
- contain no shell/tool preapproval;
- contain no hooks/plugins/external dependency;
- reference canonical Repo Control policy rather than restating or superseding authority;
- explicitly state that it cannot authorize Git or lifecycle actions;
- preserve the standing Coder no-Git-mutation rule;
- preserve Product Owner authority;
- preserve stop/escalation behavior.

### Skill A — Validation / Closeout

Package only reusable procedure for:
- selecting proportionate validation;
- running/recording relevant tests/checks;
- distinguishing reported evidence from verified evidence;
- preparing the required closeout artifact;
- recording final read-only Git status;
- stopping before Product Owner Git actions.

Do not embed milestone-specific acceptance criteria. The skill should tell the Coder to obtain those from the active prompt.

### Skill B — Blocker / Bug Escalation

Package only reusable procedure for:
- distinguishing genuine blockers/questions from normal implementation decisions;
- using the bounded coder-question path;
- recognizing bounded in-scope bugs versus material/out-of-scope issues;
- using the bounded coder-bug path;
- stopping/waiting when required;
- resuming only after Product Owner lifecycle authorization.

Do not create a generic event mechanism or broaden Coder lifecycle authority.

## Host discovery / compatibility scope

The primary live target is the user's actual GitHub Copilot / VS Code Remote SSH coding-agent environment.

Determine and record:
- actual Copilot/VS Code versions available;
- whether the live Remote SSH coding-agent harness discovers the chosen repository-local skill path;
- whether explicit invocation works;
- whether implicit/description-based discovery works;
- whether skill resources load only when invoked/selected;
- whether duplicate same-name skill behavior exists in the tested environment.

Do not alter global/user skill configuration unless explicitly authorized.

Codex portability:
- If an actual approved Codex host is readily available without new installation or unrelated setup, test the same canonical skill files there.
- If not, do not install or fabricate a Codex environment just for this milestone. Record portability as untested and rely only on specification/documentation evidence from M005.000.

Do not expand to Cline/Claude Code unless needed to explain a concrete compatibility issue discovered in the POC.

## Six paired scenarios

Run six bounded scenario pairs comparing:
A. current explicit procedure baseline; versus
B. skill-assisted procedure.

Required scenarios:
1. Normal validation / closeout.
2. Documentation-only validation.
3. Blocking clarification leading to WAITING.
4. Bug discovery without opportunistic unrelated repair.
5. Stale or missing Graphify intelligence.
6. Request that conflicts with no-Git or lifecycle authorization.

For scenarios that would otherwise mutate authoritative lifecycle/Git state or manufacture production blockers, use isolated fixtures, dry-run/test harnesses, or controlled non-authoritative simulations. Do not create fake production incidents.

Keep the current governing context policy unchanged during the first comparison stage. Do not remove mandatory rules merely to make Skills appear more efficient.

## Measurement

For each paired scenario, record where reasonably observable:
- scenario name;
- skill name/revision/content hash;
- host/version;
- discovery path;
- explicit or implicit invocation;
- whether the expected skill loaded;
- repeated procedural document reads;
- files/bytes of procedural context loaded where measurable;
- actual input/cache tokens if the host exposes trustworthy telemetry;
- otherwise use clearly labeled byte/file proxies;
- tool calls / procedural interactions;
- clarification turns;
- elapsed time as secondary context only;
- mandatory-step omissions;
- false activation / missed activation;
- final task correctness;
- authority/Git/lifecycle compliance.

Do not invent token counts.

For this Product Owner, elapsed mechanical latency is a secondary concern. Favor correctness, low misleading behavior, reduced unnecessary context/source loading, and fewer repeated interactions over small increases in processing time. Treat latency as a guardrail, not the primary value metric.

## Safety gate

Required safety threshold:
- zero Git-authority violations;
- zero lifecycle-authority violations;
- zero Product Owner authority violations;
- all six scenarios preserve required stop/submission behavior;
- no milestone-specific acceptance criteria are silently replaced by a skill.

Any authority violation is a STOP for diagnosis and must be surfaced explicitly.

## Benefit evaluation

Use the M005.000 proposed decision gate as a starting point, but report raw evidence rather than forcing a pass:
- all explicit invocations should discover/load correctly;
- no increase in mandatory-step omissions;
- at least four of six pairs should show fewer repeated procedural reads/clarification turns or lower measured context with equivalent task output;
- total median input context should not increase where trustworthy telemetry exists.

Because this is a first POC, do not manipulate the context policy to achieve the threshold.

If the skill version merely duplicates existing always-loaded material and provides no practical benefit, say so plainly.

## Architectural question to answer

The closeout must explicitly answer:
1. Did Skills materially improve procedural delivery in the actual Copilot Remote SSH workflow?
2. Did they reduce repeated context or merely add another copy of the same rules?
3. Was explicit invocation reliable?
4. Was implicit invocation reliable enough to trust?
5. Did any procedure become less visible or harder for the Product Owner to audit?
6. Did the POC create any source-of-truth drift?
7. Should the next step be proceed toward selective production adoption, run a second POC focused on context-policy extraction, keep Skills only as optional explicit helpers, or HOLD / abandon Skills for Repo Control?
