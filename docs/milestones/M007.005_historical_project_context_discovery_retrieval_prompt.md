# M007.005 — Historical Project Context Discovery / Retrieval

## 1. Objective

Implement bounded, repository-scoped, read-only Architect discovery and retrieval of historical project evidence.

This milestone resolves INTEGRATION-003 — Bounded Architect Historical Project Context Retrieval.

The capability must let the Architect selectively discover prior milestone artifacts and archived project material when planning mature repositories, without relying on prior chat history and without turning historical evidence into current authority.

M007.004 remains the current/non-governing explicit-path document reader. M007.005 must remain a distinct historical capability.

## 2. Product Owner intent

The Architect should be able to determine what prior milestone addressed a subsystem, whether an approach was previously attempted or rejected, what a prior closeout concluded, which historical files mention a feature or decision, and what archived planning evidence exists under docs/history/.

The normal workflow is progressive: bounded discovery/search → small deterministic result set with exact provenance → select one artifact → bounded historical read → use as planning evidence.

Historical evidence informs planning only. It must never supersede current governing documents, the currently selected milestone, current lifecycle state, current approved Architect dispatches, or current Product Owner decisions.

# PART B — HISTORICAL CORPUS POLICY

## 4. Define historical artifact classes

Implement an explicit historical corpus policy rather than arbitrary repository search.

At minimum support/evaluate:

A. Prior canonical milestone artifacts under the repository's configured milestone root: prior prompts, workflow sidecars, and closeouts. The currently selected milestone's active artifacts remain governed by existing active-milestone tools and should not be surfaced as history merely because they match a filename pattern.

B. Archived historical project material under explicitly allowed historical roots such as docs/history/. This may include archived milestone corpora, superseded context documents, prior planning documents, and historical notes intentionally retained by the project.

C. Explicitly configured future historical roots if the architecture benefits from registry configuration. Prefer a small per-repository historical-root policy over hard-coding one project's archive structure everywhere.

Do not silently scan the whole repository.

## 5. Exclusions

Historical discovery/retrieval must not expose .git/, Git object/history internals, source code, tests, environment/secrets files, credentials or SSH material, runtime state, arbitrary repository files, binaries, external URLs, or files outside the selected managed repository.

M007.005 is repository-document history, not Git-history browsing.

# PART C — DISCOVERY CONTRACT

## 6. Add a distinct historical discovery tool/API

Add a new read-only Architect discovery contract, separate from repo_documents, repo_document, repo_read_document, and active milestone tools.

A likely public shape is repo_history_search(...) or repo_history(...). Choose the clearest name consistent with the codebase.

The discovery operation must be deterministic and bounded.

## 7. Discovery inputs

Support the smallest useful filter set. At minimum evaluate: optional text query, optional milestone ID, optional artifact type, optional historical root/category, and bounded result limit.

Useful artifact types may include milestone_prompt, milestone_workflow, milestone_closeout, archived_context, archived_planning, and historical_document. Avoid a large taxonomy.

Do not require an AI or embedding service.

## 8. Discovery semantics

Discovery should use deterministic repository-local metadata and lexical matching.

Requirements: exact repository scoping; no cross-repository search; deterministic ordering; stable bounded result limit; exact repository-relative path in each result; artifact/source type; milestone ID when derivable; file size; brief bounded match metadata/snippet only if safe and useful; no full-file content in search results; explicit truncation/omitted-count information when result bounds apply.

Prefer simple lexical matching over semantic inference.

If no query is provided, support a bounded inventory only when filters make the request sufficiently narrow. Do not return an unbounded archive listing.

## 9. Ranking / ordering

Use a deterministic and documented ordering policy. For text search, a simple transparent ranking may use exact path/name match, exact milestone-ID match, lexical occurrence/count, then deterministic path ordering. Do not introduce opaque AI ranking.

# PART D — HISTORICAL RETRIEVAL CONTRACT

## 10. Add a selected-artifact historical read

Provide a separate bounded read for one artifact returned by discovery. A likely public shape is repo_history_document(path=...).

Requirements: explicit repository-relative path; path must belong to the historical corpus policy; current selected milestone artifacts remain routed to active/current tools where appropriate; no arbitrary path fallback; no directory read; UTF-8 text only; deterministic size cap/truncation; same or stricter path/symlink/special-file protections as M007.004.

Where practical, reuse the proven lower-level bounded text-reader/security primitives from M007.004 without merging the public contracts.

# PART E — AUTHORITY / PROVENANCE

## 11. Historical provenance

Every discovery result and retrieved artifact must make historical status unmistakable.

Return metadata such as repository key, repository ID, repository-relative path, source/artifact type, milestone ID if derivable, historical root/category, file size, content/truncation metadata for retrieval, source=current working tree if that is the read model, and an authority classification such as historical_evidence plus an explicit indication that the artifact is not current governing or lifecycle authority.

Do not imply that age/order makes a historical document authoritative.

## 12. Authority precedence

Preserve the accepted authority model: current Product Owner decisions/approved dispatches, current lifecycle and active milestone prompt, current governing documents, current non-governing documentation, then historical evidence. If the exact accepted ordering differs in current governing docs, follow it; the invariant is that historical evidence cannot silently override current authority.

If historical evidence conflicts with current governing material, the Architect may identify the conflict but Repo Control must not reconcile it automatically.

# PART F — PATH / SECURITY MODEL

## 13. Path validation

Historical retrieval must enforce selected managed repository root only, repository-relative paths only, no absolute paths, no traversal, no backslash/control-character tricks, no symlink escape, regular supported text files only, no special files, and no path escape after canonicalization.

## 14. Historical root validation

Only configured/accepted historical roots and prior milestone artifacts may be searched/read. Do not infer historical status merely from a filename containing old/archive/history.

If a registry-level historical-root field is introduced, keep it optional, validate it at registry load, keep paths repository-relative, prevent overlap with sensitive/runtime roots, and preserve compatibility for managed repos without archives.

If explicit configuration is unnecessary because a secure deterministic policy already covers current repositories, keep the implementation simpler and document it.

# PART G — BOUNDS

## 15. Search bounds

Define hard server-side bounds for max matched files considered if needed, max returned results, max snippet bytes per result, max total response bytes, and timeout if relevant.

Return returned_count, total_count if safely knowable, omitted_count, and a truncated/limited indicator. Do not load the entire historical corpus into the response.

## 16. Retrieval bounds

Use a bounded text-read contract comparable to M007.004: maximum source size, maximum returned UTF-8 bytes, deterministic truncation, size/returned-count metadata, invalid UTF-8 rejection, and no binary fallback.

Reuse established constants where sensible.

# PART H — WORKTREE / GIT SEMANTICS

## 17. Read-only working-tree model

Historical evidence is read from files currently present in the managed repository worktree.

No Git checkout, Git log traversal, Git show, fetch, reset, stage, commit, or branch mutation.

If tracked/modified/untracked metadata is cheap and already safely available, it may be included but is not required for the core historical contract.

Do not make GitHub/network access a dependency.
