# 1. Purpose

M003.004 established and live-validated a stable, bounded, provider-neutral, read-only Architect contract under:

```text
/api/architect/v1
```

M003.005 must determine the **smallest safe and practical transport/integration architecture** that allows the external Architect—currently ChatGPT—to consume that contract without requiring the Product Owner to manually copy large Architect Review Packets.

This milestone is reconnaissance only.

Do not implement the chosen integration.

The objective is to decide how the Architect should safely reach Repo Control II while preserving the security and authority model already accepted.

---

# 2. Primary Question

Answer:

```text
How should ChatGPT / the Architect obtain controlled read-only access
to Repo Control II's /api/architect/v1 contract while preserving:

- loopback-only Repo Control exposure;
- repository isolation;
- Product Owner authority;
- no arbitrary filesystem access;
- bounded deterministic evidence;
- explicit caller identity where practical;
- authentication / authorization appropriate to the transport;
- auditability;
- provider neutrality where practical;
- browser-first daily use;
- minimal setup and maintenance burden?
```

The milestone must end with one recommended architecture, not merely a list of possibilities.

# 5. Architecture Principle

The desired eventual flow is:

```text
Product Owner asks Architect
        ↓
Architect requests bounded Repo Control evidence
        ↓
approved transport / access boundary
        ↓
Repo Control /api/architect/v1
        ↓
deterministic read-only evidence
        ↓
Architect reasons over current facts
```

Repo Control remains the control plane.

The Architect remains a reasoning client.

The Product Owner remains the authority for consequential decisions and all Git mutations.

# 6. Reconnaissance Scope

Investigate realistic ways for ChatGPT / an Architect client to reach the existing read-only contract.

At minimum compare:

```text
A. MCP-style controlled tool exposure

B. local bridge / connector running on henderson-server1

C. authenticated relay or reverse-access mechanism that preserves
   Repo Control's loopback-only service boundary

D. Windows-side or desktop-side helper that bridges the existing
   SSH tunnel to an Architect integration

E. a supported ChatGPT connector / plugin / app mechanism, if one can
   safely consume private/local tools without requiring unsafe exposure

F. retaining manual packet transport temporarily if all integration
   options impose disproportionate security, maintenance, or vendor
   coupling
```

You may add another candidate only if current implementation or platform evidence makes it materially credible.

Do not expand into a broad survey of every possible agent framework.

# 10. Local Bridge Evaluation

Questions:

```text

```

# 11. Windows Helper Evaluation

Evaluate whether the Windows workstation should participate.

Questions:

```text
Can the existing SSH tunnel be reused?

Would a local Windows helper be required for ChatGPT browser access?

Would that reintroduce the desktop-broker complexity previously rejected
for Git Control?

Would it need to be running continuously?

Would Windows credentials or local ports create additional risk?

Would this approach undermine the browser-first "open browser and work"
goal?
```

A Windows helper should be rejected if it becomes a fragile orchestration dependency without clear benefit.


