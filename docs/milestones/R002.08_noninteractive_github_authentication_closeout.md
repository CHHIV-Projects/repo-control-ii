# R002.08 — Noninteractive GitHub Authentication Closeout

**Status:** Dedicated key and SSH alias configured locally; GitHub registration required
**Mode:** Operational authentication setup; no Git remote or history mutation
**Date:** 2026-10-11

## 1. Executive Result

Repo Control's live Push authentication failure is consistent with the service
running without the interactive shell's Git askpass integration. Repo Control
correctly disables terminal/askpass prompting for remote actions; the active
service has no SSH agent, and no suitable GitHub identity was available during
reconnaissance. A bounded `ssh -T git@github.com` check failed with
`Permission denied (publickey)`.

The repository's only current SSH private keys are explicitly named for other
projects and are selected only by those project-specific SSH aliases. They
were not tested or repurposed. After Product Owner approval, a new passphrase-
free Ed25519 key was created for this repository and configured under the
dedicated SSH alias `github-repo-control-ii`. The alias explicitly selects
only this key and does not change the default GitHub identity for other
repositories.

GitHub Deploy Key registration is still required before authentication can be
tested. The `origin` remote remains HTTPS; no Repo Control Push or terminal Git
Push was attempted. Changing the remote remains a separate Product Owner
approval/action.

## 4. Credential Configuration and Shell / Service Difference

No `credential.helper`, `http.*.extraheader`, `url.*.insteadOf`, or `core.askpass`
was found in repository, global, or system Git configuration. No credential
helper is configured in the effective Git configuration.

The interactive coding shell had:

```text
GIT_TERMINAL_PROMPT: disabled
GIT_ASKPASS: set (value withheld)
SSH_AUTH_SOCK: unset
SSH_ASKPASS: unset
```

The active systemd process (PID 1464 at inspection time) was running as user
`chuck`. Its environment did not contain `GIT_TERMINAL_PROMPT`, `GIT_ASKPASS`,
`SSH_ASKPASS`, `SSH_AUTH_SOCK`, `GIT_SSH`, `GIT_SSH_COMMAND`, `DISPLAY`, or
`WAYLAND_DISPLAY`. The unit has no `EnvironmentFiles`, `PassEnvironment`, or
`UnsetEnvironment` directives.

The interactive shell had Git command-line configuration variables set; the
effective auth-related setting name was `credential.interactive`. Their values
were not inspected or recorded. The shell's `GIT_ASKPASS` presence is the
material observed difference and is a plausible source of interactive
credential access. The exact askpass provider/value was not inspected, and the
reported terminal Push success was not independently reproduced; its exact
credential source therefore remains unconfirmed.

Repo Control's remote Git subprocess explicitly:

- sets `GIT_TERMINAL_PROMPT=0`;
- sets `GIT_ASKPASS=/bin/false` and `SSH_ASKPASS=/bin/false`;
- uses `stdin=DEVNULL`;
- invokes SSH with `BatchMode=yes`.

These controls are intentional and must remain. The active service environment
does not inherit the interactive shell's askpass helper.

## 7. Approved Authentication Model and Local Setup

The Product Owner approved a dedicated Ed25519 **read/write Deploy Key** for only
`CHHIV-Projects/repo-control-ii`, stored under user `chuck` at:

```text
/home/chuck/.ssh/id_ed25519_repo_control_github
```

GitHub Deploy Keys are repository-scoped; enable **Allow write access** only
for the Repo Control II repository so the existing Push operation can publish.
Do not reuse either other-project key.

For unattended systemd Push without a persistent SSH agent, a passphrase
protected private key is not available to the service at boot. The simple
service-compatible model is therefore a dedicated passphrase-free key readable
   only by `chuck` (private-key file mode `600`; `.ssh` directory is mode `700`).
   This grants the service account the ability to push to the one repository and
   carries the corresponding at-rest key risk. The key was generated with an
   empty passphrase as approved. A passphrase-protected key would require a
   separately designed reliable unattended agent model and is not recommended
   for this bounded milestone.

   The key exists at
   `/home/chuck/.ssh/id_ed25519_repo_control_github` (mode `600`, owner `chuck`).
   Its public-key fingerprint is
   `SHA256:La5j/LfT7DPG4En5vr+TKjNRWaYrV7wL3xkH4A75nvA`. No key contents are
   included in this closeout. The existing SSH config was preserved and appended
   with a dedicated alias:

      ```sshconfig
      Host github-repo-control-ii
          HostName github.com
          User git
          IdentityFile ~/.ssh/id_ed25519_repo_control_github
          IdentitiesOnly yes
          StrictHostKeyChecking yes
      ```

   `ssh -G github-repo-control-ii` confirmed the effective hostname, user, key,
   `IdentitiesOnly yes`, and `StrictHostKeyChecking yes`. The SSH config file
   remains mode `600`. The existing aliases for the other projects are unchanged.

   ### Product Owner action required: register the public Deploy Key

   On the server, display only the public key locally:

   ```bash
   cat "$HOME/.ssh/id_ed25519_repo_control_github.pub"
   ```

   Add that public key under
   `CHHIV-Projects/repo-control-ii` → **Settings** → **Deploy keys** with
   **Allow write access** enabled. Do not copy, send, or expose the private key.
   After registration, test without prompts using the dedicated alias:

   ```bash
   ssh -o BatchMode=yes -o ConnectTimeout=10 -T git@github-repo-control-ii
   ```

   GitHub may return a nonzero exit code while stating that authentication
   succeeded but shell access is unavailable. Verify the success wording. Host
   key verification remains enabled; if a host-key prompt/error occurs, stop and
   verify GitHub's published SSH fingerprints through its official documentation.
