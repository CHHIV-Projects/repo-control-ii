# 1. Goal

Define the Git Control architecture using the same pattern already proven useful in the user's server-hosted applications:

```text
Windows browser
        ↓
Repo Control browser UI
        ↓
Repo Control service layer on Linux
        ↓
standard Linux Git and selected specialist tooling
        ↓
authoritative repositories on henderson-server1
```

The browser is the control surface.

The authoritative repository, Git execution, application logic, and supporting tools remain on Linux.

R002.01 must decide how much Git functionality Repo Control should obtain directly from standard Git, how much Repo Control should add as workflow/decision support, and where external Git tools are still useful as references or future specialist tools.

---

# 2. Architectural Intent

Repo Control II should not become a reimplementation of Git.

Prefer:

```text
Git
→ provides repository facts and operations

Repo Control
→ presents those facts clearly
→ adds Product Owner workflow
→ adds review / approval / safety gates
→ adds milestone awareness
→ adds explanation and decision support
→ records evidence
```

The desired pattern is:

```text
browser frontend
→ Linux orchestration layer
→ mature Linux backend tools
```

rather than:

```text
browser frontend
→ custom reimplementation of Git internals
```

---

# 3. Background

R001.00 established that the inherited Git-control core contains useful deterministic logic.

R002.00 established:

```text
- Repo Control should provide the near-term browser Git surface;
- Product Owner actions may authorize Git mutations;
- coding agents remain prohibited from independently performing Git mutations;
- the current review surface is insufficient;
- GitButler is not selected as the primary Git UI;
- advanced Git capability should be sequenced rather than recreated immediately.
```

After R002.00 review, the Product Owner clarified that the desired Git experience is broader than simple:

```text
identify files
→ stage
→ commit
```

The Git Control arc should eventually help with real operational cases such as:

```text
Why is this file dirty?
Is this change meaningful or only whitespace?
What changed since HEAD?
Does this file belong to the current milestone?
Should I restore this file?
What was changed in the previous commit?
How far is this branch ahead/behind?
What branch am I actually on?
What will a branch switch affect?
What is local versus remote state?
What are the safe options from the current repository state?
```

R002.01 therefore evaluates the backend capabilities and UX patterns needed before implementation.

Identify standard Git commands/capabilities that can provide the required backend evidence and actions.

At minimum evaluate:

```text

git fetch --dry-run if suitable

git restore --staged
git commit
git stash

```

Do not execute mutating commands against the authoritative repository.

For each useful capability, record:

```text

whether output is deterministic/parseable
whether porcelain/plumbing output exists
whether it is appropriate for direct Repo Control use
whether the current inherited Git layer already wraps it
```

The purpose is to avoid building code that duplicates native Git capabilities.

# Part III — Product Use Cases

## 16. Define Concrete Repo Control Git Use Cases

Create a bounded use-case matrix.

At minimum include:

### Change inspection

```text
What files changed?
What changed in this file?
Is it staged?
Is it untracked?
Is the change whitespace-only?
Is it binary?
Is it large?
```

### Change diagnosis

```text
Why is this file dirty?
Was this file changed after a milestone was closed?
Does the diff look accidental?
Is it outside the active milestone?
```

### Safe cleanup

```text
Restore one file to HEAD
Unstage a file
Discard a known accidental whitespace-only change
Leave unrelated work untouched
```

Do not implement these actions in R002.01.

### Commit workflow

```text
Select exact files
Review exact diff
Stage exact files/hunks
Review staged diff
Review commit message
Commit
Verify result
```

### History

```text
Show recent commits
Show commit contents
Show file history
Show previous milestone commit
Compare current tree to prior commit
```

### Branch awareness

```text
Show current branch
Show branches
Show upstream
Show ahead/behind
Compare branch to main
Show simple branch graph
```

### Later branch operations

```text
Create branch
Switch branch
Delete branch
Merge
Rebase
```

### Remote awareness

```text
Show remotes
Show local vs upstream
Fetch
Push
Pull
```

### Recovery

```text
What changed unexpectedly?
What can safely be undone?
What would restore to HEAD do?
What data would be lost?
```

For each use case classify:

```text
Core R002 capability
Later R002 capability
External specialist capability
Not needed
```

## 18. Decide Whether a Git Library Is Needed

Evaluate whether Repo Control should:

```text
A. continue using subprocess calls to standard Git CLI;
B. adopt a Git library;
C. use a mixed model.
```

Do not add a library.

If evaluating libraries, keep it bounded.

Possible examples:

```text
GitPython
pygit2/libgit2
dulwich
```

The recommendation must consider:

```text
maturity
coverage
risk of semantic mismatch with CLI Git
maintenance
dependency burden
performance
ability to expose advanced Git features
```

Do not add a dependency merely for convenience.
