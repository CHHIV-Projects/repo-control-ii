## 3. Final Lifecycle Contract

The phase is reconstructed from events in the selected milestone's workflow
sidecar. A selected milestone without a sidecar derives to `PLANNING`.

| Phase | Contract |
|---|---|
| `PLANNING` | Preparation only. `prompt_approved` moves to `READY` and requires reported Product Owner context plus the explicit confirmation checkbox. |
| `READY` | The prompt approval is recorded. `implementation_started` explicitly hands work to implementation and moves to `IN_PROGRESS`. |
| `IN_PROGRESS` | Implementation and validation. Questions may be recorded without pausing; a question with a waiting category must also include a reason and moves to `WAITING`. Escalations and out-of-scope bug classifications also require a reason and move to `WAITING`. |
| `WAITING` | The category and reason are retained. A valid answer, decision, lock-in, escalation resolution, or in-scope bug fix must be recorded before a separate explicit `implementation_resumed` event returns to `IN_PROGRESS`. |
| `REVIEW` | An existing, currently discovered closeout must be explicitly submitted from `IN_PROGRESS`. Review requests are events. `correction_requested` returns to `IN_PROGRESS`. |
| `CLOSED` | Terminal. Explicit Product Owner acceptance is required. `milestone_closed` records an acceptance event if one is not already the latest event, followed by the closure event. No later lifecycle events are accepted. |

Transitions are validated against chronology. `WAITING` cannot be entered
without a reason, and closeout presence alone does not submit work for review.
Clean Git state, commits, pushes, and test results never advance or close a
milestone.

## 4. Event and Decision Contract

The implementation supports:

```text
prompt_approved
implementation_started
question_submitted
answer_recorded
decision_recorded
lock_in_approved
escalation_opened
escalation_resolved
bug_discovered
bug_classified
bug_fixed
test_result_recorded
implementation_resumed
closeout_submitted
review_requested
correction_requested
acceptance_recorded
milestone_closed
git_disposition_recorded
```

Informational events do not automatically change phase. `decision_recorded`
is explicitly non-binding; `lock_in_approved` is a binding Product
Owner-confirmed decision. Prompt approval, acceptance, and closure are also
Product Owner-confirmed actions.

Each event stores a unique ID, UTC timestamp, type, summary, reported actor
role, attribution disclaimer, explicit approval marker, phase before/after,
and applicable typed metadata or evidence. Event order, IDs, event shapes,
phase transitions, and references to open questions/bugs are validated when
the ledger is read. The UI displays recent events and the most recent
Product Owner-approved decision.

Actor and role are self-reported context, not authenticated identity. The
explicit Product Owner checkbox records the action requested in the UI; it
does not claim cryptographic proof of who used the browser.

## 5. Persistence Contract

The durable record is a human-readable Markdown sidecar adjacent to the
selected prompt, named by replacing `_prompt.md` with `_workflow.md`; for
example:

```text
M003.002_minimal_lifecycle_and_durable_decisions_workflow.md
```

The sidecar contains a chronological readable event rendering and a
versioned, machine-readable JSON ledger. It is milestone-scoped and records
repository ID, milestone ID, and prompt path. It is not the prompt, closeout,
or selection anchor. The canonical discovery grammar remains `prompt` and
`closeout`; recognized workflow sidecars are explicitly excluded from
artifact discovery.

The only external milestone operational state remains the existing
repository-scoped active-selection pointer. Lifecycle phase is not duplicated
in operational JSON or a database. Reloading the application re-derives phase
from the durable event history.

Writes use a same-directory temporary file, flush and `fsync`, then atomic
`os.replace`. Reads and writes use the existing artifact lock. The sidecar is
limited to 5 MB and 2,000 events, with write limits matching read limits.
Malformed, mismatched, oversized, or inconsistent sidecars produce a visible
invalid-record state and block further workflow writes; the system does not
silently reset or infer a replacement state.

The application serializes local in-process updates; the file format does not
yet provide cross-process/multi-agent conflict resolution or idempotent
submission.

## 6. Bug Handling

The supported bounded flow is:

```text
bug_discovered
→ bug_classified (in_scope or needs_escalation)
→ bug_fixed (for a classified in-scope bug)
→ test_result_recorded
```

Classification must reference an unclassified discovered bug. Fixes must
reference a classified, in-scope, not-yet-fixed bug. An out-of-scope bug
requires an escalation reason and places the milestone in `WAITING`; the
milestone does not silently expand. Open discovered bugs and fixable in-scope
bugs are surfaced in the event form. Test results record their evidence source
and outcome but are not independently verified by Repo Control.

## 7. Product Owner Authority

Explicit Product Owner role context and confirmation are required for:

- prompt approval / transition to `READY`;
- binding lock-in approval;
- acceptance;
- milestone closure.

Closure also requires the milestone to be in `REVIEW` and an acceptance event
immediately preceding closure. Other phase transitions and event types are
validated, but the UI's reported actor role is not an authentication system.
No lifecycle action performs staging, commit, push, or another Git mutation.

## 8. UI and Request Safety

The Milestone page presents the current derived phase, waiting category and
reason, event count, latest meaningful events, latest Product Owner-approved
decision, unanswered questions/open blocker indication, and a suggested next
authorized action. A compact event form captures summaries, role context,
waiting details, related question/bug, classification, test evidence, and
explicit Product Owner confirmation when applicable.

The event POST checks mutation-request protections and, under the existing
repository action lock, revalidates repository key/generation and the current
milestone ID/prompt path. Persistence rechecks the active selection, fresh
artifact inventory, sidecar containment, event references, and transition
rules. Stale repository/milestone requests are rejected rather than written
against a changed target.

## 12. Known Limitations

M003.002 does not implement:

- handoff packets;
- Architect read-only tools;
- Coder submission tools;
- full review evidence assembly;
- direct AI integration.

Role identity remains unauthenticated and is recorded honestly as reported
context. Test evidence is user-reported rather than independently collected.
The file ledger's lock is process-local; cross-process/multi-agent conflict
handling and idempotency belong to a later authenticated submission contract.

## 13. Recommended M003.003 Inputs

- Read the selected prompt, applicable prompt addenda/lock-ins, governing
  project instructions, durable event history, closeout, and available
  deterministic repository/test/Git facts into a copy/export-only handoff
  packet; do not duplicate editable source-of-truth content.
- Treat the prompt and workflow sidecar as separate artifacts and derive
  lifecycle from events; never elevate self-reported role context into
  authenticated identity.
- Define stable source references, ordering, size limits, missing/invalid
  artifact behavior, and stale-selection revalidation for packet generation.
- Keep packet generation read-only with respect to Git and milestone

- Defer direct AI integrations, role authentication, and multi-agent writes
  unless separately scoped and approved.
