# M010.007 — Product Owner-Controlled Accepted Closeout Publication to Git (Fixture-Gated)

## Objective, authority, and prerequisite
Implement the agreed **accept closeout -> optionally publish exact accepted Markdown revision to Git** workflow as an isolated, fixture-gated feature, reusing Repo Control's existing Product Owner Git Review stage/commit controls rather than introducing a second Git mechanism. The goal is a simple human workflow that links an immutable accepted closeout to its verified Git snapshot, without confusing acceptance with Git publication or allowing Coder Git mutations.

Target managed repository: `repo-control-ii`, `/home/chuck/projects/repo-control-ii`; remain on branch `db-workflow-persistence-architecture`. Before any Coder work verify live selected repository/milestone, exact M010.007 prompt, lifecycle IN_PROGRESS, authorization and installed procedure. M010.006 must be explicitly accepted and CLOSED by the Product Owner in Repo Control. A pending/approved Architect dispatch and "Prompt ready" are handoff notices, not authorization. Follow cold-chat bootstrap or warm/resume procedure as applicable. Coder must **not Stage, Commit, Push, Tag, Merge, switch global repository selection, or perform any Git mutation**.

Work from accepted M010.004 architecture (especially closeout publication contract), M010.005 isolated `InformationStore` and receipt/revision semantics, M010.006 fixture-gated `DocumentLibrary`, and existing PO Git Review safety interfaces. This milestone does NOT change the current operational authorities: physical prompt/closeout files, v1 Markdown workflow sidecars, external Architect dispatch ledger, selection pointer, procedures and installed Skills, legacy/history search, current browser/CLI/MCP interfaces, and Git workflows all continue unchanged. The isolated SQLite store is **NOT** production eligible or authorized for live use.

## Bounded functional requirements
1. **Publisher contract and exact-source acceptance.** Create a narrow, testable, caller-injected publication service over an explicit disposable `InformationStore` or equivalent fixture provider, repository identity, allowlisted milestone root, a validated accepted-closeout revision, and read-only Git inspection / existing guarded Git workflow contracts. It may publish **only** an immutable closeout revision explicitly linked to a legitimately accepted-and-closed milestone in a trusted fixture context. Reuse established lifecycle reducer/approval relationships; do not infer PO approval from a reported actor string, a document's own status label, a generic historical document, or a mutable draft. Reject wrong repository, milestone, source type, missing acceptance, changed revision/hash, invalid/unstable identity, or re-opened/not-closed state. Any fake PO acceptance must be an unmistakably explicit test-only fixture, never a production bypass.
2. **PO UX separation.** Define and implement a small fixture-injected, **unregistered** browser component or flow with distinct states: accepted_not_published -> preview_ready -> materialized_unstaged -> staged (observation only) -> committed (verified), plus failed/drifted where warranted. Show source document ID/revision/hash, target repo/branch/HEAD/path, complete proposed Markdown diff, existing publication/working-tree/index status, and optional associated code or reconnaissance context. "Accept & Close" alone MUST NOT create or stage any file. A separate PO-confirmed "Publish accepted closeout to Git" first materializes exactly the accepted Markdown at a deterministic canonical milestone path in a **caller-supplied disposable test worktree only**. Unregistered fixture UI must not be callable from production routes or make live mutations. No automatic stage/commit/push; normal existing PO Git Review remains the only production Git mutation interface.
3. **Safe target / collision / drift rules.** Constrain target to registered/allowlisted repository milestone root with canonical relative path, verify symlink/path traversal protections and repository/milestone identity. Bind preview and confirmation to exact accepted revision SHA-256 plus target path, branch/HEAD, worktree/index fingerprint as appropriate. Never overwrite a differing working-tree or tracked file, even if it happens to look like a closeout. If target already contains identical bytes, return an idempotent no-op. On changed HEAD, path, index, revision, or repo identity, demand fresh preview/PO confirmation; no unreviewed overwrite or implicit adoption. Do not touch unrelated code files.
4. **Idempotent publication record and truthful status.** Use the M010.005 schema's minimal publication record or an appropriately narrow schema extension to store a durable operation ID, exact repository/milestone/document/revision/hash, target path, observed state, and related commit ID only when verified. Exact idempotency/request retry must return the previous outcome; same key with different inputs fails. DB transaction cannot atomically commit Git; persist intermediate states and reconcile after uncertain outcomes through **read-only** repository inspection. No false `committed`/published status from file creation or a claimed commit SHA; require verification that a specific commit's tree contains the expected path and blob contents. Distinguish materialized/staged/committed, missing/drifted/failed, and optional publication versus acceptance.
5. **Controlled Git Review handoff.** Produce a materialized unstaged file and a clear next action in existing Git Review. Reuse existing PO stage/commit prepare/confirm paths without duplicating Git commands, permission gates, CSRF/confirmation rules, or giving the Coder any Git mutation capability. The closeout may be committed with code changes or alone for reconnaissance. If supported by current read-only interfaces, include a narrow observation/reconciliation hook to verify staged blob and eventual commit; otherwise implement a fixture-tested adapter with explicit NOT CONNECTED status for M010.008+ integration. Never silently auto-stage or auto-commit.
6. **Fixture-only safety and regression.** All implementation operations, write-target paths, and user-interface registration are explicitly test-injected. Test with temporary directories and synthetic source/revision/PO-gated state. **Do not run Git stage/commit/push, even in testing**; simulate the existing PO Git completion contract with explicit stubs and test commit/blob verification using read-only prebuilt Git fixtures if available. If exact Git commit-tree checks cannot be reasonably proved without staging/committing in tests, document that one boundary as NOT TESTED for later PO-controlled operational acceptance, not as PASS. No production service wiring, user-selectable arbitrary paths, live DB creation, state-root scan/write, existing closeout file changes, systemd/venv/SQLite installation, procedural release update, or managed workflow mutation. Preserve old Git and workflow behavior.
7. **Focused negative and positive tests.** Cover closeout accepted vs submitted/unaccepted/reopened/legacy-only; same revision no-op; changed same-ID request; wrong repository/milestone/branch/HEAD; malicious path/symlink; existing different file; staged/unstaged and already-published states; failed/ambiguous materialization and read-only reconciliation; exact exported Markdown SHA; never stage/commit on acceptance or publication; Coder cannot access PO actions; publication manifest/result accurately links revision and commit after independently verified evidence. Verify zero writes on rejected requests. Run relevant existing M010.005/M010.006/store, Git Review and web tests to detect regressions.
8. **Preserve original information architecture goals.** Do not narrow or silently cap historical search/retrieval. M010.006's 560-candidate/556-match completeness regression should remain passing. Its measured repeated full-corpus scan overhead (~0.46 s for 560 fixtures) is an explicit M010.008 pre-cutover efficiency item; do not expand this publication milestone into a search-rewrite project. Preserve legacy historical provenance and never treat old closeouts without workflow evidence as accepted. Current SQLite 3.45.1 remains below production eligibility gate 3.51.3 (or verified fixed backport); disposable fixture test override only, no runtime change.
