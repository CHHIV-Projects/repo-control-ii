## 4. Branch / Remote Mutation Authority Contract

Branch and remote controls live in Git Review → Branches. GET requests only inspect local repository/configuration evidence; they do not switch branches, fetch, query a remote, or otherwise execute a branch/remote operation. Every operation starts with a CSRF-protected same-origin POST, displays a separate review/confirmation page, then re-resolves and revalidates its target before execution.

Branch and remote tokens are unguessable, in-memory, repository/action-bound, single-use, and expire after five minutes. Branch tokens resolve against the fresh local branch inventory. Remote tokens resolve against the current configured-remote inventory. Browser values are never used as arbitrary branch targets, remote names, URLs, revisions, or refspecs. The only free-form Git identity accepted is a new local branch name, checked by Git's `check-ref-format --branch` and independently checked for availability.

## 5. Prepared Action / Revalidation Design

The existing `PreparedGitActions` service and token registry now also prepare these actions:

```text
create-branch, switch-branch, delete-branch,
fetch, push, publish-branch, fast-forward
```

Prepared state binds repository identity/root, HEAD, current branch, status inventory, index fingerprint, and action-specific branch tip, main tip, upstream/tracking tip and counts, remote token/configuration/URLs, configured fetch refspecs, and (for first push) the same-name remote-branch absence check. Confirmation consumes the token before final revalidation. Any changed relevant fact refuses execution.

Git operations are fixed argument arrays. Remote commands have a 60-second runtime and bounded output, disable Git terminal prompts and askpass, use batch-mode SSH, and receive no inherited stdin. There are no retries. Known executable action hooks/custom `core.hooksPath` are refused rather than run implicitly.

## 6. Branch UI Integration

The Branches view retains its local branch inventory and branch-vs-main/upstream evidence. It adds:

- **Create local branch** input, explicitly stating that creation does not switch or set an upstream.
- Branch-detail **Review switch** / **Review local branch deletion** controls only when local eligibility checks pass.
- A configured-remote area for Fetch, current-upstream Push, first Publish, and fast-forward-only Update.
- Sanitized configured URLs and eligibility reasons for unavailable operations.

Fetch and first-push remote choices use the server-observed remote list. `origin` is the default when configured. Without `origin`, a sole configured remote is the default. Multiple configured non-origin remotes require explicit selection. Remote configuration changes after preparation invalidate or refuse the action.

## 7. Create Branch Semantics

Creation validates a single literal branch name with Git, rejects empty/invalid/duplicate names and `main`, and creates from the reviewed current HEAD without switching or setting an upstream. It revalidates HEAD, current branch, name availability, index and status, then verifies the new ref points at the reviewed HEAD and that the current branch and Git-visible worktree/index state did not change.

## 8. Switch Branch / Dirty-Tree Protection

Switch targets resolve only from the current local branch inventory. Switching requires an attached current branch, a completely clean status (staged, unstaged, untracked, and unresolved paths absent), and no detected in-progress Git operation. The review names the current branch/HEAD and target branch/tip.

Execution uses `git switch --no-guess -- <validated-local-name>`. Verification requires the target branch and reviewed target OID to be current with a clean worktree. No auto-stash, branch creation, discard, or conflict handling is performed.

## 9. Safe Local Branch Delete Semantics

Deletion is offered only for a non-current, non-`main` local branch that the R002.04 ancestry service proves is an ancestor of local `refs/heads/main`. Review shows its name/tip, local-main tip, upstream if configured, current branch, and explicit **local only / remote impact none** consequence.

Execution uses ordinary `git branch -d -- <validated-local-name>`, never `-D`/`--force`, and verifies the local ref is absent while current HEAD/branch/index/status remain unchanged. The command does not contact or target any remote branch. Git may conservatively refuse deletion if its own normal safe-delete criteria are stricter than the reviewed main-ancestry fact; the refusal is surfaced without force.

## 10. Fetch Semantics

Fetch requires a configured remote resolved from the current inventory. Before offering execution, Repo Control validates that its configured fetch refspecs map only `refs/heads/*` (or an exact branch) into that remote's own `refs/remotes/<remote>/` namespace, and refuses mirror remotes or unsupported mappings. The command explicitly disables prune, automatic tags, and submodule recursion.

Review identifies the remote, sanitized URL, current branch/HEAD, expected local effects, and network use. Before/after verification requires the current branch, HEAD, index fingerprint, and status inventory to remain unchanged. Result evidence lists changed local remote-tracking refs as old/new OIDs, or states that none changed. This is local tracking-ref evidence; it is not presented as a claim that the remote is now current.

## 11. Push Semantics

Push is limited to the attached current branch and its server-observed configured remote-tracking upstream. The service resolves the corresponding remote branch and uses an explicit `refs/heads/<local>:refs/heads/<upstream-branch>` refspec. It refuses missing upstream/tracking refs, unsupported/mirror remotes, multiple push URLs, and branches with no local commits ahead of the local tracking ref.

The review shows local branch/HEAD, remote/branch, ahead/behind relative to the local tracking ref, its possible staleness, sanitized push URL, committed-only scope, and that force is not used. Dirty/untracked work is permitted and remains local. A non-fast-forward rejection is explained as the remote containing commits not present locally; the user is directed to fetch and inspect divergence, with automatic merge/rebase resolution stated as outside the supported workflow. Other remote failures remain surfaced. Repo Control does not retry or force.

## 12. First Push / Upstream Setup Semantics

For an attached branch with no upstream, Repo Control supports only same-name publication to a selected configured remote and `--set-upstream`. The remote-selection lock-in from the Product Owner is recorded in the active prompt and implemented:

```text
origin exists                         → default to origin
no origin, exactly one remote         → default to that remote
no origin, multiple configured remotes → require explicit selection
```

The selection token is resolved against current server-observed configuration at preparation and again at confirmation. Preparation and final revalidation query the actual configured push URL and fail closed if `refs/heads/<local-branch>` already exists. The command has a fixed same-name refspec, no force, no follow-tags, and no submodule recursion. Success verifies both upstream configuration and actual remote tip.

Standard Git does not provide an atomic create-only push without force/lease semantics. A concurrent actor could create the same remote branch after the final absence query but before the push. Normal non-force push still prevents history rewriting and may reject, but this narrow server-side race cannot be eliminated with the explicitly permitted CLI contract; it is called out for Product Owner awareness.

## 13. Fast-Forward-Only Update Semantics

Update requires an attached branch, configured and locally available upstream, no in-progress Git operation, completely clean worktree/index, `ahead == 0`, `behind >= 1`, and Git ancestry proving the local tip is an ancestor of upstream. It never fetches implicitly. The confirmation identifies the local tracking ref and its freshness caveat.

Execution is `git merge --ff-only <reviewed-upstream-OID>`. Verification requires the same branch, HEAD exactly equal to the reviewed upstream OID, clean state, and no in-progress operation. No merge commit, rebase, reset, or fallback is performed.

## 14. Local Tracking Ref vs Actual Remote Evidence

Three evidence classes remain distinct:

1. Local branch ancestry and local branch-vs-`main`.
2. Local branch vs local remote-tracking ref, potentially stale until explicit Fetch.
3. Actual remote response from explicit `ls-remote`/push/fetch operations.

Fetch results describe changed local tracking refs. Push reports command success separately from actual remote-tip verification; successful push is called remotely verified only when the configured push URL's exact branch tip equals the reviewed local HEAD. A failed/unavailable verification reports uncertainty, not synchronization.

## 15. Credential / Network Failure Handling

Remote URLs are sanitized before UI display: userinfo, query, and fragment are omitted; SCP-style user prefixes are hidden. Git diagnostics are also sanitized before rendering. Raw configured URLs remain only in process arguments and short-lived in-memory revalidation records; no new persistent credential store or logging was added.

Network runtime/output are bounded; terminal prompting and askpass are disabled; SSH uses batch mode; stdin is closed; no automatic retry occurs. Connectivity, authentication, permission, missing-remote, timeout, hook, and non-fast-forward errors are surfaced. If an operation may have completed partially or push verification is unavailable, the UI directs the Product Owner to inspect Git Review before retrying.

## 16. Backend Git Commands

Fixed standard-Git-CLI commands include:

```text
check-ref-format --branch
branch -- <new-name>
switch --no-guess -- <inventory-name>
branch -d -- <inventory-name>
fetch --no-prune --no-tags --recurse-submodules=no <configured-remote>
push --no-follow-tags --recurse-submodules=no <remote> <explicit-refspec>
push --set-upstream --no-follow-tags --recurse-submodules=no <remote> <same-name-refspec>
merge --ff-only <reviewed-full-OID>
ls-remote --heads -- <configured-push-URL> <exact-branch-ref>
```

Supporting reads use existing Git state and branch inspection plus `remote`, `remote get-url`, `for-each-ref`, `rev-parse`, `rev-list`, `merge-base`, and `config`. No shell interpolation, arbitrary user syntax, Git library, GitHub API, force operation, or fetch-on-page-load was introduced.

## 22. Known Limitations

- Product Owner reports the disposable-browser functional acceptance scenarios in the R002.06 handoff as PASS. The two follow-up UI corrections are covered by focused automated route/service tests; no additional live-repository mutation test was performed or needed.
- Prepared actions are in-memory; restart invalidates pending tokens. They expire after five minutes.
- The service revalidates immediately before execution, but standard Git does not make remote checks and later mutations atomic against concurrent external actors.
- On fetch/push timeout or incomplete command output, remote/local state may require inspection before any retry.
- Git's ordinary `branch -d` may refuse deletion more conservatively than the UI's main-ancestry eligibility; refusal is surfaced and never bypassed with force.
- Remote names outside the deliberately narrow supported character set, unsupported fetch refspecs, mirror remotes, multiple push destinations, or custom/executable operation hooks are unavailable through this UI.
- Deployment remains the existing manually started loopback web service plus Windows SSH port-forward. Startup/access work remains deferred to R002.07.
