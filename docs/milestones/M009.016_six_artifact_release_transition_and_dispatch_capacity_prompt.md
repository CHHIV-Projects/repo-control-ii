## Part B — Architect Dispatch Capacity

### 1. Current limitation

Repo Control currently retains at most 50 Architect Dispatch
records per managed repository.

The limit has prevented submission of additional PROMPT,
INSTRUCTION, and RESPONSE proposals even though prior
records were approved.

The Product Owner requests capacity for 500 retained records.

### 2. Required behavior

Increase supported repository-scoped retention capacity to
500 records, subject to validation of bounded storage and
read/write performance.

Preserve:

- Existing dispatch records and their original identifiers.
- Pending, approved, and rejected states.
- Approval history and associated milestone/event references.
- Atomic persistence and crash safety.
- Repository isolation.
- Existing permissions and Product Owner approval authority.
- Existing 64 KiB maximum dispatch body.
- Existing bounded API list-read behavior.

The larger retention capacity must not cause the readback
API to return hundreds of entries by default.

A repository with 50 existing records must accept its next
authorized submission without deleting history.

The 501st record must produce a clear capacity error if the
fixed limit remains 500.

Do not introduce silent eviction, automatic deletion,
record rewriting, or unbounded memory consumption.

### 3. Capacity and storage verification

Inspect the current repository-scoped JSON storage model and
identify the actual storage, serialization, and atomic-write
cost of increasing the cap.

Test representative records and larger payloads.

If 500 records creates an unacceptable safety or performance
problem, report the evidence and request a bounded Product
Owner decision rather than changing the persistence model
without approval.

Do not add a broad dispatch redesign unless the existing
bounded mechanism genuinely cannot support the requested
capacity safely.
