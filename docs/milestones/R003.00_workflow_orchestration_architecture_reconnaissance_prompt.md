# 1. Purpose

R003 begins the Workflow Orchestration arc.

R002 established and operationally accepted the Repo Control II Git foundation:

- browser-based Git review and routine mutation controls;
- Product Owner-controlled staging and commit;
- basic branch and remote operations;
- prepared-action safeguards;
- multi-repository selection;
- always-on systemd service;
- loopback-only browser service;
- Windows SSH tunnel/startup workflow;
- noninteractive GitHub Push using a dedicated repository-scoped Deploy Key.

The purpose of R003 is different.

R003 should reduce the Product Owner's current role as the **manual transport layer** between:

```text
ChatGPT / Architect
↕
Product Owner
↕
VS Code / Coding Agent
↕
Repository / Tests / Git
```

while preserving the Product Owner's role as:

```text
decision maker
approval authority

```

R003.00 is reconnaissance only.

Do **not** implement a workflow engine, new persistence layer, AI integration, coder integration, or broad UI changes in this milestone unless explicitly required to support reconnaissance evidence.

The output of this milestone should be a clear architecture/design roadmap for the first useful Workflow Orchestration implementation milestones.

# 2. Governing Principle

The system should implement the Product Owner's actual workflow rather than forcing the Product Owner to adapt to an invented process.

The intended principle is:

```text
standard process
+
flexible bounded iteration
+
durable decisions
+
explicit escalation for material change
```

Repo Control should make the normal path obvious and preserve important state without creating unnecessary ceremony.

# 3. Current Standard Operating Procedure to Analyze

Treat the following as the current real-world SOP that R003 must understand and eventually support.

## 3.1 Normal Milestone Flow

```text
1. Product Owner ↔ Architect discussion

2. Architect composes milestone prompt

3. Product Owner reviews prompt and commits it to Git

4. Coder reviews prompt and repository reality

5. Coder either:
   - proceeds;
   - asks questions;
   - identifies a blocker;
   - identifies a conflict with repository reality;
   - identifies an escalation.

6. Product Owner carries questions to Architect

7. Architect answers

8. Product Owner approves/clarifies where required

9. Product Owner carries answer back to Coder

10. Coder implements and tests

11. During implementation/testing there may be:
    - additional questions;
    - clarifications;
    - bounded bug fixes;
    - test failures;
    - stop conditions;
    - escalation;
    - Architect decisions;
    - Product Owner decisions.

12. Coder prepares closeout

13. Architect and Product Owner review closeout/evidence

14. Review may result in:
    - acceptance;
    - request for more evidence;
    - bounded correction;
    - clarification;
    - separate follow-up milestone.

15. Product Owner performs final Git staging / commit / push

16. Milestone closes
```

The milestone is a **bounded work container**, not a single prompt-response exchange.

# 4. Clarification / Decision / Scope Model to Analyze

R003 should distinguish between routine conversation and changes that materially alter the milestone.

Evaluate a three-level model similar to:

## 4.1 Routine Clarification

Example:

```text
Coder:
"Should this label say X or Y?"

Architect:
"Use X."
```

Expected handling:

```text
workflow event
no new milestone
no formal full prompt addendum required
```

## 4.2 Material Clarification / Lock-In

Example:

```text
Coder discovers repository behavior that conflicts with one part of the prompt.

Architect / Product Owner decides:
"Use the existing persistence model and supersede requirement 6 accordingly."
```

Expected handling:

```text
durable authoritative decision
or prompt addendum / lock-in
same milestone may continue if objective/scope remains bounded
```

## 4.3 Material Scope / Architecture Change

Example:

```text
discovery materially changes:
- objective;
- architecture;
- authority;
- risk;
- persistence model;
- implementation strategy;
- validation burden;
- product behavior.
```

Expected handling:

```text
stop
explicit Architect / Product Owner review
re-scope or create separate milestone
```

The reconnaissance should determine whether this three-level model is sufficient, too complex, or missing important cases.

# 5. Bug Handling Model to Analyze

The Product Owner currently allows bounded bugs discovered during implementation/testing to be fixed inside the active milestone without creating a new formal milestone.

R003 should preserve this flexibility.

Evaluate a rule such as:

```text
A bug may remain inside the active milestone when:

- it is directly related to the work being changed;
- the correction is bounded;
- it does not materially change architecture, scope, authority, or risk;
- the coder documents:
  - bug discovered;
  - classification;
  - fix;
  - validation.
```

Example:

```text
Milestone adds branch switching.

Testing reveals:
switching to the current branch produces an incorrect warning.

→ fix inside milestone
→ document as bug
→ rerun tests
→ continue
```

Contrast with a material discovery such as:

```text
repository-selection behavior may allow the wrong repo
to be targeted across browser sessions
```

which may require:

```text
stop
Architect review
Product Owner decision
re-scope or new milestone
```

The reconnaissance must recommend a practical rule that preserves flexibility without allowing silent scope expansion.

# 9. Flexibility Requirement

The workflow must not become unnecessarily bureaucratic.

The design should support the normal SOP while allowing unusual cases.

The reconnaissance should explicitly evaluate this principle:

```text
The SOP defines the normal path, not an inflexible state machine.

Repo Control should:
- make the normal path obvious;
- preserve important decisions;
- expose current state;
- enforce safety/authority boundaries.

Repo Control should not:
- require a new document for every small question;
- require a new milestone for every bug;
- force identical conversational patterns on every milestone;
- silently broaden scope;
- turn ordinary coding discussion into excessive process overhead.
```

Recommend where the system should be strict and where it should be permissive.

# 15. Stop / Escalation Conditions

Stop and ask the Product Owner before proceeding if reconnaissance indicates:

- the current workflow architecture materially conflicts with the governing context documents;
- a persistence/database decision must be made before a safe roadmap can be produced;
- existing code already implements workflow behavior that materially changes the intended direction;
- supporting the SOP would require changing the established Product Owner Git authority;
- direct AI/coder integration appears necessary before a useful first workflow slice is possible;
- repository-selection architecture creates cross-project safety concerns;
- the requested workflow would require storing secrets or credentials;
- implementation work appears necessary to answer a material architecture question;
- the milestone scope would need to expand from reconnaissance into substantial implementation.

Do not resolve those issues silently.
