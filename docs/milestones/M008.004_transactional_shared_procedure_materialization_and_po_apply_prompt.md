Each `os.replace` may be atomic for one file but a crash, out-of-space error, permission failure, process kill or concurrent edit can leave **multiple paths in mixed versions**, with no durable whole-update recovery record.

Do **not** claim POSIX filesystems supply a simultaneous atomic rename of all six paths: this milestone demands **crash-detectable, recoverable multi-file materialization and truthful status**, not unsupported ACID all-path visibility.

The recent M008.003.001 repair established that the external per-repository state directory is rebuilt by the scanner; **do not store recovery journals/backups in any location that scanner publication can erase**. Establish explicit safe ownership of durable transaction state, scanner interaction and cross-process locking before the first target write.

## 4. Safe transaction implementation

### 4.1 Prepare and revalidate

- Resolve a **single centrally registered repository** by key, stable ID and canonical absolute path. Require exact allowlisted manifest targets, valid local overlay and existing preview-provenance policy. Never infer an unregistered repo, take an arbitrary path, silently switch global Repo Control selection or change another repository.
- Before touching targets verify installed/current/target releases, canonical manifest/source hashes, lock bytes/hash, complete **server-generated** plan, expected old hashes/presence and no preview blockers (modified generated file, untrusted/invalid lock, incompatible overlay, source mismatch, symlink, nonregular file or unsafe parent). `STALE_VERSION` by itself is expected release drift and is not a defect.
- Serialize Apply and Recover *per target* across requests and processes; retain correct behavior if a scanner operates concurrently. Reject overlapping work or any unresolved transaction; do not let readers represent an incomplete operation as a completed release.
- Recheck all snapshots/identities/releases under this guard **at the final safe moment before writing**. Reject stale forms or changes to generated file/parent path between preview and confirmation, including symlink/path swap and time-of-check/time-of-use hazards.

### 4.2 Durable journal + exact recovery data

- Generate unique operation ID; before any target change, store complete bounded, integrity-checked durable journal and before-images for every managed target (including lock), with exact original presence/bytes/mode/hash, intended target hash/bytes, canonical release and manifest fingerprint, stable repository identity and path. Backups may contain only the known generated files. Use restrictive ownership/permissions; no raw bytes in browser output/logs. Ensure fsync/file+directory durability appropriate to supported Linux filesystem semantics.
- If any backup/journal preparation, write, sync, permissions or validation fails, abort **without target modification** and preserve diagnosis.
- Journal each unambiguous transition with crash-safe persistence. Mark the transaction VERIFIED only after **independent full-set status and hash validation** returns CURRENT and no outstanding journal inconsistency.
- Materialize only fixed manifest-specified files. Each replacement uses controlled tempfile/file descriptor, contents hash, safe parent containment, mode handling and appropriate sync/rename; write the release lock at the planned final step. A new lock by itself is never sufficient proof of success.
- Return a bounded success receipt with operation ID, repo key/release, hashes, affected files, completion timestamp and verified CURRENT; do not expose recovery content. No staged Git or workflow events.

### 4.3 Interruptions, failure, recovery

- For ordinary caught failure, attempt exact previous-state rollback only after verifying current paths are either the recorded before-image or known in-flight intended-image. Restore content/mode or remove *only files created by this transaction*, never broad directories/unknown paths. Independently verify exact restored pre-image and update journal. Failure to restore must be explicit RECOVERY_REQUIRED, not hidden, and must retain backups.
- After process restart, a persistent incomplete journal **must be detected** during read-only inspection, block further Apply and present a recovery diagnosis. Do not silently repair during status/preview/GET/page load/service startup or ordinary scan.
- Provide a **separate Product Owner Review Recovery → Confirm Recover** workflow tied to the original operation ID and its known exact paths/hashes. Recovery uses fresh CSRF, durable journal integrity and repository/release identity checks, one-time confirmation, interprocess serialization, snapshot revalidation and explicit PO intent. May restore known pre-update state; an alternative resume-to-intended state is permissible only if equally proven safe. Never do both opportunistically.
- If any affected target differs from **both** the saved original image and the known intended image (e.g. external editor modified the path), do not overwrite, skip or silently reconcile. Block automatic recovery, retain all evidence and give precise PO escalation instructions.
- Prevent repeated Apply, stale confirmation/replay, concurrent recovery/apply, startup/restart race, in-flight journal corruption, temporary backup disappearance, bad permission, symlink/path escape, target out-of-repo writes and journal cleanup before verified resolution.
- Retain minimal safely bounded final receipt, with a defined policy for secure backup cleanup only after verification and recovery no longer required. Journal states and any failure remain truthful even if files individually appear CURRENT. Document crash and power-loss limits without overclaiming.
