Document these standing rules:

- Repo Control II owns the canonical versioned generic shared-procedure bundle.
- Each managed repository contains its own physical/generated shared-procedure artifacts and `.repo-control/shared-procedure.lock.toml`.

- Current deterministic inspection uses `coder-procedure-status` followed by `coder-procedure-preview`.

# PART C — ONBOARDING / INTEGRATION GUIDE

## 4. `repository_onboarding_and_integration_guide.md`

Add a clear subsection such as `Shared-procedure lifecycle after onboarding` near the existing shared-procedure status/preview material.

Explain the practical lifecycle:

1. A new repository is onboarded directly to the canonical shared-procedure release current at that time.
2. Successful onboarding ends with that repository reporting `CURRENT` and its local overlay valid.
3. A later canonical release does not automatically propagate into already-managed repositories.
4. Existing repositories remain pinned to their installed release until separately reconciled.
5. Such repositories may report `STALE_VERSION`; this is normal release drift when caused by a newer canonical release.
6. For each repository, inspect status and deterministic preview before any write.
7. If the preview is clean and expected, reconciliation is separately Product Owner-authorized, materialized through the guarded internal path, then revalidated to `CURRENT` and reviewed through ordinary Git workflow.
8. If preview shows overlay invalidity, edited generated files, collisions, incompatible state, unexpected removals/changes, or another blocker, do not treat it as routine reconciliation; stop and investigate under an appropriately scoped milestone.

Make explicit that a new repository does not repeat historical Vocab catch-up milestones. It starts at the current canonical release. Only future release changes may create ordinary version-maintenance drift.

Do not claim that automatic warning, a browser Review Update button, or an Apply Update button exists today.
