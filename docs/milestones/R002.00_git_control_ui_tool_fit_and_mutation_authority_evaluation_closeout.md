## 1. Executive Recommendation

**Recommended direction: A — a narrow custom Repo Control Git UI, based on the existing Flask shell, for the near-term Git-control surface.** This is a recommendation for Product Owner / Architect approval, not an architecture lock-in.

Keep the custom scope deliberately small: trustworthy Git status, changed-file categorization, per-file diff review, selective staging, commit preparation/message review, and explicit Product Owner execution with verification and audit evidence. Defer complex branch-graph, conflict-resolution, history-editing, and forge experiences rather than attempting to reproduce them now.

GitButler is capable and its documented terminal UI can run in an SSH terminal, but its primary GUI is a local desktop application rather than a documented remote-workspace browser UI. Its remote-support issue remains open. Its virtual-workspace semantics also conflict with the inherited services' direct reliance on Git's current branch/index and ordinary `git add`/`git commit` execution. A separate GitButler TUI could be revisited if the Product Owner prefers terminal UI and is willing to make GitButler the exclusive Git mutation tool; do not mix GitButler writes with Repo Control's current write services.

This recommendation is specific to the current environment: the authoritative repository is on `henderson-server1` and the Product Owner works through VS Code Remote SSH and a browser. A web application served on the server and accessed over an SSH tunnel fits that operating model without a second checkout. GitButler's TUI is a possible remote-host fallback, but it is not the desired browser GUI and carries distinct repository workflow semantics.

The current mutation model is not inherently invalid because it has browser routes. A deliberate Product Owner action may authorize a Git mutation. The current review page is not yet sufficient: stage/commit approval lacks diff evidence, stage is `--all` only, the app authenticates no distinct user, and the service boundary currently couples commit planning to snapshots. Improve review and revalidation before expanding mutations.

## 5. Product Owner Mutation-Authority Matrix

The invariant is: **a coding agent does not decide or perform Git mutations.** A Product Owner may authorize a Repo Control action by an explicit, informed action; the browser transport itself is not the authority. All mutation paths must retain a visible preview, explicit confirmation, and scope/state revalidation.

| Action | Initial Repo Control policy | Required authority / evidence |
| --- | --- | --- |
| Status, diff, log, branch/remote/tag listing, ahead/behind | Read-only information | Available without approval; label local refs vs refreshed remote data |
| Stage / unstage | Allow near-term after implementation | PO selects exact paths/hunks; review status and diff; confirm exact plan; revalidate immediately before index change |
| Commit | Allow local commit after implementation | PO reviews staged paths and staged diff, exact message, branch/HEAD, preconditions, identity/hooks; explicit commit confirmation; no implicit push |
| Branch create | Later, low-to-moderate risk | PO confirms name and base; show resulting target and dirty state |
| Branch switch | Later | Preview source/destination and exact working-tree impact; block unsafe overwrite; explicit confirmation |
| Tag create | Later | Preview tag name, target commit, annotated/lightweight choice; explicit confirmation |
| Fetch | Later; can be read-only to working files but updates local refs | Show remote and ref scope; PO initiates; report fetched state and avoid implying push/pull |
| Push | Keep outside initial Repo Control surface | External tool initially; if added, preview remote, branch, commits, upstream, and whether force is requested; explicit confirmation; force-push remains disabled by default |
| Pull | Keep outside initial surface | External tool initially; preview remote/base and local modifications; explicit confirmation due worktree/ref changes and conflicts |
| Merge / rebase | Keep outside initial surface | External tool initially; require source/target, commit graph, working-tree status, conflict/recovery plan, and explicit confirmation |
| Reset / clean | Keep outside initial surface | Destructive; require exact affected paths/commits, data-loss warning, recovery option, and a separate explicit confirmation if ever introduced |
| Stash | Useful later / external initially | Show included/untracked paths and restore target; explicit confirmation |
| Conflict resolution | External initially | Human reviews conflict sides and final diff; do not delegate resolution approval to a coding agent |

These rules do not authorize implementation in R002.00. Existing stage/commit endpoints were inspected as evidence only.

## 6. Required Review / Approval Contract

### Stage / unstage

Before approval, display repository, branch, full HEAD, workflow/conflict state, exact selected paths/hunks, per-path status, readable diff, and explicit binary/large-file/unsupported indicators where a textual diff is unsuitable. Do not silently omit files from the reviewed scope. Bind the plan to a deterministic fingerprint and revalidate branch, HEAD, index, and worktree immediately before executing. The current `--all` plan is not equivalent to selective Product Owner staging.

### Commit

Before approval, display branch, HEAD, exact staged paths and statuses, staged diff (including binary/large-file indication), full commit message, local-only effect, hook/identity readiness, and blocked preconditions. Approval must identify the exact immutable plan. Revalidate staged fingerprint and current state before commit; report the resulting commit ID and execution evidence. No implicit staging, amendment, fetch, or push. Revisit the snapshot prerequisite as part of decoupling from the legacy scanner.

### Branch / merge / rebase / push

If introduced later, show source/destination refs, local and remote state freshness, exact commits/files affected, divergence, likely conflicts, force/non-fast-forward behavior, and recovery option before confirmation. Never make a force update the default.

## 7. Single-Operator / Authentication Assumption

**Recommendation:** explicit application authentication is **not required for the current single-Product-Owner architecture**, provided the app remains loopback-bound and access is through the trusted operator's SSH account/port-forwarding. This relies on host and SSH account security; it is not user authentication.

Before multi-user use, network binding beyond loopback, shared hosting, or delegation to other operators, define authentication, authorization, attribution, and audit identity. CSRF protection prevents some cross-site request attacks; it does not identify the person approving. Keep the local-only boundary and do not claim CSRF equals Product Owner authentication.

## 8. Custom Repo Control UI Assessment

**Strengths:** Fits the authoritative Linux repository plus VS Code Remote SSH/browser workflow; can show Repo Control workflow state and Git evidence together; existing Flask app, service boundaries, temporary-repository tests, CSRF checks, loopback binding, and prepare/review/approve sequence offer salvage value. A narrow UI can use Git's CLI as authority without building Git internals.

**Costs/risks:** Repo Control must implement and test diff presentation, exact selection, escaping/path edge cases, large/binary diffs, state revalidation, and failure recovery. Building a complete branch/history/conflict GUI would create an unnecessary second Git product. Flask remains an implementation choice, not a durable architectural requirement.

**Assessment:** Good basis for a focused Git-control browser surface; poor basis for reproducing every advanced Git UX. Keep the initial scope status → diff → exact stage plan → commit review → explicit local action.

## 9. GitButler Assessment

Evidence was reviewed from GitButler's official [getting-started guide](https://docs.gitbutler.com/guide), [desktop overview](https://docs.gitbutler.com/overview), [TUI guide](https://docs.gitbutler.com/gitbutler-tui), [CLI command reference](https://docs.gitbutler.com/commands/commands-overview), [Linux support notes](https://github.com/gitbutlerapp/gitbutler/blob/master/LINUX.md), [release tracks](https://docs.gitbutler.com/releases), [license](https://github.com/gitbutlerapp/gitbutler/blob/master/LICENSE.md), and public remote-development [issue #5941](https://github.com/gitbutlerapp/gitbutler/issues/5941). No software was installed.

- **Features:** Strong GUI/TUI for diffs, file/hunk selection, parallel/stacked virtual branches, commit creation/editing, operation history, undo/redo, conflict handling, push/fetch, and forge/PR integration. The documented `but tui` is a realistic SSH-terminal option and is substantially more capable than a plain CLI.
- **Remote-operating fit:** The official GUI is a local desktop app that imports a local directory. Official Linux packaging lists x86_64 deb/rpm/AppImage, with Ubuntu 22.04/24.04 as the documented supported distributions in `LINUX.md`; exact server distribution/GUI availability has not been confirmed. The TUI can run in the remote terminal, but does not supply the browser GUI requested by the current user operating model. Issue #5941 remains open and was updated 2026-07-20. Discussion describes remote backend/browser ideas, not a supported SSH-workspace deployment contract.
- **Experimental web backend:** Issue discussion points to experimental server/browser work and PR [#9482](https://github.com/gitbutlerapp/gitbutler/pull/9482), titled “Experiment: Gitbutler Electron.” The PR describes itself as an off-the-clock experiment with unfinished remote file picking and no server distribution plan in its checklist; it was closed after work was split into smaller changes. The current end-user docs reviewed advertise desktop, CLI, and TUI, not a supported self-hosted browser frontend. Treat backend/web capability as unverified and unsupported for this decision, not as a remote GUI option.
- **Workflow semantics:** `but setup` registers the repo, switches to `gitbutler/workspace`, configures a target branch, and may add `gb-local`. GitButler uses virtual/staked branch concepts; its docs warn vanilla Git branch/index operations may behave unexpectedly in workspace mode. It is therefore not a drop-in executor for Repo Control's current direct index-based stage/commit services. Coexistence must not mean concurrent write authorities.
- **Integration surface:** Public docs provide a CLI/TUI and machine-readable command output, but the evaluation found no documented stable general-purpose API contract for Repo Control to embed or safely drive all operations. An external `but` process can be evaluated separately; do not assume interface stability or automate mutations without a defined contract.
- **Linux/deployment:** Standalone Linux GUI support exists, but that alone does not place its UI on the Windows workstation while operating on the authoritative remote repository. SSH-terminal TUI is viable but is a different UX choice.
- **Confidence / limits:** Sufficient to recommend against GitButler as the primary browser UI in the current remote-SSH setup. Exact TUI usability on the server and any evolving server experiment are not empirically verified. If the Product Owner prefers TUI or GitButler remains attractive, authorize a disposable-repository hands-on spike later; no need to install for this architecture recommendation.

## 10. Hybrid / Split Architecture Assessment

A hybrid could keep Repo Control responsible for project/milestone state, Git facts, policy, and evidence while GitButler supplies advanced Git interaction. This avoids building a branch-graph/conflict engine, and GitButler operations can be made visible in ordinary Git state after refresh.

However, a desktop GitButler instance cannot presently be assumed to operate on the authoritative remote checkout; using its TUI would mean switching from the browser control plane to a terminal UI. More importantly, GitButler workspace-mode writes and Repo Control's current index-based stage/commit writes cannot safely be mixed without a defined exclusivity/transition contract. No documented stable embed API was found. A loosely coupled hybrid would also split review, approval, and audit across two products.

**Assessment:** Defer hybrid integration. If later adopted, make GitButler the exclusive Git mutation surface during its workspace mode; Repo Control should be read-only toward Git during that period and must not execute its own stage/commit plans. Do not let both tools independently mutate the same index/worktree.

## 13. Open-Source / Licensing Assessment

GitButler's repository currently identifies **Functional Source License 1.1 with MIT Future License (FSL-1.1-MIT)**, not a plain MIT license on day one. Source is available and the terms permit internal use, copying, modification, and derivative works for permitted purposes; the license restricts a defined “Competing Use” during the two-year period before the additional MIT grant becomes effective for that version.

This is fair-source/source-available, not an unrestricted OSI-style MIT license during the restricted period. A private internal use is expressly listed as permitted, but redistributing or offering a GitButler-based or substantially similar commercial product/service may raise license questions. Verify the exact license attached to the version used and seek legal review before bundling, modifying for distribution, or offering Repo Control commercially. Prefer upstream use/configuration over a fork; no fork appears technically necessary for ordinary standalone use.

This is an engineering evaluation, not legal advice. The recommendation does not adopt, redistribute, or embed GitButler.

## 14. Selected Architecture

**Recommended selection: A — Custom Repo Control Git UI, narrowly scoped to the remote-accessible core workflow.**

Why: it fits the actual server/browser/SSH-forwarding environment, lets Repo Control keep a single Product Owner review/approval trail, uses ordinary Git facts as the source of truth, avoids requiring a second workstation checkout, and avoids mixing GitButler virtual-workspace state with existing Git services. This is not a recommendation to reproduce advanced GitButler features.

The immediate product boundary is a narrow custom web review surface. Keep branch graphs, advanced history surgery, push/pull, merge/rebase, and conflict resolution out of scope until demonstrated necessary. GitButler's TUI remains a possible external tool for an explicit later decision, not a concurrent mutation engine.

## 15. Repo Control Ownership Boundary

Repo Control should own the browser-facing core Git-control workflow: repository selection, deterministic Git facts, changed-file and diff presentation, exact action plan, Product Owner review/confirmation, precondition revalidation, local stage/commit orchestration, and evidence that records outcome. Git remains the authority for branch/index/commit state. Workflow/milestone orchestration remains Repo Control's responsibility and must not be conflated with Git state.

## 16. External Tool Ownership Boundary

No external Git UI is selected for the near-term core workflow. GitButler may later be used as a separate advanced Git UI/TUI only under an explicit boundary:

- one Git mutation authority at a time;
- if GitButler workspace mode is active, Repo Control's stage/commit execution is disabled;
- Repo Control consumes Git-derived read-only state and records relevant evidence after refresh;
- no silent `but` command execution or assumed embed API.
