# M010.004 — Repo Control Information Architecture and Transition Design (Design-Only)

## Objective and controlling boundary
Define a practical, unified **Repo Control information architecture** for the existing Repo Control II application. Expand the M010 persistence arc from workflow sidecars alone to the Product Owner's intended model: Repo Control centrally manages milestone prompts, workflow events, approvals, closeouts, and optionally governed project documents; approved closeouts can be explicitly published into Git alongside software changes. Preserve every functioning existing workflow until its replacement has been implemented, verified, and separately authorized for cutover. Prioritize less duplicate handling, fewer files, clearer authority and substantially reduced Product Owner copying, not a platform rewrite.

## Design context and explicit Product Owner direction
Read the M010.001–M010.003 accepted design/POC/closeout evidence, the current project context/architecture/workflow and canonical shared-procedure rules, and relevant actual source interfaces. In M010.003, the proposed SQLite design kept prompts, closeouts, governing documents, selection and dispatches in their original stores. **This milestone reconsiders that boundary** before any M010.004+ SQLite implementation. Do not silently treat M010.003's narrower placement proposal as final authority for the revised scope; preserve its tested findings, v1 lifecycle invariants and residual WAL-corruption record.

Product Owner priorities:
- One self-contained, hobby-scale, single-user Repo Control installation on one Linux machine; reuse working Repo Control II components.
- Eventually use SQLite as the likely central workflow/document store, without assuming every file or derived graph must live inside SQLite.
- Prompts and workflow activity are operational records. Closeouts are especially valuable human-readable historical summaries: Product Owner wishes to **accept a closeout, then optionally publish the exact approved revision into Git** with the relevant code/reconnaissance changes.
- Keep source code, tests, Git state and source-truth in Git. Preserve bootstrap and executable agent instructions available to cold Coder sessions even if Repo Control is temporarily inaccessible.
- Users must be able to select, browse, view exact versions, compare, search, and extract/download documents; Architect and Coder require complete read access through bounded, explicit, provenance-rich tools, not manual copy/paste. Role-limited write/approval remains a separate authority.
- Existing `*_prompt.md`, `*_workflow.md`, `*_closeout.md`, context/architecture/workflow documents, shared procedure publication/installation, agent handoff, Git actions, and graph facilities **continue without alteration until replacement parity and PO-approved transition**. Do not prematurely delete, move, redirect, or deprecate functioning artifacts.
- Accept proportionate routine database/hardware risk; retain the M010.002 deliberately corrupted WAL result as FAIL/B1 historical evidence, but no bespoke WAL recovery engine, secondary event ledger, general replication system, intensive disaster-recovery research, or unrequested enterprise/multi-user features.

## Required bounded architectural outputs
1. **Current map and minimal-change feasibility.** Inspect with targeted symbol/source/file ranges, leveraging Repository Intelligence if materially useful and explaining if not. Inventory existing authoritative stores and exactly who reads/writes them: workflow sidecars/reducer and event lifecycles; prompt and closeout handling; document role mapping; repository registration/selection; historical search; Architect read-only MCP and proposal/approval; Coder CLI and bootstrap; canonical procedure release, lock, physical generated skill/AGENTS/copilot artifacts; graph build/status/provenance; Git-control UI and status; local service/state-root. Distinguish current operational dependencies, code version, runtime, and what would be affected by moving document ownership. Avoid a wholesale repo audit.
2. **Authority matrix with crisp placement choices.** For each class (prompts, workflow/event ledger, closeouts, project context, architecture, workflow/coding guide, parking lot, shared procedures/Skills, generated agent entrypoints/locks, graph/index data, graph provenance, source code/tests/config, Git metadata, history documents, selection pointer, Architect dispatches), recommend (a) the ultimate authoritative owner, (b) exact consumer-facing access path, (c) whether it must remain a repository file/materialized cache for startup/offline use, (d) optional Git publication/snapshot policy and (e) what is explicitly out of initial scope. Do NOT confuse central authoring with mandatory relocation of every repository document. Preserve Git as code authority, code-derived graph rebuildability, and clear per-repository document versions. Resolve cross-repository identification, historical versioning, and the chicken-and-egg bootstrap problem without duplicating writable authority.
3. **Documents and lifecycle contract.** Define a minimal central document library: repository/milestone/type IDs, original source path/migration hash, Markdown content, immutable approved/reviewed revisions, draft-versus-approved status, version timestamps, provenance, link/attachment considerations, full-content retrieval, search/filter, export and optional approval policy. Integrate stable document revision IDs with workflow records: prompt selection/approval identity; closeout submission/acceptance; Architect dispatch linked decisions; immutable historical evidence. Preserve all 21 current event types and six lifecycle phases, exact source payloads, bindings, questions/bugs/escalations, acceptance/reopen/closure and current PO authority. Distinguish documents with mutable working drafts from approved immutable revisions. State essential transactional consistency without inventing a distributed transaction manager.
4. **Explicit closeout-to-Git publishing UX.** Specify a simple PO-controlled workflow: Coder submits document -> PO accepts exact closeout revision -> separately choose 'Publish approved closeout to Git' -> deterministic Markdown file preview/diff and target commit association -> ordinary existing PO Git staging/commit controls -> Repo Control records success/failure, published document revision/hash/commit. Publishing is optional and NOT identical to acceptance; no auto-commit, no Coder Git mutations, no duplicate editable Git authority and no claim of an atomic SQLite+Git commit. Define safe idempotent retry, collision and publication drift handling, and accurate UI statuses. Consider closeouts documenting reconnaissance with no code change.
5. **User and agent access contract.** Outline repository-aware document browser and bounded search, exact view/version compare, single/bulk Markdown export, and clear authority labels. Architect and Coder should obtain full intended document content through Repo Control tools with stable IDs, optional range/chunk retrieval for large items, hashes and source attribution, while respecting tool payload bounds. Keep approval/edit privileges governed separately. Detail minimal additions or adaptations to existing MCP/CLI and bootstrap, including useful behavior when the service is down; avoid requiring operator to paste Architect responses or complete duplicate summary forms.
6. **Canonical procedures, context, and intelligence boundaries.** Explain how a centrally managed source of project context and reusable procedure releases can coexist with pinned generated `AGENTS.md`, `.github/copilot-instructions.md`, Skills, per-repo overlays and lock hashes; do not discard existing PO Apply/Recover/version provenance. State whether context documents are centrally authored versus copied to repos in the first phase, how reconciled versions work, and whether generated artifacts are installation products rather than master content. Treat repository graphs/indexes as rebuildable derivative data tied to Git commit/source hashes; do not mistake cached graphs for original source authority. No mandatory migration of everything into SQLite.
7. **Runtime and packaging choice.** Briefly compare continuing existing `systemd + pinned Python environment + embedded SQLite` versus containerizing the Repo Control application with persistent, owner-protected host storage and bounded access to repositories/Git/agent tools. SQLite itself is embedded, not a separate database-server container. Provide one recommendation with actual integration/operations cost, no speculative benefits. Design a check of the actual Python-linked SQLite version for the known WAL-reset fix (M010.003 conservative gate >=3.51.3 or documented fixed backport), without upgrading the host, installing, or containerizing in this milestone.
8. **Evolution vs Repo Control III.** Assess whether existing Repo Control II layering can support the central document/library model economically. Recommend retain/restructure Repo Control II or start Repo Control III ONLY if specific code-coupling and risk evidence justifies it. Do not initiate or register a new repository. Keep branch and arc identity unless PO separately decides otherwise.
9. **Small replacement roadmap with explicit cutover gates.** Propose *few* bounded M010.005+ milestones separating minimal schema/facade and fixture tests, document browsing/agent access, optional Git publication, data import/parity, and separately authorized live transitions. The existing v1 sidecars and Markdown documents MUST remain fully functional, authoritative, and readable until all relevant replacement readers/writers, handoff tools, docs, procedures and Git access pass parity. Migration initially uses read-only copies/disposable fixtures; no dual writable authority. Define one-way authority switches with preflight/rollback and what old files become afterward. Do not overdesign recovery or require arbitrary numeric RPO/RTO before continuing architectural work. If a transitional hybrid is recommended, name exact boundaries and avoid circular bootstrap or hidden manual handoffs.
