## Milestone Mode

```text

```

This is the first R002 milestone that authorizes Repo Control to perform local Git mutations from the browser.

The Product Owner remains the mutation authority.

The coding agent may implement and test mutation behavior only in isolated temporary test repositories.

The coding agent must **not** stage, unstage, restore, commit, branch-switch, fetch, push, tag, or otherwise mutate the authoritative Repo Control repository.

---

## Reasoning Level

Use high reasoning.

The milestone crosses a major trust boundary:

```text
read-only evidence
→ Product Owner decision
→ Git mutation
```

Correctness is not enough.

The implementation must also make it difficult to:

```text
execute the wrong action;
execute against stale evidence;
affect the wrong path;
commit unintended staged content;
repeat an action accidentally;
or turn a preview into an implicit mutation.
```

# 1. Product Goal

Extend the accepted Git Review experience so the Product Owner can safely perform the routine local Git actions required during normal development:

```text
stage selected changes
unstage selected changes
restore selected unstaged changes
restore a selected tracked file to HEAD
commit explicitly staged changes
```

The normal workflow should become:

```text
inspect
↓
preview
↓
prepare / confirm
↓
revalidate current Git state
↓
execute exactly one authorized action
↓
verify actual post-action Git state
↓
return to Git Review
```

No mutation should occur merely by viewing a page, following a normal GET link, or opening a preview.

# Part I — Mutation Authority Contract

## 8. Product Owner Is the Executor

Repo Control may execute a local Git mutation only after an explicit Product Owner browser action.

The coding agent is not authorized to use the new functionality against the authoritative repository during implementation.

The browser action must be deliberate and specific.

Do not implement:

```text
auto-stage
auto-commit
cleanup suggestions that execute automatically
background mutation
mutation on page load
mutation on GET
```

---

## 9. Required Mutation Flow

Every supported mutation must follow the same conceptual contract:

```text
1. Inspect current evidence
2. Preview exact consequence
3. Prepare a bounded action
4. Show confirmation page / confirmation state
5. Product Owner explicitly confirms
6. Server re-reads authoritative Git state
7. Server verifies the prepared action is still valid
8. Execute exact bounded Git action
9. Re-read Git state
10. Display verified result
```

If revalidation fails:

```text
DO NOT EXECUTE
```

Instead:

```text
Prepared action is stale.
Repository state changed.
Review current evidence again.
```

---

## 10. No GET Mutations

All Git mutation endpoints must require:

```text
POST
```

A normal GET request must never mutate:

```text
worktree
index
HEAD
refs
commit history
```

Use Post/Redirect/Get or an equivalent pattern so browser refresh/back navigation does not repeat a completed mutation.

---

# Part II — Prepared Action / Confirmation Safety

## 11. Prepared Action

Implement a small bounded prepared-action mechanism for mutation confirmation.

Prefer:

```text
in-memory only
short lived
single use
unguessable token
no new persistent database
```

A prepared action should be bound to the exact repository/action/current state needed for safe execution.

Do not persist long-lived mutation plans unless existing architecture absolutely requires it.

---

## 12. Prepared Action Contents

The server-side prepared action should contain enough state to establish:

```text
repository identity
action type
selected path(s)
current branch
HEAD OID
relevant Git status
relevant index/worktree identity
comparison / preview evidence identity
creation time / expiry
```

For commit, it must also bind to the exact staged state being reviewed.

Do not rely on:

```text
filesystem timestamps alone
browser-hidden fields alone
human-readable labels alone
```

for stale-state protection.

---

## 13. Fresh-State Revalidation

Immediately before execution, recompute the action-relevant Git state.

Examples:

```text
stage:
selected worktree/index state must still match prepared state

unstage:
selected staged/index state and HEAD must still match

restore unstaged:
selected worktree/index state must still match preview

restore to HEAD:
HEAD plus selected index/worktree state must still match preview

commit:
HEAD and the complete staged scope/content identity must still match
```

Unrelated state may remain irrelevant where Git semantics allow it.

Do not invalidate an otherwise safe commit merely because an unrelated unstaged file changed, unless the implementation cannot distinguish safely.

---

## 14. Token Safety

Prepared-action tokens must be:

```text
unguessable
single use
short lived
bound to one action
bound to one repository
```

A token must fail if:

```text
expired
already used
unknown
wrong action
wrong repository
state no longer matches
```

Do not treat a token itself as evidence that Git state is still current.

Revalidation is still required.

---

# Part III — Global Mutation Guards

## 15. Block Unsupported Repository States

Mutation controls should fail closed when the repository has an unsupported in-progress state such as:

```text
merge
rebase
cherry-pick
revert
bisect
unresolved conflicts
```

Do not attempt conflict resolution in R002.05.

Detached HEAD should not permit commit in the normal R002.05 flow.

If stage/unstage/restore behavior in detached HEAD is not clearly worth supporting, disable all R002.05 mutation controls there for simplicity.

Document the chosen behavior.

---

## 16. Repository Identity

Continue to operate only on the Repo Control instance's configured repository root.

Do not accept arbitrary repository paths from browser input.

Mutation requests must not be able to target a different repository.

---

## 17. Path Identity

Use the same byte-safe/literal-path principles established in R002.02/R002.03.

User-supplied text must not become arbitrary Git pathspec syntax.

Resolve browser selection tokens against the fresh Git inventory.

Use literal pathspec handling.

No shell interpolation.

# Part IV — Selective Stage

## 18. Stage Scope

Support staging explicitly selected paths.

At minimum, support routine cases:

```text
tracked modified file
tracked deleted file
untracked regular file
path with staged + additional unstaged changes
```

Where the existing status model safely supports rename semantics, staging a rename may include both current and original path as necessary.

If rename/copy staging cannot be made unambiguous within existing evidence, fail closed for that case and document it.

---

## 19. No Stage-All

Do not use:

```text
git add -A
git add .
git add --all
```

as the normal R002.05 implementation.

The Product Owner must know which path(s) are being staged.

A future UI may offer explicit multi-selection, but the backend must still receive an explicit bounded path set.

Per-file staging is acceptable for the initial implementation.

---

## 20. Stage Preview

Before staging, show:

```text
selected path
current state
what content/state will be added to the index
whether the path is currently untracked
whether existing staged content will be updated by additional worktree changes
whether evidence is incomplete
```

Stage is not normally content-destructive, but it still changes the index and must use the prepared-action/revalidation flow.

---

## 21. Stage Execution

Use an explicit path-bounded Git command.

A likely implementation is:

```text
git add -- <literal selected path(s)>
```

Do not use shell expansion.

After execution, verify the selected path's new Git state.

Do not claim success merely because the command returned zero if the expected resulting state is not observed.

---

# Part V — Selective Unstage

## 22. Unstage Scope

Support unstaging explicitly selected staged paths.

Relevant cases include:

```text
staged modification
staged addition
staged deletion
staged + additional unstaged changes
```

No unrelated staged path may be changed.

---

## 23. Unstage Semantics

Use semantics equivalent to:

```text
restore index for selected path from HEAD
leave worktree content unchanged
```

A likely implementation is:

```text
git restore --staged -- <literal path>
```

Document any different command if chosen.

For a staged addition, the file should become untracked if it remains in the worktree.

For a staged deletion, the deletion should become unstaged if the worktree path remains absent.

For staged + unstaged content, worktree content must remain untouched.

---

## 24. Unstage Preview

Reuse the R002.03 unstage consequence model where possible.

The confirmation must clearly state:

```text
INDEX WILL CHANGE
WORKTREE WILL NOT BE REPLACED
```

and show the relevant staged evidence.

---

# Part VI — Restore Unstaged Changes

## 25. Restore-Unstaged Scope

Support a tracked selected path with ordinary unstaged changes when the existing R002.03 preview evidence is complete and supported.

Semantics:

```text
working tree
→ replaced from current index

index
→ unchanged
```

This operation is destructive to current unstaged content.

---

## 26. Destructive Action Requirements

For restore-unstaged execution:

```text
complete relevant preview evidence is required;
selected state must revalidate exactly;
confirmation must clearly describe discarded content;
the action must be path-bounded;
post-action state must be verified.
```

If required preview evidence is:

```text
truncated
binary in a way that prevents safe review
undecodable
unsupported
conflicted
ambiguous rename/copy
```

do not offer execution in this baseline.

Manual Git remains the fallback.

---

## 27. Restore-Unstaged Execution

A likely implementation is:

```text
git restore --worktree -- <literal path>
```

or the equivalent explicit safe command.

Do not change the index.

For a file with staged + additional unstaged changes, the staged version must remain staged after the restore.

---

# Part VII — Restore Selected File to HEAD

## 28. Restore-to-HEAD Scope

Support ordinary tracked paths where R002.03 can fully establish the effect of replacing both:

```text
index
and
worktree
```

with the selected file's `HEAD` version.

A likely implementation is:

```text
git restore --source=HEAD --staged --worktree -- <literal path>
```

Do not execute until exact state is revalidated.

---

## 29. Restore-to-HEAD Is Highly Destructive

The confirmation page must clearly state that this action can discard:

```text
staged changes
and
unstaged changes
```

for the selected path.

Show:

```text
HEAD OID used as source
staged diff that would be lost
worktree-vs-HEAD diff that would be lost
affected Git layers
```

---

## 30. Unsupported Restore-to-HEAD Cases

Do not offer restore-to-HEAD execution for:

```text
untracked paths
path absent from HEAD / staged new file if execution would imply deleting the only worktree copy
conflicted paths
ambiguous rename/copy state
incomplete required evidence
unsupported binary/undecodable evidence where the Product Owner cannot review the consequence
```

This bounded baseline intentionally prefers refusing an edge case over implementing broad reset/checkout behavior.

---

# Part VIII — Local Commit

## 31. Commit Only Explicitly Staged Content

Commit must never stage files implicitly.

Do not use:

```text
git commit -a
git add before commit
```

The commit operation applies only to the exact staged state the Product Owner reviews.

Unstaged/untracked files may remain in the working tree and must remain uncommitted.

---

## 32. Commit Review

Before allowing confirmation, show:

```text
current branch
HEAD OID
complete staged file inventory
status for each staged path
bounded staged diff evidence
any remaining unstaged/untracked changes as a separate warning/summary
commit message to be used
```

The UI must make clear:

```text
Only staged content will be committed.
```

---

## 33. Commit Message

Require an explicit Product Owner-supplied commit message.

At minimum support a normal one-line commit subject.

Optional body support may be included only if it remains simple.

Do not launch an editor.

Do not generate an AI commit message in this milestone.

Do not silently rewrite the Product Owner's message.

Reject an empty/whitespace-only message.

Use argument-array/stdin handling; never shell-interpolate the message.

---

## 34. Commit Restrictions

Do not implement:

```text
--amend
--allow-empty
--all / -a
--no-verify as a default bypass
GPG/signing configuration changes
author rewriting
date rewriting
```

If the repository has active custom commit hooks or hook behavior that makes safe deterministic testing impossible, report it and escalate rather than bypassing security/process controls silently.

---

## 35. Commit Revalidation

Immediately before commit:

```text
HEAD must still match prepared HEAD;
current branch must still match;
no unsupported Git operation/conflict may have appeared;
the staged file inventory must still match;
the staged content identity must still match the reviewed state.
```

Unrelated unstaged changes need not invalidate the commit if the implementation can prove the staged state is unchanged.

If staged state differs:

```text
DO NOT COMMIT
```

Return to review.

---

## 36. Commit Execution

Use standard Git CLI without shell interpolation.

A likely form is:

```text
git commit -m <message>
```

or another non-interactive argument-array/stdin equivalent.

After success, verify:

```text
new HEAD differs from prior HEAD;
new commit subject/message matches expectation;
staged state is cleared for committed paths;
remaining unstaged/untracked state is accurately reported.
```

Do not push.

# Part X — Mutation Result UX

## 39. Result Must Be Verified, Not Assumed

After each action, show a concise result based on fresh Git inspection.

Examples:

```text
Stage complete
Path is now staged.

Unstage complete
Path is no longer staged; worktree content remains.

Restore complete
Unstaged changes for this path are no longer present.

Commit complete
Created <short OID> <subject>.
```

If verification does not match expectation:

```text
Action command returned, but expected Git state was not verified.
```

Treat that as an error/unknown state.

# 59. Definition of Done

R002.05 is complete when:

```text
- selected routine paths can be staged;
- selected staged paths can be unstaged;
- supported unstaged tracked changes can be restored from the index;
- supported tracked paths can be restored to HEAD;
- staged content can be committed with an explicit Product Owner message;
- no commit implicitly stages content;
- every mutation uses preview / prepare / explicit confirm / revalidate / execute / verify;
- prepared actions are short-lived, single-use, and state-bound;
- stale actions fail closed;
- destructive restore requires complete supported evidence;
- mutation routes are POST-only;
- browser refresh cannot repeat a completed mutation;
- unsupported conflict/rename/incomplete cases fail closed as defined;
- the authoritative Repo Control repository is never mutated by coder tests;
- all actual mutation tests use isolated temporary repositories;
- R002.02–R002.04 read-only functionality remains intact;
- full regression suite passes;
- primary routine Git mutation moves into Git Review;
- legacy Workflow is removed from primary navigation if no required non-Git behavior blocks that change;
- no branch or remote mutation is added;
- one closeout exists under the exact required filename;
- the Product Owner receives a safe manual acceptance procedure.
```

Core principle:

```text
Repo Control may change Git only after the Product Owner
has seen the consequence, explicitly confirmed it,
and the server has proven the reviewed state is still current.
```



# R002.05 — Product Owner UX / Batch Action Addendum

## Status

This addendum continues **R002.05 — Safe Local Git Actions**.

The initial R002.05 implementation established the required mutation-safety architecture and has been checkpoint-committed. Product Owner browser review identified a usability limitation before R002.05 should be considered operationally complete.

The current implementation supports only one changed path at a time for stage, unstage, and restore actions. The existing closeout explicitly identifies this as a known limitation.

This addendum does **not** reopen the mutation-safety architecture.

It changes the normal Product Owner interaction model from:

```text
select one file
→ review action
→ confirm
→ repeat for next file

to:
review work set
→ explicitly select one or more files
→ choose one compatible action
→ review the selected set
→ confirm once
→ revalidate the entire selected set
→ execute
→ verify the entire result

The goal is:
safe
+
batch-oriented
+
low-click
+
desktop-efficient

Do not proceed to R002.06 until this R002.05 addendum is implemented, tested, and reviewed.
1. Product Owner UX Findings
Manual browser review identified three related issues.
1.1 Excessive Serial Processing
The current workflow assumes primarily one-file-at-a-time operation.
For a milestone containing many changed files, this requires repeated:
file selection
action review
confirmation
return
next file

This is too inefficient for the Product Owner's normal workflow.
Routine Git activity usually involves a set of files receiving the same action.
Examples:
stage these 8 milestone files
unstage these 3 files
restore these 2 unwanted changes

The UI should support that model directly.
1.2 Excessive Vertical Navigation
The current selected-file page contains useful evidence, but routine work requires substantial scrolling between:
file list
diagnosis
preview choices
local actions
diff

The Product Owner wants to preserve detailed evidence without requiring all of it to remain expanded during normal work.
1.3 Product Direction
Move toward a more horizontal, desktop-oriented workflow based on:
changed-file table
checkbox selection
select-all capability
shared action controls
optional/openable detail
one confirmation per selected batch

The Product Owner's supplied spreadsheet-like sketch is directional only.
Do not treat it as a literal required visual design.
Choose the simplest coherent browser layout that satisfies the workflow.
2. Safety Architecture Remains Locked
Do not weaken the accepted R002.05 mutation contract.
The following remain mandatory:
explicit Product Owner initiation
POST-only mutation
CSRF protection
prepared action
unguessable token
short-lived token
single-use confirmation
fresh-state revalidation
exact path scope
fixed Git argument arrays
no shell interpolation
post-action verification
fail closed on stale state
Post/Redirect/Get after execution

Batch support must extend these protections rather than bypass them.
3. Primary Interaction Model
The default Changes view should become selection-oriented.
Conceptually:
Git Review — Changes

[ ] Select all visible

State             Git       File
--------------------------------------------------------
[ ] New           ??        git_actions.py
[ ] Modified      .M        app.py
[ ] Modified      .M        git_review.html
[ ] Modified      .M        README.md
[ ] Staged        M.        example.py
[ ] Both          MM        another.py

Selected: 3

Routine actions:
[ Stage selected ]
[ Unstage selected ]

Discard / restore:
[ Restore unstaged ]
[ Restore to HEAD ]

Staged for commit: 6 files
[ Review Commit ]

This is conceptual.
Exact layout and labels may differ.
4. Changed-File Table
Replace or substantially revise the current narrow changed-file list so the primary work surface behaves like a desktop table.
At minimum expose:
selection checkbox
human-readable file state
native Git XY status
file path/name
detail/open affordance

Optional concise information may include:
+/- line summary
staged/unstaged indicator
unsupported-state indicator

Do not overload each row with every diagnostic field.
5. Selection Model
Support explicit selection of multiple changed paths.
At minimum:
select one file
select multiple files
deselect individual file
select all visible
clear selection

The selected set must be based on the actual displayed Git inventory.
Do not allow arbitrary browser-submitted path strings to define mutation scope.
Continue using server-resolved path identity.
6. Select All Semantics
Support:
Select all visible

This means:
select every path explicitly present in the current displayed/filterable set

It must not mean:
git add -A
git add .
git add --all

Even when every visible path is selected, the backend must execute against the explicit selected path set.
If filtering/grouping is implemented, Select All should apply only to the current visible set unless clearly labeled otherwise.
7. State Grouping / Filtering
Preserve understandable Git-state groupings such as:
New / Untracked
Unstaged
Staged
Staged + Unstaged
Conflict / Unsupported

A lightweight filter may be added if useful:
All
New
Unstaged
Staged

Do not build a complex filtering framework.
8. Shared Action Toolbar
Do not place a complete set of mutation buttons in every file row.
Use a shared action area based on the current selection.
Examples:
Stage selected
Unstage selected
Restore unstaged
Restore to HEAD

The toolbar should clearly display:
number of selected files

and preferably enough state summary to make the selection understandable.
9. Action Eligibility
An action should initially be enabled only when every selected path supports that action.
Example:
Selected:
3 ordinary unstaged tracked files

Stage selected             available
Restore unstaged           available
Restore to HEAD            available
Unstage selected           unavailable

Another example:
Selected:
2 unstaged tracked files
1 untracked file

Stage selected             available
Restore unstaged           unavailable
Restore to HEAD            unavailable

Do not silently execute an action against only a subset of the selection.
Do not present:
3 of 4 files processed

as normal batch behavior.
For this baseline:
all selected paths eligible
or
action unavailable

10. Batch Stage
Support staging multiple explicitly selected supported paths in one Product Owner action.
The prepared confirmation must show the exact selected paths.
The backend may use:
git add -- <literal path 1> <literal path 2> ...

or another explicit bounded path-array implementation.
Do not use stage-all commands.
The selected paths must be revalidated before execution.
After execution, verify each selected path reached the expected staged state.
11. Batch Unstage
Support unstaging multiple explicitly selected supported staged paths.
The confirmation must make clear:
INDEX WILL CHANGE
WORKTREE CONTENT WILL NOT BE REPLACED

Revalidate every selected path before execution.
After execution:
all selected paths must verify as no longer staged

while preserving their expected worktree state.
12. Batch Restore Unstaged
Support multiple selected ordinary tracked paths only when every selected path has complete, supported restore evidence.
This is destructive.
The confirmation must clearly state:
UNSTAGED WORKTREE CONTENT FOR ALL SELECTED PATHS WILL BE DISCARDED

Show the explicit path list.
Make detailed per-file loss evidence available before confirmation.
The UI does not necessarily need to show every full diff expanded simultaneously.
If even one selected path has:
incomplete evidence
binary unsupported evidence
conflict
rename/copy ambiguity
unsupported file type
stale state

the batch must not execute.
13. Batch Restore to HEAD
Support multiple selected supported tracked paths only when every path satisfies the existing R002.05 Restore-to-HEAD safety contract.
The confirmation must clearly state:
STAGED AND UNSTAGED CHANGES FOR THE SELECTED PATHS MAY BE DISCARDED

Show:
HEAD source
selected path list
affected layers
per-file evidence available on demand

If one path cannot be reviewed completely:
do not execute the batch

14. Atomic Product Behavior
The Product Owner expectation for a prepared batch is:
all selected paths pass validation
→ execute

ANY selected path fails validation
→ execute none

Do not intentionally implement partial batch success.
If Git itself mutates some paths and then returns an unexpected failure that prevents true atomicity, report the resulting state explicitly and require Git Review inspection.
Do not falsely claim transactional guarantees that standard Git CLI does not provide.
The normal product contract should nevertheless be fail-before-execute whenever pre-execution validation detects a problem.
15. Batch Prepared Action
Extend the existing prepared-action mechanism rather than building another mutation architecture.
A prepared batch action must bind:
repository identity
action type
current branch
HEAD
ordered or canonical selected path set
relevant complete index identity
per-selected-path state identity
required worktree evidence
required HEAD evidence
creation time
expiration

The confirmation page must display the selected set.
Tokens remain:
short lived
single use
unguessable
action bound
repository bound

16. Batch Revalidation
Immediately before execution, revalidate the entire selected set.
If any selected path differs materially from the prepared evidence:
DO NOT EXECUTE ANY SELECTED PATH

Display a clear stale-state message such as:
The selected Git state changed after review.
No action was performed.
Review the current files again.

Prefer showing which selected path caused the batch to become stale if that can be done accurately.
17. Detail Presentation
Preserve the detailed R002.02–R002.05 evidence, but stop making all of it part of the mandatory primary workflow.
The Product Owner likes the available detail.
The issue is placement and required scrolling, not the existence of evidence.
18. Default Detail Hierarchy
Prefer a hierarchy similar to:
Primary / always visible:
- file
- state
- Git status
- concise change summary

Easy access:
- diff

Collapsed / optional:
- diagnosis
- known from Git
- advisory signals
- scope evidence
- unknown intent
- advanced Git evidence

Exact grouping is a UI decision.
Do not delete useful evidence merely to simplify the screen.
19. Detail Panel / Drawer
Evaluate using the available desktop width for a persistent or user-opened detail area.
A reasonable design is:
┌──────────────────────────────────────────┬──────────────────────┐
│ Changed-files selection table            │ Selected file detail │
│                                          │                      │
│ [ ] app.py                               │ app.py               │
│ [ ] git_actions.py                       │ Modified / Unstaged  │
│ [ ] README.md                            │ +90 / -35            │
│                                          │                      │
│                                          │ Diff                 │
│                                          │ Diagnosis ▸          │
│                                          │ Advanced evidence ▸  │
└──────────────────────────────────────────┴──────────────────────┘

A drawer, expandable side panel, modal, or similar desktop-oriented solution is acceptable.
Do not create a new SPA framework solely for this.
20. Reduce Duplicate Preview / Review UX
The current interface contains both:
Possible choices — preview only

and:
Local actions for this selected path

This produces conceptual and visual duplication such as:
Preview Restore Unstaged
Review Restore Unstaged

Evaluate consolidation.
The Product Owner should not need to understand an artificial distinction between two adjacent buttons for the same conceptual operation.
Preferred direction:
choose action
→ review consequences
→ confirm if desired

The existing read-only preview service may remain the evidence engine underneath.
Do not remove the safety preview.
Reduce duplicated user interaction.
21. Destructive Actions Remain Visually Distinct
Keep routine and destructive actions separated.
Conceptually:
Routine
[ Stage selected ] [ Unstage selected ]

Discard / Restore
[ Restore unstaged ] [ Restore to HEAD ]

Restore actions should remain visually distinct and receive stronger confirmation wording.
Do not normalize destructive actions to look identical to staging.
22. Commit Workflow Streamlining
Commit is inherently a staged-set operation and should be presented that way.
Provide an obvious staged summary such as:
6 files staged
[ Review staged files ] [ Commit staged files ]

The commit review must continue to show:
all staged paths
status of each
staged diff evidence
remaining unstaged paths
remaining untracked paths
commit subject

No implicit staging.
23. Commit Does Not Need Checkbox Selection
Do not create an alternate checkbox subset of already staged files solely for commit in this milestone.
The accepted contract remains:
Commit = commit the complete currently staged set

If the Product Owner does not want a staged file included:
Unstage it first

This keeps Git semantics understandable and avoids building a second partial-commit selection model.
24. Preserve Read-Only History / Branches
Do not regress:
History
Commit detail
File history
Branches
Branch comparison

Batch-selection controls belong to the Changes view.
Do not put mutation checkboxes into historical commit/file-history views.
25. Tests — Selection
Add tests for:
multiple selection
select all visible semantics
clear selection
explicit path-set preservation
unsupported mixed selection
arbitrary browser path injection rejected

If selection is primarily client-side, ensure backend requests still independently validate the submitted selection against fresh Git inventory.
26. Tests — Batch Stage
Cover at minimum:
stage multiple tracked paths
stage tracked + untracked paths
stage multiple paths without touching an unselected path
mixed eligible state
stale one-of-many path blocks entire action
prepared path set cannot be expanded at confirmation
token replay blocked

27. Tests — Batch Unstage
Cover:
unstage multiple paths
worktree preserved for all
unselected staged paths remain staged
one stale selected path blocks batch

28. Tests — Batch Restore
Cover both restore modes:
multiple eligible paths
all selected paths restored
unselected path unchanged
unsupported selected member prevents preparation or execution
one stale selected member blocks entire batch
destructive warning rendered

No production/authoritative worktree may be used for these tests.
29. Tests — No Partial Intentional Execution
Add explicit tests proving:
selected path A valid
selected path B stale
→ neither A nor B is intentionally executed

This must be tested before the mutation command runs.
30. Tests — UI Regression
Retain tests covering:
single-file detail
diff
diagnosis evidence
history
branches
commit
CSRF
same-origin validation
POST-only mutation
prepared-token expiration/replay/cancel
legacy mutation routes disabled

31. Manual Product Owner Acceptance
After implementation, update the R002.05 closeout with a revised manual acceptance plan.
The Product Owner should be able to test in the disposable repository:

Do not test destructive actions on valuable Repo Control work.

35. Stop / Escalation Conditions
Stop and report if:
batch operation requires abandoning stale-state revalidation;
safe explicit path sets cannot be passed to Git;
multi-path restore semantics become ambiguous;
the only implementation requires partial action without clear reporting;
the existing prepared-action architecture cannot support path sets without broad redesign;
a new persistent database becomes necessary;
browser UI streamlining requires a framework replacement;
or the work materially exceeds batch/local-action UX.

36. Product Owner Lock-In
The intended normal Git workflow is now:
review repository changes
        ↓
select the files that belong together
        ↓
perform one applicable action on the selected set
        ↓
review consequences once
        ↓
confirm once
        ↓
Repo Control revalidates every selected path
        ↓
execute
        ↓
verify

Detailed evidence remains available, but routine Git operation should not require opening and processing every file serially.
The design priority is:
preserve R002.05 safety
while removing unnecessary clicks, repetition, and scrolling

Proceed with this addendum within R002.05.
Do not begin R002.06.
