# Part III — Create Local Branch

## 13. Creation Scope

Support creating one new local branch from the repository's **current HEAD**.

Do not support arbitrary source revisions in this baseline.

If the Product Owner wants a branch from `main`, the normal workflow is:

```text
switch to main
then create the branch
```

---

## 14. Branch Name Validation

Validate the requested name with Git using `git check-ref-format --branch <name>` or an equivalent strict Git-native check.

Also refuse empty names, an existing local branch name, and `main`.

Do not accept arbitrary Git flags or refspec syntax as branch names.

---

## 15. Create Semantics

Creation should create the branch but should **not automatically switch** to it.

Conceptually:

```text
current HEAD
    ↓
new local branch ref
```

A likely command is:

```text
git branch -- <new-branch>
```

Do not create an upstream automatically at local branch creation time.

Publishing/upstream setup belongs to first push.

---

## 16. Create Review / Verification

Before confirmation show:

```text
new branch name
source = current HEAD
current branch
current HEAD OID
remote impact = none
```

Revalidate current HEAD and branch-name availability before execution.

After creation verify:

```text
new local branch exists
tip equals reviewed source HEAD
current branch did not change
worktree did not change
```

---

# Part IV — Switch Local Branch

## 17. Switch Scope

Support switching only to an existing local branch from the server-resolved branch inventory.

Do not accept arbitrary branch text from the browser as execution authority.

Do not auto-create a branch from a remote-tracking ref.

---

## 18. Dirty-Tree Protection

For the bounded initial implementation, branch switching requires a completely clean working tree.

Block switching when any of the following exists:

```text
staged change
unstaged tracked change
untracked path
unresolved conflict
unsupported in-progress Git operation
```

Do not auto-stash, auto-commit, discard changes, or attempt Git's more permissive switch behavior.

---

## 19. Switch Review / Execution

Before confirmation show:

```text
current branch
target branch
current HEAD
target tip
working tree = clean
```

Revalidate immediately before execution.

Use an exact validated local-branch command equivalent to:

```text
git switch --no-guess <local-branch>
```

After execution verify current branch, HEAD, and clean working tree.

---

# Part V — Safe Local Branch Delete

## 20. Delete Scope

Support deletion only for a local branch that:

```text
is not current
is not main
still exists at the reviewed tip
is fully merged into local main by Git ancestry
```

Use the same R002.04 definition: branch tip is an ancestor of `refs/heads/main`.

---

## 21. No Force Delete

Use only normal safe-delete semantics, such as:

```text
git branch -d -- <validated-branch>
```

Never use `-D` or `--force`.

If Git refuses deletion, surface the refusal.

---

## 22. Remote Branch Is Separate

Deleting a local branch must not delete its remote branch.

If the branch has an upstream, the review must clearly say:

```text
This deletes only the local branch.
The remote branch remains.
```

Remote branch deletion is outside R002.

---

## 23. Delete Review / Revalidation

Before confirmation show branch name, branch tip, relationship to main, fully merged status, current branch, upstream if any, and explicit remote impact = none.

Revalidate all safety facts before execution, then verify the local ref is gone.

---

# Part VI — Fetch

## 24. Fetch Scope

Support fetching an existing configured remote.

Do not support remote creation/editing/deletion.

Prefer `origin` in the UI when present, but resolve execution targets from the actual configured remote inventory.

---

## 25. Fetch Semantics

Fetch updates local remote-tracking knowledge.

It must not switch branches, modify the worktree/index, merge, rebase, or fast-forward the local branch automatically.

A likely command is:

```text
git fetch <validated-remote>
```

Do not add `--prune` in this baseline.

Do not automatically fetch on page load.

---

## 26. Fetch Review

Before confirmation show:

```text
remote name
sanitized remote URL
current branch
current HEAD
worktree/index effect = none expected
local remote-tracking refs may change
network access will occur
```

Do not expose embedded credentials or secrets.

---

## 27. Fetch Execution / Verification

Use non-interactive Git behavior such as `GIT_TERMINAL_PROMPT=0`.

Bound network runtime/output.

After success, refresh branch/upstream comparisons and show updated local remote-tracking state.

Do not claim the local branch moved.

---

# Part VII — Push

## 28. Push Scope

Support non-force push of the **current attached local branch only**.

Do not provide arbitrary source/destination refspec entry.

Support:

```text
A. current branch has configured remote upstream
B. current branch has no upstream and is being published for the first time to a configured remote using the same branch name
```

---

## 29. Existing-Upstream Push

For a branch with configured remote upstream, show:

```text
local branch
local HEAD
remote name
remote branch
local ahead/behind relative to local tracking ref
remote freshness warning
force = no
```

Never use force or force-with-lease.

A remote non-fast-forward rejection is a safe failure and must be surfaced.

---

## 30. First Push / Set Upstream

For a current branch with no upstream, support:

```text
local <branch>
→ configured remote/<same branch name>
```

and set that remote branch as upstream.

Before offering it, require the same-name remote branch to be absent, unless the implementation can prove a no-surprise same-tip case. Prefer fail-closed if it already exists.

A likely command is:

```text
git push --set-upstream <remote> refs/heads/<branch>:refs/heads/<branch>
```

using validated refs and fixed arguments.

Do not allow browser-provided arbitrary refspec text.

---

## 31. Push Does Not Require a Clean Worktree

Push concerns committed history.

Do not block push merely because unrelated unstaged/untracked work exists.

The UI must state:

```text
Only committed history is pushed.
Uncommitted changes are not included.
```

Current branch, HEAD, and upstream/target must still revalidate.

---

## 32. Push Verification

After successful push, verify the actual remote branch tip where practical with a bounded read-only query such as:

```text
git ls-remote --heads <remote> <exact-branch-ref>
```

Verify remote tip equals pushed local HEAD.

If verification is unavailable after an apparently successful push, say so rather than claiming verified synchronization.

---

# Part VIII — Fast-Forward-Only Local Update

## 33. Purpose

Support only the routine behind-only case:

```text
upstream contains newer commits
local current branch has no unique local commits
Product Owner wants local branch/worktree advanced
```

Do not implement general Pull.

---

## 34. Preconditions

Fast-forward update is available only when:

```text
HEAD is attached to a local branch
configured upstream exists locally
working tree is completely clean
no conflict / in-progress operation exists
local branch is behind upstream by >= 1
local branch is ahead of upstream by 0
local tip is an ancestor of upstream tip
```

If diverged, do not merge, rebase, or reset.

---

## 35. Freshness

Upstream comparison uses the local remote-tracking ref and may be stale until Fetch.

Preferred workflow:

```text
Fetch
↓
review refreshed relationship
↓
Fast-forward update
```

Do not silently bundle fetch into the update action.

---

## 36. Fast-Forward Review / Execution

Before confirmation show:

```text
current branch
current HEAD
configured upstream
upstream tip
behind count
ahead count = 0
working tree = clean
operation = fast-forward only
merge commit = none
```

Use an exact command equivalent to:

```text
git merge --ff-only <validated-upstream-ref>
```

Do not use `git pull`, `git reset --hard`, or normal merge without `--ff-only`.

After execution verify branch unchanged, HEAD equals reviewed upstream tip, worktree clean, and no merge commit created.

# 64. Definition of Done

R002.06 is complete when:

```text
- Product Owner can create a validated local branch from current HEAD;
- creation does not switch branches automatically;
- Product Owner can switch among existing local branches;
- switching is blocked whenever the working tree is not completely clean;
- Product Owner can delete only a non-current, non-main local branch proven fully merged into main;
- local branch deletion never deletes a remote branch;
- Product Owner can explicitly fetch a configured remote;
- fetch refreshes local remote-tracking refs without moving local branch/worktree;
- Product Owner can push the current branch without force;
- uncommitted content is visibly excluded from push;
- first push can safely publish same-name branch and set upstream when no conflicting remote branch exists;
```
