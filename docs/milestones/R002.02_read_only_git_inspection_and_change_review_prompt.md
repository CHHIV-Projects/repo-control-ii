# 1. Goal

Implement a browser-based Git inspection surface that lets the Product Owner open Repo Control and understand the current repository state without using Git CLI syntax.

The Product Owner should be able to answer:

```text
What repository am I looking at?
What branch am I on?
What is HEAD?

Which files changed?
Which changes are staged?

What changed in this file?
Is this diff incomplete because the file is binary, too large, or unsupported?

How fresh is the shown upstream/ahead-behind information?
```

# Part I — Implementation Scope

## 7. Read-Only Git Review Surface

Implement one focused browser surface for Git inspection.

It should display, at minimum:

```text
repository identity/path
branch
HEAD commit ID
clean/dirty state
upstream name if configured
ahead/behind counts from local tracking refs
freshness warning that local tracking refs are not live remote state
changed files grouped by Git status category
conflict/active-operation state
```

The UI should clearly distinguish:

```text
staged
unstaged
staged + unstaged
untracked
renamed/copied if represented
conflicted/unmerged
```

Do not silently collapse distinct Git states into a generic “modified” label.

---

## 8. File Selection for Inspection

The user must be able to select a changed file and inspect its evidence.

Selecting a file must:

```text
not stage it
not unstage it
not restore it
not modify workflow state
not invoke any mutation service
```

Selection is inspection only.

The interface may use a file list with detail pane, a separate detail route, or another simple existing-project UI pattern.

Prefer the smallest implementation that fits the inherited Flask structure.

Do not build a large client-side application unless current code requires it.

---

## 9. Diff Evidence

For tracked changed files, show bounded Git diff evidence.

Support the distinction between:

```text
unstaged diff:
worktree vs index

staged diff:
index vs HEAD
```

When a file has both staged and unstaged changes, show both states distinctly.

The UI must make the comparison basis clear.

Examples:

```text
Unstaged — working tree vs index
Staged — index vs HEAD
```

Do not present an ambiguous single diff when two different states exist.

---

## 10. Untracked Files

For untracked files, provide either a bounded content preview or an explicit unsupported/not-yet-previewed state.

Choose the smallest safe implementation.

If preview is implemented:

- impose a clear size bound;
- do not silently truncate without telling the user;
- handle text decoding safely;
- do not execute or parse the file as code;
- do not add it to Git.

The closeout must document the chosen behavior.

---

## 11. Binary / Large / Unsupported Files

Do not treat absence of textual diff as “no change.”

For binary, very large, undecodable, or otherwise unsupported content, show:

```text
file path
Git status
available metadata
reason full text diff is not displayed
whether evidence is complete or intentionally bounded
```

Clearly distinguish:

```text
no textual diff available
```

from:

```text
no change
```

Use conservative size/output limits.

Document them in code/tests and closeout.

---

## 12. Whitespace Signals

Expose whitespace information only as advisory evidence.

Possible signals may include:

```text
git diff --check
whitespace-equivalent comparison
```

Rules:

```text
- do not label a change harmless;
- do not label a change accidental;
- do not automatically restore it;
- do not collapse the normal diff merely because whitespace is involved.
```

Suggested wording:

```text
Whitespace warning
Possible whitespace-only difference
No whitespace issue detected
```

Avoid semantic claims.

---

## 13. Git Error / Unknown State Handling

If Git cannot establish a fact:

```text
show unknown/error
```

Do not default to:

```text
clean
safe
no difference
```

Examples:

```text
upstream unavailable
detached HEAD
unsupported path state
Git command failure
diff unavailable
repository validation failure
```

The browser should surface a useful bounded explanation rather than crashing or silently omitting the issue.

## R002.02 Product Owner / Architect Clarification

Proceed with implementation. No escalation is required.

The implementation cautions identified in preflight are accepted, with the following lock-ins:

1. Read-only route boundary

The new Git Review route/service must remain read-only end to end.

Do not reuse `generate_milestone_status` or another path that writes workflow/snapshot artifacts simply to obtain Git facts.

Existing application-startup behavior is inherited behavior and is not part of R002.02 redesign.

For read-only route tests, it is acceptable to establish the baseline after normal application initialization. After that baseline is established, loading/using the new Git Review route must produce no additional:

- worktree changes;
- index changes;
- ref changes;
- Git mutations;
- Repo Control workflow/snapshot writes caused by the new route.

The test should distinguish inherited startup behavior from behavior caused by the new review surface.

2. Bound subprocess collection, not only rendering

Accepted.

Bounds must be enforced while collecting Git subprocess output, not merely after an unlimited `subprocess.run(..., capture_output=True)` result has already been buffered.

Use a bounded collection strategy appropriate to the existing implementation.

Behavior when a bound is reached:

- status/state inventory:
  do not silently parse a partial repository state as complete;
  report that status evidence is incomplete / exceeded the configured limit.

- diff or file preview:
  bounded/truncated evidence may be displayed only if the UI clearly says it is incomplete.

Exact limits may be chosen conservatively during implementation and must be documented in tests and closeout.

Do not optimize for extremely large repositories in this milestone; establish a safe bounded contract.

3. Untracked files

Choose the useful option:

- provide a bounded preview for reasonably small text files;
- do not attempt full preview for binary, very large, or undecodable files;
- show metadata plus an explicit reason when preview is unavailable;
- clearly mark any truncated preview as incomplete;
- never add the file to Git.

Exact preview-size limits may be selected conservatively and documented.

4. Path handling

Spaces, tabs/newlines where Git permits them, and HTML-special characters must not break parsing or rendering.

Do not assume every Linux pathname is valid UTF-8.

For undecodable path bytes:

- do not crash;
- do not silently omit the path;
- show a safely escaped/displayable representation or an explicit unsupported-path state.

Preserve the underlying Git identity sufficiently that the UI cannot accidentally refer to a different path.

5. Staged and unstaged evidence

Accepted.

Keep these comparisons separate:

- staged = index vs HEAD
- unstaged = working tree vs index

A file containing both must display both independently.

Do not merge them into one synthetic diff.

6. Conflicted files

Treat conflict/unmerged state explicitly.

Do not render absence of an ordinary staged/unstaged patch as “unchanged.”

Where normal diff evidence is incomplete or unsuitable because of an unmerged state, say so and display the Git conflict state that is known.

Conflict resolution remains out of scope.

7. `git diff --check`

Treat whitespace diagnostics separately from Git execution failure.

A result reporting whitespace problems is evidence to display, not a failed review request.

Continue showing the normal diff.

Do not infer:

- harmless;
- accidental;
- safe to discard.

Whitespace findings remain advisory signals only.

8. UI layout

No additional architectural decision is required before implementation.

Use the simplest layout that fits the current Flask application cleanly.

A changed-file list plus selected-file detail view is preferred conceptually, but a separate file-detail route is equally acceptable if it fits the existing code better.

Do not build a SPA or broad UI redesign for R002.02.

The Product Owner will evaluate the actual browser experience after implementation and we will refine the Git interface in subsequent R002.xx milestones.

9. Scope discipline

R002.02 remains evidence-first and read-only.

Do not add:

- stage;
- unstage;
- restore;
- commit;
- branch mutation;
- remote mutation;
- workflow-state mutation;
- AI interpretation.

The objective is to produce a trustworthy first Git Review surface that we can actually use and then improve iteratively.

Proceed.

The current page uses a narrow centered content column and leaves excessive unused space on both sides of the browser window.

Do not create a broad CSS redesign outside what is needed for this correction.
