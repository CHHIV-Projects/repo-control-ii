# 1. Goal

Implement a browser-based Git inspection surface that lets the Product Owner open Repo Control and understand the current repository state without using Git CLI syntax.

The Product Owner should be able to answer:

```text
What repository am I looking at?
What branch am I on?
What is HEAD?
Is the working tree clean or dirty?
Which files changed?
Which changes are staged?
Which changes are unstaged?
Which files are untracked?
Are there conflicts?
What changed in this file?
Is this diff incomplete because the file is binary, too large, or unsupported?
Are there whitespace warnings or whitespace-equivalent signals?
How fresh is the shown upstream/ahead-behind information?
```

The UI must remain read-only.

# Part I — Implementation Scope

## 7. Read-Only Git Review Surface

Implement one focused browser surface for Git inspection.

It should display, at minimum:

```text
repository identity/path
branch
HEAD commit ID
clean/dirty state
upstream name if configured
ahead/behind counts from local tracking refs
freshness warning that local tracking refs are not live remote state
changed files grouped by Git status category
conflict/active-operation state
```

The UI should clearly distinguish:

```text
staged
unstaged
staged + unstaged
untracked
renamed/copied if represented
conflicted/unmerged
```

Do not silently collapse distinct Git states into a generic “modified” label.

---

## 8. File Selection for Inspection

The user must be able to select a changed file and inspect its evidence.

Selecting a file must:

```text
not stage it
not unstage it
not restore it
not modify workflow state
not invoke any mutation service
```

Selection is inspection only.

The interface may use a file list with detail pane, a separate detail route, or another simple existing-project UI pattern.

Prefer the smallest implementation that fits the inherited Flask structure.

Do not build a large client-side application unless current code requires it.

---

## 9. Diff Evidence

For tracked changed files, show bounded Git diff evidence.

Support the distinction between:

```text
unstaged diff:
worktree vs index

staged diff:
index vs HEAD
```

When a file has both staged and unstaged changes, show both states distinctly.

The UI must make the comparison basis clear.

Examples:

```text
Unstaged — working tree vs index
Staged — index vs HEAD
```

Do not present an ambiguous single diff when two different states exist.

---

## 10. Untracked Files

For untracked files, provide either a bounded content preview or an explicit unsupported/not-yet-previewed state.

Choose the smallest safe implementation.

If preview is implemented:

- impose a clear size bound;
- do not silently truncate without telling the user;
- handle text decoding safely;
- do not execute or parse the file as code;
- do not add it to Git.

The closeout must document the chosen behavior.

---

## 11. Binary / Large / Unsupported Files

Do not treat absence of textual diff as “no change.”

For binary, very large, undecodable, or otherwise unsupported content, show:

```text
file path
Git status
available metadata
reason full text diff is not displayed
whether evidence is complete or intentionally bounded
```

Clearly distinguish:

```text
no textual diff available
```

from:

```text
no change
```

Use conservative size/output limits.

Document them in code/tests and closeout.

---

## 12. Whitespace Signals

Expose whitespace information only as advisory evidence.

Possible signals may include:

```text
git diff --check
whitespace-equivalent comparison
```

Rules:

```text
- do not label a change harmless;
- do not label a change accidental;
- do not automatically restore it;
- do not collapse the normal diff merely because whitespace is involved.
```

Suggested wording:

```text
Whitespace warning
Possible whitespace-only difference
No whitespace issue detected
```

Avoid semantic claims.

---

## 13. Git Error / Unknown State Handling

If Git cannot establish a fact:

```text
show unknown/error
```

Do not default to:

```text
clean
safe
no difference
```

Examples:

```text
upstream unavailable
detached HEAD
unsupported path state
Git command failure
diff unavailable
repository validation failure
```

The browser should surface a useful bounded explanation rather than crashing or silently omitting the issue.

## 15. Standard Git CLI Authority

Use standard Git CLI commands through fixed argument arrays.

Do not use shell-string interpolation.

Prefer stable/machine-oriented formats for parsed state.

For human-facing diff content, use bounded Git-generated diff output with explicit comparison context.

Do not introduce GitPython, pygit2/libgit2, Dulwich, or another Git library in R002.02.

---

```text

```

---

## 17. Bounds and Safety

Implement explicit bounds for diff/preview output.

The implementation must:

```text
avoid unbounded browser payloads
avoid unbounded subprocess output
avoid shell interpolation
handle unusual paths safely
handle missing/deleted files
handle rename state where supported
avoid exposing repository data outside the selected repository
```

If a result is truncated or suppressed because of bounds, say so in the UI.

Do not silently present partial evidence as complete.

---

If the existing UI does not need remote URLs for R002.02, omit them.

# 33. Definition of Done

R002.02 is complete when:

```text
- Repo Control has a browser-accessible read-only Git review surface;
- repository, branch, HEAD, and working-tree state are visible;
- changed files are categorized accurately;
- selected files can be inspected without mutation;
- staged and unstaged diff evidence are distinguished;
- untracked behavior is explicit;
- binary/large/unsupported behavior is explicit;
- whitespace signals are advisory only;
- error/unknown states are visible rather than silently treated as clean;
- output is bounded and safe;
- automated tests cover meaningful Git states;
- read-only behavior is demonstrated;
- existing Git regression tests still pass;
- the full test suite passes unless a documented unrelated blocker prevents it;
- no new Git mutation capability was added;
- no external Git tool or library was installed;
- one closeout exists under the exact required filename;
- the Product Owner has a concrete browser surface to evaluate before R002.03 is designed.
```

The milestone should produce the first genuinely useful Repo Control II Git browser experience while preserving the principle:

```text
evidence first
→ understand state
→ then design corrective actions
```
