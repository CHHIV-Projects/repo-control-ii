# M003.012 — Single-User Workflow Compression

## Objective
Reduce Product Owner workflow friction in Repo Control’s browser UI while preserving the existing milestone lifecycle model, event ledger, authorization boundaries, and Git safety rules.

This milestone compresses the human action surface for the current single-user Product Owner workflow. It must not weaken lifecycle prerequisites, collapse event semantics, or introduce implicit Git or Coder authority.

## Product Owner Decisions Already Made
Implement these combined browser actions:

1. Approve & Start
- Approve the milestone prompt and begin implementation in one deliberate action.
- Internally preserve two ordered events: prompt_approved, then implementation_started.
- Both events remain individually visible in workflow history.

2. Resolve & Resume
- Resolve the active blocking condition and resume implementation in one action.
- Record the appropriate answer/decision/resolution event first.
- Where applicable, preserve an optional binding lock-in as a distinct event.
- Then record implementation_resumed.
- UI must be context-sensitive to the active WAITING condition.

3. Accept & Close
- Accept completed milestone work and close the milestone in one action.
- Internally preserve two ordered events: acceptance_recorded, then milestone_closed.
- Both remain individually visible in workflow history.

## Single-User UI Simplification
For normal Product Owner browser actions:
- remove the actor dropdown;
- remove the explicit Product Owner confirmation checkbox;
- the deliberate action button itself is Product Owner authorization;
- use deterministic default summaries where useful;
- keep summaries editable only where useful;
- display only fields relevant to the current phase/action;
- clearly explain the effect of each combined action before submission.

Do not introduce multi-user authentication or role infrastructure.

## Lifecycle and Authority Boundaries
Compression applies to browser interaction, not the lifecycle model.

Preserve:
- PLANNING, READY, IN_PROGRESS, WAITING, REVIEW, CLOSED;
- existing underlying event types and prerequisite validation;
- Product Owner authority over approval, blocking-condition resolution, acceptance, and closure;
- Coder prohibition on Git mutations;
- explicit lifecycle history;
- stale-state protection and server-authoritative phase checks;
- atomic/consistent workflow-sidecar updates.

A combined action must fail safely if any prerequisite for either constituent event is not satisfied. Do not leave partial advancement or ambiguous state.

## Existing Behavior to Preserve
Do not regress M003.010 behavior: server-authoritative polling, automatic browser refresh for external lifecycle changes, preservation/blocking when edited forms become stale, phase-aware controls, aliases for questions/bugs, deterministic defaults, and no WebSocket requirement.

Do not regress M003.011 behavior: Architect dispatches remain separate from lifecycle; dispatch approval does not itself change lifecycle state; PROMPT approval/save is distinct from milestone prompt approval/start; approved INSTRUCTION/RESPONSE dispatches remain available through coder-context; Architect retains no Git, shell, arbitrary file-write, or PO lifecycle authority.

## Implementation Guidance
Prefer the smallest coherent change and reuse existing authoritative lifecycle primitives.

Approve & Start:
- valid from the appropriate PLANNING state;
- perform prompt_approved followed by implementation_started;
- result IN_PROGRESS.

Resolve & Resume:
- valid only from WAITING with a resolvable blocking condition;
- record resolution/answer before resume;
- preserve optional binding lock-in as distinct when requested;
- result IN_PROGRESS only after successful resolution and resume.

Accept & Close:
- valid only from REVIEW when acceptance prerequisites are satisfied;
- perform acceptance_recorded followed by milestone_closed;
- result CLOSED.

If the persistence layer cannot safely support paired updates without partial-state risk, implement a bounded atomic mechanism rather than weakening consistency.

## UX Expectations

Do not expose the old redundant actor selector or PO-confirmation checkbox for these normal actions. Preserve useful entered text on validation errors. Polling/external-state-change behavior must continue to work.
