## 1. Product context and intended outcome

Repo Control II already has Graphify-backed bounded structural queries, per-use measurement/consumer ratings, source-inspection feedback, refresh receipts (M008.001), and separate controlled benchmark records (M004.002). The Product Owner wants to know whether Repository Intelligence *actually saves context/evidence volume* rather than relying on impression or an empty comparative table. Our original discussion included a misunderstanding about token size: the broad rule of thumb is **approximately four English-text characters per token, not four words per token**. This is only an estimator, not the model's tokenizer or billing count.

Historical M004.002 corrected non-blind, non-equivalent-stopping-rule replay reported:

## 2. Non-negotiable measurement definitions

Define and document a stable, independently testable **Evidence Metric Contract** (method names and version identifiers chosen deterministically and documented):

1. **Response/evidence bytes:** `len(exact_returned_evidence_text.encode("utf-8"))`, for the established bounded normalized JSON evidence text, after all actual truncation/pruning that affects the caller-visible evidence. Be precise whether existing measurements exclude a CLI newline, MCP protocol framing, HTTP headers and/or any service envelope. Prefer preserving M004.002's existing byte-count boundary and comparing only like-for-like surfaces.
2. **Evidence characters:** Python Unicode code-point count `len(exact_returned_evidence_text)`. Label explicitly as characters/code points, not bytes or words. Do not infer character count from UTF-8 bytes for non-ASCII text.
3. **Baseline estimate:** `estimated_evidence_tokens = ceil(evidence_characters / 4)` with explicit method ID such as `char4-ceil-v1`. This is a *rule-of-thumb estimate* on that text, **not** exact tokens for any production model. State that `~1 token = 4 English characters ≈ 0.75 English words` is an approximation; languages, whitespace, JSON, paths, identifiers and models may differ substantially.
4. **Preferred fixed benchmark reference tokenizer:** Prefer `tiktoken` with `o200k_base` as the **single cross-agent reference tokenizer** for controlled source-first vs Intelligence-first comparisons. Fix the exact package version, named encoding, vocabulary asset identity/hash (SHA-256), input serialization/whitespace and ordinary-text versus special-token handling. Provision and verify the encoding cache/asset locally so actual benchmark runs succeed with **network unavailable**; do not rely on silent first-run downloads. Count identical returned evidence text in both arms with the same reference encoding, and store separately named `reference_tokenizer_evidence_tokens` and immutable method/version/asset identity. This number is exact only for the text and selected encoding, never 'actual Codex/Copilot tokens.' Do **not** use model-name auto-selection for the benchmark reference. Evaluate feasibility within existing packaging/runtime/privilege/dependency limits; if significant new runtime/dependency, network access or authorization would be needed, do **not** install or fetch it silently. Record a specific adoption blocker, use the versioned char4 fallback, and request a bounded PO decision only if essential. Optional native/tokenizer-specific counts for Claude/Gemini/GPT-OSS or future models are expressly out of scope in M008.002.
5. **Method provenance:** Each computed figure must carry estimator/tokenizer ID, immutable semantic version, exact counted-surface description, measurement availability/quality and the timestamp or release context needed for future comparison. Store exact observed bytes/chars from the current response path, not retrospective guesses. Mark unmeasurable values UNKNOWN/NOT MEASURED, not zero.
6. **Two denominators:** For a *controlled task*, distinguish returned tool/structural evidence from subsequent independently retrieved source windows; preserve and label `source_evidence_bytes`, `tool_evidence_bytes`, `total_evidence_bytes`, `files_inspected`, `interactions`, and measured mechanical elapsed time. Do not sum a source excerpt both as a graph citation and a separate inspection unless it was actually delivered twice under the explicitly declared measurement protocol.
7. **Savings only on comparable measures:** A token-reduction percentage may be computed **only when both CONTROL and Intelligence-first arms recorded text/token figures using the same explicitly documented method and comparable evidence boundary**. Use `(control - intelligence) / control * 100`, with zero-denominator handling; negative values are increased volume, not hidden. For historical byte-only data, report byte comparisons only, with no token-savings number.
8. **Out of scope for observation:** Copilot/chat host injected context, hidden reasoning, prompt caching, tool-call system framing, model output tokens, actual provider-billed tokens and entire agent-turn/model-session cost **are not observable** through current Repo Control evidence collection. Do not extrapolate these from the measured evidence slice. An exact tokenizer count over known text is exact *for that text and tokenizer*, not exact agent token consumption.
9. **Separation of estimation and prices:** No external price lookup or money-savings claim is required. If future model economics/prices change, historic token/evidence values and method IDs must remain comparable; pricing/scenario assumptions, if ever added, belong in a separate versioned layer.

## 4. Normal-use evidence-token accounting

- Count only the bounded caller-visible evidence, including explicit outcome, errors/truncation/omission fields actually delivered. Do not count unsent unpruned graphs, server-side internal payloads, Python reprs or source snapshots.
- Define and test inclusion/exclusion of normalized JSON metadata vs evidence fields, CLI newline, MCP wrapper and HTTP headers. Preserve established response byte limits; measurement must not alter evidence contents or make response-size limits fail unexpectedly. If adding metric fields to an evidence envelope creates a counting cycle, resolve via separate analytics metadata rather than recursive count.
- Preserve existing `response_bytes` meaning; do not silently overwrite/reinterpret historical records. For normal automatic telemetry, always keep the lightweight `char4-ceil-v1` estimate; do not put `tiktoken` work or downloads on the latency-critical service request path merely to obtain a benchmark count. ## 5. Controlled comparative benchmarking

**Cross-model benchmark policy:** The fixed `o200k_base` count is a stable common *reference yardstick*, not an assertion that Codex, GitHub Copilot, Claude, Gemini or a local model uses that encoding. Never aggregate a model-native count into the fixed-reference series or change its tokenizer based on which assistant consumed the evidence. Future optional per-model tokenizers must be separately versioned series, not retroactive replacements. Store corpus/task identifier, exact source snapshot, counting boundary and complete tokenizer-method provenance so benchmarks remain comparable over time.



Controlled comparisons are **occasional deliberate experiments**, not automatic doubles of normal work. Keep the existing trusted-local benchmark recording boundary (no remote arbitrary benchmark ingestion).

Create or refine a reproducible, low-effort procedure and/or narrow local fixture runner for matched real structural questions:

- Explicit fixed question/task, repository + source snapshot/HEAD/source identity, benchmark method/protocol version, control vs intelligence-first strategy, stopping rules, source inspection allowances, data collection boundary, selected sources/generation, and limitations.
- Equivalent accuracy/completeness stopping criteria for both arms, rather than making the control inspect every grep match while Intelligence stops after two cited files. Record when equivalence could not be established; do not assert causal savings.
- Both arms collect actual returned evidence bytes/chars and char4 estimated tokens using the same named method and measurement boundary, plus files inspected, source evidence bytes, tool/read interactions, and measured local elapsed milliseconds. **Prefer additionally counting both arms with exactly the same pinned offline `o200k_base` reference tokenizer and store that reference-tokenizer count separately**, never substituting it for model-native/total-session usage. The control arm may use deterministic grep/file-read fixtures; Intelligence-first may query CURRENT Graphify then validate against source. If fixed-tokenizer adoption is not practical, explain the reason and compare matched versioned char4 estimates; if actual complete text is unavailable for an arm, omit that arm's tokenizer comparison instead of deriving exact tokens from old byte totals.
- Record whether a source window was actually read or only scanned/located. Define overlap/deduplication counting consistently and report it. No invisible or inferred Copilot host prompts/model tokens.
- Retain representative success, ambiguity, unsupported, truncation and fallback cases; preserve failure receipts and quality/outcome ratings without retroactively rewriting historical assessments. One small honest fixture or controlled replay to validate the new protocol is sufficient; do not require costly rerunning every historical question. Do not manufacture a new result merely to fill the table.
- Preserve historical M004.002 comparisons unchanged, labeled legacy byte-only methodology, non-blind and unequal stopping rules. Existing record import/backfill must be additive and conditional; unknown fields stay unknown.
- Formal controlled comparison records remain separate from normal use and refresh events, capped at existing documented capacity.
