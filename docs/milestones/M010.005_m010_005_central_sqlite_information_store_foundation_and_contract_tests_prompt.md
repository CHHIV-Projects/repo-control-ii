# M010.005 — Central SQLite Information Store Foundation and Contract Tests

## Objective and authority
Implement the smallest reusable **fixture-only** SQLite information-store foundation for Repo Control II following the accepted M010.004 information-architecture closeout. The goal is to prove the central data model and stable application-owned contracts for immutable document revisions, workflow event/projection persistence, Architect dispatch status, transaction receipts, and exact document-to-workflow links. This milestone MUST NOT alter current Repo Control operations or promote SQLite to managed authority.

Expected repository: `repo-control-ii` at `/home/chuck/projects/repo-control-ii`; keep the existing `db-workflow-persistence-architecture` branch. Before Coder work, live Repo Control must verify M010.004 CLOSED and exact M010.005 selection, prompt, IN_PROGRESS lifecycle, and authorization. Follow the installed cold-chat bootstrap or warm/resume procedures as applicable; mere prompt presence or "Prompt ready" is not authorization. The Coder never stages, commits, pushes, tags, merges, or changes global repository selection.

Current v1 Markdown workflow sidecars, physical prompt/closeout files, separate dispatch ledger, selection pointers, five registry-mapped context documents, procedure releases/locks/agent entrypoints, Git interface, intelligence data, and all browser/CLI/Architect behavior remain **unchanged, authoritative and fully operational** until a separately approved future cutover. M010.001–M010.004 design/POC evidence informs the work; M010.004 controls the updated target authority boundary, superseding M010.003's placement of prompt/closeout/dispatch authority. Retain M010.002 corrupt-WAL FAIL/B1 as historical evidence, not a new stress-test mandate.

## Deliberately limited implementation
1. **Bounded preflight and reuse.** Inspect relevant lifecycle reducer/event schema, current prompt/closeout/dispatch fields, M010.002 disposable POC, and M010.004 exact authority/schema/API contract. Use targeted code/symbol/file-range inspection and repository intelligence where materially useful (or explain why not). Reuse established event validation/reducer semantics; do not reinvent the lifecycle, introduce a new persistence engine, or broadly refactor existing consumers.
2. **Isolated SQLite store.** Add a small repository-owned module/facade whose connection and file path are **explicitly provided by the caller** for tests. Never autodiscover or open the production state-root database, workflow files, registry, service, or managed sidecars from this module. Use SQLite `BEGIN IMMEDIATE`, foreign keys, WAL and `synchronous=FULL` as supported in disposable tests. Specify `application_id`, `user_version`, and fail-closed incompatible-schema handling. No production creation/activation path, no automatic live migration and no startup integration.
3. **Minimal records and immutability.** Implement only required repository/milestone identity, versioned `document` and immutable `document_revision` (UTF-8 full Markdown, SHA-256, logical type, source/provenance, parent revision, draft/approved linkage), original ordered `workflow_event` JSON with stable event IDs/timestamps/sequence, reducer projection + store revision, `workflow_document_link` keyed to exact revision/hash, typed Architect `dispatch` plus append-only status/PO decision history, `transaction_receipt` keyed to request ID/hash, and minimal publication identity/status *records* if necessary to avoid future destructive schema changes. Do NOT implement Git publication itself. Prefer a small documented schema without speculative tables, general attachments/blobs, permission systems, or a generalized CMS.
4. **Explicit contract API for fixture consumers.** Provide a narrow testable store interface for initialize disposable DB, create immutable document revisions, select an approved prompt revision, submit/link closeout revision, append a validated workflow event batch, load current reducer-derived snapshot, page events, and record/read dispatch decisions. Support bounded listing/get-by-exact-revision and revision/identity/hash retrieval needed by M010.006. Defer browser document library, full-text search, export, version diff rendering, MCP/CLI wiring, and actual publication to M010.006–M010.007.
5. **Preserve existing domain authority.** Keep all 21 lifecycle event types and six phases exactly, including WAITING/question/answer/bug/escalation linkages, PO approval/binding, lock-ins, closeout/acceptance/closure/reopen, and audit-only context verification. Never infer real PO authorization merely from a database row or reported actor label. Preserve the existing reducer as the semantics oracle. Ensure a protected operation not valid under current reducer/PO contract cannot be made valid by the DB store. When a fixture needs a fake PO confirmation, make it an explicit trusted fixture input and assert rejection without it; do not introduce a production impersonation facility.
6. **Atomicity, retry and concurrency.** Couple workflow batch, linked document revisions, receipt and projection in one transaction. New event IDs are unique within the defined repo/milestone boundary, sequence is contiguous, exact source payloads remain unchanged, and stale repository/selection/prompt-revision/expected-state or schema IDs fail with **zero changes**. The same transaction/request ID + canonical request hash returns its first saved result, even after an ambiguous response; same ID with different content fails. Receipt lookup precedes stale-revision refusal on exact retry. SQLite single-writer locking is adequate; give explicit bounded busy errors. Avoid unrelated lock/recovery frameworks.
7. **Version gate without environment disruption.** Expose a testable check for the actual Python-linked `sqlite3.sqlite_version_info` and a clearly reported production-eligibility result. The documented conservative production floor is SQLite 3.51.3 (or an explicitly verified fixed backport), while the current project interpreter was observed with 3.45.1. Do not install or upgrade Python/SQLite. **Disposable fixture execution may characterize the existing older library**, with an explicit test-only construction boundary and report indicating NOT PRODUCTION ELIGIBLE; it must never be mistaken for passing the production runtime gate. Test the gate using controlled version inputs and actual runtime reporting. Do not disable the future production gate via global environment flag.
8. **Read-only fixture importer and parity.** Add a bounded importer for **caller-supplied copies/controlled test fixtures** of v1 prompt, closeout, workflow sidecar and dispatch data. Preserve complete source bytes or exact event JSON, source hashes, event order/IDs, document provenance and links where evidence supports them. Do not invent missing historical event-time prompt hashes, approvals or transaction boundaries. Reject malformed/ambiguous sources explicitly. Full corpus migration belongs to M010.008; no scan or write to the currently selected managed workflow.
9. **Local validation and explicit limits.** Supply focused unit/contract tests using only temporary/disposable databases and synthetic/reusable fixture data. Cover document revision immutability, exact text/hash retrieval, approved revision identity, workflow-to-document links, all 21 events/six phases and reducer parity, dispatch state/approval linkage, multi-event atomicity, pre-commit rollback, same-ID retry, stale revision rejection, uniqueness, paging without duplicate/missing events, wrong prompt/repository/schema detection, bounded writer contention, fixture import/provenance, and SQLite runtime-gate classification. Reuse already validated M010.002 tests and components where suitable without copying a large alternate POC. Ordinary transaction failure tests suffice; do not spend effort repeating artificial physical-WAL corruption or disk-failure campaigns. Report skipped/untestable cases rather than inventing PASS.
