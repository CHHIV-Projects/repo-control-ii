# M005.002 — Agent Skills SOP Adoption Decision and Explicit Invocation Validation

## Objective

Finish the M005 Agent Procedure arc with a concrete Product Owner-ready SOP decision.

M005.000 established that Agent Skills are a credible procedure-packaging mechanism. M005.001 proved native Copilot Remote SSH discovery/loading for two instruction-only skills, but could not establish clean causal context savings because control sessions were contaminated by automatic skill availability/selection.

This milestone should not chase another token benchmark. Instead, determine whether the two existing skills should become accepted standing SOP helpers, under what invocation rule, and whether any immediate third skill is justified.

Primary candidate skills already created:
- `.agents/skills/repo-control-validation-closeout/SKILL.md`
- `.agents/skills/repo-control-blocker-bug-escalation/SKILL.md`

## Product intent

The Product Owner wants Agent Skills to improve routine operation, but not to replace `coding_agent_rules.md`, `project_workflow.md`, milestone prompts, Repo Control lifecycle authority, or Product Owner control.

Use this model:

```text
Governing documents
= authoritative policy / source of truth

Skills
= reusable operating procedure derived from policy

Milestone prompt
= task-specific scope / acceptance criteria

Repo Control
= deterministic enforcement / lifecycle / Product Owner authority
```

The goal is better procedural delivery and reduced repetition where safe, not policy migration for its own sake.

## Core decision to make

For each existing skill, choose exactly one status:
- ADOPT AS EXPLICIT SOP HELPER
- RETAIN AS OPTIONAL EXPERIMENTAL HELPER
- REVISE THEN ADOPT
- REJECT / REMOVE

Do not treat implicit activation as authority.

Evaluate the two skills on:
- correctness;
- clarity;
- overlap with governing rules;
- risk of semantic drift;
- visibility/auditability to the Product Owner;
- usefulness in real milestone work;
- whether explicit invocation is reliable and understandable;
- whether accidental/implicit activation could cause harm;
- maintenance burden;
- whether the procedure is stable enough to deserve a reusable skill.

## Explicit-invocation operating model

Test and recommend a practical SOP in which mandatory behavior does not depend on hidden implicit skill selection.

Candidate model to evaluate:

```text
Normal Coder work
-> governing rules remain mandatory
-> active prompt remains task authority

When validation/closeout begins
-> explicitly invoke repo-control-validation-closeout

When a genuine blocker or bug escalation is encountered
-> explicitly invoke repo-control-blocker-bug-escalation

Implicit skill activation
-> may assist
-> is never relied upon for mandatory gates or authority
```

Determine whether this is simple and reliable enough for routine use.

## Live validation

Use a small number of real, non-destructive procedure checks in the actual Copilot Remote SSH environment.

At minimum verify:
1. explicit loading of each skill still works from the canonical repository-local path;
2. the Coder can state when each skill should be invoked;
3. each skill points back to canonical authority rather than replacing it;
4. no skill grants Git/lifecycle/Product Owner authority;
5. no executable content, hooks, `allowed-tools`, or external dependencies exist;
6. an unrelated request does not require either skill;
7. the procedure remains understandable if the skill does not load.

Do not manufacture production WAITING states, bugs, or Git mutations merely to test the skill.

## Decide whether a third skill is justified now

Evaluate only one possible additional SOP skill:

`repo-control-preflight`

Ask whether a compact explicit preflight skill would materially help with repetitive startup tasks such as:
- `coder-context` / authorization;
- branch/repository identity;
- expected dirty-path classification;
- Graphify freshness when relevant;
- prompt/closeout pairing awareness;
- targeted governing-document reading.

Do not create it automatically.

Create `repo-control-preflight` in this milestone only if all of the following are true:
- it is clearly distinct from the existing two skills;
- the procedure is stable and repeatedly used;
- it does not become the sole carrier of authorization/no-Git rules;
- it is small and instruction-only;
- it reduces practical repetition without creating confusing overlap;
- the closeout explains why immediate adoption is justified.

Otherwise recommend it for later and do not create it.

Do not add any other skill in M005.002.
