# M008.000 — Closed Milestone Recovery and Outstanding-Dispatch Closure Guard

**Project:** Repo Control II  
**Repository:** `/home/chuck/projects/repo-control-ii`  
**Branch:** `main`  
**Milestone type:** Workflow lifecycle implementation  
**Primary objective:** Add a safe Product Owner-only way to reopen an accidentally closed milestone without rewriting history, and prevent accidental closure when an approved applicable Architect correction is demonstrably newer than the current closeout.

## 1. Background / motivating incident

A real Vocab App incident exposed a lifecycle gap:

- Vocab milestone `M002.003` reached REVIEW with a closeout.
- Architect submitted and the Product Owner approved a bounded correction instruction requiring isolated PostgreSQL validation.
- The approved correction dispatch occurred after the current closeout.
- The Product Owner accidentally selected **Accept & Close** approximately five seconds later.
- Repo Control correctly reconstructed M002.003 as `CLOSED`.
- A fresh Coder correctly refused to act because CLOSED grants no implementation authority.
- The approved correction still belongs to M002.003 and the Vocab worktree remains uncommitted, but current Repo Control provides no safe reopen operation.

This milestone must solve the generic lifecycle problem in Repo Control II. Do not hard-code Vocab-specific behavior.

## 2. Product decisions / lock-ins

Implement these decisions unless repository reality exposes a material blocker:

1. A closed milestone may be reopened only by an explicit Product Owner browser action.
2. Reopening is append-only. Never delete, rewrite, invalidate, or edit prior `acceptance_recorded` or `milestone_closed` events.
3. Add a durable reopen event and reconstruct current lifecycle from chronology.
4. Reopen may target:
   - `REVIEW` when the PO wants to reconsider/review without authorizing edits;
   - `IN_PROGRESS` when bounded work/correction under the same milestone remains authorized.
5. A reopen requires an explicit human-entered reason.
6. Reopening does not change the canonical prompt, approved lock-ins, repository selection, Git state, or historical dispatches.
7. Coder/Architect cannot reopen milestones. This is Product Owner lifecycle authority only.
8. **Accept & Close** must detect a clearly outstanding approved applicable Architect `INSTRUCTION` or `RESPONSE` and present a blocking/strong confirmation guard rather than silently closing.
9. The minimum deterministic outstanding-dispatch rule is:
   - dispatch is APPROVED;
   - dispatch applies to the selected repository and milestone;
   - type is `INSTRUCTION` or `RESPONSE`;
   - its approval timestamp is later than the most recent `closeout_submitted` event.
   This means an approved correction newer than the closeout is presumed not represented by that closeout.
10. Once a subsequent amended closeout is submitted after that dispatch, the dispatch no longer blocks ordinary Accept & Close under this rule.
11. Do not invent a hidden AI determination of whether an instruction was “consumed.” Use deterministic timestamps/events.
12. The Product Owner may deliberately override the closure guard only through an explicit second confirmation that identifies the outstanding dispatch(es). Preserve the override as durable workflow evidence if current event architecture supports doing so cleanly; otherwise STOP and raise the narrow design question before inventing a new authority model.
13. Reopening already-committed work is allowed in principle because workflow history is append-only, but the UI must clearly warn that prior Git history is not rewritten and subsequent work will require a later commit. Repo Control must not perform any Git mutation as part of reopen.
14. This milestone does not broaden when reopening is *appropriate*: use it for accidental/premature closure or bounded continuation under the same objective. Material changes in objective, architecture, authority, risk, or scope still require re-scope/new milestone.

## 4. Lifecycle event and reconstruction

Add the smallest durable event model necessary for reopening.

Preferred semantic event:

`milestone_reopened`

It must preserve at least:

- milestone identity;
- reported actor role = Product Owner;
- timestamp;
- reason;
- prior phase = CLOSED;
- target phase = REVIEW or IN_PROGRESS.

Use the repository's existing durable workflow/event representation rather than creating a parallel state store.

Lifecycle reconstruction must interpret the chronological event sequence so that:

```text
... → acceptance_recorded → milestone_closed → milestone_reopened(target=REVIEW)
= current phase REVIEW
```

and:

```text
... → acceptance_recorded → milestone_closed → milestone_reopened(target=IN_PROGRESS)
= current phase IN_PROGRESS
```

Prior acceptance and closure remain visible historical events.

A later normal lifecycle sequence must still work, e.g.:

```text
CLOSED
→ reopened IN_PROGRESS
→ closeout_submitted
→ REVIEW
→ acceptance_recorded
→ milestone_closed
→ CLOSED
```

Do not create special “second milestone” identity or clone artifacts.

## 5. Browser Product Owner reopen action

For a selected CLOSED milestone, add a Product Owner-facing **Reopen milestone** action.

The review/confirmation surface must clearly display:

- repository;
- milestone ID/title where available;
- current phase CLOSED;
- prior acceptance/closure remains historical;
- required reason field;
- target state choice: REVIEW or IN_PROGRESS;
- explicit statement that reopening does not alter Git or erase prior history;
- if the repository has committed changes after prior closure and this can be determined safely from current evidence, explain that future work will require a later commit but do not imply history rewriting.

Use existing CSRF, prepared-action/revalidation, repository-generation, milestone-selection and lifecycle safety patterns.

On confirmation:

- revalidate repository selection/generation;
- revalidate selected milestone and that it remains CLOSED;
- append the reopen event;
- reconstruct the selected target phase;
- do not modify prompt/closeout/source files except the normal tracked workflow sidecar event append;
- do not perform Git mutation.

After reopening to IN_PROGRESS, `coder-context` must surface current implementation/correction authority and any approved applicable dispatches normally.

After reopening to REVIEW, Coder editing authority remains absent.

## 6. Accept & Close outstanding-dispatch guard

Before final Accept & Close of a REVIEW milestone, inspect applicable approved Architect `INSTRUCTION`/`RESPONSE` dispatches relative to the latest `closeout_submitted`.

If any approved applicable dispatch has `approved_at` later than the latest closeout submission:

- do not perform an ordinary one-click closure;
- surface an explicit warning that the closeout predates approved Architect guidance;
- show each relevant dispatch ID, type, approval time, and a bounded human-readable excerpt/summary using existing safe display behavior;
- provide a path to cancel/review rather than close;
- if implementing an override, require an explicit second confirmation and durable reason/evidence per Section 2.

If there is no closeout in REVIEW, preserve existing closeout-required rules.

If all approved applicable dispatches predate the latest closeout, closure proceeds under the existing review/acceptance path.

Pending/rejected dispatches must not trigger this guard.

Dispatches for another repository/milestone must not trigger it.

PROMPT dispatches must not trigger it.

## 7. Coder context after reopen

Validate that a fresh/resumed Coder session does not need special chat memory.

For IN_PROGRESS reopen:

- `coder-context` reports M008 test fixture/current selected milestone as IN_PROGRESS;
- the canonical prompt remains the same;
- approved applicable INSTRUCTION/RESPONSE dispatches remain visible;
- current authorization permits only the existing milestone scope/bounded correction;
- no prior acceptance/closure event is erased.

For REVIEW reopen:

- `coder-context` reports REVIEW and does not authorize implementation.

Do not weaken the existing rule that CLOSED itself authorizes nothing.
