Reconcile Repo Control II governing documentation with the workflow/control-plane capabilities that were actually implemented and accepted during the completed M003 arc.

Do not use this milestone to define a detailed future roadmap.

## Required Historical Reconciliation

At minimum, verify and record the accepted implications of the completed M003 arc.

### 1. Architect evidence access

Record that Repo Control now exposes a bounded Architect MCP evidence interface for the selected repository/milestone.

The Architect can retrieve bounded repository, milestone, prompt, workflow, closeout, Git, evidence, governing-document, and review information through fixed read-only tools.

Natural Architect requests authorize only the minimum read-only evidence needed. This does not give the Architect arbitrary repository, shell, Git, filesystem, lifecycle, or Product Owner authority.

### 2. Architect-to-Coder dispatch transport

Record that M003.011 established a separate bounded proposal/transport channel.

Supported Architect proposal classes are:
- PROMPT
- INSTRUCTION
- RESPONSE

Architect submissions enter PENDING state and have no Coder or lifecycle authority until Product Owner approval.

The Product Owner remains the approval authority.

PROMPT approval can materialize only the server-derived canonical milestone prompt artifact. It does not select, approve, start, stage, commit, or push a milestone.

Approved INSTRUCTION/RESPONSE dispatches can be surfaced to the local Coder through coder-context.

Rejected and pending dispatches are not authorized Coder guidance.

Architect dispatch approval does not itself record lifecycle events.

### 3. Prompt transport replaces manual transfer where applicable

Record that milestone prompt drafts can now be delivered Architect -> Repo Control -> Product Owner review -> canonical repository prompt without manual copy/paste or file transfer.

This is a transport convenience, not lifecycle approval.

Preserve the distinction between:
- Approve & Save Prompt in the dispatch system; and
- Product Owner milestone lifecycle approval/start.

Also record the practical operational lesson discovered during M003.012: after a PROMPT is materialized, the prompt artifact should normally be reviewed/committed before implementation starts. The active workflow sidecar is the narrow dirty-tree exception; a newly materialized prompt is not intended to become a silent general dirty-tree exception.

### 4. Local Coder workflow interface

Record that the Coder remains local and does not have its own MCP integration.

The local CLI provides bounded context/status plus explicit submission paths for Coder questions, bugs, test evidence, and closeout submission.

The Coder still must not perform Git mutations.

Approved Architect dispatches are a separate section of coder-context, not standing lifecycle authority.

### 5. Milestone lifecycle model

Record the accepted six-phase lifecycle:

PLANNING -> READY -> IN_PROGRESS -> WAITING -> REVIEW -> CLOSED

Preserve the underlying event vocabulary and ordered event history.

Tests and Git state do not automatically advance lifecycle.

Lifecycle transitions remain server-authoritative and Product Owner controlled where appropriate.

### 6. Single-user workflow compression

Record that M003.012 compressed the Product Owner browser action surface while preserving distinct underlying events.

Normal Product Owner actions are:

- Approve & Start
  - prompt_approved
  - implementation_started

- Resolve & Resume
  - answer/decision/resolution event as applicable
  - optional separate binding lock-in where applicable
  - implementation_resumed

- Accept & Close
  - acceptance_recorded
  - milestone_closed

The browser no longer requires the redundant actor dropdown or explicit Product Owner confirmation checkbox for normal single-user Product Owner actions. The deliberate action button is the authorization gesture in this single-user model.

Compression changes the human interaction surface, not the lifecycle semantics.

### 7. Polling and stale-state behavior

Record that browser workflow state is server-authoritative and periodically refreshed.

Untouched forms may refresh automatically when workflow state changes externally.

Edited forms preserve entered text and block stale submission rather than silently overwriting user input.

No WebSocket/event-bus architecture was introduced.

### 8. Workflow sidecar and Git interpretation

Record explicitly that the active milestone workflow sidecar is expected operational state and may be modified/untracked while the milestone is active.

That active sidecar alone does not violate the clean-working-tree precondition.

Any other unexplained dirty path remains a blocker unless separately authorized/explained.

Do not broaden this exception.

### 9. Git and authority boundaries

Preserve the standing rule that coding agents do not Stage, Commit, Push, Tag, Merge, Rebase, Reset, Stash, Clean, Switch/Checkout branches, create/delete branches, or mutate remotes.

Product Owner retains repository mutation authority through Repo Control or manual Git operations.

Architect dispatch, lifecycle actions, and Coder workflow events must not silently perform Git mutations.

### 10. Repo Control architectural identity

Reconcile the governing documents so Repo Control is described consistently as a control plane rather than an AI project manager or giant bespoke agent framework.

Its durable value is:
- Product Owner authority;
- deterministic repository/project state;
- explicit workflow/lifecycle;
- bounded evidence routing;
- safe integration of interchangeable specialized tools.

Specialized subsystems should remain replaceable and should not be reimplemented inside Repo Control without a strong reason.
