# Part IV — Branch Awareness

## 15. Branch Inventory

Create a read-only **Branches** view showing **all local branches**.

This is a formal R002 requirement.

For each local branch display, at minimum:

```text
branch name
current-branch indicator
branch tip / short commit ID
last commit subject

relationship to main
configured upstream if any

```

---

## 16. Main as the Primary Reference

For this product/workflow, `main` is the normal branch reference point.

For every local branch other than `main`, calculate and display its relationship to `main`.

At minimum:

```text
commits ahead of main
commits behind main
fully merged into main: yes/no
```

For `main`, display an appropriate self/reference state rather than meaningless ahead/behind values.

---

## 17. Exact Branch-vs-Main Semantics

Use Git ancestry, not heuristics.

Recommended concepts:

```text
ahead of main
= commits reachable from branch tip that are not reachable from main

behind main
= commits reachable from main that are not reachable from branch tip
```

Use a reliable Git mechanism such as:

```text
git rev-list --left-right --count main...<branch>
```

or another equivalent explicit ancestry calculation.

Document which side maps to which count.

Do not reverse the labels.

---

## 18. "Merged into main" Semantics

A branch should be labeled:

```text
Fully merged into main
```

only if Git establishes that the branch tip is an ancestor of `main`.

A suitable read-only fact is:

```text
git merge-base --is-ancestor <branch> main
```

or an equivalent ancestry check.

Do not define "merged" using:

```text
same file content
commit subject
branch age
branch name
zero ahead/behind alone without understanding semantics
```

The UI should distinguish:

```text
Fully merged into main
Not fully merged into main
```

Do not call an unmerged branch unsafe or obsolete merely because it is not merged.

---

## 19. Branch Relationship Examples

The UI should make states understandable.

Examples:

```text
feature/foo
3 ahead / 0 behind main
Not fully merged into main

old-complete-work
0 ahead / 5 behind main
Fully merged into main

long-running-work
4 ahead / 9 behind main
Not fully merged into main
```

Do not require the Product Owner to infer meaning from raw rev-list counts.

---

## 20. Upstream Relationship

For each local branch, if an upstream is configured, display:

```text
upstream ref
ahead of upstream
behind upstream
```

Use local remote-tracking refs only.

Do not fetch.

Clearly label:

```text
Remote-tracking information is based on local refs and may be stale.
```

A branch with no configured upstream must be shown as:

```text
No upstream configured
```

not:

```text
0 ahead / 0 behind
```

---

## 21. Remote-Tracking Ref Freshness

R002.04 must remain offline/read-only.

Do not contact GitHub or the remote.

The page should make clear:

```text
main vs local branch
```

is current local repository ancestry,

while:

```text
branch vs origin/branch
```

depends on whatever remote-tracking refs were last fetched.

Do not conflate the two.
