## 2. Resulting Behavior

- On `SessionStart`, the adapter runs canonical local context retrieval through:
  - `/home/chuck/projects/repo-control-ii/.venv/bin/python -m repoctl.cli coder-context --format json --repository <cwd>`.
- It validates event shape, managed-worktree scope, repository identity, prompt identity, lifecycle/authorization coherence, and dispatch/reference structure.
- It emits bounded `additionalContext` with:
  - repository key/path/id,
  - selected milestone/prompt identity,
  - lifecycle/authorization status,
  - concise workflow state and references,
  - deterministic byte/token estimate metadata.
- Failure modes return explicit `INVALID_NO_AUTHORITY` (or `NO_AUTHORITY`) instead of success-shaped output.
- Prompt body / dispatch body / operator prompt text are not included in emitted context or diagnostics.

The adapter maps existing canonical CLI fields rather than creating a second authority source: `repository` (name, key, id, canonical path), `selection` and `milestone` (id, phase), `prompt` (path, SHA-256 identity, byte size), `authorization` (boolean/status/message), `workflow` (phase, next action, waiting state, open questions/bugs, latest binding lock-in, event count), approved Architect dispatch references, and standing document/policy references. Full prompt and dispatch bodies are deliberately excluded.

The recorded ordinary (non-probe) integration sample was **2,413 UTF-8 bytes / 604 estimated evidence tokens**. The estimate method is `ceil(UTF-8 bytes / 4)`, a character/byte heuristic, not a model tokenizer. This is the measured sample, not a guarantee of every lifecycle payload. The serialized envelope is capped at 8,192 UTF-8 bytes; if it exceeds the cap it fails closed rather than truncating required identity, lifecycle, authorization, or stop conditions. Open-condition and dispatch reference lists include at most four items and report omitted counts; reference text is capped at 240 characters, authority/waiting/lock-in text at 512, dispatch aliases at 32, timestamps at 64, and prompt path at 1,024. Input event text is capped at 1,000,000 characters and canonical CLI stdout at 1,000,000 bytes.

## 4. Architecture / Integration Notes

- Adapter stays repo-local and read-only; no global/user hook install was used.
- Hook command remains fixed-argument and non-shell-interpolated.
- Acceptance-only receipt/marker mode is implemented as explicit opt-in (`--acceptance-receipt`) and was used only during Gate C evidence collection; it is disabled in active hook config.
- The selected mechanism is the Copilot shared-harness command `SessionStart` hook, returning the host-consumed `additionalContext`. It was chosen over instruction-only bootstrap because instruction discovery alone did not establish execution or first-request context delivery. A `userPromptSubmitted` command hook was not selected because its ordinary command output is not the consumed initialization-context channel. Codex was not selected: its remote VS Code extension was present, but Codex hook execution/acceptance was unverified and the standalone Codex CLI was absent.

The adapter executes on that Linux worktree using `/home/chuck/projects/repo-control-ii/.venv/bin/python`.
- Agent Host configuration showed workspace trust enabled and `file:///home/chuck` in trusted URIs; the Product Owner clarified that `/home/chuck` is in the Trusted Folders list, and Repo Control II is below it. No trust or permission change was made. A direct SDK `folderTrust.isTrusted` RPC was not observed. The Product Owner reported selecting Copilot/shared harness in the exact workspace and seeing `.github/hooks/repo_control_context.json` in the Copilot Hooks customization view. This is operator-reported UI evidence; config discovery is separate from execution proof.
- Windows-local VS Code version, Windows Copilot extension/client profile, local user settings and enterprise policy were not observable from this Linux execution environment.

## 8. Known Limitations

- `Checkpoint Restored` UI action is not proven to trigger `SessionStart(source=resume)` in this host path.
- Resume freshness therefore remains unverified; reopened chats can present stale context risk.
- Hooks customization view evidence is operator-reported (UI not directly instrumented from this environment).
- SessionStart injects point-in-time context guidance; it is not a fail-closed file/shell/tool permission boundary. The startup authorization is not standing permission. Agents must retrieve current canonical context before consequential actions, especially after restoring a conversation.
- Host callback timeout/error fall-through, `preToolUse` coverage, other model choices, compaction/subagent paths, and Codex hook behavior were not validated.
