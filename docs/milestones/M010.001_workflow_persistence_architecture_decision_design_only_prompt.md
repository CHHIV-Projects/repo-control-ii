# M010.001 — Workflow Persistence Architecture Decision (Design-Only)

## Arc and objective
Begin a NEW M010.xxx arc, "Workflow Persistence Architecture and Transition", following the explicit Product Owner decision to stop custom v2 workflow-storage development in M009.021.004. This first milestone is DESIGN-ONLY: determine the simplest durable, recoverable, auditable workflow persistence architecture for a self-contained, single-user Repo Control installation on ONE Linux host. SQLite is the leading candidate, PostgreSQL is an alternative, and v1 sidecar extension and the experimental immutable-file v2 engine are comparison baselines. Recommend an architecture, decision boundaries, phased transition plan and testable acceptance contract; do NOT implement a new database, modify production workflow state or migrate any managed history.

No assumption that M009.021.004 is closed until live Repo Control shows it; ensure the Product Owner has separately created, selected and approved exact M010.001 prompt and IN_PROGRESS lifecycle before Coder work. ## Product requirements and constraints
- Hobby/personal use, single user, always-on Linux mini-server. Repo Control is intended to remain a self-contained installation; multiple Coder/Architect/browser *processes* may operate on the same repository, but multi-user distribution or cross-host database sharing is NOT a present requirement.
- Product Owner's familiarity with PostgreSQL in Photo Organizer is an application dependency, not evidence of DBA expertise or willingness to administer an additional database server. Prefer fewer moving parts, easier backups and reliable recovery, and explicit operational controls over speculative scalability.
- Existing v1 workflow sidecars remain current managed authority during the arc. The accepted cross-process lock correction from M009.021.002 remains protected. The M009.021.003/M009.021.004 v2 source and test results are historical experimental evidence, not deployed or approved authoritative storage. No live cutover, service restart, rollback, archival deletion, Git mutation, managed-ledger modification or schema change.
- Preserve the reserved M009.022 Resource/Execution Safety and M009.023 Retention/Final Limits Acceptance purposes, including separate Coder summary/waiting_reason defect. No silent cancellation or automatic renumbering; M010 is a separate arc.
- An event store is only successful if it preserves exact source event identity, ordering and content, all existing lifecycle semantics and 21 event-type transition invariants, PO decision/approval binding, open question/bug/escalation linkage, stale generation rejection, current-vs-historical authority and complete auditability. A relational database does not supply those domain guarantees automatically.

## Required reconnaissance and design outputs
1. Inventory actual workflow data and APIs read-only. Identify which files, selectors, hashes and identity records are currently authoritative; enumerate v1 source/size limits (2,000 events and 5,000,000 bytes), process concurrency, workflow event schema, derived state, approval/closure/reopen, Coder/Architect HTTP/MCP, browser, handoff/history, state-root locking and active-service dependencies. Measure representative read-only live sidecar counts/sizes within authorization and avoid broad unbounded enumeration. Distinguish code source/production deployment versions; do not assume committed code is deployed.
2. Define measurable requirement classes: correctness and provenance, crash durability/retry, concurrent writers, snapshot queries and pagination, security/role/permissions, performance and expected real growth, audit verifiability, backup/restoration, maintenance/recovery under failures, portability, and graceful resource limits. Make a short authoritative requirements/invariants table with evidence sources and explicit assumptions. Clarify how existing canonical Markdown workflow and Git-visible docs can remain useful without ambiguous competing sources of truth.
3. Compare at least four options using the SAME requirements: (A) SQLite local file with WAL/transactions, (B) PostgreSQL separate service/container, (C) minimally improved v1 file-based ledger, (D) current experimental immutable-segment/B+ tree custom v2. Compare one-host process concurrency and locking semantics; durability settings and same-host local storage constraints; high-integrity event append and dedup via unique IDs; read projections; full-history audit/hashes; potential recovery and migration model; operational footprint; filesystem/file count; resource costs; safe backup and restore; and code/test complexity. No invented benchmark; cite source/tests and identify measured versus hypothetical qualities.
4. Consider SQLite schema at CONCEPTUAL level: append-only events with immutable IDs, per-milestone scoped sequence and expected revision, unique transaction IDs, original JSON payload/hash, linkage to repo/milestone/prompt hash, and transactionally updated current milestone projection; indexes for event pagination, unresolved question/bug/decision references and historical lookup. Preserve original event chronology and 21-type transition validation. Define how a complete audit independently recomputes projections and verifies a snapshot, and how exported human-readable documents can be verified against DB identity without implying they're an independent authority.
5. Model corruption, power failure, partial write, writer race, stale client, lock contention, database unavailability, missing WAL, backup/restore and cross-version cutover outcomes. Compare relational transaction guarantees with what remains application responsibility (domain correctness, idempotent retry, accurate lifecycle state, provenance and audit). Design conservative backup and disaster-recovery options for single Linux host with local SSD and Synology backup target; use database-aware backup, not copying a live WAL-mode DB file to NAS. No external-access exposure.
6. Propose a bounded disposable SQLite proof-of-concept for a future separately authorized M010.002: replay the same controlled v1 event fixtures and above-cap histories without modifying live state; multi-process concurrent writers; injected transaction interruption/rollback; read replay/projection parity; idempotent retry; snapshot paging; backup/restore integrity; disk footprint, files, RSS/FD, elapsed time and write contention. Include the exact success/failure acceptance thresholds or mark thresholds requiring a PO decision. Compare equivalent prior v2 fixture measurements, not mismatched workloads.
7. Decide an authority transition plan in outline: v1 remains writable until independently approved migration/cutover; a fixture migration preserves original event IDs/order/timestamps/prompt identities and hashes; old/new readers fail closed when inconsistent; explicit backups, PO quiescence and rollback/forward repair; staged application-consumer integration, test/review gates, separate PO operational rollout. Never write tests to actual selected managed state.
8. Identify explicit material decisions for PO: (i) SQLite vs alternate store, (ii) source-of-truth migration from Markdown to database and audit export semantics, (iii) acceptance of SQLite single-writer concurrency for measured workload, (iv) SQLite operating envelope and backup policy, (v) future milestones/transition strategy and preservation/retirement of experimental v2 source. Do not turn open choices into silent design assumptions.
