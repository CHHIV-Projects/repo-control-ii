## 2. Resulting Behavior

- `state_artifact_lock` now locks
  `<canonical-state-root>/.locks/state-artifacts.lock`; the private `.locks`
  directory is mode `0700`, and the persistent lock file is mode `0600`.
- The lock uses no-follow opens, validates owner/type/permissions/link count
  and pathname identity, checks that the lock file remains stable while held,
  and reports a bounded 10-second acquisition timeout as a distinct busy
  error.
- A same-thread nested acquisition for the same canonical root reuses the
  outer descriptor and updates its depth; nesting a different root is
  rejected. Threads serialize through the process-local RLock and processes
  through the persistent `flock`.
- Web mutation order is
  `repository_action_lock` → `STATE_ARTIFACT_LOCK` → persistent state-root
  `flock`. The web wrapper rejects reversed acquisition; busy and unavailable
  lock conditions receive explicit responses.
- Workflow readers/writers, combined actions, reopen, selection pointers,
  scanner state, Architect dispatches, and procedure transaction/remap
  operations share this state-root lock. The global lock deliberately
  serializes distinct milestones using the same state root.
- V1 serialization, event schema, marker, order, IDs, replay behavior, and
  limits remain unchanged. No managed workflow history was migrated.

These are source and fixture-test results only. They do not establish that a
deployed service or managed state is protected.

## 4. Architecture / Integration Notes

The design follows M009.021.001 §4.4: one state-root lock owner, with no
per-milestone lock domain. Same-root calls use one held descriptor; different
roots cannot be nested. Atomic replacement remains the v1 file-write
mechanism, not the process-serialization mechanism. Dispatch-guidance reads
during combined closeout remain inside the same lock owner and use safe
same-thread reentry.

The lock protects only processes using the new file-lock convention. Older
running versions use a different lock domain and do not coordinate with this
lock. Consequently, this change must not be described as a production fix
until the Product Owner has planned and executed a compatible cutover and
verified live behavior.

**Repository Intelligence: USED** — a targeted caller query over the then
CURRENT graph identified scanner, dispatch, and procedure-remap/transaction
callers and materially informed the integration scope. Its structural
evidence was assessed PARTIAL after direct source inspection; source and
runtime tests, not the graph, establish behavior. The current graph reports
STALE (`supported_source_inputs_changed`). Refresh was considered and not
attempted: direct caller inspection and the complete test suite supplied the
needed evidence, and refreshing a structural graph was not necessary for this
bounded closeout. The freshness-only `stats` check is not counted as a
structural query use.

Controlled fixture observation: a process held the state-root lock for
120 ms; a waiting thread entered after 120.9 ms. The persistent lock file
occupied zero content bytes, the observing process's file-descriptor count
was unchanged (11 before and after), and the harness maximum RSS was 20,352
KiB. This is a bounded contention/resource observation, not a throughput
benchmark, production measurement, or power-loss durability proof.

## 8. Known Limitations

- The code-level lock change is uncommitted and undeployed. Existing
  processes using the prior lock domain can still race with one another or
  with new processes; production concurrency is not claimed fixed.
- v1 still has its 2,000-event and 5,000,000-byte limits and full-history
  read/replay/write costs. No limit was increased, and no data was migrated.
- This test environment does not prove cross-filesystem `flock` behavior,
  hardware/power-loss durability, or mixed-version live-service correctness.
- A global state-root lock serializes unrelated same-root state operations;
  no parallel-throughput guarantee is made.

Product Owner-only operational checklist before any live cutover:

1. Inventory all live v1 workflow sidecars, readers, writers, and running
   service versions; record exact versions and state roots.
2. Verify backups and a non-mutating migration/cutover dry run; explicitly

4. Coordinate a version-compatible deployment/restart and verify all
   instances use the same persistent per-state-root lock protocol.
5. Run a live two-process concurrent-writer smoke test, then independently
   audit event identities/order and monitor lock/integrity errors.
6. Preapprove recovery handling. Before a v2 manifest commit, restore may
