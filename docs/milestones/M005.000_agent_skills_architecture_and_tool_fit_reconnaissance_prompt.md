# M005.000 — Agent Skills Architecture and Tool-Fit Reconnaissance

## Objective

Evaluate Agent Skills and adjacent mature procedural/tooling approaches for Repo Control II before any implementation commitment.

The purpose is to determine whether modular, progressively disclosed agent procedures can reduce repeated prompt/context load, improve procedural consistency, and complement Repo Control's existing workflow authority without creating another bespoke agent framework or competing source of truth.

This is reconnaissance only. Do not implement Agent Skills integration in this milestone.

## Product context

Repo Control remains the control plane for:
- Product Owner authority and approvals;
- milestone/lifecycle state;
- deterministic project/repository state;
- Git control and mutation boundaries;
- evidence routing and safe integration of specialized tools.

The strategic rule remains: do not build a large custom agent framework when a mature external standard/tool can own a specialized responsibility.

M004 established Graphify-backed repository intelligence as provisional shared infrastructure for Architect and Coder. Use it naturally where it helps this reconnaissance, and note whether it materially reduces broad source inspection. Do not modify Graphify merely to support this milestone.

## Reconnaissance questions

Research the current Agent Skills ecosystem/standard and closely related mature approaches that could serve the same procedural role. Prefer primary documentation, source repositories, specifications, and current implementation evidence over secondary commentary.

At minimum determine:

### 1. What Agent Skills actually are
- Current specification/model and terminology.
- How skills are discovered, selected, loaded, and executed.
- Whether they are declarative instructions, executable tools, prompt packages, scripts, or combinations.
- How progressive disclosure/context loading works in practice.
- What is standardized versus implementation-specific.

### 2. Supported environments and maturity
Evaluate realistic support/adoption for the coding environments relevant to this project, including where evidence exists:
- GitHub Copilot / VS Code coding agents;
- OpenAI Codex or related coding-agent workflows;
- Cline or comparable local/IDE agents;
- other mature agent frameworks only when materially relevant.

Do not assume cross-agent portability merely because file formats look similar. Distinguish native support, convention-based support, adapters, and speculative compatibility.

### 3. Repo-resident versus user/global procedure
Evaluate:
- repository-local skills;
- user/global skills;
- shared reusable skills across projects;
- precedence/override behavior;
- versioning and update implications.

Recommend which kinds of Repo Control procedure belong in each location, if any.

### 4. Candidate procedure from current Repo Control practice
Classify current recurring instructions into at least these buckets:
- governing authority that should remain in Repo Control/context docs;
- reusable agent procedure that may be a good skill candidate;
- milestone-specific instructions that should remain in prompts;
- deterministic checks that should remain code/tool enforcement rather than prose/skills.

Use actual current project conventions as evidence. Examples to examine include:
- preflight/status checks;
- no-Git-mutation rule for Coders;
- test/closeout expectations;
- blocker/question escalation;
- bounded bug handling;
- evidence/reporting format;
- lifecycle interaction;
- documentation update behavior.

Do not move authority into skills merely to shorten prompts.

### 5. Context/token reduction potential
Assess whether skills can realistically reduce:
- repeated standing instructions in milestone prompts;
- repeated governing-document loading;
- broad procedural context sent to models.

Describe what could be loaded only when relevant versus what must always remain visible.

Do not fabricate token savings. If exact token measurements are unavailable, describe measurable proxies and propose how to measure real savings later.

### 6. Relationship to Repo Control
Recommend a clean boundary:
- what Agent Skills should own;
- what Repo Control should own;
- whether Repo Control should merely expose/select skills, validate them, index them, or remain mostly unaware of them;
- how Product Owner authority remains explicit;
- how Coder and Architect could share compatible procedural assets without collapsing their roles.

Avoid creating a new custom skill engine unless there is a concrete gap that mature tooling cannot satisfy.

### 7. Relationship to Graphify and other specialized tools
Explain how Agent Skills/procedural assets could complement Graphify repository intelligence:
- Graphify supplies repository structure/evidence;
- skills supply repeatable procedure;
- Repo Control supplies workflow/authority/integration.

Identify any useful interaction, but do not tightly couple them.

Also note whether GitHub Spec Kit or another mature specification/planning tool overlaps materially with the same problem. Distinguish complementary roles from duplication.

### 8. Reuse before invention
Look for existing high-quality skills/templates/procedural repositories relevant to:
- repository reconnaissance;
- coding-agent preflight;
- testing/validation;
- documentation/closeout;
- code review;
- Git safety;
- architecture review.

Identify reusable candidates where evidence supports them. Do not copy or install anything in this milestone.

### 9. Risks and failure modes
Include at least:
- hidden/implicit instructions reducing Product Owner visibility;
- skill drift from governing documentation;
- multiple sources of truth;
- stale skills;
- vendor-specific formats falsely treated as portable;
- overloading context with too many skills;
- procedural instructions conflicting with deterministic Repo Control safeguards;
- executable skill content expanding security authority.
