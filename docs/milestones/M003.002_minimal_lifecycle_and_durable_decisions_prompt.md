# 2. Governing Workflow Model

Treat the following Product Owner workflow as authoritative for this milestone.

## 2.1 Standard SOP

The normal milestone flow is:

```text
1. Product Owner ↔ Architect discussion

2. Architect composes prompt

3. Product Owner reviews and commits prompt

4. Coder reviews prompt and repository reality

5. Coder either:
   - proceeds;
   - asks questions;
   - identifies blocker;
   - identifies repository conflict;
   - escalates.

6. Product Owner carries material questions to Architect

7. Architect answers

8. Product Owner approves binding decisions where required

9. Answer returns to Coder

10. Coder implements and tests

11. During implementation/testing there may be:
    - additional questions;
    - clarifications;
    - bounded bugs;
    - test failures;
    - stop conditions;
    - escalations;
    - Architect decisions;
    - Product Owner decisions.

12. Coder prepares closeout

13. Architect and Product Owner review

14. Review may result in:
    - acceptance;
    - request for more evidence;
    - bounded correction;
    - clarification;
    - separate follow-up milestone.

15. Product Owner performs final Git staging / commit / push

16. Milestone closes
```

The SOP defines the normal path, not an inflexible state machine.

# 3. Minimal Lifecycle

R003.00 recommended six coarse lifecycle phases.

Implement only:

```text
PLANNING
READY
IN_PROGRESS
WAITING
REVIEW
CLOSED
```

Do not add additional phases unless repository evidence proves one is necessary and the Product Owner approves it.

## 3.1 Meanings

### PLANNING

Milestone selected but prompt/approval/preparation is not yet complete.

### READY

The authoritative prompt and required Product Owner approval are recorded and the milestone may be handed to the Coder.

### IN_PROGRESS

Implementation or validation is actively underway.

### WAITING

Work is paused for:

```text
clarification
decision
blocker
escalation
other explicitly recorded reason
```

WAITING should carry structured reason information rather than creating separate phases for each waiting type.

### REVIEW

Coder closeout/evidence is available for Architect/Product Owner review, or review is actively occurring.

A bounded correction may return the milestone to IN_PROGRESS.

### CLOSED

The Product Owner has explicitly accepted the outcome and recorded the milestone closure.

Do not infer CLOSED from:

```text
closeout existence
clean Git state
commit existence
push
test pass
```

# 4. Lifecycle Transition Principles

Transitions should normally be explicit.

Do not silently advance the milestone based only on artifact presence.

The UI may suggest a possible next transition when deterministic evidence supports it, but explicit approval is required where authority matters.

At minimum preserve these boundaries:

```text
PLANNING → READY
requires Product Owner approval of prompt / governing lock-ins

READY → IN_PROGRESS
may be explicit Product Owner/Coder handoff action

IN_PROGRESS → WAITING
may occur because of a recorded question/blocker/escalation

WAITING → IN_PROGRESS
requires a valid answer/decision/resolution

IN_PROGRESS → REVIEW
occurs when closeout/review evidence is submitted

REVIEW → IN_PROGRESS
allowed for bounded correction

REVIEW → CLOSED
requires explicit Product Owner acceptance
```

Do not implement automatic Git mutation as part of any transition.

# 7. Routine Clarification vs Durable Decision vs Addendum

Implement/support the following distinction.

## 7.1 Routine Conversation

No durable record is required for a transient explanation or wording choice that does not affect future implementation.

Do not force every coder question into project documentation.

## 7.2 Durable Decision Event

Record a question/answer/decision when it:

```text
changes coder behavior
resolves a blocker
establishes an assumption
needs to survive chat loss
matters to later review
```

This should remain lightweight.

## 7.3 Authoritative Lock-In / Addendum

A formal binding decision is required when guidance:

```text
supersedes
materially refines
or resolves ambiguity in
```

the milestone prompt while preserving the same approved objective.

Binding decisions require explicit Product Owner approval.

## 7.4 Re-Scope / New Milestone

Stop and escalate when a discovery materially changes:

```text
objective
architecture
authority
risk
persistence
implementation strategy
validation burden
product behavior
```

Do not silently broaden the active milestone.

# 8. Bug Handling

Preserve the Product Owner's existing flexible bug workflow.

A bug may remain inside the active milestone when:

```text
it is directly related to the changed behavior
the fix is bounded
architecture/scope/authority/risk remain unchanged
the coder documents discovery
the coder documents classification
the coder documents fix
the coder documents focused validation
```

A new milestone is not required for every bug.

Escalate when a bug indicates:

```text
cross-project safety concern
material security issue
authority-boundary problem
broad architecture change
unrelated subsystem work
materially larger validation burden
```

The system should record the bug event and classification without forcing unnecessary ceremony.

# 9. Product Owner Approval Boundaries

M003.002 must preserve explicit Product Owner authority.

At minimum:

| Action | Authority |
|---|---|
| Select active milestone | Product Owner |
| Mark prompt authoritative / READY | Product Owner |
| Record routine technical answer | Architect or Coder contextually, but non-binding unless approved |
| Make answer binding / approve lock-in | Product Owner |
| Classify clearly bounded in-scope bug | Coder may propose; Architect/PO review if uncertain |
| Re-scope / architecture / authority / risk change | Product Owner after Architect review |
| Submit closeout | Coder |
| Request more evidence / bounded correction | Architect may recommend |
| Accept implementation | Product Owner |
| Close milestone | Product Owner |
| Stage / Commit / Push / other Git mutation | Product Owner |

Do not infer authority from browser access alone.

If the current browser has no user-role identity model, record the action as Product Owner-controlled UI behavior without pretending to cryptographically identify the actor.

# 10. Persistence Architecture

Use the R003.00 hybrid model.

## 10.1 Durable Tracked State

Keep authoritative milestone decisions/events in tracked human-readable project artifacts.

Do not store the only copy of an authoritative decision in:

```text
operational JSON
browser session
chat history
logs
```

## 10.2 Operational State

The current operational pointer remains outside the repository:

```text
~/.local/share/repoctl/<repository_id>/milestones/selection.json
```

Extend operational state only if required for:

```text
current lifecycle phase
waiting reason
UI convenience
```

If phase becomes operational state, document how it is reconciled with durable tracked evidence and how restart/recovery behaves.

Prefer minimal operational state.

## 10.3 No Database

Do not add SQLite or another database in M003.002 unless a concrete requirement makes the file model unsafe.

If so, stop and escalate.

# 22. Stop / Escalation Conditions

Stop and ask the Product Owner before proceeding if:

- durable events cannot be represented cleanly in tracked human-readable artifacts;
- a new canonical artifact type is required and conflicts with the current artifact standard;
- lifecycle state cannot survive restart without introducing a database or broader persistence redesign;
- current UI cannot safely distinguish informational events from binding decisions;
- actor identity cannot be represented honestly without introducing an authentication model;
- stale requests cannot be bounded using existing repository/milestone generation protections;
- implementing this requires changes to Git authority;
- workflow state becomes dependent on Git cleanliness;
- the implementation would force every routine conversation into formal documentation;
- scope expands into handoff packets or direct integrations.

Do not silently redesign around these issues.

# 24. Completion Criteria

M003.002 is complete when:

- the selected milestone has an explicit lifecycle phase;
- the six-state minimal lifecycle is implemented without unnecessary extra phases;
- WAITING captures reason without multiplying states;
- meaningful questions/answers/decisions/bugs/review actions can be durably recorded;
- binding decisions are distinguished from routine events;
- Product Owner approval boundaries are explicit;
- bounded bugs can remain inside the milestone;
- material scope/architecture/risk changes still require escalation;

- stale repository/milestone requests cannot record against the wrong target;
- lifecycle changes do not mutate Git;
- focused tests pass;
- full test suite passes;
- manual acceptance instructions are complete;
- no unauthorized Git mutation occurred.

The desired end state is:

```text
Repo Control knows which milestone is active,
knows its explicit workflow phase,
preserves the decisions and meaningful events that govern the work,
and shows the next authorized action,
without becoming an autonomous project manager
or removing Product Owner authority.
```
