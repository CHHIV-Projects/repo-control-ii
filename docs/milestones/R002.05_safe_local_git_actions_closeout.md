## 3. Mutation Authority Contract

Git Review is the sole primary browser surface for the new local actions. The Changes view uses a desktop-oriented changed-file table, selectable only from server-rendered inventory tokens, and a shared toolbar. Select all applies to every visible path (there is no filter); it never maps to `git add -A`, `git add .`, or another implicit set. Each batch is capped at 256 paths and 32 KiB of combined path bytes. Mixed eligibility disables an action in the UI and is independently rejected by the server.

`GET` routes inspect and render state only. A mutation starts with a CSRF-protected `POST` that prepares the selected set; the server then renders a separate confirmation page. A second CSRF-protected `POST` with the short-lived capability token confirms. Immediately before execution, the server re-reads all selected Git state; if any member is stale, no command is run. It executes one fixed argument-array Git command with explicit literal pathspecs and verifies the result for every selected path.

No mutation is triggered by page load, selection, preview, refresh, or browser navigation. No stage-all, automatic staging, automatic commit, branch/remote action, push, fetch, pull, reset, stash, clean, merge, rebase, or conflict-resolution behavior was added.

## 4. Prepared Action / Confirmation Design

`PreparedGitActions` stores prepared records in a per-app, lock-protected in-memory map. Tokens are generated with `secrets.token_urlsafe(32)`, expire after five minutes, are single-use, and are capped at 64 live records. A prepared batch binds the action, configured repository identity/root, branch, HEAD, canonical ordered selected-path set, complete index identity, per-path status/index/worktree/HEAD identity and preview evidence, and expiry. Commit remains bound to the full currently staged set and evidence; it has no checkbox subset. No database or persistent mutation plan was added.

Tokens remain in hidden POST fields rather than URLs. A wrong-action confirmation is rejected; a token is consumed on actual confirmation attempt, including stale-state refusal. Cancel removes the token without running Git.

## 5. Fresh-State Revalidation Design

Before confirmation execution, path actions re-inspect the configured repository, branch, HEAD, operation/conflict state, status, complete index inventory, and every selected path's index records, worktree content/mode identity, HEAD record, and clean-filter attributes. The complete ordered path set must match the prepared record. If any selected member is stale or no longer eligible, no mutation command is run for any member. Commit re-captures HEAD/branch, the complete index, staged raw inventory/content evidence, staged paths, and bounded staged diff. A mismatch blocks execution and requires a fresh review.

Path actions conservatively bind the complete index fingerprint, so an unrelated staged-index change can invalidate a path action. Commit identity distinguishes staged state from unrelated unstaged file contents: an unrelated unstaged edit after preparation does not invalidate a commit if the staged scope remains identical.

## 6. Stage UX and Semantics

The Changes table provides checkboxes for its actual displayed Git inventory, including select-all-visible and clear-selection controls. The shared toolbar enables Stage only when every selected path supports it. Confirmation lists each exact path and exposes its evidence on demand. The command is `git add -- :(literal)<path-1> ... :(literal)<path-n>`; it never uses a stage-all command. It stages each selected path, including current worktree content; for staged-plus-unstaged paths, the current worktree version replaces that selected path's index content. Every selected result is verified and unselected paths remain outside the explicit pathspec list.

## 7. Unstage UX and Semantics

Unstage is enabled only when every selected path is staged and supported. The single confirmation states **INDEX WILL CHANGE** and **WORKTREE CONTENT WILL NOT BE REPLACED**, and lists the complete selected set. The command is `git restore --staged -- :(literal)<path-1> ... :(literal)<path-n>`. Staged additions become untracked when present; staged deletions become unstaged deletions; staged-plus-unstaged content retains each worktree version. Unselected staged paths remain unchanged. Every selected path is verified no longer staged and its worktree identity unchanged.

## 8. Restore-Unstaged UX and Semantics

Restore Unstaged is enabled only when every selected path is an ordinary tracked path with complete supported evidence. One visually destructive confirmation states **UNSTAGED WORKTREE CONTENT FOR ALL SELECTED PATHS WILL BE DISCARDED**, lists every selected path, and provides per-path loss evidence in expandable sections. The command is `git restore --worktree -- :(literal)<path-1> ... :(literal)<path-n>`. The index is verified unchanged and every selected path has no remaining unstaged change. For staged-plus-unstaged content, its staged version remains staged and is restored into the worktree.

Binary, truncated, undecodable, unsupported, or otherwise incomplete preview evidence prevents this action from being offered. Tracked deletions are supported where the preview is complete.

## 9. Restore-to-HEAD UX and Semantics

Restore to HEAD is enabled only when every selected tracked path is present at HEAD and has complete supported evidence. One confirmation shows the HEAD OID, complete path list, both affected layers, and per-path staged/worktree evidence on demand. It states **STAGED AND UNSTAGED CHANGES FOR THE SELECTED PATHS MAY BE DISCARDED**. The command is `git restore --source=HEAD --staged --worktree -- :(literal)<path-1> ... :(literal)<path-n>`. Every selected path is verified unchanged relative to HEAD, and HEAD did not move.

Untracked or newly staged paths absent from HEAD, conflicted paths, renames/copies, and incomplete evidence are refused.

## 10. Commit UX and Semantics

Git Review shows current branch and HEAD, the complete bounded staged-path inventory with each status, a staged diff, and unstaged/untracked paths separately. The Product Owner supplies a nonempty single-line subject (maximum 500 characters). Preparation and confirmation repeat that only reviewed staged content will be committed; no implicit staging occurs. No editor, AI-generated message, amend, allow-empty, `-a`, signing-configuration change, or hook bypass was added.

Commit executes `git commit -m <exact reviewed subject>` using an argument array. Active executable commit hooks or a configured custom `core.hooksPath` make commit unavailable. Binary, undecodable, over-limit, or incomplete staged diff evidence also blocks commit. Verification requires HEAD to advance, the new subject to match, and no staged changes to remain. Unstaged and untracked paths are reported as remaining and stay outside the commit.

## 11. Unsupported / Fail-Closed Cases

All local actions are blocked for detached HEAD, in-progress merge/rebase/cherry-pick/revert/bisect states, and unresolved conflicts. Rename/copy and submodule states, unsupported file types (including symlinks), paths exceeding the content-identity ceiling, configured clean filters, unavailable Git evidence, and oversized inventories fail closed. Restore actions require complete evidence; commits require complete reviewable staged evidence and supported hooks. Manual Git remains the fallback for refused states.

## 13. Browser / Token Safety

All new mutation endpoints are POST-only and require CSRF validation. When `Origin` or `Referer` is present, it must match the current scheme and host; `Sec-Fetch-Site: cross-site` is rejected. Prepared confirmation tokens are unguessable, short-lived, action- and repository-bound, and single-use. Confirmation success uses Post/Redirect/Get; replay is refused. Flask HTTP method errors retain their correct HTTP status instead of being converted into generic 500 responses.

## 14. Post-Action Verification

Stage verifies every selected path is staged and has no unreviewed unstaged remainder. Unstage verifies every selected path is no longer staged and each worktree identity did not change. Restore-Unstaged verifies every selected path has no unstaged state and its index fingerprint is unchanged. Restore-to-HEAD verifies no selected changes remain and HEAD is unchanged. Commit verifies a new HEAD, matching subject, and a cleared staged set. A failed command or failed verification is reported as failure/uncertain; it is not presented as success. Standard Git CLI does not provide a transaction spanning the worktree/index for these multi-path commands; the service fails before execution on known stale/unsupported state and reports actual state if Git itself fails during a command.

## 15. Backend Git Commands

All calls use the existing bounded Git subprocess runner with argument arrays, `GIT_OPTIONAL_LOCKS=0`, and `GIT_TERMINAL_PROMPT=0`. Evidence commands have bounded output/time; mutation commands have a 30-second timeout and 64 KiB output caps. The mutation commands are:

```text
git add -- :(literal)<selected path 1> ... :(literal)<selected path N>
git restore --staged -- :(literal)<selected path 1> ... :(literal)<selected path N>
git restore --worktree -- :(literal)<selected path 1> ... :(literal)<selected path N>
git restore --source=HEAD --staged --worktree -- :(literal)<selected path 1> ... :(literal)<selected path N>
git commit -m <reviewed subject>
```

Supporting read commands inspect status, index entries, HEAD/path entries, attributes, staged inventory/diff, branch, and hooks. No network command is used.

## 21. Known Limitations

- Prepared tokens are in-memory and become invalid after application restart; the Product Owner must prepare and confirm within five minutes.
- Batch path actions are limited to 256 selected paths and 32 KiB combined path bytes; there is no filter, so select-all-visible covers the complete displayed inventory.
- The action service refuses paths above its 256 MiB content identity ceiling and bounded status/index/diff inventories.
- Concurrent out-of-band Git activity between final revalidation and Git process execution cannot be made atomic with standard Git CLI operations. Index locks are checked before mutation and all outcomes are verified afterward; if verification is uncertain, inspect Git Review before retrying.
- Standard Git does not make multi-path commands transactional. The application prevents intentional partial action when preflight detects a stale/ineligible member; if Git itself errors after making changes, the error state must be inspected in Git Review.
- The application remains a single Product Owner, loopback-bound browser service and still requires manual `repoctl web` startup and an SSH port-forward. This milestone does not change deployment/access.
