## 3. Mutation Authority Contract

Git Review is the sole primary browser surface for the new local actions. `GET` routes inspect and render state only. A mutation starts with a CSRF-protected `POST` that prepares the selected action; the server then renders a separate confirmation page. A second CSRF-protected `POST` with the short-lived capability token confirms. Immediately before execution, the server re-reads relevant Git state; it refuses stale state. It executes a fixed argument-array Git command and verifies the resulting Git state before reporting success.

No mutation is triggered by page load, selection, preview, refresh, or browser navigation. No stage-all, automatic staging, automatic commit, branch/remote action, push, fetch, pull, reset, stash, clean, merge, rebase, or conflict-resolution behavior was added.

## 4. Prepared Action / Confirmation Design

`PreparedGitActions` stores prepared records in a per-app, lock-protected in-memory map. Tokens are generated with `secrets.token_urlsafe(32)`, expire after five minutes, are single-use, and are capped at 64 live records. Records bind the action, configured repository identity/root, branch, HEAD, selected path and relevant state fingerprints (or, for commit, the full index and staged evidence), preview, and expiry. No database or persistent mutation plan was added.

Tokens remain in hidden POST fields rather than URLs. A wrong-action confirmation is rejected; a token is consumed on actual confirmation attempt, including stale-state refusal. Cancel removes the token without running Git.

## 5. Fresh-State Revalidation Design

Before confirmation execution, path actions re-inspect the configured repository, branch, HEAD, operation/conflict state, status, complete index inventory, selected path index records, selected worktree content/mode identity, selected HEAD record, and clean-filter attributes. Commit re-captures HEAD/branch, the complete index, staged raw inventory/content evidence, staged paths, and bounded staged diff. A mismatch blocks execution and requires a fresh review.

Path actions conservatively bind the complete index fingerprint, so an unrelated staged-index change can invalidate a path action. Commit identity distinguishes staged state from unrelated unstaged file contents: an unrelated unstaged edit after preparation does not invalidate a commit if the staged scope remains identical.

## 6. Stage UX and Semantics

The selected-file detail offers a Stage review action only for supported changed paths. Its confirmation identifies the path and affected index layer and shows staged/worktree or untracked content evidence, with incomplete evidence called out. The command is `git add -- :(literal)<path>`. It stages one selected path, including its current worktree contents; if the path was already staged with additional worktree edits, the selected worktree version replaces that path's index content. Other paths remain untouched. The resulting staged state is verified.

## 7. Unstage UX and Semantics

Unstage is offered for supported staged paths. Confirmation describes the index change and preserves the worktree; the selected staged evidence is shown. The command is `git restore --staged -- :(literal)<path>`. Staged additions become untracked when present in the worktree; staged deletions become unstaged deletions; staged-plus-unstaged content retains the worktree version. Other staged paths remain unchanged. The result verifies the selected path is no longer staged and its worktree identity is unchanged.

## 8. Restore-Unstaged UX and Semantics

Restore Unstaged is offered only when the existing selected-path preview has complete supported evidence. Confirmation is visually destructive and explicitly warns that the path's unstaged worktree content will be discarded. The command is `git restore --worktree -- :(literal)<path>`. The index is verified unchanged, and the selected path is verified to have no remaining unstaged change. For staged-plus-unstaged content, the staged version remains staged and is restored into the worktree.

Binary, truncated, undecodable, unsupported, or otherwise incomplete preview evidence prevents this action from being offered. Tracked deletions are supported where the preview is complete.

## 9. Restore-to-HEAD UX and Semantics

Restore to HEAD is offered only for supported tracked paths present at HEAD with complete evidence. The confirmation identifies the current HEAD OID, both affected layers, the staged/worktree evidence, and explicitly warns that staged and unstaged changes for that path can be discarded. The command is `git restore --source=HEAD --staged --worktree -- :(literal)<path>`. Post-action verification confirms the path is no longer changed and HEAD did not move.

Untracked or newly staged paths absent from HEAD, conflicted paths, renames/copies, and incomplete evidence are refused.

## 10. Commit UX and Semantics

Git Review shows current branch and HEAD, the complete bounded staged-path inventory with each status, a staged diff, and unstaged/untracked paths separately. The Product Owner supplies a nonempty single-line subject (maximum 500 characters). Preparation and confirmation repeat that only reviewed staged content will be committed; no implicit staging occurs. No editor, AI-generated message, amend, allow-empty, `-a`, signing-configuration change, or hook bypass was added.

Commit executes `git commit -m <exact reviewed subject>` using an argument array. Active executable commit hooks or a configured custom `core.hooksPath` make commit unavailable. Binary, undecodable, over-limit, or incomplete staged diff evidence also blocks commit. Verification requires HEAD to advance, the new subject to match, and no staged changes to remain. Unstaged and untracked paths are reported as remaining and stay outside the commit.

## 11. Unsupported / Fail-Closed Cases

All local actions are blocked for detached HEAD, in-progress merge/rebase/cherry-pick/revert/bisect states, and unresolved conflicts. Rename/copy and submodule states, unsupported file types (including symlinks), paths exceeding the content-identity ceiling, configured clean filters, unavailable Git evidence, and oversized inventories fail closed. Restore actions require complete evidence; commits require complete reviewable staged evidence and supported hooks. Manual Git remains the fallback for refused states.

## 12. Legacy Workflow / Navigation Treatment

Primary navigation now contains Dashboard and Git Review. Workflow remains directly available as a read-only historical artifact page; its primary stage/commit controls were removed. The legacy Workflow snapshot creation, stage preparation/approval, and commit preparation/approval POST routes return HTTP 410 and cannot perform their former actions. Existing historical plans and execution artifacts were not deleted.

## 13. Browser / Token Safety

All new mutation endpoints are POST-only and require CSRF validation. When `Origin` or `Referer` is present, it must match the current scheme and host; `Sec-Fetch-Site: cross-site` is rejected. Prepared confirmation tokens are unguessable, short-lived, action- and repository-bound, and single-use. Confirmation success uses Post/Redirect/Get; replay is refused. Flask HTTP method errors retain their correct HTTP status instead of being converted into generic 500 responses.

## 14. Post-Action Verification

Stage verifies the selected path is staged and has no unreviewed unstaged remainder. Unstage verifies it is no longer staged and its worktree identity did not change. Restore-Unstaged verifies unstaged state is gone and the index fingerprint is unchanged. Restore-to-HEAD verifies no selected change remains and HEAD is unchanged. Commit verifies a new HEAD, matching subject, and a cleared staged set. A failed command or failed verification is reported as failure/uncertain; it is not presented as success.

## 15. Backend Git Commands

All calls use the existing bounded Git subprocess runner with argument arrays, `GIT_OPTIONAL_LOCKS=0`, and `GIT_TERMINAL_PROMPT=0`. Evidence commands have bounded output/time; mutation commands have a 30-second timeout and 64 KiB output caps. The mutation commands are:

```text
git add -- :(literal)<selected path>
git restore --staged -- :(literal)<selected path>
git restore --worktree -- :(literal)<selected path>
git restore --source=HEAD --staged --worktree -- :(literal)<selected path>
git commit -m <reviewed subject>
```

Supporting read commands inspect status, index entries, HEAD/path entries, attributes, staged inventory/diff, branch, and hooks. No network command is used.

## 21. Known Limitations

- Prepared tokens are in-memory and become invalid after application restart; the Product Owner must prepare and confirm within five minutes.
- Only one changed path at a time can be staged, unstaged, or restored.
- The action service refuses paths above its 256 MiB content identity ceiling and bounded status/index/diff inventories.
- Concurrent out-of-band Git activity between final revalidation and Git process execution cannot be made atomic with standard Git CLI operations. Index locks are checked before mutation and all outcomes are verified afterward; if verification is uncertain, inspect Git Review before retrying.
- The application remains a single Product Owner, loopback-bound browser service and still requires manual `repoctl web` startup and an SSH port-forward. This milestone does not change deployment/access.
