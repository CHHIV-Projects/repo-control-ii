## 2. Resulting Behavior

- Each new use measures the compact normalized JSON response after evidence pruning and count metadata are finalized. The UTF-8 byte count preserves `response_bytes`; characters are `len(text)` Unicode code points; the estimate is `(characters + 3) // 4`.
- The measured surface includes the returned service envelope, outcome, warnings, errors, and truncation/omission metadata. It excludes CLI pretty-print formatting/newline, MCP wrapper/protocol framing, and HTTP headers. Non-ASCII values are JSON-escaped by the canonical serializer before code-point counting.
- Measurement metadata is kept in the bounded use record, not inserted into the evidence response. This avoids recursive counting and prevents measurement fields from reducing evidence available under existing response limits.
- SQLite adds nullable `evidence_characters`, `estimated_evidence_tokens`, estimator method/version, surface, and quality columns. Existing rows retain their original bytes, IDs, ratings, inspection values, and `misleading_ever` state; legacy token fields remain NULL and display as “Not measured.”
- Controlled records retain the old arm fields and add separate source/tool/total evidence bytes and characters, `files_inspected`, read-versus-located-only source-window counts, char4 method provenance, and snapshot/task/stopping-rule provenance. Reduction is shown only when stop rules and method/surface are comparable. Zero control has no percentage; negative reductions remain visible.
- Corrected fixed-reference records additionally store per-arm `o200k_base` evidence-token counts and package/method/encoding/asset/surface provenance. Fixed-reference reductions require matched stop and completion criteria and identical tokenizer metadata and measured surface. Legacy byte-only and previous char4-only payloads remain unchanged and display reference counts as “Not measured.”
- The benchmark runner accepts bounded JSON via stdin, requires canonical compact normalized JSON for tool evidence, counts actual read source windows separately, counts each delivered item occurrence once, and never stores raw input. Normal Intelligence query code does not import the reference-tokenizer module or package.
- Normal uses, explicit controlled comparisons, and graph-refresh receipts remain separate. The page explains its empty comparison state, identifies compatible records/methods, and distinguishes estimates from model-native or billed tokens.
- The Intelligence page derives the newest fixed-reference-comparable record from stored records, shows both evidence-token counts, the signed reduction formula and the equivalent increased-evidence figure when negative, and limits interpretation to that one task. Older records remain deterministically grouped in a collapsed historical table; the compact comparison table retains measurement/provenance details in accessible disclosures.
- The responsive width (`min(96vw, 1680px)`) is scoped to this page; its tables scroll internally on narrow screens. Recent uses remain collapsed one-line summaries with the existing feedback forms and guards inside. The page links to an operator guide; no benchmark payload, measurement, database schema, rating, or history was changed.

## 4. Architecture / Integration Notes

- The existing central query service computes measurements after final pruning/count updates, and the same code path serves Coder and Architect. It adds no source scans, provider calls, or tokenizer work.
- The fixed reference is `tiktoken==0.11.0`, method `o200k-base-reference-v1` version `1`, encoding `o200k_base`. The selected wheel SHA-256 is `7f929255c705efec7a28bf515e29dc74220b2f07544a8c81b8d69e8efc4578bd`, pinned in the hash-enforced requirements manifest and checked against the exact file entry in the PyPI release JSON (`https://pypi.org/pypi/tiktoken/0.11.0/json`). The official asset is `https://openaipublic.blob.core.windows.net/encodings/o200k_base.tiktoken`, SHA-256 `446a9538cb6c348e3516120d7c08b09f57c36495e2acfffe59a5bf8b0cfb1a2d`, matching the hash embedded in that pinned release.
- Provisioning is isolated to a user-owned Python 3.12 benchmark venv and cache outside the application environment. The loader checks the exact cached URL-keyed asset and SHA-256 before checking/loading `tiktoken`; it sets `TIKTOKEN_CACHE_DIR` deterministically and fails closed on absent/corrupt assets. Counts use `encode_ordinary`, so special-token-looking strings count as ordinary text. No production dependency, service, Graphify runtime, or query networking was changed.
- Normal tool namespace imports were tested in a clean subprocess: importing `repoctl.intelligence.service` did not load `repoctl.intelligence.reference_tokens` or `tiktoken`. A real runner invocation with Python socket `connect`, `connect_ex`, and `sendto` blocked completed with zero network attempts. An OS network namespace attempt (`unshare --net`) was unavailable in this environment (`Operation not permitted`); no privileged firewall changes were made.
- Controlled comparisons use `controlled-evidence-v1`. Both arms record the same counted surface and method, task/question ID, repository/source identity and HEAD, timestamp, stopping rule, and whether stopping-rule equivalence was achieved. Source and tool evidence units are recorded separately; each actually delivered occurrence is counted once, and raw question/source/evidence text is not stored.
- One real controlled record was persisted through the benchmark runner with ID `m008002-o200k-4943a4616d8f48148410d131ed441aa8`. It used fixed HEAD `36ad97ca143c87cdb8cb1a134575936d9f020037`, repository source identity `178226baaa1c900daffe21bd1a59e39629b64596b603eeea7e594dce2d601cf9`, and CURRENT graph generation `25159cf9859244aa807c9c1412db310b`. Both arms found and read the identical `record()` source window and met the declared completion/stopping criteria. The source-first arm recorded 1,336 bytes, 334 char4-estimated tokens, and 310 `o200k_base` tokens; the Intelligence-first arm recorded 2,474 bytes, 619 char4-estimated tokens, and 670 `o200k_base` tokens. The reference reduction is **−116.1%** (more evidence in Intelligence-first), char4 reduction **−85.3%**, and byte reduction **−85.2%**. Interactions were 2 per arm; each read one source window and inspected one file. Mechanical elapsed was 2.513 ms vs 355.842 ms, respectively; this includes local command startup/query work and is not human or model reasoning time. The result is a bounded command-level comparison, not a blind/model-quality experiment.
- A separate synthetic test fixture validates compatible, negative, zero-denominator, mismatched-asset, incomplete, and unknown-reference paths; it is not presented as a real benchmark.
- Historical benchmark payloads are only decorated for display in memory. No historical bytes are converted to token estimates, and no history is rewritten.
- Usability grouping and latest-record selection are read-only projections over those decorated rows, ordered by recorded timestamp with benchmark ID as a deterministic tie-breaker. The fixed Markdown guide is served through `/intelligence/guide`; responsive styling is scoped to the Intelligence page and does not widen Git Review pages.

## 8. Known Limitations

- Char4 is approximate: `~1 token = 4 English characters ≈ 0.75 English words` is only a rough rule. JSON, whitespace, identifiers, paths, and other languages may differ substantially.
- These measurements do not capture Copilot/Codex host context, hidden reasoning, tool framing, model output, provider billing, or total agent-session consumption.
- The compact service-JSON boundary is canonical and common across consumers; final CLI/MCP presentation formatting and transport wrappers are intentionally excluded.
- The fixed reference remains a common cross-agent yardstick, not any receiving model's native tokenizer. The demonstrated comparison is one bounded task and is not causal or general evidence of tool value; its mechanical elapsed times include command/query startup.
- Installed-service behavior after PO/operator reload, a post-change normal-use query reflected in the running page, and visual browser acceptance remain pending. The integrated browser could not reach the local preview, so responsive layout is covered by scoped CSS and rendered HTML tests, not an actual 1600px/390px visual check.
