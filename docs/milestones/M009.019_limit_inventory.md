### Classification and priority

- **A — Security/governance invariant:** preserve absent an approved
  alternative with equal or better safety.
- **B — Resource-protection budget:** bound work/storage; tune only from
  measurements and retain truthful failure/incomplete reporting.
- **C — Pagination/display bound:** page size may be small if navigation and
  completeness are reliable.
- **D — Functional/usability cap:** can hide eligible information or block a
  normal operation.
- **E — Unknown justification / unbounded path:** evidence is insufficient
  to assert the intended trade-off or a comparable safeguard is absent.
- **P0:** false negative, undiscoverable eligible information, or operational
  failure; **P1:** common user friction or significant integrity/resource
  risk; **P2:** tuning/maintenance issue with a visible fallback.

All recommendations below are provisional proposals, not decisions.
`RETAIN` means preserve for now; `REDESIGN` means replace behavior rather
than simply raise a number; `NEEDS REVIEW` means retain until the Product
Owner has evidence and chooses separately.

## Decision appendix — historical search alternatives

The observed production-reported example has 548 candidates, so it crosses
the current 300-read budget while remaining below the 2,000-candidate cap.
The exact-path document read is a separate successful operation; that proves
readability of the known path, not completeness of discovery.

1. **Bounded streaming full-match evaluation with continuation.** Walk and
   evaluate a deterministic candidate stream in bounded work units; return a
   cursor only when more eligible work remains. Cursor must bind repository
   identity, query/filters, root and traversal version, and a stable snapshot
   or explicit mutation-invalidating generation. Requires carefully bounded
   cursor state and invalidation/expiry semantics. It can stop within CPU/byte
   budget without claiming a complete zero-match result.
2. **Index/cache with invalidation.** Build a lexical index over approved
   roots and page query results from it. Fast repeated queries, but introduces
   cache ownership, stale-index detection, concurrent updates, disk/memory
   retention, source confidentiality, rebuild cost and consistency semantics.
   No such index exists now; this is the largest new maintenance burden.
3. **Exhaustive filter-first search with paged results.** Apply filters and
   stable ordering, evaluate every candidate under an explicit overall
   candidate/byte/time envelope, then paginate the complete match set. Simple
   semantics and no index, but rescanning can be costly; if an envelope ends
