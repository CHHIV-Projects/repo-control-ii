# Milestone M011.001 — Shared Procedure Transaction and Deployment Compatibility

## 1. Scope Completed

Repaired the managed R8 procedure-transaction storage contract and implemented
the approved Product Owner-controlled worktree boundary as one design. The
running browser now uses the existing private service-user transaction store
instead of deriving storage from the intentionally root-owned R8 parent.
Browser Confirm seals an exact request without modifying a worktree; an
inactive same-UID systemd one-shot revalidates and executes only that request
for the selected registered repository.

The implementation preserves the accepted managed SQLite R8 authority,
registry, selection, recovery policy, legacy journals, Git boundary, and
published procedure 1.5.0. It did not update Vocab App or Photo Organizer.

## 2. Resulting Behavior

- `/home/chuck/.local/share/.repoctl-procedure-transactions` is the explicit
  private journal/request root. It remains `chuck:chuck` mode `0700`.
- Missing, inaccessible, incorrectly owned/mode, or symlinked configured
  storage reports `STORAGE_UNAVAILABLE`. Malformed or integrity-invalid
  journal/request content still reports `CORRUPT`.
- Preserved terminal overlay journals remain readable after a later registry
  overlay remap; active recovery remains bound to the current exact mapping.
- Preview and Review are read-only. Confirm stores one exact request bound to
  repository key/ID/path, live selection generation, reviewed plan or recovery
  journal, and target snapshots/hashes.
- `repo-control-procedure-update@<key>.service` runs as `chuck:chuck`, checks
  live repository selection, executes once, and exits. A stale selection fails
  before target writes and permits a fresh review.
- The main service receives only the private journal-root write exception.
  Each inactive repository instance receives the selected repository root only
  for its lifetime; nested `.git`, `docs/context`, and `docs/milestones` remain
  read-only, and every nonselected repository remains read-only.
- An executor death before a journal exists remains retryable. Once an active
  journal exists, status exposes recovery. A separately reviewed Recover may
  supersede only its matching interrupted request and restores exact original
  images.

## 4. Architecture / Integration Notes

The design uses no privileged helper, new daemon, schema migration, authority
cutover, blanket `/home` exception, persistent worktree exception, ACL change,
or permission change. Root `AGENTS.md` requires parent-directory rename rights,
so the approved exception is temporal and limited to the selected one-shot
namespace. Application allowlists, repository identity, reviewed hashes,
current snapshots, confirmation expiry, live-selection revalidation, and
nested systemd read-only mounts constrain the actual operation.

The five installed files are root-owned mode `0644`. The live main service
retains `ProtectSystem=strict` and `ProtectHome=read-only`. All three executor
instances are `static` and `inactive`. Prior configuration was captured under
`/root/repo-control-m011001-before`; undo restores only these five paths and
restarts the same managed R8 service.

Repository Intelligence: **NOT USED** — a final stats query reported `STALE`
because supported source inputs changed, with zero returned structural nodes.
Refresh was considered but not attempted: direct source inspection, exact
filesystem metadata, effective systemd properties, live health, journal
inspection, focused tests, and two real transient-systemd fixture runs answered
the acceptance questions. A refreshed static graph would not replace the
required runtime sandbox and crash/recovery evidence.

## 12. Reopened Correction Addendum — 2026-11-22

This addendum preserves the original accepted closeout above and records the
later bounded correction. The correction was required after real Photo

### 12.1 Correction scope and root cause

`procedure_action_preconditions(require_bundle_integrity=True)` reused
`active_release_preparation()` as an installation gate. Under managed SQLite,
that helper returned `UNAVAILABLE` before independently validating the
published bundle whenever the selected milestone contained an unverified
imported prompt or guidance. That was correct for milestone implementation and
new release publication, but it incorrectly disabled installation of the
already-published, independently hash-verified procedure 1.5.0.

The correction separates these capabilities:

- `UNVERIFIED_IMPORTED_HISTORY` continues to deny milestone implementation and
  new release-preparation authority. It does not approve or reinterpret any
  historical prompt, guidance, or decision.
- Existing published-procedure installation may proceed only after canonical
  bundle/manifest/source integrity validates. Existing repository identity,
  overlay, selection generation, exact plan digest, target snapshots, expiring
  review token, sealed request, transaction state, one-shot execution, and
  recovery checks remain unchanged.
- `RELEASE_INTEGRITY_UNAVAILABLE`, `RELEASE_AUTHORITY_UNAVAILABLE`, canonical
  corruption, or an actively authorized release preparation still blocks
  Review Apply.

The former acceptance tests proved clean fixture workflows and the one-shot
transaction mechanism, but did not model the actual combination of imported
unverified prompt plus imported unverified guidance on a closed migrated
milestone. That missing production state, rather than the transaction journal,
was the decisive coverage gap.

### 12.2 Product Owner checkbox correction

The complete served-template and route audit found three redundant identity or
self-attestation gates that duplicated an already deliberate named action:

| Surface | Removed duplicate | Binding retained |
|---|---|---|
| Closed milestone reopen | “I am the Product Owner” checkbox | CSRF, repository/milestone, phase, prompt identity, event count, target phase, and required reason |
| Pending Architect dispatch approve/reject | Generic Product Owner confirmation checkbox | CSRF, repository generation, exact dispatch fingerprint, and named approve/reject route |
| Accepted closeout export | Generic “confirm this preview as Product Owner” checkbox | accepted document revision/hash, preview fingerprint, repository generation, Git drift checks, and named Export action |

Content-specific acknowledgements remain: confirming exact imported prompt or
guidance bytes as a new decision, and deliberately closing despite listed newer
guidance with a required reason. Git Review file-selection and document-library
selection checkboxes are selections, not identity claims. Product Owner role
attribution remains explicitly unauthenticated; the removed checkboxes never
provided authentication.

### 12.5 Additional defects and quality observations

The correction and rollout exposed broader reliability concerns:

1. **Authority concerns are over-coupled.** Milestone approval, imported-history
   confidence, published-release integrity, backup coverage, repository
   selection, browser session generation, and execution authority can inhibit
   one another even when the intended operation needs only a subset.
2. **Production migrations are underrepresented in tests.** Clean fixtures did
   not model the actual imported-history combination that failed in Photo
   Organizer.
3. **Broad procedure regressions are not currently meaningful.** Sixty-three
   tests fail before exercising application code because their helper is tied
   to a superseded canonical version.
4. **Production executes from a mutable worktree.** Python source changes need
   a restart while templates may be read immediately, permitting mixed-version
   behavior during an uncommitted rollout.
5. **Operator scripts lacked a hostile-environment harness.** The first
   correction rollout printed `rg: command not found` because root's restricted
   `PATH` lacked `rg`; the negated shell command masked exit 127 and printed a
   false audit PASS. The audit was replaced with the pinned Python runtime and
   reverified without another restart. Runtime source hashes, R8 authority, and
   service readiness were unaffected, but the false PASS was a real script
   defect.
6. **Restart/browser generation handling is brittle.** Immediately after the
   restart, stale browser requests produced workflow-fragment 409 responses and
   two repository-selection 400 responses before refresh and successful
   selection. This failed safely, but normal recovery depends too heavily on
   the user recognizing stale client state.
7. **Acceptance was fragmented.** Focused milestones repeatedly proved local
   mechanisms without one continuously maintained production-state matrix that
   includes migrated history, systemd, backup identity, browser sessions,
   multi-repository switching, and operator environment.

These observations do not establish that every listed architectural concern is
a confirmed defect. They identify high-risk coupling and missing evidence that
requires dedicated reconnaissance before further piecemeal repair.

### 12.9 Recommendations

1. Separate explicit capabilities for milestone authority, published-release
   integrity, backup readiness, repository selection, and execution authority;
   one capability's failure should not disable an unrelated operation.
2. Build one production-shaped acceptance harness covering the real service
   account, sanitized root/service environments, effective systemd sandbox,
   all registered repositories, imported history, browser switching/restart,
   backup coverage, and one-shot execution/recovery.
3. Repair procedure fixtures so previous/current releases are explicit test
   inputs rather than assumptions about the live canonical bundle; restore the
   broad suite to green before relying on it.
4. Deploy an immutable versioned application artifact or release directory
   atomically instead of executing production from a mutable worktree.
5. Treat operator scripts as production code: test minimal `PATH`, missing
   tools, partial failure, repeat invocation, start limits, bounded rollback,
   and the rule that a missing verifier can never produce PASS.
6. Require a current Repository Intelligence impact query for cross-module
   changes, then validate graph findings against source and production-shaped
   runtime evidence.
7. Add one end-to-end Product Owner browser gate on genuine migrated production
   state before closing changes to authority, selection, persistence, backup,
   Git, or procedure deployment.
