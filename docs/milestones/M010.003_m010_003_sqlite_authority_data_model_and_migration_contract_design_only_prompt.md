## Product Owner decisions and risk posture
- The target is ONE self-contained Repo Control instance on ONE Linux machine for a single Product Owner, not a multi-tenant or distributed database service. Prefer Python standard-library sqlite3 and a modern fixed SQLite library, minimal file count, and existing server operations over PostgreSQL administration or new custom storage layers.
- SQLite is the leading CANDIDATE, not yet production-approved. Its M010.002 fixture results passed lifecycle parity, 10,000-event workload, eight-writer accounting, retry, paging, audit and consistent backup/restore. Original deliberately damaged-WAL fail-closed criterion remains FAIL and classified B1; do not erase or relabel it.
- Accept proportionate residual risk: no custom WAL repair, parallel append-only recovery ledger, general replication engine, elaborate disaster-recovery controls, invented numerical RPO/RTO, mandatory NAS tooling, or another extensive artificial corruption-testing arc. A database-consistent backup and restore path plus ordinary transactional/integrity protections are the intended baseline. Do not recast M010.002's deliberate WAL-header damage as a routine commit failure.
- Current POC ran Python 3.12.3 with SQLite 3.45.1; documented WAL-reset concurrency issue is distinct from deliberate header corruption. Design a feasible, inspectable Python-runtime SQLite version preflight/pinning policy using a known fixed version, without installing packages or upgrading the host in M010.003.
- Git actions (Stage, Commit, Push, Tag, Merge), global repository selection, service changes, managed state writes, or destructive steps are exclusively Product Owner/operator actions under their separately approved workflows.

## Required bounded design work
1. **Current integration map (targeted reconnaissance).** Identify authoritative v1 sidecar/read/write/locking/reducer/revision APIs, selected milestone pointer and prompt hash, event chronology, approval/lock-in, closing/reopening, questions/bugs/escalations, handoff/dispatch and history interfaces, browser/MCP/CLI consumers, Git-visible status and active sidecar handling. Use targeted source/symbol/file-range inspection and repository intelligence when useful, or document why not. Avoid broad repeated full-repo scanning. Trace exactly the smallest set of callers that an eventual cutover would change.
2. **One source of truth.** Recommend a precise SQLite authority boundary: what resides in a single local DB versus stays in Git or the existing state root (repository registry, prompt files, closeout and human-readable documents, Architect dispatch metadata, selected milestone pointer, workflow event history/projection). Distinguish Git authority over Git operations from the workflow event authority. Define whether historical `*_workflow.md` files remain immutable archival records and whether future Markdown workflow views are generated one-way, disposable or materialized for Git. Prohibit dual-writable v1/SQLite ledgers and ambiguity about which store accepts lifecycle changes. State how external readers/historical tools retain reliable access and how an active/exported Markdown view avoids stale authority confusion.
3. **Minimal database schema/contract.** Define tables/keys/constraints for repository, milestone/prompt identity and hash, ordered original event JSON with preserved event ID/type/timestamp/attribution/binding, per-milestone sequence/revision, stable transaction ID+request hash/receipt for idempotent retry, derived current projection, and needed lookup indexes. Reuse the established v1 lifecycle reducer as the source of domain semantics; do NOT reimplement the reducer in SQL. Define data types, optional schema versions, migrations, reject rules for stale prompt/expected revision, immutable append and projection parity, lifecycle revision and a bounded query/paging contract. Favor a minimal schema over speculative extensibility.
4. **Writer and consumer boundaries.** Define a small repository-owned workflow-store interface with append, load/snapshot, history paging, audit and consistent backup/restore operations. Identify how existing browser, coder-CLI, Architect MCP and history consumers will use it without sidecar-specific assumptions, and how Product Owner confirmation rules and approved dispatch visibility are preserved. Differentiate domain approval authority from storage-layer atomicity. Keep ordinary single-writer SQLite concurrency and finite busy/retry handling; avoid distributed coordination frameworks.
5. **Reversible, PO-controlled transition design.** Plan in steps only: (a) fixture replay/import from selected historical v1 sidecars, preserving source events, identities and order; (b) comparator/audit against v1-reduced lifecycle state and historical linkages; (c) bounded consumer adapter cutover; (d) explicit PO quiescence, consistent backup and single authoritative switch; (e) verified rollback plan for pre- and post-cutover failures without split-brain writing; (f) retention/archive policy for legacy sidecars and treatment of non-authoritative custom-v2 artifacts. Distinguish read-only fixtures from actual managed history. State which subsequent milestone owns each implementation/validation/operational step.
6. **Proportionate operations.** Design local SSD DB directory/owner permissions, WAL/FULL or documented equivalent, fixed SQLite runtime compatibility gate, startup sanity check, and a simple database-aware backup/restore procedure compatible with existing server/NAS backup practices where practicable. Recovery may restore a last verified snapshot with acknowledged loss of newer activity; any such decision must be visible to the Product Owner, never silent. No independent external event-log completeness anchor or granular recovery engine required. Mark numeric RPO/RTO/cadence/retention as deferred PO choices; offer no additional database dependencies unless decisively justified.
7. **Decision and implementation readiness.** Produce one coherent recommended final model rather than an unconstrained options catalog: short rationale against staying with v1 or running PostgreSQL, expected reduction in custom code/operations without unsupported numeric savings, minimal API/schema outline, authority matrix (before/transition/after), traceable lifecycle/identity invariants, version/runtime gate, top 3–5 realistic risks and mitigations, and a staged M010.004+ plan with small independently reviewable implementation units. Explicitly label decisions that genuinely require later PO approval and default/recommended choices that follow the risk posture above.
