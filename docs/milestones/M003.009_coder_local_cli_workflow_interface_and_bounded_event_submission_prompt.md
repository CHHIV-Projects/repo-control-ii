# 1. Objective

Implement the accepted M003.008 architecture that closes the remaining local Coder interaction loop with the smallest practical provider-neutral interface.

The target operating model is:

```text
Prompt / workflow state
→ Coder via local repoctl CLI

Coder meaningful question / bug / test / closeout signal
→ bounded local repoctl CLI submission
→ durable milestone workflow sidecar

Architect
→ continues using existing read-only MCP

Architect answer / recommendation
→ Product Owner approval / durable workflow action in Milestone tab

Coder
→ reads updated state with local repoctl CLI
→ resumes only when lifecycle authorizes it
```

This milestone should make the Coder interaction path operational without adding Coder MCP, new network services, background polling, or broad write authority.

---

# 2. Accepted Architecture

Treat M003.008 as controlling architectural direction.

## 2.1 Prompt → Coder

Use a local Repo Control CLI interface.

Required primary command:

```bash
repoctl coder-context
```

A compact read-only status form may also be provided:

```bash
repoctl coder-status
```

The Coder already operates on `henderson-server1` against the local repository, so no Coder MCP is required.

## 2.2 Coder → Workflow

Allow direct Coder submission of exactly four bounded non-authoritative workflow event classes:

```text
question_submitted
bug_discovered
test_result_recorded
closeout_submitted
```

No other workflow event type may be submitted through the Coder CLI.

## 2.3 Architect

Architect MCP remains read-only and unchanged.

Do not add Architect write tools.

## 2.4 Product Owner

Product Owner remains exclusive authority for:

```text
active milestone selection
prompt approval / READY
binding lock-ins
authoritative decisions where approval is required
resume from WAITING
review acceptance
milestone closure
all Git mutations
```

## 2.5 Milestone Tab

The Milestone tab remains the Product Owner control and audit surface.

Do not convert it into a chat application in this milestone.

# 3. Architect Repository Review Findings

The Architect independently inspected the current repository before composing this prompt.

Important current implementation facts:

1. `src/repoctl/cli.py` currently uses `argparse` and explicit command dispatch. New Coder commands should follow the existing CLI style rather than introducing a new command framework.

2. `src/repoctl/workflow/milestones.py` already provides:
   - `discover_milestones(...)`
   - `load_milestone_selection(...)`
   - external selection persistence under the configured Repo Control state root
   - repository/milestone containment and symlink protections.

3. `src/repoctl/workflow/lifecycle.py` already defines:
   - the six accepted phases;
   - the workflow event vocabulary;
   - durable tracked sidecar rendering;
   - event reduction / transition validation;
   - selection revalidation before reads/writes;
   - `load_milestone_workflow(...)`;
   - `record_milestone_event(...)`;
   - shared locking via `STATE_ARTIFACT_LOCK`;
   - atomic sidecar writes.

4. The existing lifecycle engine already supports the four accepted Coder event types:
   - `question_submitted`
   - `bug_discovered`
   - `test_result_recorded`
   - `closeout_submitted`

5. Existing lifecycle behavior includes:
   - `question_submitted` only while `IN_PROGRESS`;
   - a question with waiting metadata transitions to `WAITING`;
   - `bug_discovered` only while `IN_PROGRESS` or `WAITING`;
   - `test_result_recorded` only in `IN_PROGRESS`, `WAITING`, or `REVIEW` and requires evidence source + result;
   - `closeout_submitted` only in `IN_PROGRESS`, requires the currently discovered matching closeout artifact, and transitions to `REVIEW`;
   - Product Owner-only enforcement already exists for binding events such as prompt approval, lock-ins, acceptance, and closure.

6. `src/repoctl/workflow/handoff_packets.py` currently builds large Coder packets containing the full prompt plus standing workflow/rules documents. M003.009 should reduce routine dependence on these packets, but must not remove the packet capability.

7. Active milestone selection is external operational state, not an in-repository “latest milestone” heuristic. The Coder interface must reuse this authority rather than infer the milestone from filenames.

The Coder should verify these findings during preflight and raise only material discrepancies.

## 6.1 Prompt Content

For normal connected Coder use, include the authoritative prompt content or provide an equally deterministic immediate way to obtain it in the same command flow.


Do not embed the full contents of:


in the routine output.

Instead provide deterministic repository-relative references.

This is the key context-efficiency improvement over the existing monolithic Coder packet.

## 6.2 Lifecycle Authorization Message

Examples:

```text

WAITING

Implementation authorized: NO, except explicitly requested bounded correction after lifecycle transition

CLOSED
Implementation authorized: NO
```

Use actual accepted lifecycle semantics rather than merely these example strings.

## 6.3 JSON Contract

# 8. `repoctl coder-question`

Implement:

```bash
repoctl coder-question "<summary>" [--repository <path>] [--blocking] [--category clarification|decision|blocker|other]
```

## 8.1 Required invariants

Always force:

```text
event_type = question_submitted
actor_role = coder
po_approved = false
```

The caller may not override these values.

Do not expose a generic event-type option.

## 8.2 Non-blocking Question

Without `--blocking`:

```text
record question_submitted
remain IN_PROGRESS
do not provide waiting_category
do not provide waiting_reason
```

The lifecycle layer should remain authoritative for phase validation.

## 8.3 Blocking Question

With `--blocking`:

```text
record question_submitted
provide waiting_category
provide waiting_reason
transition IN_PROGRESS → WAITING through existing lifecycle validation
```

If no category is specified, use a conservative default such as:

```text
blocker
```

The question summary may serve as the waiting reason unless a cleaner bounded CLI shape is justified.

Do not bypass `record_milestone_event(...)`.

## 8.4 Output

Return:

```text
event recorded
event ID if available
milestone ID
phase before / after
current next action
```

No Git action.

# 31. Completion Criteria

M003.009 is complete when:

- local Coder can deterministically discover the selected milestone without Product Owner copy/paste;
- `repoctl coder-context` exposes prompt + workflow state + authority boundary;
- compact Coder status is available;
- Coder can submit exactly the accepted bounded event classes:
  - question

  - test result
