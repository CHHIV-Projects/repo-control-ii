# R002.08 — Noninteractive GitHub Authentication for Repo Control

## Milestone Purpose

Resolve the remaining live GitHub Push authentication defect in Repo Control without weakening the existing noninteractive Git safety boundary.

R002.07 is accepted and complete. Repo Control is now running as an always-on Linux systemd service with browser-first Windows access through the accepted SSH tunnel workflow.

The remaining defect is specific to live GitHub authentication from the Repo Control service environment.

Observed Repo Control Push failure:

```text
remote_action_execution_failed

Remote failed: error: unable to read askpass response from '/bin/false'
fatal: could not read Username for 'https://github.com': terminal prompts disabled.

Git action outcome is not verified; inspect Git Review before retrying.
```

The same repository can be pushed successfully from the Linux terminal.

This strongly suggests that:

- the repository, branch, upstream, and remote are valid;
- Repo Control's noninteractive Git subprocess is behaving as designed;
- the failure is caused by GitHub credential availability in the Repo Control service environment;
- the fix must not re-enable interactive credential prompting.

The preferred solution to evaluate is GitHub SSH authentication using a server-side SSH key, with the repository remote changed from HTTPS to SSH if appropriate.

---

The goal is to establish a secure, noninteractive GitHub authentication path that allows Repo Control to execute its already-supported Push operation successfully.

## Phase 2 — GitHub SSH Authentication Reconnaissance

Determine whether `henderson-server1` already has a usable SSH identity for GitHub.

Inspect safely:

- `~/.ssh/` filenames and permissions;
- `~/.ssh/config`, if present;
- GitHub host entries in `known_hosts`;
- whether an SSH agent is in use;
- whether the systemd service currently has access to an agent socket;
- whether a suitable private key already exists for user `chuck`.

Do NOT display private-key contents.

If a likely existing key is present, test GitHub authentication using a bounded command such as:

```bash
ssh -T git@github.com
```

or an equivalent non-mutating SSH authentication check.

Expected GitHub behavior may include a successful authentication message while still denying shell access.

If the host key is not yet trusted, do not disable host-key verification. Escalate for Product Owner action if first-time host-key confirmation is required.

## Phase 3 — Decide Authentication Model

Evaluate the simplest secure noninteractive model.

Preferred order:

1. Existing server-side SSH key already authorized with GitHub.
2. New dedicated SSH key for Repo Control / GitHub access, created for user `chuck`.
3. Existing SSH agent model, only if it works reliably under the systemd service.
4. HTTPS credential-helper/token approaches only if SSH is unsuitable.

Strong preference:

```text
GitHub SSH remote:
git@github.com:CHHIV-Projects/repo-control-ii.git
```

Do not introduce browser credential prompts.

Do not store GitHub usernames/tokens in Repo Control configuration.

Do not weaken:

```text
GIT_TERMINAL_PROMPT=0
```

or equivalent noninteractive protections.

Do not set insecure SSH options such as:

```text
StrictHostKeyChecking=no
```

## Phase 4 — Product Owner Escalation if a New Key Is Needed

If no suitable SSH key exists, STOP before creating or registering one automatically.

Provide the Product Owner with a bounded recommendation including:

- proposed key filename;
- proposed algorithm;
- whether a passphrase is appropriate for an unattended systemd workflow;
- exact key-generation command;
- exact public-key display command;
- where in GitHub the public key must be added;
- how to verify the GitHub host key safely;
- how to test authentication.

Preferred modern key type:

```text
ed25519
```

A dedicated key name is preferred, for example:

```text
~/.ssh/id_ed25519_repo_control_github
```

If a dedicated key is used, prefer a narrow SSH config entry rather than relying on ambiguous key discovery.

Example concept only:

```text
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_repo_control_github
    IdentitiesOnly yes
```

Do not overwrite an existing SSH configuration without reconciling it.
