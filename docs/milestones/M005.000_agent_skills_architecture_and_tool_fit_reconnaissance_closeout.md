### 2.1 What Agent Skills actually standardize

Source-backed findings from [S1] and host documentation [S3-S7]:

1. A skill is a directory containing `SKILL.md`: YAML metadata followed by Markdown instructions. Optional references, templates/assets, and executable scripts make it a procedure package, not necessarily an executable tool.
2. Required metadata is `name` and `description`. The specification constrains names to a matching directory name, at most 64 characters, lowercase alphanumeric/hyphen form without leading/trailing/consecutive hyphens; descriptions are nonempty and at most 1,024 characters. Optional fields include license, compatibility, string-valued metadata, and experimental `allowed-tools`.
3. **Discovery** is performed by the host scanning its supported locations. A valid directory alone does not guarantee discovery in every host, harness, workspace, or remote environment.
4. **Selection** can be explicit or model-driven through descriptions. Host-specific invocation syntax and configuration determine which is available. Discovery is not proof of invocation.
5. **Loading** is progressive: the initial catalog contains metadata; activation loads the body; supporting references/resources are read when needed. This reduces irrelevant body loading, not all context cost.
6. **Execution** remains the host/model using its available tools. Markdown does not create a deterministic workflow state machine or permission boundary. Scripts are real executable code with the host's permissions and side effects.
7. The specification's approximate metadata/body token guidance and under-500-line body recommendation are authoring guidance, not measured Repo Control savings.

The standard does **not** establish a universal discovery directory, duplicate-name precedence, invocation syntax, automatic dependency installation, script sandbox, or Repo Control authorization. `allowed-tools` is experimental and implementation-specific. In Copilot CLI, the current documentation explicitly describes it as preapproval that can remove tool confirmation; it is not a portable deny-by-default security policy [S4].

The implementation guide [S2] is useful for authors of agent hosts, but does not justify turning Repo Control into another host. Its general precedence advice must not override product-specific evidence: Cline documents global-over-project precedence, while Codex says duplicate names can both appear.

### 4.4 Recommended boundary

```text
Agent host + reviewed skills -> reusable procedure and selective loading
Repo Control                -> selected scope, PO authority, lifecycle, evidence routing
Graphify                    -> bounded static repository structure/evidence
```

- Initially Repo Control should remain mostly unaware of skills: **no new API, MCP tool, catalog, index, selector, loader, validator service or browser integration is needed**. The existing CLI and authoritative documents suffice.
- A later POC may record skill name/revision/hash and invocation evidence in ordinary closeout/test evidence. This does not require a new event type.
- Host/format validation may check skill structure; it does not certify behavioral safety, authority compliance or factual correctness.
- Coder and Architect can share neutral evidence/analysis checklists, but role-specific invocation must remain explicit. A Coder procedure may submit bounded non-PO events; an Architect procedure must use only its approved proposal/evidence interfaces. Sharing text does not collapse permissions or imply both hosts can discover the same local folder.
- Graph-related procedure may request CURRENT status, target a symbol and verify critical code. It should handle stale/missing/unsupported results explicitly and never refresh without PO authority. No Graphify dependency is needed for a validation/closeout skill.

### 4.6 Risks and controls

| Failure mode | Required control / POC evidence |
|---|---|
| Hidden or implicit instructions bypass PO visibility | Repo-local reviewable text; explicit invocation first; record selected skill/path/revision and which body/references loaded |
| Drift or multiple truths | Link canonical governing sources; do not copy authority into skills; review procedure and governing changes together |
| Stale procedure or command syntax | Pin revision/hash; verify current CLI help and host behavior; revalidate after updates |
| False portability / name collisions | Test each host and scope; inspect personal/plugin catalogs and duplicate names; no universal override assumption |
| Too many skills or false triggers | Two narrow candidates, negative trigger tests, catalog/body byte accounting and omission checks |
| Procedure conflicts with deterministic controls | Tool/lifecycle rejection remains authoritative; stop and escalate rather than work around it |
| Scripts, dynamic injection, hooks or tool preapproval expand authority | Initial instruction-only bodies; no scripts/hooks/installers/preapproved shell; review all later executable dependencies before authorization |
| Optional skill not invoked when a mandatory gate matters | Mandatory bootstrap and gates remain visible outside optional skill selection |

These are architecture risks, not findings of exploitable vulnerabilities in the repository.
