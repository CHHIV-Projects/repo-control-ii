# M004.000 — Graphify Architecture and Tool-Fit Reconnaissance

## Objective
Evaluate Graphify as the candidate repository-intelligence layer for Repo Control II before any production integration. Determine whether Graphify can provide useful, model-agnostic repository intelligence to both the ChatGPT Architect and interchangeable local coding agents without Repo Control reimplementing code-graph functionality.

This is a reconnaissance and architecture-decision milestone. Do not integrate Graphify into Repo Control production code in this milestone.

## Current Direction
The Product Owner wants the next arc to focus on repository intelligence using Graphify, followed later by Agent Skills/procedure work.

The intended architectural direction is:

Graphify owns repository parsing, graph construction, relationship analysis, and graph-native queries.
Repo Control owns repository selection, workflow/authority, bounded evidence routing, browser integration, and safe exposure of useful intelligence to consumers.
The Architect and Coder should be consumers of the same repository-intelligence source rather than maintaining model-specific graph systems.

The key question is not simply whether Graphify works. It is whether it is a good specialized subsystem for Repo Control to integrate rather than duplicate.

## Candidate Under Evaluation
Evaluate the current official open-source Graphify project from Graphify Labs, not unrelated packages/projects with the same name.

Current public project signals to verify against authoritative sources during reconnaissance include:
- official repository: Graphify-Labs/graphify;
- Python package currently documented as graphifyy with CLI command graphify;
- deterministic local code parsing using tree-sitter AST;
- graph.json / graph.html / GRAPH_REPORT.md outputs;
- CLI query/path/explain capabilities;
- incremental/update behavior;
- MCP server support via python -m graphify.serve, including stdio and HTTP transports;
- structured MCP tools reportedly including graph query, node/neighbors/path and PR-impact functions;
- support for Python and other common languages;
- code mapping intended to operate locally without requiring an LLM, while some non-code semantic/multimodal inputs may use an assistant/model/API;
- open-source licensing and any separate commercial/enterprise offering.

Treat these as research leads, not assumed facts. Verify current behavior, interfaces, licensing, version/release state, and constraints from the official repository/documentation.

## Required Questions

### 1. Model Independence
Determine whether Graphify's core code-repository graph can be built and queried independently of a specific AI model or coding assistant.

Distinguish clearly between:
- deterministic/local AST extraction;
- any graph inference/clustering steps;
- optional semantic/document/multimodal processing that may require a model;
- assistant-specific slash-command/skill wrappers;
- core CLI/API/MCP functionality.

Conclude whether switching among Copilot, Codex, Claude, Gemini, or another Coder would require rebuilding/replacing the repository-intelligence layer.

### 2. Architect Accessibility
Determine whether the ChatGPT Architect can consume Graphify intelligence through Repo Control without directly depending on a coding-agent plugin.

Evaluate at least these integration shapes:
- Repo Control reads/query-processes Graphify's graph.json locally and exposes bounded Architect MCP tools;
- Repo Control invokes Graphify CLI query operations;
- Repo Control talks to Graphify's MCP server locally and re-exposes a deliberately bounded subset through the existing Repo Control Architect MCP service;
- direct second MCP connection from ChatGPT to Graphify, only as a comparison, not the preferred design unless evidence strongly favors it.

Recommend the cleanest boundary and explain why.

### 3. Coder Accessibility
Determine how an interchangeable local Coder should consume the same graph intelligence.

Compare:
- local Graphify CLI;
- Graphify MCP configured in the coding environment;
- Repo Control local CLI wrapper;
- generated static graph/report artifacts.

The recommendation must preserve the standing rule that Repo Control is the authority/control plane, not a giant custom agent framework.

### 4. Repository Intelligence Value
Identify the concrete questions Graphify can answer reliably enough to justify integration. Examples to investigate:
- symbol/file/module relationships;
- imports/dependencies;
- callers/callees or call-flow information;
- architectural communities/clusters;
- shortest relationship path between concepts;
- changed-file impact neighborhood;
- tests related to code areas;
- PR/change impact;
- cross-document/code relationships where relevant.

Separate deterministic/extracted facts from inferred relationships. Explain how provenance/confidence is represented and what Repo Control should surface to users/agents.

### 5. Repo Control II Fit
Use Repo Control II itself as the reference repository for architecture analysis. Determine whether Graphify supports its Python/Flask/HTML/JavaScript structure well enough to be useful.

Do not modify production Repo Control source merely to make Graphify fit.

Identify what a later M004.001 local proof of concept should measure on this repository, such as:
- graph build time;
- graph size;
- node/edge counts;
- update time after a small change;
- accuracy of selected dependency/call/path questions;
- usefulness of graph.html/report outputs;
- stability/repeatability;
- local CPU/RAM/disk impact;
- whether no source leaves the machine during code-only indexing.

### 6. Runtime and Deployment Fit
Evaluate suitability for the existing Ubuntu Server 24.04 headless environment and Python 3.12 project workflow.

Determine:
- installation options and isolation strategy;
- whether Graphify should live in its own tool environment rather than Repo Control's application venv;
- required runtime dependencies;
- background service requirements, if any;
- whether an always-on service is actually needed for the initial integration;
- graph storage location and whether generated graph data should be tracked in Git or treated as derived/runtime state;
- update strategy after commits/branch changes;
- implications of Graphify's optional Git hooks versus Repo Control's existing Git-authority boundaries.

Do not install persistent services or Git hooks during this reconnaissance.

### 7. Security and Privacy
Assess:
- what data leaves the machine for code-only operation;
- when model/API calls may occur;
- whether telemetry exists and how it is controlled;
- implications of serving Graphify over HTTP/MCP;
- secrets/exclusion behavior (.gitignore/.graphifyignore or equivalent);
- whether graph artifacts themselves may contain sensitive source-derived information.

Prefer loopback/local-only integration unless a later requirement justifies broader exposure.

### 8. Licensing and Project Health
Verify:
- current open-source license(s);
- distinction between open-source Graphify and any commercial Graphify platform/Enterprise offering;
- repository activity/current development status;
- release/package maturity;
- documentation/test quality;
- obvious maintenance or lock-in concerns.

Do not assume marketing claims or benchmark claims are independently validated. Record them separately from directly verified capabilities.

### 9. Build-vs-Integrate Decision
Explicitly answer:
- What should Graphify own?
- What should Repo Control own?
- What should Repo Control deliberately NOT build if Graphify is adopted?
- Which Graphify capabilities should be exposed to Architect?
- Which should be exposed to Coder?
- Which should remain human/browser-only, if any?

The preferred architecture should keep Graphify replaceable. Repo Control should depend on a narrow repository-intelligence adapter/contract rather than spreading Graphify-specific assumptions throughout the application.

## Research Method
Use authoritative current sources first: official Graphify GitHub repository, project documentation, package metadata, architecture/docs, source code where necessary, and official product site only for commercial-platform distinctions. Community commentary may supplement but must not override primary evidence.

It is acceptable to inspect or clone Graphify into a temporary location outside the Repo Control repository if needed for source-level reconnaissance. Do not vendor it into Repo Control, alter Repo Control dependencies, install Git hooks, or start persistent services.

If a temporary executable/install is needed to verify a claim, keep it isolated from the Repo Control application environment and report exactly what was done. Prefer read-only/source inspection first.

- add Graphify dependencies to Repo Control's application environment;
- install Graphify Git hooks;
- create an always-on Graphify service;
- expose a new network port;

- add Coder MCP integration yet;

- begin Agent Skills integration;
- perform broad benchmarking unrelated to Repo Control's use case.
