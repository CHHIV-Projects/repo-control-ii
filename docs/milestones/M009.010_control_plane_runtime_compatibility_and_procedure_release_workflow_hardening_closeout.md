# Milestone M009.010 — Control-Plane Runtime Compatibility and Procedure Release Workflow Hardening

## 1. Scope Completed

- Added a fail-closed runtime capability handshake before writing the newer context-verification record. The check observes the running service's capabilities rather than relying only on local source or Git state.
- Added registered event capability requirements, producer/reader schema reporting, and bounded failure diagnostics for unavailable, unknown, or incompatible runtimes.
- Added a prompt-authorized shared-procedure release-preparation flow with a manifest-bound marker, allowlisted source paths, read-only candidate validation/preview, and atomic manifest publication.
- Preserved useful Procedure Updates diagnostics when canonical integrity is unavailable, including the configured repository list and per-repository unavailable comparison state.
- Kept Apply disabled during canonical release preparation or canonical integrity failure, while preserving independently safe transaction recovery and its separate confirmation.
- Documented Product Owner-controlled runtime reconciliation and the candidate-release workflow.

## 2. Resulting Behavior

- `coder-verify` probes a bounded loopback runtime endpoint before appending a context-verification event. Unsupported or unproven capabilities block the write before workflow sidecar replacement; existing version-1 records remain readable.
- The runtime reports process-specific capabilities through `/healthz` and Architect status. Local Coder status reports producer schemas and release-preparation state.
- An approved release-preparation marker binds the candidate version and canonical source allowlist to the base manifest digest. Preview validates the complete candidate without writing; publish rechecks authorization and integrity before replacing only the manifest.
- Canonical integrity errors no longer appear as an empty managed-repository list. Apply remains fail-closed. Recovery continues to rely on verified journals, original images, target-state checks, and explicit confirmation; it does not depend on or publish the canonical bundle.
- The Product Owner retains control of service deployment/restart and each managed-repository Apply. No automatic service action or Git operation was added.

## 4. Architecture / Integration Notes

- Runtime capabilities are reported by the running web process and compared with a central registry of event requirements. The probe is limited to loopback HTTP, a short timeout, and a bounded response. It neither restarts the service nor grants lifecycle authority.
- Release preparation is distinct from ordinary verification and generic milestone work. It requires live `IN_PROGRESS` authorization, an explicit prompt marker, an unchanged base manifest, and source changes within the approved allowlist. Candidate validation uses the ordinary strict bundle loader.
- Recovery remains independent of Apply and canonical publication. The Procedure Updates UI and recovery routes keep the established journal/image verification and confirmation safeguards even when canonical comparison is unavailable.
- `coder-procedure-status` reported canonical procedure release 1.3.0 as `CURRENT`, with a valid overlay; release preparation for M009.010 is `NOT_REQUESTED`.
- Repository Intelligence: **NOT USED** — direct source/control-flow inspection and regression tests were sufficient for the bounded runtime and recovery-path questions. Graph freshness was not queried; no graph refresh was considered necessary or attempted. This is a usage classification, not a claim that the graph was unavailable or stale.

## 8. Known Limitations

- Compatibility was validated with local tests and fixtures, not against a live deployed service. A Coder cannot establish that the Product Owner has deployed the accepted source merely from Git or local disk.
- The runtime capability handshake protects only event types registered with explicit capability requirements. Future event/schema additions must register their reader requirements.
- A `RELEASE_PUBLISHED` result verifies the published canonical bundle and candidate release; managed-repository rollout remains a separately confirmed Product Owner operation.
