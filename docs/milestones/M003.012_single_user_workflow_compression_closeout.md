## Exact UI and Lifecycle Behavior

### Approve & Start

From PLANNING, the deliberate browser submission records `prompt_approved` followed by `implementation_started` and returns IN_PROGRESS. READY remains the first event's real intermediate phase and remains visible in the ledger. Existing READY milestones retain the individual Start implementation action.

### Resolve & Resume

From WAITING, the server identifies the condition that caused the current wait:

- a blocking question requires `answer_recorded` referencing that exact question, not another open question;
- an escalation, including one caused by out-of-scope bug classification, uses `escalation_resolved`;
- optional nonempty binding lock-in text creates a distinct `lock_in_approved`;
- `implementation_resumed` is last, returning IN_PROGRESS.

The active question alias is preselected even when unrelated questions are open. The default summary identifies that alias and remains editable. Escalation resolution does not show a question selector. The optional lock-in field is shown only for the combined resolution action. Existing separately recorded resolutions retain the contextual individual Resume action.

### Accept & Close

From REVIEW, the deliberate browser submission records `acceptance_recorded` followed by `milestone_closed`, returning CLOSED. Existing behavior reuses a valid immediately preceding acceptance rather than duplicating it. CLOSED remains terminal.
