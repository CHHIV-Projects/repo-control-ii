# M004.001 — Local Graphify Proof of Concept

## Objective

Run a bounded local proof of concept of the Graphify repository-intelligence engine against Repo Control II and determine whether its measured value is sufficient to justify a later Repo Control integration milestone.

M004.000 concluded **ADOPT FOR POC**, not production adoption. This milestone must convert the remaining uncertainties into measured evidence.

Do not integrate Graphify into Repo Control production code in this milestone.

## Decision Context

M004.000 established the following provisional direction:

- Graphify is a credible model-agnostic structural repository-intelligence engine.
- Graphify should own parsing, graph construction/resolution, clustering, and graph-native queries.
- Repo Control should own repository identity/selection, freshness, authority, bounded evidence routing, and consumer access.
- Architect and Coder should eventually consume the same underlying repository-intelligence source.
- Graphify must remain replaceable behind a narrow Repo Control adapter.
- Python/JavaScript support appears promising; HTML/Jinja and dynamic Flask/browser relationships may be incomplete.
- Static graph evidence is not runtime truth, test coverage, or proof of behavior.
- Privacy, accuracy, resource use, incremental correctness, and actual CLI/MCP response shapes remain unproven.

M004.001 exists to test those points directly.

## Product Owner Intent

Keep this practical.

The goal is not to exhaustively benchmark Graphify or prove every supported language. The goal is to answer:

1. Does it work reliably on Repo Control II?
2. Does it produce repository intelligence that is genuinely useful to Architect and Coder?
3. Can it operate locally and safely without source-code egress?
4. Is update/query performance reasonable for this project's size and workflow?
5. Are the native CLI/MCP interfaces good enough to integrate without Repo Control rebuilding a graph engine?
6. Are the gaps tolerable, especially around Flask/Jinja/browser relationships?

A bounded failure is acceptable evidence. Do not manipulate the test merely to manufacture a PASS.

## Version and Isolation

Use the Graphify version accepted by M004.000 unless current installation reality requires an explicit stop:

- package: `graphifyy`
- accepted reconnaissance version: `0.9.91`
- Python compatibility: expected to include Python 3.12

Install Graphify in an isolated user-owned tool environment outside Repo Control's application virtual environment and outside the repository worktree.

Requirements:

- do not add Graphify to Repo Control application dependencies;
- do not use `graphify install` or any command that registers assistant integrations;
- do not install Git hooks;
- do not modify Git configuration;
- do not configure coding-agent plugins/skills;
- do not create a persistent Graphify service;
- do not expose a network listener;
- set `GRAPHIFY_NO_AUTO_REFRESH=1`;
- use an isolated HOME/config/cache for POC execution where practical;
- keep graph/cache/output artifacts outside the Repo Control repository;
- record the exact executable/environment/version used.

If installing or running the pinned package requires unexpected privileged changes, stop and report rather than broadening scope.

## Code-Only / Local Privacy Boundary

The initial POC must exercise the structural code pipeline only.

Use explicit code-only operation. Do not enable:

- semantic document processing;
- model-backed deduplication;
- remote model APIs;
- Graphify Cloud;
- hosted MCP;
- optional assistant/model backends.

Run with provider credentials removed from the POC environment where practical.

The POC must determine whether Graphify can build and query the Repo Control II code graph without requiring outbound source-code transmission.

Use the safest practical method available to observe or deny outbound network access during the actual code-only build/query runs. Record the method and result. Dependency/package provisioning may use the network before the offline test; distinguish provisioning traffic from Graphify runtime behavior.

Do not claim "zero egress" merely because no API key was configured.

## Dataset

Use Repo Control II as the primary dataset.

Record:

- current branch;
- HEAD;
- working-tree state;
- source scope/exclusions;
- file/language inventory relevant to the graph;
- Graphify version/schema metadata.

Do not modify production Repo Control source to improve Graphify results.

For incremental add/change/rename/delete tests, use a disposable copy or other isolated test fixture rather than editing the authoritative worktree.

Exclude obvious non-source/runtime/dependency/generated/cache/secret paths.

## Required POC Work

### 1. Cold Build

Build a fresh code-only Graphify graph for Repo Control II.

Record at least:

- wall-clock build time;
- peak memory if practical;
- CPU observations if practical;
- generated graph/cache/output disk size;
- node count;
- edge count;
- relation/confidence counts where available;
- community count/algorithm where available;
- skipped/failed files;
- graph schema and producer version;
- output artifact paths.

Confirm that graph artifacts remain outside the application worktree.

### 2. No-Change / Warm Update

Run the supported update path without source changes.

Record:

- elapsed time;
- whether Graphify correctly recognizes unchanged content;
- whether topology/counts remain materially stable;
- any unexpected cache/config/output mutations.

### 3. Incremental Correctness

On a disposable copy or controlled fixture derived from Repo Control II, exercise a small bounded sequence covering:

- add;
- modify;
- rename;
- delete;

for a simple Python function/import or similarly traceable structure.

Compare incremental output with a fresh rebuild sufficiently to detect:

- stale deleted nodes;
- dangling edges;
- missed renamed symbols;
- incorrect merge/deduplication;
- unrelated destructive graph shrinkage.

Exact byte-for-byte output equality is not required if ordering/community metadata is nondeterministic. Compare normalized structural meaning.

### 4. Ground-Truth Query Set

Before judging Graphify's answers, define a compact manual reference set from known Repo Control II code.

Target roughly 20 checks, not hundreds.

Cover useful structural questions such as:

- symbol definition/file ownership;
- imports/dependencies;
- direct callers/callees;
- cross-file call/reference relationships;
- shortest relationship path;
- changed-area/reverse impact neighborhood;
- likely related tests;
- JavaScript callback/function relationships;
- duplicate/ambiguous symbol lookup.

Include at least several known difficult cross-layer questions involving Flask routes, nested functions/decorators, Jinja/template references, `render_template`, `url_for`, or browser fetch/route relationships.

Separate supported structural checks from known HTML/Jinja/dynamic limitations rather than letting unsupported cases distort the useful-code score.

For returned relationships, inspect source file/location, relation type, direction, and confidence/provenance where Graphify provides them.

### 5. Accuracy / Usefulness Assessment

Report enough measured evidence to answer whether the graph is useful.

Suggested decision targets from M004.000:

- >=90% precision on relationships Graphify affirmatively asserts in the supported reference set;
- >=80% recovery of supported expected relationships.

Treat these as decision guides, not incentives to redefine the reference set after seeing results.

Explicitly list meaningful false positives and false negatives.

A missing graph relationship must not be described as proof that no runtime relationship exists.

### 6. CLI Evaluation

Exercise the relevant local CLI surfaces against the generated graph, including where supported:

- query;
- path;
- explain;
- affected / reverse-impact.

Record:

- actual command shapes;
- output format;
- ambiguity/error behavior;
- usefulness to a human/Coder;
- startup/query latency;
- whether output appears stable enough for a narrow adapter.

Do not build a parser/wrapper in Repo Control during this milestone.

### 7. Local MCP Evaluation

Start Graphify's MCP server only as an ephemeral local stdio process for the POC.

Do not enable HTTP transport or a listening socket.

Verify the actual current MCP inventory and exercise a bounded subset relevant to later integration, prioritizing:

- graph stats;
- node lookup;
- neighbors;
- graph query;
- shortest path;
- communities only if useful.

Do not exercise GitHub/PR network tools unless required merely to establish their presence; they are outside the intended initial integration boundary.

Record:

- initialize/tools/list behavior;
- actual request/response shapes;
- error handling;
- ambiguity handling;
- response-size behavior;
- whether results are structured enough to adapt safely;
- whether a warm stdio process materially improves latency over repeated CLI invocation.

### 8. Performance / Resource Assessment

This is a small repository POC, not a performance benchmark suite.

Use the following M004.000 proposed thresholds as review triggers:

- cold build <= 120 seconds;
- warm/no-change update <= 15 seconds;
- one-file incremental update <= 30 seconds;
- peak build RSS <= 2 GiB;
- generated state <= 250 MiB;
- warm stdio query p95 <= 2 seconds over a modest fixed query sample;
- cold CLI query p95 <= 5 seconds.

Exceeding a threshold does not automatically fail the milestone. Report the result and assess whether the cost is reasonable for actual Repo Control usage.

### 9. Offline Viewer / Human Artifact Check

Inspect the generated report and HTML visualization.

Determine:

- whether they are useful for human orientation;
- whether the HTML viewer works offline;
- whether it attempts external resource fetches;
- whether it should remain a human-only artifact rather than an Architect/Coder evidence interface.

Do not host the viewer from Repo Control.

### 10. Freshness and Identity Implications

Determine what Repo Control would need to know to distinguish:

- graph built from current HEAD;
- graph built from a dirty working tree;
- stale graph after source changes;
- graph produced by a different Graphify/schema version;
- graph built with different exclusions/options.

Propose the minimum freshness/manifest facts a later adapter would need.

Do not implement that adapter yet.

## Architect and Coder Usefulness

Explicitly judge the POC from both consumer perspectives.

### Architect

Would bounded graph evidence improve architecture/review questions such as:

- where a subsystem is defined;
- what depends on a module/symbol;
- what code is structurally near a change;
- which tests appear related;
- what path connects two concepts?

Identify the smallest useful eventual Architect operation set.

### Coder

Would the same graph reduce repeated raw repository scanning during implementation?

Identify whether direct CLI is sufficient as a fallback and what a later Repo Control local intelligence command should expose.

Do not add either interface in M004.001.

## Decision Gate

End with one of:

- **GO TO INTEGRATION** — Graphify demonstrated sufficient value and acceptable safety/operational characteristics for a bounded M004.002 integration.
- **HOLD** — promising but one or more specific POC gaps require resolution before integration.
- **REJECT** — measured value, reliability, privacy, or operational fit is insufficient.

A GO decision must not mean Graphify is generally "trusted." It means the measured subset is good enough to place behind Repo Control's bounded evidence contract.
