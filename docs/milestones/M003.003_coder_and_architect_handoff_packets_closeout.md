## 3. Governing Document Contract

The server-side registry supports these document roles:

```text
context
architecture
workflow
coding_agent_rules
parking_lot
```

They are configured under `[repositories.<key>.documents]` in
[ops/repositories.toml](../../ops/repositories.toml). The Repo Control II
entry explicitly configures all five roles. The Vocab App entry has no
document-role configuration. Single-repository CLI mode uses the five
repository-relative Repo Control document defaults as server-side
configuration.

Registry loading validates supported role names and repository-relative path
syntax, rejects traversal/absolute/backslash paths, symlinked components, and
paths resolving outside the configured worktree. Packet generation rechecks
each source path, regular-file status, containment, UTF-8 readability, size,
and obvious PEM/OpenSSH private-key markers. No browser field can name a
document or repository path.

| Packet | Required sources | Optional/configured sources |
|---|---|---|
| Coder | Selected prompt, `coding_agent_rules`, and `workflow` governing documents. | Workflow sidecar if present; current closeout only for a bounded correction packet. Project context, architecture, and parking lot are intentionally omitted. |
| Architect Review | Selected prompt and fresh deterministic local Git state. A closeout is required when phase is `REVIEW`. | Workflow sidecar/history, matching closeout outside `REVIEW`, and configured `context`, `architecture`, and `workflow` documents. Coding-agent rules and parking lot are intentionally omitted. |

Missing required configured roles, missing configured source files, invalid
sidecars, or unsafe sources fail visibly; Repo Control does not substitute a
different document. Configured optional documents are included when the
Architect packet uses them; unconfigured roles are stated as intentional
omissions.

## 4. Coder Packet Contract

Section order:

1. Generation context: repository identity/path, milestone, lifecycle, branch,
   HEAD, UTC generation time, and authorization warning.
2. Full authoritative milestone prompt and source path.
3. Product Owner-approved binding lock-ins, with event IDs and reported actor
   context; non-binding `decision_recorded` events are never promoted to
   instructions.
4. Current open questions, blockers, escalations, unresolved bugs, and
   waiting reason where applicable.
5. In correction mode, the latest bounded correction request and existing
   closeout for context.
6. Configured coding-agent rules and standing workflow rules in full.
7. Repository identity/validation guidance.
8. Explicit Git mutation prohibition and source references.

Phase warnings never imply false authorization. `PLANNING` does not authorize
implementation; `WAITING` explicitly prohibits resumption; `REVIEW` tells the
Coder that no implementation is authorized unless the Product Owner/Architect
requests a bounded correction; `CLOSED` prohibits new implementation. An
`IN_PROGRESS` packet following a recorded correction request is labeled
correction mode and says not to expand scope. A legacy `R...` milestone with
no workflow sidecar uses limited legacy mode and does not claim a lifecycle
phase or decision history.

## 5. Architect Review Packet Contract

Section order:

1. Generation context and phase/authorization warning.
2. Full authoritative prompt/objective.
3. Product Owner-approved binding lock-ins.
4. Up to 30 latest workflow events, each with event ID, timestamp, type, and
   reported actor context; any omitted earlier history points to the full
   sidecar.
5. Open questions, blockers, escalations, unresolved bugs, and waiting details.
6. Matching closeout, when available; its absence blocks packet generation
   during `REVIEW`.
7. Fresh deterministic Git branch, full HEAD, clean/dirty state, staged/
   unstaged/untracked/unmerged counts and up to 40 paths per category. Full
   diffs are not included. Ahead/behind uses local tracking refs and explicitly
   states that no remote refresh occurred; if unavailable, the reason is
   surfaced.
8. Up to 30 reported test-result events with source, outcome, event ID, and
   an explicit statement that Repo Control did not independently verify them.
9. Configured project context, architecture, and workflow governing documents
   where available.
10. Source references and the read-only generation disclaimer.

Legacy milestones without a workflow sidecar may still produce a packet in
limited mode. Lifecycle, approval, and decision history are stated as
unavailable rather than inferred. Malformed or mismatched sidecars fail
visibly.

## 6. Freshness and Revalidation

Each handoff POST applies CSRF and origin checks and runs under the existing
repository action lock. It validates:

- submitted repository key and registry generation against the active
  repository;
- current selected milestone ID and canonical prompt path against the form;
- the saved selection pointer and a fresh milestone inventory;
- the prompt and any used closeout/sidecar paths and contents;
- configured governing-document paths and contents;
- current Git state via the existing read-only Git-state inspection.

Stale repository or milestone requests are rejected with a conflict response.
Git state is freshly observed from local data; packet generation does not
fetch or contact a remote.

## 7. Copy / Export Behavior

The Milestone page has a separate Handoff area with independent
**Generate Coder Packet** and **Generate Architect Review Packet** actions.
The generated Markdown is displayed in a read-only, selectable text area.
The **Copy packet** button uses the browser clipboard API; if unavailable or
denied, it selects the packet text for manual copying with a visible status
message.

No download or repository file is created. Generated content exists only in
the response page. The packet includes its own generation timestamp and
source references; repeated generation from unchanged sources retains stable
section ordering and content apart from generation time and fresh Git facts.

## 8. Security and Read-Only Evidence

Source paths are server-controlled and constrained beneath the selected
repository. Symlinks, invalid UTF-8, oversized sources, and obvious private
key markers block inclusion. Packet size is capped at 512,000 bytes, each
included Markdown source at 128,000 bytes, workflow sidecar reads at 5 MB,
event summaries at 30 items, and Git paths at 40 per status category. Limits
cause a visible error or explicit omission; source content is never silently
truncated.

Packet generation invokes only read-only local Git inspection. The tests
verify unchanged HEAD, refs, index, workflow sidecar, and selection pointer.
The web tests also verify no new sidecar is written, stale requests are
rejected, and one repository's packet does not include another repository's
distinctive prompt content. No packet event is appended.

## 12. Known Limitations

M003.003 does not implement:

- direct Architect tools;
- Coder submission tools;
- role authentication;
- multi-agent writes;
- full lifecycle UX hardening;
- automated tool-to-tool transport.

There is no cross-process atomic snapshot across all source documents and Git;
each required source and Git state is freshly inspected during request
handling. Workflow actor roles remain reported, not authenticated.
Binding lock-ins are included as recorded events; no supersession model exists,
so the packet does not infer that an earlier lock-in has been revoked.
