## 2. Resulting Behavior

1. Status and preview remain read-only. The PO reviews the exact registered repository, release, target actions, hashes, blockers, overlay, and diffs.
2. Review Apply issues a separate short-lived confirmation; Confirm Apply revalidates the plan and consumes the token once.
3. The transaction journals exact originals and intended images, updates fixed generated files, writes the lock last, and reports success only after independently verified CURRENT. A no-op is reported without file rewrites.
4. Interrupted or failed transactions block further Apply. GET/status/preview do not repair or recover. A separate PO-confirmed recovery restores only known original images; conflicts require manual investigation.
5. Apply and Recover do not change local `docs/context` authorities, another repository, repository selection, milestone state, or Git index/HEAD/remotes. Ordinary PO Git Review remains separate.

### Transaction Design and Recovery Invariants

- **Storage choice:** use a private sibling of scanner state, not `<state_root>/<repository_id>` (scanner publication may replace it), and not a managed worktree. The configured path is `<state-root parent>/.<state-root-name>-procedure-transactions/<repository_id>/<operation_id>/`; for the service default this is `/home/chuck/.local/share/.repoctl-procedure-transactions/`. The state-root parent is checked as a service-owned, non-group/world-writable directory. Transaction directories are owned, non-symlink directories mode `0700`; operation files are exclusive/no-follow regular files mode `0600`. The stable sibling allows recovery records to survive scans.
- **Serialization choice:** reuse `state_artifact_lock(state_root)` rather than introduce a second lock domain. It uses the existing thread lock and cross-process `flock`, and excludes scanner publication as well as Apply/Recover actions. It serializes across repositories (less parallelism, simpler ordering) and does not lock arbitrary filesystem writers.
- **Bounded records:** schema version 1; max generated target/image 1 MiB each; max aggregate before/after images 8 MiB; max journal 256 KiB; max retained terminal history 10; max outstanding confirmations 32; confirmation TTL 300 seconds. Journals bind repository key, stable ID, canonical path/root identity, release, manifest and source hashes, full plan digest, six fixed relative targets, parent-directory identities, original presence/hash/mode/group, intended hash/mode/group, state, and timestamps. Image names are deterministic per operation/target index and hashes are rechecked before use.
- **Durability sequence:** write PREPARING journal before image creation; each image is created exclusively without following symlinks, written and fsynced; sync operation and parent directories; then persist PREPARED. Journal updates use a same-directory exclusive temporary file, write/fsync, atomic replace, and parent-directory fsync. Apply persists APPLYING before any target write. For each target it stages a same-directory temporary file, fsyncs, applies approved mode/group, rechecks parent identity and target snapshot, replaces and syncs the directory. Five generated artifacts precede the lock. Independent full-set status and target hashes must match before VERIFIED is persisted.
- **Confirmation boundary:** Review Update GET/status/preview stay read-only. Apply review is POST and issues a random short-lived one-use token; only its hash and bounded binding are stored. Confirm Apply revalidates repository identity, active selection/generation, plan, release/source, overlay and target snapshots under the lock. Beginning an Apply invalidates any other outstanding Apply tokens for that registered repository. Recover has its own operation/journal-bound review and one-use confirmation. No startup, GET, Coder command, Architect dispatch, or preview performs writes or recovery.
- **Rollback/recovery invariant:** caught failure or PO Recover first validates the complete target set; every path must equal its recorded before or after state. Restore generated files before lock, unlink only transaction-created files with matching expected state, remove only empty directories recorded as created, and independently verify the originals. Unknown edits, altered/missing required images, unsafe parents, failed journal updates or incomplete rollback remain blocked and preserve available evidence. A PREPARING record may be recovered only if targets remain at original state; incomplete image cleanup is treated as preparation residue, never as authority to replay.
- **Retention:** durable VERIFIED or RECOVERED is recorded before image cleanup. Cleanup failure is returned truthfully as `cleanup_pending`; terminal receipts are retained within bounded history and pruning only removes known, validated terminal operation files. Recovered operation IDs cannot be replayed against a later operation.
- **Trust/permission boundary:** canonical manifest target set is checked against the fixed five paths and exact lock path. Repository root and parents are opened without following symlinks; targets must be service-owned regular files within size/mode limits. Tokens are CSRF-bound browser confirmations, not proof of human identity. Loopback service policy remains; no root/sudo capability, Coder Git authority, arbitrary path input, or bulk rollout was added.
- **Alternatives and limits:** journals inside scanner state or worktrees were rejected because scans could erase state and worktree changes are user-visible. A second transaction-lock mechanism was rejected in favor of the already shared scanner lock. POSIX replacement is atomic per path, not as a six-file set. The lock cannot constrain a non-cooperating writer: an in-worktree parent-directory rename after final validation but before rename was injected in a fixture; the transaction detected the changed parent and blocked recovery, but the open directory descriptor had already written the intended first file into the moved in-worktree directory. No outside-root target was created in that fixture. A writer able to move the open parent outside the root in that interval remains a fundamental limitation of ordinary file replacement; no claim of protection from that race or arbitrary external writer is made.

- The Repo Control service remains loopback-only. CSRF and the UI's PO role attribution express intent but do not authenticate a human identity; no privilege escalation or Coder write authority was added.

## 8. Known Limitations

- The six-path update is not simultaneously visible: outside readers may observe a mixed set while individual atomic replacements proceed.
- The process lock excludes Repo Control transactions and scanner publication, not arbitrary external writers. A non-cooperating writer can race the final check-to-rename interval. The deterministic parent-rename test demonstrates that the first target can be written through an already-open directory descriptor into the moved directory before identity verification blocks the transaction; recovery now refuses the disappeared transaction-created parent. If another writer moves that directory outside the repository, path escape during this narrow interval cannot be ruled out by the current design.
- Corrupt/missing journals or recovery images, unknown target edits, and unsafe paths require operator investigation; the workflow intentionally does not guess or overwrite.
- A process interruption while creating the initial journal may leave preparation residue; the implementation attempts bounded cleanup and never begins target writes until PREPARED is durable. Residue that cannot be validated or removed requires operator investigation.
- The service is loopback-only, but its browser PO attribution is not human authentication. Hardware power-loss behavior beyond tested fsync semantics is not claimed.
- The M008.004 Coder work did not deploy/restart the service or update any live registered repository. PO acceptance and any real one-repository Apply remain separate decisions.
