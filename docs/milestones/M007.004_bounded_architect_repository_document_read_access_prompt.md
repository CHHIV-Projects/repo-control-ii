# M007.004 — Bounded Architect Repository-Document Read Access

## 1. Objective

Implement bounded, repository-scoped, read-only Architect access to explicitly selected repository documentation beyond the five registered governing-document roles.

This milestone resolves `INTEGRATION-002 — Bounded Architect Repository-Document Read Access`.

The capability must allow the Architect to inspect relevant current/non-governing documentation — including modified and untracked documentation — without granting arbitrary filesystem, shell, Git, lifecycle, write, or network authority.

This is a current-document retrieval capability. Historical discovery/retrieval remains separate and belongs to M007.005.

---

## 2. Product Owner intent

The Architect should be able to review relevant repository documentation directly through Repo Control rather than relying on:
- prior chat memory;
- GitHub availability;
- copied/pasted file contents;
- broad filesystem access;
- Coder-generated summaries as a substitute for primary evidence.

The normal use case is:

```text
Architect knows or is given a repository-relative document path
→ asks Repo Control for that document
→ Repo Control validates the path against a narrow policy
→ returns bounded text + provenance
→ Architect reviews the actual current repository content
```

The feature should support documents such as:
- `docs/guides/*.md`
- design notes
- planning notes
- other relevant Markdown/text documentation
- uncommitted or untracked documentation when present in the selected managed repository

It must remain narrow enough that this is not an arbitrary file browser.

# PART B — CONTRACT

## 4. Add a distinct Architect document-read capability

Do not overload the existing five-role `repo_document(role)` contract.

Add a separate explicit-path read contract for current/non-governing repository documentation.

A likely public tool/API shape is:

```text
repo_file / repo_text_document / repo_read_document
(path=<repository-relative-path>)
```

Choose the clearest name consistent with current code conventions.

The existing governing-role tools remain authoritative for those five roles and should continue unchanged.

## 5. Input contract

The new tool must accept:
- selected/expected managed repository identity through the existing Architect scoping contract;
- a repository-relative document path;
- no absolute paths;
- no caller-supplied repository root;
- no caller-supplied arbitrary filesystem root.

Optional bounded controls such as requested byte limit may be supported only if they preserve server-side maximums and do not weaken safety.

Do not add directory listing/discovery unless strictly required. M007.005 will handle historical discovery separately.

---

# PART C — ALLOWLIST / PATH POLICY

## 6. Repository-relative path validation

The server must:

- resolve only inside the selected managed repository;
- reject absolute paths;
- reject traversal (`..`);
- reject path escape after canonicalization;
- reject symlink escape;
- reject non-regular files;
- reject directories;
- reject device/socket/FIFO/special files;
- reject files outside allowlisted documentation roots/types;
- fail clearly when the path does not exist.

Use deterministic validation.

## 7. Allowlisted roots

Prefer a narrow allowlist appropriate to documentation.

At minimum evaluate:
- `docs/**`
- `.github/**` where documentation/instruction files are relevant
- `.repo-control/**` only for text documentation artifacts if appropriate
- `.agents/**` only where reading Skill text is justified

Do not automatically allow:
- `src/**`
- `tests/**`
- arbitrary repo root files
- secrets/configuration directories
- `.git/**`
- environment files
- SSH material
- credentials
- runtime state roots

If README-style root files are a useful legitimate case, add only a narrow explicit filename allowlist such as `README.md`, not arbitrary root access.

## 8. Extension/content policy

Allow only bounded textual documentation types, for example:
- `.md`
- `.txt`
- possibly `.rst`

Add others only with clear need.

Reject binary files and unsupported extensions.

Do not invoke OCR, parsers, or document conversion in this capability.

# PART D — BOUNDS / ENCODING / OUTPUT

## 9. Size limits

Define a hard server-side maximum response size.

Requirements:
- bounded bytes read;
- deterministic truncation behavior;
- explicit `truncated` flag;
- original file size returned;
- returned byte/character count;
- no unbounded file reads.

Choose a limit consistent with existing Architect evidence size conventions. Prefer reusing an existing central bound if suitable.

## 10. Text decoding

Require UTF-8 or a deliberately narrow supported text encoding policy.

If decoding fails:
- return a clear unsupported/invalid-encoding error;
- do not fall back to binary output.

Normalize nothing that would change file meaning.

## 11. Provenance

Return enough metadata for trustworthy review:

- repository key;
- repository ID;
- canonical repository-relative path;
- source type, e.g. `repository_document`;
- current file size;
- whether tracked / modified / untracked if safely available;
- content;
- truncation state;
- observed/read timestamp only if current API conventions already use one.

Do not claim Git tracking state if it cannot be determined safely/boundedly.

# PART E — GIT / WORKTREE SEMANTICS

## 12. Read current working-tree content

The tool must read the actual current working-tree file, not only committed Git content.

It must therefore support:

- committed unchanged docs;
- modified tracked docs;
- untracked docs.

This is the key M006 use case: Architect review of newly created untracked guides before commit.

Do not:
- stage;
- commit;
- fetch;
- checkout;
- use Git to rewrite files;
- require the file to exist on GitHub.

## 13. Git status metadata

If tracked/modified/untracked state is included, use bounded read-only Git inspection.

Do not make Git metadata a hard dependency for reading a valid allowlisted file unless current architecture strongly supports it.

The file content itself comes from the working tree.
