## 2. Resulting Behavior

- Historical search now scans the complete accepted document content (up to
  the existing 5,000,000-byte source-file bound), rather than searching only
  the 128,000-byte public read excerpt.
- The existing per-request lexical budgets remain 300 files and 16,000,000
  bytes. When either budget stops a query, the response includes
  `has_more`, `next_cursor`, `limited`, and `total_count_complete=false`.
  Repeating the same query, filters, and limit with the cursor continues at
  the next unexamined candidate.
- Both query and inventory results use deterministic repository-relative
  path order. The default page size remains 10 and the maximum remains 20.
  Query `total_count` is cumulative while continuation remains and complete
  on the final page. Inventory counts are complete when discovery succeeds.
- The stateless cursor is signed and bound to the repository identity/root,
  selected milestone, query, filters, limit, and candidate-path/file-metadata
  fingerprint. Malformed, tampered, restart-invalidated, or
  parameter-mismatched cursors
  fail with `invalid_history_cursor` (400); a changed candidate set fails
  with `stale_history_cursor` (409). A service restart invalidates outstanding
  cursors because the signing key is process-local.
- The existing candidate/discovery bounds remain unchanged: 2,000 files,
  2,000 directories, and 50,000 directory entries. If discovery reaches a
  bound, the API now fails explicitly with `historical_discovery_incomplete`
  (503), rather than returning a partial list that could look complete.
- A document that cannot be safely or completely searched returns an
  explicit error. Search results and exact-path reads retain historical
  provenance, current-milestone exclusion, approved-root confinement,
  no-follow path traversal, and M009.018 descriptor-ownership behavior
  documented in the
  [M009.018 closeout](./M009.018_historical_discovery_file_descriptor_leak_and_service_reliability_correction_closeout.md).

## 4. Architecture / Integration Notes

The HTTP and MCP search surfaces share the same contract; the MCP adapter
accepts the returned `next_cursor` as `cursor`. Pagination is stateless and
re-discovers the bounded candidate set on each request. Candidate metadata
fingerprints detect ordinary additions, removals, replacements, and edits
between pages; document reads also verify the file snapshot against discovery.
No new database, index, cache, or persistent search state was introduced.

Results now sort by path instead of the former relevance ranking. This
explicit ordering change makes a stateless traversal stable without rescanning
all documents to rank the full match set. The response exposes
`ordering=repository_relative_path_ascending`; the maximum result page and
response-byte ceilings remain.

Repository Intelligence: **NOT USED** — direct source, caller, adapter, and
test inspection established the small end-to-end search path; structural
queries were not materially useful. The read-only `stats` check reported
`STALE` with reason `supported_source_inputs_changed`. No refresh was
attempted because graph evidence would not materially improve this localized

## 7. Deviations from Prompt

- To make stateless pagination stable and bounded, result order is now
  repository-relative path order rather than global relevance ranking. The
  contract documents and labels this order.
- Existing candidate-discovery caps were not raised. Reaching them now
  produces an explicit 503 error; continuation beyond those caps remains a
  separately reviewable follow-up rather than an incomplete or false
  no-match response.
- Unsafe, oversized, or invalid-encoding candidate content now fails search
  explicitly instead of being silently omitted from a purported complete
  result.

## 8. Known Limitations

- The 2,000-candidate, 2,000-directory, and 50,000-entry discovery ceilings
  remain. Searches that hit them fail explicitly and cannot continue beyond
  the bound.
- Every page re-enumerates the bounded candidate inventory. Large corpora may
  require multiple requests; the measured 1,006-candidate fixture completed
  its late-match search and full inventory traversal in 1.35 seconds locally.
- Cursors become invalid after service restart or candidate-set mutation;
  callers must restart the search. No live service or provider-native
  behavior was tested.
- The path-ordering change replaces global relevance ranking. No persistent
  index or ranking cache was introduced.
