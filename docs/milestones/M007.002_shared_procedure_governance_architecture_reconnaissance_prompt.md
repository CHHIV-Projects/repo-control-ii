# M007.002 — Shared Procedure Governance Architecture Reconnaissance

## 1. Objective

Perform a bounded architecture/repository reconnaissance for centrally governing the **generic Repo Control Coder procedure** across all managed repositories.

The problem to solve is procedure drift. Today, managed repositories may carry repository-local copies of:

- `docs/context/coding_agent_rules.md` bootstrap content;
- `docs/context/project_workflow.md` Repo Control procedure;
- repository-local Agent Skills under `.agents/skills/**`.

M007.001 proved that direct Coder CLI repository resolution can now converge on the central managed-repository registry. However, Product Owner fresh-session testing showed different behavior across repositories:

- a fresh Repo Control II Coder chat given only `Prompt ready.` correctly bootstrapped from Repo Control and stopped at REVIEW / authorization NO;
- a fresh Vocab App Coder chat given only `Prompt ready.` did not demonstrate bootstrap/context retrieval and instead asked the user to send the prompt.

This milestone must determine how much of the Coder bootstrap/workflow/Skill procedure should have **one canonical central source**, how repository-specific overlays should work, how coding hosts discover procedure, and how Repo Control can prevent or detect drift.

This is a reconnaissance/design milestone only. Do not implement synchronization, generation, copying, symlinks, host integration, or repository mutations beyond authorized documentation/closeout work.

---

## 2. Product Owner intent

The Product Owner wants Repo Control behavior to remain consistent across all managed repositories.

The target principle is:

```text
Generic Repo Control procedure
→ centrally governed / one canonical source

Repository-specific constraints
→ small explicit local overlay

Current managed Repo Control state
→ authoritative runtime/lifecycle/configuration

Chat history
→ optional convenience, never required
```

The system should avoid independent hand-maintained copies of the same generic procedure because they can drift and cause different Coder behavior across projects.

This milestone should evaluate bootstrap, workflow, and Skills together because they jointly determine whether a fresh Coder knows:

- how to identify its managed repository;
- how to invoke `coder-context`;
- how to interpret `Prompt ready.`, `Correction ready.`, and `Instruction ready.`;
- when implementation is authorized;
- which procedure Skill to load;
- which Git/lifecycle/authority boundaries apply.

# PART D — DEFINE CENTRAL VS LOCAL AUTHORITY

## 8. Bootstrap authority model

Recommend what should become centrally governed generic bootstrap procedure.

At minimum evaluate whether the following belong in one canonical shared definition:

- meaning of minimal handoffs;
- mandatory `coder-context` retrieval;
- canonical Repo Control CLI invocation;
- repository identity verification;
- lifecycle/authorization checks;
- read-only Git preflight;
- no-Git-mutation rule;
- pre-work feedback rule;
- stop/escalation rules;
- Skill routing/loading;
- evidence/closeout boundary;
- treatment of approved Architect dispatches.

Then define what should remain repository-specific overlay, such as:

- repository identity/path expectations where needed;
- production data/runtime safety;
- project-specific test constraints;
- project-specific service boundaries;
- product-specific model/data rules.

## 9. Workflow authority model

Do the same for `project_workflow.md`.

Determine which sections are truly generic Repo Control operating process and should not be independently rewritten per project, versus which sections legitimately adapt workflow to a project's runtime/data/testing needs.

Evaluate whether a project-local workflow should become:

```text
small overlay
+ explicit reference/version to central generic workflow
```

instead of a near-duplicate full workflow document.

Preserve human readability and offline/repository-local operability where practical.

## 10. Skill authority model

Determine how the three accepted generic Skills should be governed.

The target is one canonical definition per generic Skill.

Evaluate candidate mechanisms such as:

- deterministic materialization/copy from canonical source into each managed repository;
- generated repository-local files with version/hash header;
- symlink/shared-path model;
- host-supported external shared Skill location;
- install-time/onboarding synchronization;
- Repo Control validation-only model with manual sync;
- another simpler mechanism supported by evidence.

Do not pick a mechanism merely because it is technically elegant. Prefer the mechanism that:
- coding hosts reliably discover;
- is easy to understand;
- makes drift detectable;
- works for existing and new repos;
- does not require a custom Skill runtime;
- preserves repository isolation;
- keeps Git history/review understandable;
- does not silently mutate repositories.

# PART G — SECURITY / AUTHORITY / FAILURE MODES

## 15. Preserve authority boundaries

The design must preserve:

- Product Owner ownership of lifecycle approvals and Git mutation;
- Coder no-Git-mutation rule;
- Architect proposal-only mutation path;
- central Repo Control state authority;
- current governing product context/architecture as project-specific;
- Skills as procedure, never authority;
- no chat-history dependency.

A shared procedure mechanism must not let one repository's overlay alter another repository.

## 16. Failure behavior

Define fail-closed behavior for:

- missing canonical shared procedure;
- missing local materialized Skill where host requires it;
- hash/version mismatch;
- malformed overlay;
- unknown local edits to managed generic content;
- central source unavailable;
- repo on an older accepted procedure version;
- host fails to discover expected bootstrap/Skill.

The Coder should not silently proceed under an unknown or drifted procedure when safety/authority is uncertain.
