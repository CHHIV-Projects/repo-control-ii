`docs/guides/repo_control_user_guide.md`

## 4. Audience and style

Primary audience: Product Owner/operator using the Repo Control browser and normal Architect/Coder workflow.

The guide must be:

- concise;
- task-oriented;
- grouped by category;
- readable without understanding implementation internals;
- explicit about what the Product Owner does;
- explicit about when to stop and ask for help;
- based on current accepted behavior.

Avoid long historical explanations.

Use short sections with this pattern where practical:

```text
What it is
What you do
What to expect
Common problem / recovery
```

## 5. Required user-guide coverage

At minimum cover:

### A. Core concepts / definitions

Define briefly:

- Repository
- Milestone
- Active milestone
- Governing documents
- Architect
- Coder
- Product Owner
- Architect Dispatch
- PROMPT
- INSTRUCTION
- RESPONSE
- Repository Intelligence
- Skill
- Workflow sidecar
- Closeout

### B. Lifecycle states

Explain the six states and Product Owner implications:

```text
PLANNING
READY
IN_PROGRESS
WAITING
REVIEW
CLOSED
```

Explain the difference between:

- normal implementation;
- WAITING/question;
- bounded correction;
- material re-scope/new milestone.

### C. Repository selection

Explain:

- selecting the correct repository;
- why active repository matters;
- confirming repository/path before action;
- what to do if browser/Architect/Coder disagree.

### D. Milestone workflow

Give concise operating instructions for:

- reviewing an Architect prompt;
- Approve & Start;
- handing off to Coder;
- handling Coder questions/blockers;
- Resolve & Resume;
- reviewing closeout;
- Request bounded correction;
- Accept & Close.

### E. Architect Dispatches

Explain:

- pending versus approved;
- PROMPT vs INSTRUCTION vs RESPONSE;
- approval does not itself mean the Coder has acted;
- approved instructions should be treated as authoritative only for their approved milestone;
- known current limitation that an approved instruction may not always be surfaced obviously to the Coder and may require explicit Coder-context checking.

Do not normalize the limitation as desired behavior; identify it as a known limitation with a pointer to the parking lot.

### F. Git Review

Explain the normal user tasks:

- identify modified/untracked/staged files;
- inspect diffs;
- Stage selected;
- Commit staged;
- Push;
- branch/upstream/ahead/behind;
- difference between untracked, unstaged, staged;
- when browser action is intentionally unavailable;
- manual Git as a controlled escape hatch for unsupported corner cases.

Do not over-document advanced Git not currently supported.

### G. Repository Intelligence

Explain:

- what it is and is not;
- Graphify/static structural evidence;
- CURRENT/STALE/MISSING/etc.;
- Product Owner-controlled refresh;
- when Architect/Coder should use it;
- why missing edges are not runtime proof;
- usage/value measurement;
- current expectation that the consuming Coder should rate materially used intelligence;
- Product Owner is not expected to judge technical usefulness when they did not consume the evidence.

### H. Governing documents

Explain the five canonical roles:

- project_context.md
- project_architecture.md
- project_workflow.md
- coding_agent_rules.md
- canonical_parking_lot.md

Explain current authority versus historical milestone evidence.

### I. Skills

Explain:

- repository-local shared Skills;
- explicit loading preferred;
- Skills provide procedure, not authority;
- prompt and governing documents still control scope.

### J. Common recovery situations

Include short guidance for:

- wrong repository selected;
- stale Repository Intelligence;
- Coder asks a question;
- workflow is WAITING;
- closeout needs correction;
- unexpected dirty file;
- browser action unavailable;
- Architect/Coder state mismatch.

Keep this section operational, not exhaustive.

# DELIVERABLE 2 — REPOSITORY ONBOARDING AND INTEGRATION GUIDE

Create:

`docs/guides/repository_onboarding_and_integration_guide.md`

## 6. Purpose

Document a repeatable Repo Control onboarding process based on the accepted Repo Control architecture and the real Vocab App onboarding experience.

Support two explicit onboarding paths:

```text
A. New repository
B. Established repository
```

Clearly identify responsibility for each step:

- Product Owner
- Architect
- Coder

## 7. New-repository path

Cover, at minimum:

1. Create repository/directory.
2. Initialize Git/GitHub as appropriate.
3. Establish noninteractive Git authentication compatible with Repo Control.
4. Add repository to the central Repo Control registry.
5. Establish canonical milestone root:
   - `docs/milestones/`
6. Establish canonical governing documents:
   - `docs/context/project_context.md`
   - `docs/context/project_architecture.md`
   - `docs/context/project_workflow.md`
   - `docs/context/coding_agent_rules.md`
   - `docs/context/canonical_parking_lot.md`
7. Install/copy accepted shared Repo Control Skills under `.agents/skills/`.
8. Verify Coder host can discover/load Skills.
9. Verify browser, Architect, and Coder resolve the intended repository.
10. Build/refresh Repository Intelligence when code exists and structural evidence would be useful.
11. Verify Git Review and normal lifecycle operation.
12. Begin product milestones only after integration checks pass.

## 8. Established-repository path

Cover the more complex migration sequence learned from Vocab:

1. Reconnaissance before normalization.
2. Inventory:
   - existing context/architecture/workflow/coding rules;
   - existing milestone/prompt/closeout corpus;
   - Git state;
   - source/runtime structure;
   - existing agent instructions;
   - historical references.
3. Classify governing material:
   - current authoritative;
   - stale but useful;
   - duplicate/mislabeled;
   - historical only.
4. Reconstruct missing canonical architecture/context from current evidence rather than copying stale prose.
5. Preserve legacy evidence under history locations where appropriate.
6. Normalize to canonical five governing documents.
7. Install/verify shared Skills.
8. Normalize canonical milestone root to `docs/milestones/`.
9. Keep legacy historical milestone corpus outside active recursive discovery, e.g. `docs/history/milestones/`.
10. Use a controlled cutover when changing an active milestone root:
    - prepare new-root copies first;
    - Product Owner changes registry/reloads/reselects;
    - verify new-root lifecycle;
    - retire old-root recovery copies only after successful verification.
11. Configure central registry document mappings.
12. Verify browser/Architect/Coder agreement.
13. Verify Repository Intelligence is CURRENT when needed.
14. Ensure the Coder can actually use intelligence and rate materially relied-on uses.
15. Confirm Git auth/remote behavior is compatible with Repo Control noninteractive execution.
16. Close onboarding before beginning normal product work.

Do not make the Vocab repository itself normative where the architecture says otherwise; use it as evidence for general onboarding lessons.

## 9. Maximum Repo Control Advantage checklist

Provide a concise checklist that can be used after onboarding.

At minimum:

- central registry entry correct;
- repository path correct;
- canonical milestone root configured;
- all five governing docs configured/present;
- historical material separated from active authority;
- shared Skills installed;
- Skills host-visible/explicitly loadable;
- Git remote/auth noninteractive;
- browser repository selection correct;
- Architect MCP resolves same repository;
- Coder resolves same repository/path/milestone;
- lifecycle actions work;
- approved dispatches visible/retrievable;
- Repository Intelligence built/CURRENT when applicable;
- Coder uses targeted intelligence where helpful;
- Coder rates materially relied-on intelligence;
- Git Review works for routine changes;
- known limitations recorded rather than silently worked around;
- no coding-agent Git mutation authority.

## 10. Onboarding stop/rollback rules

Explicitly include:

- do not remove old milestone-root recovery copies before new-root selection works;
- do not rewrite historical evidence merely to normalize names;
- do not let old historical artifacts become current governing authority;
- do not let legacy milestone filenames pollute canonical active discovery;
- do not let a Coder mutate central Repo Control configuration unless specifically designed/authorized in a future capability;
- stop when browser/Architect/Coder disagree on repository identity or active milestone.

# DELIVERABLE 3 — CANONICAL PARKING LOT RECONCILIATION

`docs/context/canonical_parking_lot.md`

## 11. Add/reconcile Vocab-discovered Repo Control follow-ups

Use the existing stable-ID/category style. Reuse an existing item if one already covers the issue; do not create duplicates.

At minimum preserve these distinct unresolved concerns:

### A. External managed-repository Coder CLI / central-registry resolution

Observed behavior:

- authoritative browser/MCP resolve registered repository key;
- direct Coder CLI can fall back to repository key `default`;
- explicit repository/milestone-root arguments may be required;
- multiple legacy `repoctl` installations can lead a Coder to the wrong executable.

Desired future outcome:

- stable authoritative executable resolution;
- direct Coder context should consume or deterministically resolve the same managed-repository configuration as browser/MCP;
- no project-local Repo Control installation should be required merely to operate a managed repository.

### B. Dashboard Refresh Status HTTP 500

Preserve the concrete Vocab onboarding observation as a Repo Control II UI defect candidate:

- Dashboard `Refresh Status` returned HTTP 500 / `unexpected_error`;
- Git Review/Milestone views otherwise operated;
- requires Repo Control II diagnosis, not Vocab repair.

### C. Approved Architect instruction visibility to Coder

Observed workflow gap:

- Product Owner approved an Architect INSTRUCTION;
- Product Owner requested bounded correction;
- Coder did not immediately surface/use the approved instruction until explicitly told to look for it.

Desired future outcome:

- authoritative Coder context should clearly surface applicable approved INSTRUCTION/RESPONSE dispatches for the active milestone, especially after correction authorization;
- Coder should not need broad document searching to discover an approved dispatch.

### D. Repository Intelligence consumer-rating workflow

Observed behavior:

- Intelligence use records exist;
- material Coder uses remained UNRATED;
- Product Owner cannot meaningfully evaluate technical usefulness for evidence they did not consume.

Desired future outcome:

- consuming Coder rates materially relied-on intelligence uses before closeout;
- optional short rationale;
- Architect-consumed intelligence should likewise be rateable by the Architect path when practical;
- Product Owner rating remains optional rather than expected;
- value metrics should reflect the consumer's experience.

Do not manufacture ratings for historical uses.

### E. Controlled Governing Document Maintenance

Add a future capability for a lightweight controlled path to maintain:

- project_context.md
- project_architecture.md
- project_workflow.md
- coding_agent_rules.md
- canonical_parking_lot.md

Desired direction:

- Product Owner/Architect can propose/update small factual or planning changes without requiring a full implementation milestone every time;
- retain review, provenance, authority boundaries, validation, and no-Coder-Git rules;
- distinguish lightweight factual maintenance from material architecture/scope/policy changes that still require a milestone;
- avoid stale governing documents accumulating because updates are too cumbersome.

Do not implement the capability in this milestone.
