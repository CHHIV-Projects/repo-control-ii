### INTEGRATION-001 — Coder repository resolution

The local CLI entry point is the installed `repoctl` console script
(`pyproject.toml:15-16`). Both `coder-context` and `coder-status` accept
`--repository`, `--state-root`, and `--milestone-root`
(`src/repoctl/cli.py:83-107`). Without `--repository`, the Coder interface
uses the current working directory as the target Git root
(`src/repoctl/workflow/coder_interface.py:31-39`).

Coder resolution reads `ops/repositories.toml` **inside the selected
repository** and matches its configured path to the selected Git root
(`coder_interface.py:41-58`). Read, parse, or validation errors fall through
to a synthetic `default` configuration with `docs/milestones` and default
document paths (`coder_interface.py:59-70`). In contrast, the browser's
multi-repository registry is server-configured in Repo Control II's
`ops/repositories.toml`; the Coder CLI does not currently resolve the
browser's selected registry entry by key from that central file.

Selection and workflow state are loaded using a repository ID and the
external state root (`coder_interface.py:132-173`; `workflow/milestones.py:
219-302`). Authorization is derived from lifecycle phase
(`coder_interface.py:75-130`). Coder context returns the selected prompt,
approved active-milestone `INSTRUCTION`/`RESPONSE` dispatches, and references
to standing documents (`coder_interface.py:245-290`). It does not load the
standing document contents through the CLI. The effective `repoctl`
executable is determined by the caller's installation/module invocation and,
for a console script, shell `PATH`; this Coder path does not locate a
canonical executable itself.

**Read-only Vocab characterization:** the central server registry maps key
`vocab-app` to `/home/chuck/projects/vocab-app` and `docs/milestones`
(`ops/repositories.toml:14-24`). The Vocab worktree exists on `main`, and no
Vocab-local `ops/repositories.toml` is present. Running the explicitly
selected Repo Control virtual-environment module from the Vocab root with
`coder-status --format json` reported key `default`, path
`/home/chuck/projects/vocab-app`, repository ID
`vocab-app--0d81efec80ef`, and selected milestone `M001.002` in `CLOSED`.
Thus the observed **key/configuration mismatch is reproduced**, but this
particular Vocab setup still resolves the same milestone because its fallback
root/defaults and path-derived repository ID happen to fit the existing
configuration. This does not establish convergence for a repository with a
different configured milestone root, document roles, or registry metadata.
The status probe was read-only; no Vocab file or Git state changed.

The current shell did not expose a `repoctl` console command on `PATH`; the
probe explicitly used Repo Control II's `.venv/bin/python -m repoctl.cli`.
Consequently, a wrong legacy executable was **not** reproduced here. Source
and environment evidence establish a PATH/version selection risk, not that
multiple installations are currently active.

**Recommended contract:** resolve one canonical installed Repo Control CLI
and the same server-controlled registry/configuration used by the browser and
Architect. Identify a managed repository by exact canonical path-to-key
mapping (or an explicit validated key/path), then return the same key, path,
milestone root, current selection/lifecycle, applicable approved dispatches,
and standing references. If the working directory maps to zero or multiple
managed repositories, or the registry cannot be read/validated, fail clearly;
do not silently mint a `default` managed identity. An explicit selection
should disambiguate, not bypass registry validation. Keep compatibility with
the co-located VS Code Remote SSH model and do not require a Repo Control
installation inside every managed project.

### INTEGRATION-002 — Current non-governing document access

The Architect MCP exposes fixed evidence tools for repository status,
milestone/prompt/workflow/closeout, Git/evidence/review, governing documents,
dispatches, and Repository Intelligence, plus typed proposal submissions
(`src/repoctl/mcp/architect_adapter.py:40-180`). Read schemas reject extra
arguments. `repo_documents` inventories the five configured governing roles;
`repo_document` accepts only `context`, `architecture`, `workflow`,
`coding_agent_rules`, or `parking_lot`
(`architect_adapter.py:26-29,153-170`).

The adapter routes a role to
`GET /api/architect/v1/documents/<role>`; the API contract resolves only the
configured role (`architect_adapter.py:393-407`;
`web/app.py:677-683`; `web/architect_contract.py:514-529`). The server selects
the active repository and checks its generation; governing paths are
repository-relative and reject traversal and symlink components
(`web/repository_registry.py:69-99,157-181`;
`web/architect_contract.py:34-57`). Reads are bounded and return complete
content or an explicit oversized error, not silent truncation
(`architect_contract.py:261-288`).

Therefore an existing non-governing guide has no selectable role/path, even
when uncommitted. An uncommitted file at one of the five configured governing
paths can be read from the working tree; this does not extend to other
uncommitted documentation.

**Recommended design:** retain `repo_document(role)` as the explicit
current-authority interface. Add a separate narrow document-read interface
for an explicitly selected repository-relative path, restricted to approved
documentation/text roots and extensions. Resolve only within the
server-selected repository; reject absolute/traversal paths, symlinks,
non-regular files, binary/non-text content, invalid encodings, and oversized
content with explicit errors. Read the current working-tree bytes so tracked,
modified, and untracked deliverables can be reviewed; include source path,
repository key/generation, byte count, and an accurate working-tree/tracking
provenance where available. Return complete content below a fixed cap or
refuse it explicitly; never imply a truncated result is complete. Keep path
selection separate from directory listing/discovery unless a later approved
need warrants a similarly bounded inventory.

### Proposed INTEGRATION-003 — Historical project context

Active milestone discovery is rooted in the configured milestone root
(`docs/milestones` for Repo Control II and Vocab). The discovery service
recursively scans only that validated root, recognizes prompt/closeout naming
patterns, skips workflow sidecars as candidates, and does not select
closeouts without prompts (`workflow/milestones.py:94-181`). The operational
selection pointer is revalidated against that discovery inventory
(`milestones.py:219-302`). A separate `docs/history/**` root is therefore
outside current active selection and is not searched as a fallback.

Architect tools retrieve the **active** prompt, workflow, closeout, and five
governing documents; they do not search or read historical prompts,
sidecars, closeouts, or `docs/history/**` by path or milestone ID. Git Review
history is not a substitute: it inspects repository commits and the history
of a selected tracked file, not a historical artifact corpus
(`workflow/git_history.py:272-340`). Vocab has historical material under
`docs/history/context/**` and `docs/history/milestones/**`, but the active
registry exposes only its current governing documents and configured active
milestone root.

For a mature project, current context may not retain why a design was chosen,
which alternatives or experiments were rejected, which prior PO decisions
shaped the baseline, or what incomplete historical work remains useful.
History should help the Architect plan; **current governing documents and
current Repo Control lifecycle alone define present authority**. The Vocab
layout is evidence that archived material can be physically separated from
active milestone discovery, not evidence that the Architect can currently
retrieve it.

**Recommended design:** add a separate historical discovery/retrieval
interface with progressive disclosure: first return a bounded, deterministically
ordered inventory/search result (milestone ID, artifact type, relative path,
title/summary if available, and historical provenance), then read one
explicitly selected result. Support filters for milestone ID and artifact
type, and bounded term search/snippets; do not return the full corpus. Scope
search to configured historical roots and approved planning-document
locations, including a documented `docs/history/**` convention. Identify
every result as historical evidence and preserve its exact source path.
Do not add historical prompts to active milestone discovery or alter current
selection rules. Return explicit limits/errors and label whether results came
from the working tree, including uncommitted historical files.

`INTEGRATION-002` and `INTEGRATION-003` should remain **distinct user-facing
capabilities**: one reads a specifically selected current/non-governing
document; the other discovers historical planning evidence and then reads a
selected result. They can share a lower-level repository-scoped safe text
reader for root enforcement, path/symlink checks, text validation, byte
limits, and provenance. This reuse must not become a general file API with
arbitrary paths or implicitly broaden either capability.

## 4. Architecture / Integration Notes

Recommended shared model:

```text
Server-controlled managed-repository registry
  ├─ canonical repository key/path/config
  ├─ Coder bootstrap resolves same config and fails on ambiguity
  └─ Architect API selects active key + generation
       ├─ Current authority retrieval
       │    ├─ active milestone, lifecycle, approved dispatches
       │    └─ five fixed governing-document roles
       ├─ Current non-governing document review (INTEGRATION-002)
       └─ Historical discovery, then selected-artifact read (INTEGRATION-003)

Product Owner authority
  ├─ approves lifecycle/scope and binding decisions
  ├─ approves Architect proposals
  └─ owns Git mutations

Coder bootstrap
  └─ uses canonical CLI/config to reach the same managed identity and
     current authorization; no chat-history dependency
```

The common lower layer should be a small repository-relative text-source
resolver/reader, not an arbitrary file endpoint. Higher layers retain separate
contracts and labels for current governing authority, current supporting
documents, and historical planning evidence. Reads must not trigger Git
mutations, lifecycle changes, network access, graph refreshes, or hidden
refresh/build operations.

New read-capability threat surfaces include cross-repository disclosure after
active selection changes; path traversal and symlink escape; oversized or
binary input; prompt-injection content in arbitrary repository text; accidental
exposure of secrets or non-project files; and confusion between uncommitted,
current, and historical material. Mitigations are server-selected repository
identity/generation preconditions, narrow configured roots/extensions,
canonical path checks, symlink rejection, regular-file and encoding checks,
strict byte/output caps, source/provenance labels, explicit errors, and no
write/shell/network/lifecycle/Git authority. Historical results must never be
presented as current policy or active selection.
