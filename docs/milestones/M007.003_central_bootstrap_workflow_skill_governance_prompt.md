# M007.003 — Central Bootstrap / Workflow / Skill Governance

## 1. Objective

Implement the centrally governed shared Coder procedure architecture accepted from M007.002.

The goal is to eliminate independent hand-maintained copies of generic Repo Control procedure across managed repositories while preserving project-specific overlays and Product Owner control.

This milestone must establish:

- one canonical versioned generic Repo Control procedure bundle;
- deterministic repository-local materialization of host-discoverable bootstrap and the three generic Agent Skills;
- a clear project-specific overlay boundary;
- deterministic version/hash drift detection;
- a safe Product Owner-reviewed reconciliation workflow;
- initial adoption in Repo Control II;
- a bounded, reviewable migration path for Vocab App without changing Vocab product behavior.

Do not broaden into Architect document retrieval, historical context retrieval, Coder MCP, lifecycle redesign, or unrelated documentation cleanup.

---

## 2. Accepted architecture from M007.002

Treat the following as the accepted design baseline unless current deterministic evidence reveals a blocker:

1. Generic Repo Control procedure must have one canonical source.
2. Repository-specific product/runtime/test constraints remain local overlays.
3. `project_context.md`, `project_architecture.md`, and `canonical_parking_lot.md` remain repository-specific.
4. The large Repo Control II `project_workflow.md` remains Repo Control II's comprehensive operational/implementation document; managed repositories should not copy it wholesale.
5. Managed repositories should instead carry:
   - a short host-recognized bootstrap entrypoint generated/materialized from the canonical bundle;
   - repository-local physical copies of the three generic Skills generated/materialized from the canonical bundle;
   - a small project-specific bootstrap/workflow overlay;
   - a deterministic manifest/lock recording release/version and SHA-256 expectations.
6. The preferred host-recognized bootstrap target for current VS Code Copilot use is `.github/copilot-instructions.md`, subject to implementation-time verification.
7. Symlinks and arbitrary external shared directories are not accepted as required mechanisms.
8. Reconciliation must produce ordinary reviewable diffs and must not silently mutate managed repositories.
9. `WORKFLOW-005 — Authoritative Coder Context Convergence` remains open until later fresh/resumed host acceptance.
10. Vocab contains confirmed stale transition guidance around `--milestone-root milestones`; this milestone may reconcile shared-procedure/bootstrap material only within an explicitly bounded migration step. Do not change Vocab product logic or unrelated product context.

# PART B — DEFINE THE CANONICAL SHARED PROCEDURE BUNDLE

## 4. Canonical bundle location and structure

Implement one clear canonical source under Repo Control II.

Choose the smallest maintainable structure consistent with current architecture. A likely shape is:

```text
<repo-control-ii>/shared/procedure/
  manifest.toml|json|yaml
  bootstrap.md
  workflow_core.md
  skills/
    repo-control-implementation/SKILL.md
    repo-control-blocker-bug-escalation/SKILL.md
    repo-control-validation-closeout/SKILL.md
```

The exact path/format may differ if current repository conventions support something cleaner.

Requirements:

- versioned release identifier;
- deterministic file list;
- SHA-256 for each generated generic artifact or source artifact;
- manifest schema version;
- no project-specific paths embedded in the generic core;
- no product-specific runtime/data/testing rules embedded in the generic core;
- human-readable source files;
- no custom Skill runtime.

## 5. Generic bootstrap core

Extract/define a generic bootstrap core that includes at minimum:

- minimal handoff semantics:
  - `Prompt ready.`
  - `Correction ready.`
  - `Instruction ready.`
- canonical Repo Control CLI invocation;
- mandatory `coder-context` retrieval;
- managed repository identity verification;
- lifecycle and implementation authorization checks;
- approved dispatch interpretation;
- read-only Git preflight;
- absolute Coder no-Git-mutation rule;
- pre-work feedback rule;
- blocker/question/escalation behavior;
- Skill routing/loading;
- deterministic evidence principles;
- closeout/REVIEW boundary;
- no chat-history dependency.

Do not hard-code Repo Control II as the required workspace.

The generic core must refer to the managed repository resolved by Repo Control.

## 6. Generic workflow core

Extract only the reusable Repo Control operating process needed by managed repositories.

Do not duplicate Repo Control II implementation history, service topology, current feature inventory, or product architecture.

The generic workflow core should cover:

- roles and authority;

- Architect dispatch consumption;

- Git authority separation;

- generic Coder procedure.

Keep it substantially smaller than the current Repo Control II `project_workflow.md`.

# PART C — PROJECT-SPECIFIC OVERLAY MODEL

## 7. Overlay contract

Define and implement a simple repository-local overlay contract.

The overlay must be allowed to contain repository-specific items such as:

- project/runtime/data safety rules;
- product-specific model/data authority;
- service/container constraints;
- repository-specific test commands;
- deployment/production boundaries;
- project-specific validation prerequisites.

The overlay must **not** override:

- Product Owner authority;
- lifecycle semantics;
- central Repo Control state;
- no-Git-mutation rule;
- generic dispatch interpretation;
- generic stop/escalation rules;
- generic Skill authority limits.

Prefer a human-readable Markdown overlay plus minimal metadata only if needed.

Avoid a complicated inheritance language or policy DSL.

## 8. Current governing document relationship

For Repo Control II itself:
- retain comprehensive project workflow/architecture documentation where appropriate;

# PART D — MATERIALIZATION / RENDERING

## 9. Deterministic renderer/materializer

Implement a deterministic component that can render the canonical bundle for a target managed repository.

It must be able to produce, at minimum:

1. host-recognized bootstrap output, targeting:
   - `.github/copilot-instructions.md`
2. the three repository-local Skill files under:
   - `.agents/skills/.../SKILL.md`
3. a shared-procedure lock/manifest in the managed repository;
4. any minimal generated reference content required for the project overlay model.

Requirements:

- deterministic output;
- stable ordering;
- no timestamps/random IDs in generated content unless required;
- exact provenance/source version recorded;
- SHA-256 expectations;
- target repository must be centrally managed;
- repository isolation enforced;
- no silent cross-repository writes;
- generated generic files clearly identified as managed/generated where practical.

## 10. Preview before mutation

The normal reconciliation model must support a **preview/proposed diff** before any managed repository file write.

At minimum provide a read-only/preview operation that reports:

- current shared-procedure release;
- target release;
- files to create/update/remove;
- exact drift/mismatch state;
- whether overlay remains untouched;
- blocked/conflicting files;
- expected hashes before/after;
- whether host bootstrap is missing.

The Product Owner must be able to inspect the proposed changes before materialization.

Do not create an autonomous background synchronization process.

# PART E — DRIFT DETECTION

## 11. Deterministic drift status

Implement deterministic drift detection for each managed repository.

Suggested status vocabulary may include:

```text
CURRENT
MISSING
STALE_VERSION
HASH_MISMATCH
UNMANAGED_EDIT
OVERLAY_INVALID
INCOMPATIBLE
UNKNOWN
```

Use the smallest useful set.

Detection must be deterministic and based on version/hash/manifest/file presence, not semantic AI comparison.

At minimum detect:

- missing host bootstrap;
- missing Skill;
- stale Skill;
- edited generated Skill;
- stale bootstrap;
- edited generated bootstrap;
- missing/corrupt lock;
- version mismatch;
- malformed overlay;
- target path collision/nonregular file if relevant.

Output should identify the exact affected path and expected/current state without dumping unrelated file content.

## 12. CLI/browser exposure

Implement the smallest practical operator interface.

At minimum provide CLI support for:
- inspect shared-procedure status for the current/explicit managed repository;
- preview reconciliation/materialization.

If existing browser architecture makes a small read-only status view low-risk and natural, it may be included, but do not broaden into a large UI feature.

Any actual repository write action must remain explicitly PO-approved and bounded.

# PART F — WRITE / RECONCILIATION AUTHORITY

## 13. Reconciliation write boundary

Implement the safest bounded write model consistent with Repo Control's authority rules.

Preferred shape:

```text
inspect
→ preview
→ explicit Product Owner action
→ materialize exact prepared changes
→ verify hashes/status
→ ordinary Git review
→ Product Owner Git mutation separately
```

Requirements:

- no Coder authority to trigger repository writes outside the active implementation files it is already authorized to edit during this milestone;
- future operational reconciliation must be Product Owner controlled;
- do not stage/commit/push;
- prepared action must be repository- and state-bound if using existing prepared-action patterns;
- refuse stale preview/action state;
- refuse unmanaged target repos;
- refuse cross-repo path escape;
- preserve overlay files;
- do not overwrite conflicting project-specific files silently;
- rollback strategy documented.

If implementing an operational browser write action would materially broaden M007.003, stop and escalate rather than expanding scope. A CLI/prepared reconciliation design plus tested internal service boundary is acceptable if browser mutation belongs later.
