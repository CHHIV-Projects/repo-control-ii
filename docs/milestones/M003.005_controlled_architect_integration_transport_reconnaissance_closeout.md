## 1. Executive Result

PASS. Recommend a ChatGPT custom MCP app connected through OpenAI Secure MCP
Tunnel to a narrow, read-only MCP adapter running on `henderson-server1`. The
adapter should make only fixed GET requests to Repo Control's existing
`/api/architect/v1` endpoints over loopback. Repo Control remains bound to
`127.0.0.1:8765`; neither it nor the adapter needs a public or LAN listener.

The topology is supported by current OpenAI documentation: ChatGPT custom MCP
apps may use a Secure MCP Tunnel, and the tunnel client forwards work from an
outbound-only connection to an MCP server reachable on the private host. The
recommended adapter keeps the MCP tool contract portable and limits the
Architect to individually named reads rather than arbitrary HTTP requests.

Two matters are not established by repository or public documentation and must
be checked before implementation is considered accepted:

1. The Product Owner's ChatGPT workspace must permit adding and using a custom
   MCP app, and the relevant Platform organization must grant Tunnels Read +
   Use to the runtime-key principal and app creator.
2. OpenAI documents Harpoon as a built-in MCP server for allowlisted HTTP
   callouts from supported agent or API flows. The reviewed material does not
   establish that a ChatGPT custom app can select and invoke Harpoon's channel
   directly. Test that possibility as a low-cost implementation spike before
   writing an adapter; do not assume it works.

If the workspace cannot use Secure MCP Tunnel, retain the existing manual
Architect Review Packet workflow until a supported alternative is agreed.
Do not compensate by making Repo Control public.

## 3. Existing Repo Control Boundary

The API is served by the existing Flask process under `/api/architect/v1`.
Its GET routes are `/status`, `/milestone`, `/prompt`, `/workflow`, `/closeout`,
`/git`, `/evidence`, `/documents`, `/documents/{role}`, and `/review`.
Repository and milestone identity come from server configuration and the
repository-scoped selection pointer, not caller-supplied filesystem paths.
Responses are bounded, identify their source scope, and support optional
stale-selection preconditions. The API does not fetch Git remotes, run tests,
or mutate Git/workflow state.

The API does not authenticate an individual caller. Its current trust boundary
is loopback and the accepted SSH local-tunnel path. The existing service unit
runs as `chuck` and binds only to `127.0.0.1:8765`. Repo Control's browser
application also contains mutation routes; a transport must not expose those.
No repository path, shell, arbitrary URL, generic proxy, browser route, or
mutation operation is in scope.

The existing Windows launcher is useful for a person opening the browser UI.
It does not make a Windows-local listener reachable to ChatGPT's cloud-hosted
web product and is not needed in the recommended server-side path.

## 4. Current ChatGPT Capability Findings

Confirmed in current OpenAI documentation accessed 2026-10-12:

- ChatGPT on the web supports custom MCP servers/apps. The documented setup
  offers a Server URL or Tunnel connection, and supports SSE and streaming
  HTTP MCP transports.
- Secure MCP Tunnel is documented for private/local MCP servers. A customer-
  run `tunnel-client` makes outbound HTTPS requests to OpenAI and forwards
  MCP work to a private MCP server reachable inside the host's network. No
  inbound public listener is required.
- ChatGPT app creation and use remain subject to workspace permissions and
  security restrictions. The tunnel must be associated with the target
  ChatGPT workspace. Running the tunnel client and selecting the tunnel
  require Platform Tunnels Read + Use; creating or editing a tunnel requires
  Read + Manage.
- OpenAI documents a custom MCP app authentication choice of no authentication
  as well as OAuth. For the proposed private tunnel, the relevant access
  boundary is the tunnel's Platform/workspace association, not a public
  unauthenticated endpoint.
- The tunnel client needs outbound HTTPS to `api.openai.com:443` by default
  and private-network reachability to its configured MCP server.

Not confirmed for this Product Owner:

- Whether the specific ChatGPT account/workspace allows custom MCP apps and
  tunnel associations, and whether an administrator must enable them.
- Whether the Product Owner has the Platform organization permissions and
  runtime-key ability described above.
- Whether ChatGPT app-level audit/compliance logging is available under the
  Product Owner's plan and workspace configuration.
- Whether ChatGPT custom apps can directly consume Harpoon's separate
  allowlisted HTTP-callout channel. OpenAI documents Harpoon for supported
  agent or API flows, but the reviewed ChatGPT custom-MCP setup documentation
  does not explain that channel mapping.

These points require Product Owner/workspace-admin confirmation and, for
Harpoon, an end-to-end test. No plan entitlement is inferred here.

## 5. Candidate Architectures

### A. Public MCP endpoint or public proxy

**Path:** ChatGPT web -> public HTTPS MCP endpoint/proxy -> private adapter ->
loopback Repo Control API.

This could preserve the Repo Control listener itself as loopback-only, but
would create an Internet-reachable service, TLS/identity management, firewall
and patching obligations, and a new attack surface. A proxy must still enforce
fixed read-only operations and repository scope. A generic unauthenticated
endpoint is unacceptable. Reject in favor of the supported outbound tunnel.

### B. Local bridge on `henderson-server1` without a relay

**Path:** local MCP client -> local bridge -> `127.0.0.1:8765`.

This is suitable for a client running on the server, but ChatGPT web cannot
directly connect to the server's loopback address. It does not solve the
transport problem by itself. A bridge would need a supported private
connection mechanism, so do not build one as a standalone service.

### C. Generic authenticated relay/reverse tunnel

**Path:** ChatGPT -> third-party relay or reverse-access service -> server-side
agent/bridge -> `127.0.0.1:8765`.

This can avoid inbound Repo Control exposure, but introduces another vendor,
relay identity, credential lifecycle, and operational failure modes. It is
inferior to the specifically documented OpenAI Secure MCP Tunnel for a
ChatGPT-first use case unless future provider-neutral access becomes a
concrete requirement. Do not add a generic relay preemptively.

### D. Windows-side or desktop helper

**Path:** ChatGPT web/cloud -> (no supported path to Windows loopback); the
existing SSH tunnel only serves Windows-local clients -> `henderson-server1`.

The existing SSH tunnel can continue to support human browser use, but a
Windows helper would need to remain running and bridge a workstation-local
port to an Architect integration. The reviewed ChatGPT custom MCP docs direct
users to ChatGPT on the web and a server URL or Secure MCP Tunnel; they do not
establish the proposed browser-to-Windows-local bridge. This adds desktop
dependency, workstation credential/port exposure, startup and reconnect
failure modes, and does not improve the server's always-on model. Reject.

### E. ChatGPT custom MCP app through Secure MCP Tunnel

**Path:** ChatGPT web custom app -> OpenAI-hosted tunnel endpoint -> outbound
poll/response connection from `tunnel-client` on `henderson-server1` -> local
stdio MCP adapter -> `127.0.0.1:8765/api/architect/v1/*`.

No inbound Repo Control or MCP port is needed. A small adapter provides
explicitly named, read-only tools, each mapped to a fixed API endpoint. This
uses OpenAI-specific transport at the outer boundary but leaves the MCP
adapter and Repo Control API portable. Recommend, conditional on workspace
permissions and the M003.006 compatibility/acceptance checks.

OpenAI's built-in Harpoon is a possible lower-maintenance alternative: its
target templates fix the origin, method, path, query, headers, and validated
parameters, and support GET. However, the reviewed material does not prove
that the ChatGPT custom app can invoke Harpoon targets through the tunnel.
Treat that as a testable alternative, not the selected production topology.

### F. Continue manual packet transport

**Path:** Product Owner uses Repo Control's Architect Review Packet -> copies
the bounded packet into ChatGPT.

This has the smallest integration and credential footprint and remains a
safe fallback. It has more copying/context friction and can become stale
between packet generation and discussion. Retain it if the custom MCP/tunnel
path is unavailable or fails its read-only boundary tests; it is not preferred
once the supported tunnel path is accepted.

## 7. Recommended Topology

```text
Product Owner in ChatGPT web
        |
        | custom MCP app; workspace/tunnel access
        v
OpenAI-hosted Secure MCP Tunnel endpoint
        ^
        | outbound HTTPS poll/response; runtime API key
        |
tunnel-client on henderson-server1 (systemd)
        |
        | local stdio MCP child (preferred; no MCP listener)
        v
thin MCP adapter: named, read-only tools only
        |
        | fixed GETs to 127.0.0.1:8765/api/architect/v1/*
        v
Repo Control II (existing systemd service; unchanged)
```

This separates transport from authority:

- Repo Control remains the control plane and selects repository/milestone
  state.
- The adapter exposes only targeted reads from the existing API; it does not
  implement a parallel evidence source.
- ChatGPT requests evidence and reasons over it. Product Owner remains
  responsible for decisions and every consequential or Git-mutating action.
- The Product Owner opens ChatGPT, selects the installed custom app when
  needed, and asks a project question. The Architect can request fresh,
  targeted status/review/prompt/workflow/Git/evidence/document/closeout
  evidence rather than receiving an entire packet every time.

## 8. Authentication, Authorization, and Repository Isolation

**Caller and transport identity:** The long-running `tunnel-client` uses a
Platform runtime API key with Tunnels Read + Use, scoped as narrowly as the
Platform permits. The tunnel is associated with the intended ChatGPT workspace.
ChatGPT's app/workspace permissions control who can add and use the app.
Repo Control itself continues not to assert a person or role identity; the
local request is trusted as coming through the configured tunnel process.

**Credential placement:** Keep the runtime key outside the repository and
ChatGPT conversation, readable only by the tunnel service identity. Prefer a
systemd credential or a dedicated permission-restricted secret file. Do not
put it in unit arguments, checked-in YAML, logs, or the application config.
Use a restricted runtime key, not an administrative key. Tunnel ID is
configuration, not an authentication secret. Rotation requires updating the
local secret and restarting the tunnel client; revocation is performed through
the Platform key/tunnel controls. Exact Platform UI and key availability must
be verified by the Product Owner.

**Read-only authorization:** The adapter should expose only named tools for
the required API reads. Each tool must hard-code one API route and HTTP GET;
none accepts a URL, path, repository path, arbitrary method, shell command, or
Repo Control browser route. `documents/{role}` must constrain role to the
supported allowlist. Use the API's expected repository/generation/milestone
preconditions on follow-up reads where known. Mark tools read-only in MCP
metadata, but rely on implementation-level fixed routing and Repo Control's
GET routes rather than annotations alone. Do not expose browser Git or
workflow mutation routes.

Repository and milestone identity remain server-resolved. Do not add caller-
selected repository paths or an alternate registry. Responses must retain
Repo Control's source scope and stale-state/error behavior.

## 9. Audit and Data Handling

OpenAI documentation states that individual Secure MCP Tunnel transport
requests are not emitted as ChatGPT Compliance Platform app events. Tunnel
metadata create/update/delete events are available in Platform Audit Logs.
Normal app-level compliance logging applies to custom-app activity, but
availability for the Product Owner's workspace/plan is unverified.

For implementation, use the adapter's service journal (or the narrow service
log it already writes) for one metadata-only structured record per tool call:

```text
UTC timestamp
transport identity (configured tunnel/app label, not an asserted person)
fixed tool/endpoint category
repository key and milestone ID when returned
HTTP/result status
duration
```

Do not log API keys, authorization headers, tool payloads containing source
content, prompt/document bodies, full chat text, or secrets. Keep content
available only in the response requested by ChatGPT. Do not add a separate
database or audit persistence layer in M003.006 unless a concrete retention
requirement is approved.

## 10. Operations, Availability, and Residual Risks

**Startup and restart:** Implement the tunnel client as a separate systemd
service on `henderson-server1`, supervised independently from Repo Control.
It starts after networking, reconnects after interruption, and is restarted
on failure. Repo Control stays independently managed. The existing Windows
SSH tunnel is not a dependency for the ChatGPT path.

**Failure and recovery:** ChatGPT reads fail when the tunnel client, Repo
Control, host, outbound OpenAI connectivity, or associated ChatGPT workspace
is unavailable. Check the tunnel client's health/readiness and journal, then
Repo Control's local health and systemd status. Do not return cached or
success-shaped evidence on failure. Retry only after the original failing
boundary is clear.

**Upgrade and disable:** Pin and document a supported tunnel-client release;
upgrade separately from Repo Control and verify MCP tools after restart.
Disable access by stopping/disabling the local service and, when necessary,
revoking the runtime key or deleting/disassociating the tunnel and disabling
the ChatGPT app. Keep the manual packet workflow available.

**Meaningful risks and mitigations:**

- **Credential compromise:** Runtime key could be abused for tunnel access.
  Use a restricted runtime key, service-only secret access, no repository
  storage, redacted logs, rotation, and revocation.
- **Over-broad capability or future drift:** An adapter or tool update might
  add arbitrary paths or mutation calls. Use fixed route implementations,
  no generic proxy, tests that reject unsupported tools/methods/arguments,
  and review changes to the advertised tool list before publishing.
- **Exposed project content / prompt injection:** Requested prompts, workflow
  records, and governing documents are sent to ChatGPT and can contain
  untrusted instructions. Keep tool scope minimal, use targeted reads, and
  treat retrieved content as evidence rather than authority to mutate.
- **No person-level identity at Repo Control:** The API sees a local transport
  caller, not a verified human. Preserve workspace access restrictions and
  metadata-only records; do not describe those records as individual
  attribution.
- **Tunnel/OpenAI outage or vendor coupling:** ChatGPT access depends on
  OpenAI's tunnel service and account permissions. The underlying Repo
  Control API and MCP adapter remain provider-neutral, and manual packets
  remain a fallback.
- **Stale or mixed evidence:** The API does not guarantee one atomic snapshot
  across files, selection, and Git. Use fresh targeted calls and expected
  identity/generation preconditions; surface 409 and other errors explicitly.
- **Accidental public exposure:** No inbound listener or router change is
  needed. Keep Repo Control loopback-bound; prefer stdio MCP over adding a
  local network listener.

Accepted residual risk: OpenAI is a processor/transport for evidence explicitly
requested by the Architect; use remains subject to the Product Owner's
workspace and data controls. This closeout does not independently establish
those account-level controls.

## 11. Performance and Context Efficiency

Prefer fresh, targeted requests to caching. `/review` gives a bounded
cross-section without prompt/document bodies; request `/prompt`,
`/workflow`, `/closeout`, `/evidence`, or one governing-document role only
when relevant. Existing API limits and explicit truncation/error reporting
remain authoritative. Avoid a tool that fetches every source by default.
Expected request count and response payload depend on the discussion; no new
cache is justified by the evidence available.
