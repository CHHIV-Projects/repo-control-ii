The POC uses Python's standard-library `sqlite3` and the existing v1 lifecycle reducer as its semantic oracle. Every database, tamper fixture, interruption fixture, and restore target was disposable under `/tmp`, outside the repository and Repo Control state root.

The POC stores a repository/milestone/prompt identity, ordered source event payloads, transaction-ID/request-hash receipts, an expected revision, and a reducer-derived projection. It uses `BEGIN IMMEDIATE`, WAL, `synchronous=FULL`, foreign keys, a 10,000 ms busy timeout, unique event IDs/sequences, event payload hashes, and an atomic event/receipt/projection transaction.

Phase B coverage includes a valid history containing all 21 event types and all six lifecycle phases; 2,001 events and 6,124,662 serialized event bytes; a 10,000-event workload with 10,427,640 serialized bytes; eight processes × 250 one-event transactions; exact-request retry and duplicate-ID rejection; pre-commit and post-commit/before-acknowledgment process interruption; 100-event snapshot paging while later writes occur; payload/sequence/hash/projection tampering; a larger active-WAL Online Backup API restore; and bounded missing/corrupt-database and busy-timeout checks.

No production workflow code, managed state, service, dependency, configuration, migration, or live-ledger test write was changed or performed. The generated workflow sidecar was read-only.

## 4. Architecture / Integration Notes

The fixture database has `milestone_state`, `workflow_event`, and `transaction_receipt` tables. Each append validates the expected revision and prompt hash, replays the prior history through the v1 reducer, writes its receipt and source events, then updates the projection in one SQL transaction. A repeated transaction ID with the same request returns its saved result; reuse with different content and stale revisions fail explicitly. Snapshot reads replay and compare the stored projection.

Current line counts are 660 for the POC implementation and 1,162 for its tests (1,822 combined), versus 2,759 for the custom-v2 implementation and 1,091 for its tests (3,850 combined). This is a 52.7% lower combined line count, but not an equivalent feature or maintenance comparison: the POC relies on the private v1 reducer, and the custom-v2 implementation includes different segment/index and ledger machinery. The POC implementation is notably smaller; evidence does not establish that it is simpler to maintain than the complete v1 workflow system.

Potential benefits are SQLite's atomic multi-row transactions, built-in WAL mode, uniqueness constraints, and a compact local event/projection store. Remaining risks include SQLite's single-writer model, lack of production integration and migration design, reliance on private v1 reducer helpers, and untested production backup/recovery, crash, long-history, and operational behavior.

### Phase B failure and bounded diagnostic comparison

The original corrupt-WAL acceptance failure remains **FAIL**. The initial bounded diagnostic compared an active-WAL Online Backup API snapshot, a writer-process exit after commit, and matching intact/corrupted database-plus-WAL copies. Those fixtures used synthetic data on local `/tmp`; no repair or custom recovery was attempted. The later A6 authorization covered the remaining Phase B characterization reported in Section 5.

| Case | Exact setup and observation | Result |
|---|---|---|
| Online Backup API with active WAL | Source at revision 2 / 4 events with a live 28,872-byte WAL. `sqlite3.Connection.backup()` produced a standalone destination at revision 2 / 4 events; `PRAGMA integrity_check` returned `ok`. The earlier measured backup duration was about 12.531 ms. | **PASS, bounded snapshot only.** This does not show the API repairs a damaged WAL or provide a recovery policy. |
| Writer process exit after commit, before acknowledgment | A child process committed its transaction and exited with code 73 before an acknowledgment could be returned. With the intact 28,872-byte WAL, the parent observed revision 2 / 4 events. After closing the keeper connection, a fresh POC connection reopened revision 2 / 4 events; `integrity_check` returned `ok`. | **PASS, process-exit case only.** This is not a physical power-loss or storage-device failure test. |
| Matched intact file-pair copy | From one source at revision 2 / 4 events and an active 28,872-byte WAL, the main database and WAL were copied to a disposable directory after the transaction completed, without copying `-shm` and without an active write transaction. The copied database reopened at revision 2 / 4 events with integrity `ok`. | **PASS, controlled copy.** |
| Same copy after deliberate WAL-header corruption | A matching copy was made from the same source; the first byte of its WAL header was flipped. SQLite reopened without an error, reported revision 1 / 2 events, and returned integrity `ok`, silently omitting the committed second transaction. | **FAIL.** The damaged WAL was ignored and the older main-database state was exposed. |

Environment for these diagnostics: Python 3.12.3, SQLite 3.45.1, Linux on local ext4 `/tmp`. All databases and copies were temporary and removed after each run. These outcomes concern only the disposable POC, not managed v1 sidecars or production.

The result demonstrates a detection boundary: `PRAGMA integrity_check` can report that the database state SQLite opened is structurally consistent, but that result does not prove the event history is complete. In the matched corruption case, two committed events were absent while the integrity check still returned `ok`. The Online Backup API successfully created a snapshot while the WAL was intact; it did not demonstrate recovery from an already damaged WAL. This still fails the prompt's explicit requirement for corrupt-WAL error behavior. No fail-closed handling or independent completeness signal has been demonstrated.

#### Separate SQLite version risk

The diagnostic runtime was SQLite 3.45.1. SQLite's [WAL documentation](https://www.sqlite.org/wal.html#the_wal_reset_bug) describes a separate WAL-reset concurrency bug affecting releases through 3.51.2, fixed in 3.51.3 with backports including 3.50.7 and 3.44.6. Thus 3.45.1 falls within the documented affected range. This is distinct from the deliberate header-corruption result and was not reproduced or tested here. No dependency, system SQLite, or configuration change was made. Any separately authorized concurrency characterization should account for this version risk rather than treating this diagnostic as evidence about that bug.

Other official references consulted: SQLite [Write-Ahead Logging](https://www.sqlite.org/wal.html), [Online Backup API](https://www.sqlite.org/backup.html), [How To Corrupt An SQLite Database File](https://www.sqlite.org/howtocorrupt.html), and [`PRAGMA integrity_check`](https://www.sqlite.org/pragma.html#pragma_integrity_check).

#### Interpretation and remaining boundary

The POC audit checks the database state it can open: SQLite structural integrity, foreign keys, repository/milestone/prompt identity, event payload hashes, receipt/revision consistency, reducer replay, and stored projection. Those checks passed on the stale damaged copies because their remaining rows formed a valid older history. A known expected fixture or another retained snapshot can expose the revision/event-count mismatch, but the comparison in this test used the same disposable `/tmp` host and volume; it is not independently protected recovery evidence. Without an approved independent anchor or verified snapshot, completeness after arbitrary database/WAL corruption remains **UNVERIFIED**. No forced repair, fallback, overwrite, or new recovery machinery was attempted.

The measurements in this historical follow-up describe one small local fixture and do not establish an RPO, RTO, backup cadence, retention policy, or operating ceiling. Those remain open PO decisions. The new results support a database-aware snapshot as a candidate recovery path; they do not pass the prompt's original strict corrupt-WAL fail-closed criterion.

Execution note: the first harness attempt stopped before testing because it opened the keeper connection after writes and the WAL had already checkpointed. Corrected runs opened the keeper before writes; a reporting attempt also had to capture WAL size before closing the final keeper. These were harness setup/reporting issues, not changes to the POC. No managed path was involved.

Repository Intelligence: NOT USED — direct source/API inspection and disposable runtime fixtures sufficed; no structural graph query was materially useful. The last observed graph status was CURRENT with `head_changed` provenance; no refresh was attempted because this fixture-only evaluation did not require broader structural evidence. That observation may not include these POC files; no graph evidence is used as source or runtime proof.

## 5. Validation Performed

### Fixture definitions and observed measurements

- Lifecycle parity: a fixed history with 22 events covering all 21 supported event types, all six lifecycle phases, and question/answer, bug classification/fix, escalation, decision, test, closeout, acceptance, reopen, Git-disposition, and context-verification linkage. IDs, payloads, prompt identity, timestamps, order, and batch sizes are deterministic.
- Large history/backup: 2,001 events and 6,124,662 serialized event bytes. Append took 108.841 ms. With an active WAL, the source files measured database 8,683,520 bytes, WAL 8,730,312 bytes, and SHM 32,768 bytes. Online Backup API time was 32.143 ms; the restored database was 8,683,520 bytes, `PRAGMA integrity_check` returned `ok`, and full POC audit and event/projection replay matched.
- 10,000-event workload: 10,427,640 serialized bytes in ten 1,000-event transactions. Append p50 113.133 ms, p95 241.064 ms, max 241.064 ms; total workload/audit/paging/checkpoint elapsed 1,618.268 ms; full audit 169.211 ms. The 100-event page latency was p50 0.660 ms, p95 0.677 ms, max 0.818 ms. A passive checkpoint reported busy=0 and checkpointed all 418/418 frames in 23.115 ms. Measured files were database 15,945,728 bytes, WAL 5,121,192 bytes, SHM 32,768 bytes (three files). Current RSS was 113,556 KiB and open descriptors 13 at measurement.
- Multiprocess writers: eight processes × 250 one-event transactions; 2,000 acknowledged, 3,406 explicit revision rejections, 5,406 total bounded attempts, zero busy errors, zero duplicate events, and zero lost acknowledged events. Each transaction was retried with the identical transaction ID/request; maximum attempts for one worker were 1,305. Elapsed time was 55,976.772 ms with the configured finite busy timeout of 10,000 ms.
- Interruptions: a child was terminated after writing within an uncommitted transaction and before commit; the parent saw no event and successfully retried that transaction. A second child exited with code 73 after commit and before acknowledgment; retrying the exact transaction returned its receipt, with exactly two complete events/receipts and no duplicate.
- Snapshot paging: captured a 250-event snapshot, appended 25 later events, then retrieved the original snapshot in pages of 100, 100, and 50 exactly once. Mismatched snapshot counts and cursors beyond the boundary raised `CursorConflict`.
- Tamper detection: independently modified a disposable fixture's payload, sequence, hash, and projection. Each audit raised `IntegrityFailure`.
- Error behavior: missing database raised `PocError`; corrupt database raised `sqlite3.DatabaseError`; a held write lock produced an explicit `sqlite3.OperationalError` after 101.811 ms under a temporary 100 ms timeout. Permissions and disk-full behavior were not tested.
- Rollback/idempotency/identity: retained Phase A checks verify atomic event/projection rollback, exact-request idempotency, changed-request rejection, stale-revision rejection, changed-prompt rejection, and duplicate event-ID rejection.
- Environment: Python 3.12.3, SQLite 3.45.1, Linux local ext4 `/tmp`; settings were WAL, `synchronous=FULL`, foreign keys enabled, 10,000 ms busy timeout, schema version 1. No runtime or dependency was installed or changed.

## 8. Known Limitations

The evidence covers disposable local fixtures on one host. The original corrupt-WAL fail-closed behavior remains unfulfilled: SQLite ignored the damaged WAL and exposed an older, internally consistent history. The integrity audit verifies the state SQLite opened, not independent history completeness. The Online Backup API restores the tested active-WAL fixture but does not establish a recovery policy or independently protected anchor.

The only available runtime measured was Python 3.12.3 / SQLite 3.45.1; the separately documented SQLite 3.45.1 WAL-reset concurrency risk remains, and no fixed runtime was available in the checked interpreters. Process termination is not physical power-loss evidence. Synthetic padding tests storage size and replay, not realistic production payload distributions. The POC uses private v1 reducer helpers. Line-count comparison is non-equivalent feature coverage; smaller source size does not establish lower total maintenance burden. Latencies and resource values are characterization samples, not SLOs or capacity guarantees.
