# M004.002 — Repo Control Graphify Integration and Value Measurement

## Objective

Integrate the proven Graphify repository-intelligence subset into Repo Control II behind a narrow, provider-replaceable adapter, and add a simple measurement system that lets the Product Owner determine whether repository intelligence is creating real workflow value.

The integration must make structural repository intelligence directly useful to both Architect and Coder while preserving Repo Control authority, bounded evidence, deterministic freshness, and existing Git/lifecycle boundaries.

This milestone is not successful merely because Graphify can be called. It must also make its practical value visible and easy to review.

## Preconditions

M004.001 must be accepted and CLOSED before implementation begins.

Use the accepted M004.001 POC evidence as the measured baseline:

- Graphify 0.9.91 proved viable for local code-only structural analysis.
- Repo Control II POC graph: 1,322 nodes / 5,251 edges.
- Supported frozen checks: 19/20 recovered.
- Bounded precision audit: 27/27 inspected assertions correct.
- Flask/Jinja/browser cross-layer checks: 1/5 recovered.
- Cold build approximately 3.4 s.
- No-change update approximately 2.0 s.
- Incremental updates approximately 2.5 s.
- Warm stdio MCP query latency was low.
- Native MCP results are primarily text and may return failure/ambiguity content with isError=false.
- Native output budgets are not hard byte limits.
- Community/report identity showed an inconsistency.
- HTML viewer is not self-contained offline and is not a primary integration objective.

Treat those as accepted evidence, not as guarantees for all future versions or repositories.

## Product Owner Intent

The objective is broad structural intelligence with narrow authority.

Do not narrow Graphify until it provides little more than grep.

After this milestone, the Architect and Coder should be able to obtain useful, source-cited structural evidence such as:

- where a symbol is defined;
- what file/module owns it;
- what calls it;
- what it calls;
- what imports or references it;
- what symbols/files are structurally nearby;
- what tests appear related;
- what may be affected by a change;
- what relationship path connects two symbols;
- bounded contextual evidence around a subsystem.

The integration must preserve limitations honestly. Missing structural evidence is not proof that no runtime relationship exists.

## Architectural Boundary

Graphify owns:

- code parsing / AST extraction;
- graph construction;
- symbol resolution/deduplication;
- graph-native relationships;
- native traversal/query operations.

Repo Control owns:

- allowlisted repository identity;
- selected repository and registry generation;
- graph build/refresh authorization;
- source snapshot/freshness identity;
- safe artifact location;
- Graphify process/runtime isolation;
- bounded query contracts;
- output byte/time/depth/result limits;
- failure/ambiguity normalization;
- evidence provenance;
- Architect and Coder access;
- value measurement.

Repo Control must not build:

- a replacement parser;
- a second call/dependency graph engine;
- custom clustering/community detection;
- a generic graph query language;
- an AI semantic repository analyzer in this milestone.

Graphify-specific details should remain behind a narrow repository-intelligence provider/adapter boundary so a future engine can replace it.

## Runtime / Installation

Do not depend on the retained Copilot session-state POC environment as durable infrastructure.

Create a stable user-owned Graphify tool/runtime location outside the Repo Control repository and outside Repo Control's application virtual environment.

Requirements:

- pin the Graphify version used by this milestone;
- preserve code-only/local operation;
- set GRAPHIFY_NO_AUTO_REFRESH=1;
- do not run graphify install;
- do not install Git hooks;
- do not add Graphify to Repo Control application dependencies;
- no Graphify Cloud;
- no semantic/model-backed processing;
- no HTTP listener;
- no additional externally exposed service;
- use a fixed executable/argument vector;
- keep graph/cache/runtime state external to repository content.

A long-running local stdio Graphify child may be used if justified by the POC and implementation simplicity, but Repo Control must own its lifecycle and failure handling.

## Graph Build and Freshness

Implement the minimum safe Graphify build/refresh lifecycle needed for useful queries.

Repo Control must distinguish at least:

- MISSING
- BUILDING
- CURRENT
- STALE
- FAILED
- INCOMPATIBLE

A graph must not be considered current merely because a graph file exists.

Record enough identity to tie a graph generation to its source:

- repository key/id;
- branch/HEAD for context;
- deterministic source-content identity sufficient to detect dirty working-tree changes;
- included/excluded source scope;
- Graphify producer version;
- graph schema version;
- build options;
- graph generation/build timestamp;
- graph/artifact identity/hash where practical;
- build result.

Source changes that invalidate graph identity must conservatively mark evidence stale.

Do not silently serve failed or stale graph evidence as current.

## Initial Intelligence Operations

Expose a useful first set rather than an artificially tiny demonstration.

At minimum evaluate and implement the following if the native contract can be made safe without substantial reimplementation:

1. repository intelligence status/stats;
2. symbol/node lookup with disambiguation;
3. incoming/outgoing filtered relationships / neighbors;
4. callers/callees where Graphify relation evidence supports that interpretation;
5. import/reference relationships;
6. likely related tests / reverse-impact neighborhood;
7. bounded lexical/relationship query around a concept;
8. generic relationship path with explicit relationship types and a clear warning that it is not necessarily a call chain.

Community/clustering-based architectural claims are excluded from the first integration because the POC found inconsistent report/MCP community identity.

HTML viewer integration is excluded. The Product Owner does not need a visual graph for this milestone.

If one requested operation cannot be exposed safely without significant Graphify text parsing or recreating graph logic, HOLD that operation individually rather than shrinking the entire integration.

## Evidence Contract

Architect and Coder must consume the same underlying repository-intelligence contract.

Each result should provide, as applicable:

- repository identity;
- graph generation/freshness;
- operation;
- query arguments after normalization;
- node/symbol identity;
- source file and line/location where available;
- relation type;
- relation direction;
- confidence/provenance tier where available;
- returned count;
- omitted count;
- truncation flag;
- warning/inconclusive status;
- explicit normalized outcome.

Use explicit normalized outcomes such as:

- OK
- AMBIGUOUS
- NOT_FOUND
- STALE
- FAILED
- TRUNCATED
- INCONCLUSIVE

Do not treat Graphify MCP isError=false as proof that the requested repository operation succeeded.

Repo Control should prevalidate graph state and normalize tested Graphify ambiguity/failure text into its own outcome envelope.

If reliable normalization would require a broad fragile text parser, stop/HOLD that operation and report it.

## Hard Bounds

Repo Control must impose independent safety and context-efficiency bounds.

Do not trust Graphify token_budget as a hard output cap.

Implement bounded defaults and explicit omission reporting for:

- maximum response bytes;
- maximum nodes/results;
- maximum edges/relationships;
- maximum traversal depth;
- request timeout.

Choose practical defaults based on M004.001 evidence rather than arbitrary very-small values.

The goal is to avoid uncontrolled 770 KB-style responses while still returning enough evidence to be genuinely useful.

When more results exist, say so explicitly and allow the user/agent to narrow the query.

## Architect Access

Expose the selected repository-intelligence operations through the existing Repo Control Architect MCP boundary.

Requirements:

- fixed bounded tool inventory;
- no arbitrary Graphify tool names;
- no arbitrary graph paths;
- no arbitrary filesystem paths;
- no shell;
- no Graphify build/refresh authority through ordinary read queries;
- no Git/lifecycle mutation authority;
- repository and registry-generation preconditions consistent with existing Architect tools.

The Architect should be able to request targeted repository evidence without manual Product Owner file transfer.

Tool inventory changes may require explicit ChatGPT custom-app refresh; document this if applicable.

## Coder Access

Expose the same intelligence through a bounded local Coder CLI surface.

Do not append full graph data to coder-context.

Prefer explicit targeted commands/operations that return the same normalized evidence envelope used by Architect.

The Coder remains prohibited from Git mutations and Product Owner lifecycle actions.

Direct Graphify CLI may remain a diagnostic/fallback tool, but normal workflow should use Repo Control's shared contract once implemented.

## Repository Intelligence Value Measurement

This measurement system is a required deliverable, not optional instrumentation.

The Product Owner must be able to understand at a glance whether repository intelligence is saving effort or merely adding complexity.

### Principle

Measure workflow value, not just Graphify performance.

Graphify may measure graph/query characteristics. Repo Control should measure whether using repository intelligence reduces repository-reading effort and interaction cost while preserving answer quality.

### Per-Use Measurement

For each Repo Control repository-intelligence query, record a small bounded measurement record outside repository source content.

At minimum capture:

- timestamp;
- repository key;
- graph generation;
- consumer: Architect or Coder;
- operation category;
- query latency;
- response bytes;
- number of nodes/relationships returned;
- truncation/ambiguity/failure outcome;
- whether follow-up source inspection was required, when this can be known;
- optional usefulness assessment.

Do not record full source bodies or sensitive query payloads merely for analytics.

### Human Usefulness Rating

Provide an intentionally simple Product Owner/consumer rating for completed intelligence uses:

- USEFUL
- PARTIAL
- NO_VALUE
- MISLEADING
- UNSUPPORTED

Do not require a rating for every query if that becomes annoying. The UI/workflow should allow easy review and lightweight feedback.

A MISLEADING result must remain visible in the measurement summary and must not be averaged away.

### Baseline / Comparative Measurement

Create a small representative benchmark set from real Repo Control II repository-understanding tasks.

Use approximately 8–12 practical tasks drawn from historical work or current architecture questions, covering areas such as:

- symbol location;
- caller/callee discovery;
- dependency/import tracing;
- test identification;
- affected-area investigation;
- relationship path;
- subsystem/context discovery;
- at least one known unsupported cross-layer/template case.

For each benchmark, compare as practical:

CONTROL:
- normal source/grep/read workflow without Graphify evidence first.

GRAPHIFY:
- Graphify/Repo Control intelligence first, followed by source inspection only as needed.

Measure where practical:

- files inspected;
- relevant source lines/bytes/tokens read or sent to model;
- number of tool/query interactions;
- elapsed time to a useful answer;
- correctness/usefulness outcome.

Do not fabricate token precision if exact model-token accounting is unavailable. A clearly labeled character/byte or estimated-token measure is acceptable.

### Product Owner Review Page

Add a simple browser review surface for repository-intelligence value.

The page should answer, without requiring interpretation of raw logs:

- How many intelligence uses occurred?
- What percentage were USEFUL/PARTIAL/NO_VALUE/MISLEADING/UNSUPPORTED?
- What is median/p95 query latency?
- What is typical response size?
- How often are results truncated or ambiguous?
- For comparative benchmark tasks, did Graphify reduce files inspected, evidence/context size, interactions, or elapsed time?
- Which operation categories are producing the most value?
- Which operation categories are producing failures/noise?
- Are there any MISLEADING results?

Prefer a compact summary/table and simple trend/aggregate presentation over an analytics dashboard.

The Product Owner should be able to look at this page after normal use and decide:

- Graphify is clearly helping;
- Graphify is mixed;
- Graphify adds little value;
- a specific operation is useful while another should be removed or replaced.

### Value Decision Guidance

Do not hardcode a single pass/fail percentage yet.

Instead, make the measurements visible and preserve enough data for a later evidence-based decision.

The measurement system should support later statements such as:

- repository files inspected decreased materially;
- context/evidence volume decreased materially;
- query/interaction count decreased;
- time-to-useful-answer decreased;
- most uses were useful;
- misleading results were rare or absent;

or the opposite.

The purpose is to make it easy to decide whether to continue Graphify, augment it, replace it, or explore another repository-intelligence approach.

## Product Owner UX

Keep the UX simple.

At minimum provide:

- intelligence status/freshness visibility;
- a way to build/refresh deliberately if Product Owner authorization is required by the chosen design;
- a Repository Intelligence Value/Measurements review page;
- clear stale/failed states;
- clear indication that evidence is structural/static rather than runtime truth.

Do not add a large graph visualization or complex analytics interface.

## Live Acceptance

Perform bounded live acceptance after implementation.

At minimum demonstrate:

1. build or refresh a current graph for Repo Control II;
2. Architect-accessible query returns source-cited structural evidence;
3. Coder local query returns equivalent evidence from the same graph generation;
4. ambiguous/missing query is normalized correctly;
5. deliberately broad query is bounded/truncated safely;
6. source modification or controlled fixture demonstrates stale-state handling without corrupting the authoritative worktree;
7. measurement record appears;
8. Product Owner measurement review page is readable and understandable.

Do not require elaborate manual rehearsal of every edge case if automated coverage is strong.
