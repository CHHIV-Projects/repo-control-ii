## 2. Resulting Behavior

- The v2 anchor is a bounded manifest tied to repository, milestone, and prompt identity. It roots immutable content-addressed segments and index/projection pages.
- Segments retain event identity and order. The projection maintains lifecycle and reference indexes; a complete audit remains a distinct operation from bounded event pagination.
- The append path uses the existing state-root lock, writes immutable artifacts before the anchor commit point, and records pending transactions so unresolved writes block unrelated appends and exact retries can reconcile by transaction identity.
- Fixture migration requires explicit `fixture_only=True`, preserves the v1 source image, and replaces the authority anchor only after staging and auditing v2 history. No automatic migration or orphan pruning is provided.
- Legacy v1 behavior remains the active managed-workflow path: its parser, writer compatibility, marker, semantics, 2,000-event and 5,000,000-byte limits remain unchanged. The accepted M009.021.002 concurrency repair was not altered.

These are standalone source and fixture-test observations. They do not establish production safety, complete WF-01 acceptance, or compatibility with deployed consumers and older processes.

### Storage cost and operations observations

All measurements below are synthetic fixture observations, not production capacity or throughput guarantees.

| Measurement | Observed result |
|---|---:|
| 10,000-event serialized event payload | 12,477,504 bytes |
| Segment storage | 12,558,351 bytes across 161 files |
| Index storage | 52,316,342 bytes across 12,935 files |
| Index bytes / event-payload bytes | approximately 4.2x |
| Index files per event | approximately 1.29 |
| Peak RSS at 10,000 events | 49,292 KiB |
| File descriptor high-water / end | 9 / 9 |
| Full audit at 10,000 events | 0.95 seconds |
| 10,000 events read in 100 pages | 0.386 seconds; largest serialized page 125,555 bytes |

Cumulative append checkpoints in the 10,000-event workload were 9.23 seconds at 1,999 events, 9.31 seconds at 2,000, 9.38 seconds at 2,001, 33.24 seconds at 5,000, and 83.99 seconds at 10,000. A separate 1,000 single-event-transaction run took 86.96 seconds. These workloads are not directly comparable: one is cumulative batched append work and the other repeatedly commits single-event transactions. The target for relevant index lookup/update is approximately O(log N); these aggregate measurements do not establish that complexity and show substantial growth that requires independent cost/safety acceptance before integration.

The index footprint creates meaningful file/inode, metadata, backup, and filesystem pressure. Content-addressed immutable pages and segments, including abandoned artifacts, are retained; automatic pruning is not implemented. Lock contention, aggregate bytes read/written, long-duration disk growth, ENOSPC behavior, and acceptable deployment capacity were not measured. The 12,935-file observation is not a capacity approval. Full behavior at disk-full boundaries and operational orphan cleanup remain unresolved.
