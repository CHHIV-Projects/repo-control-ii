# M009.010 — Control-Plane Runtime Compatibility and Procedure Release Workflow Hardening

## Objective and authorization

Prevent recurrence of the operational failure observed during Repo Control II M009.009: a newer co-located Coder CLI appended a durable `context_verification_recorded` event that the older running browser service could not parse, making the active workflow unreadable; separately, authorized canonical shared-procedure edits invalidated published manifest hashes during release preparation, causing `ProcedureGovernanceError`, blocking agent verification, and making Procedure Updates misleadingly show no managed repositories.

Implement reliable and auditable compatibility gates and an explicit, controlled canonical release-preparation state. Preserve fail-closed lifecycle authority, event history, artifact integrity, Product Owner apply/rollout authority, and Coder Git restrictions. This is **Repo Control II only**, after Product Owner acceptance/closure and deployment preparation of M009.009. A pending Architect proposal gives no implementation authorization. Verify M009.010 selected and `IN_PROGRESS` before consequential work.

## Grounded incident / prior constraints

- Target: `repo-control-ii`, `/home/chuck/projects/repo-control-ii`. Preserve M009.008 context-verification audit semantics and M009.009 Intelligence freshness and shared procedure 1.3.0; no rollback of these accepted behaviors.
- In M009.009, the CLI recorded `context_verification_recorded` in the workflow sidecar while the browser service (process started Oct 28) still held older parser code. `repo_status`, `repo_workflow`, and browser Milestone failed with `malformed_workflow_sidecar: unsupported event type`. Reloading the browser service restored readability without editing the sidecar.
- The Coder had modified `shared/procedure/workflow_core.md` and two canonical Skills while preparing release 1.3.0, before updating `shared/procedure/manifest.toml`. Bundle-integrity checking correctly reported a source-hash mismatch; `coder-verify` returned PARTIAL_UNVERIFIED and the Procedure Updates page misleadingly displayed `No managed repositories are configured`.
- A service restart loads editable source from the active checkout; the control plane must not silently load unfinished work as an ordinary deploy. Product Owner owns service operation and Git, not Coder.
- Investigate actual current code, service/runtime entrypoints, CLI vs web parser ownership, schema/version metadata, transaction design, procedure release validator and UI, and test infrastructure before settling on a narrow design. Document the exact failure chain and proven vs hypothesized causes.

## A. Durable workflow event compatibility

1. Define explicit compatibility contract for durable workflow/event schema: producer capabilities and deployed reader capabilities must be compatible **before** a newly introduced event is appended. The central check must verify the *running service's* effective schema/capabilities, not just the disk's source version or Git HEAD.
2. Provide a bounded fail-closed mechanism for older running service vs newer local CLI, including a clear operator-facing error (`runtime_upgrade_required` or equivalent), rather than allowing a write that renders the milestone unreadable. Preserve atomic sidecar updates, lifecycle event validation, and append-only audit semantics; no silent dropping, coercion, rewriting, or unapproved deletion of unknown events.
3. Preserve supported co-located CLI workflows when the browser is temporarily unavailable only if safe authority and compatibility can be established deterministically. If compatibility cannot be proven, block the risky event write clearly without granting authority. Keep normal read-only Git/status available wherever safe.
4. Design for forward evolution (future event types/schema changes) without requiring manual reminders or ad hoc restarts. Prefer a small central compatibility handshake or equivalent bounded mechanism over introducing an always-running monitoring service or forcing automatic restarts.
5. Present actionable diagnostics: deployed runtime identity/capability, on-disk CLI/schema identity, mismatch classification, and safe Product Owner controlled remedy. Do not expose secrets, shell injection surfaces, or unauthorized service-management actions.

## B. Canonical procedure release preparation

6. Preserve the integrity rule that only manifest-matching, versioned canonical bundles can be published, previewed for Apply, or applied to a managed repo; preserve exact source hashes, overlay protection, transactional Apply/Recover, and individual PO confirmation. Never implement a 'ignore hash mismatch' setting.
7. Distinguish **authorized canonical release editing in progress** from missing/corrupted canonical authority or an unknown unauthorized file modification. Define deterministic status/diagnostics and documentation; do not mistake ordinary repo-installed `STALE_VERSION` (expected release drift) for broken canonical content.
8. Ensure Coder verification can support an approved milestone *whose explicit task is preparing a canonical shared release* without a deadlock: establish live repository/milestone/lifecycle authorization separately from release integrity; show `release_in_preparation`/integrity-unavailable clearly; permit only explicitly authorized release-preparation actions, never generic work, procedure Apply, unverified generated instructions, or an implicit authorization bypass. If this cannot be safely designed in scope, stop and raise a bounded question.
9. Provide a deterministic authoring/validation flow for candidate version + source hashes + bundle integrity + read-only preview; publish only a complete internally consistent release. Avoid manual hash copying as a required Product Owner ritual where a safe existing mechanism can be reused.
10. Keep Procedure Updates useful when canonical bundle validation fails: display the actual integrity error and, where safe, the configured repository list; show per-repo comparison as unavailable, not `No managed repositories are configured`. Block Apply/Recover as appropriate, while preserving independent established recovery behavior and not concealing corrupt or incomplete transactions.
