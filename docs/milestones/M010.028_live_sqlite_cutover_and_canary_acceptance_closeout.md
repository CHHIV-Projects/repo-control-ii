## 4. Architecture / Integration Notes

Gate A and Gate B are distinct exact-plan approval boundaries. Gate A binds
the live service to a held candidate without an application write. Gate B
binds inode-specific permission release to one nonce-bearing workflow event,
then uses forward recovery. Both browser and CLI require the candidate-specific
coverage binding. Backup/monitor units are sandboxed to the exact R8 candidate,
local staging/restore roots, and approved NAS destination.

R7 failed before Python startup because its scanner cache path did not exist
inside the systemd namespace. The permanent correction statically binds every
runtime and `ReadWritePaths` path, requires `StartLimitBurst=1`, and exercises
the real namespace with a root-run transient `/usr/bin/true` probe before
capture.

The first R8 backup succeeded, but a one-time generated wrapper mistakenly
reused the obsolete R7 volatile-timestamp detector. Read-only evidence resolved
the firing as successful; no backup or canary was repeated. The wrapper was
corrected to the already-reviewed blocking `systemctl start` design used by
Gate B.

Repository Intelligence: NOT USED — direct source inspection, focused tests,
exact hashes, live systemd/health/CLI evidence, SQLite queries, NAS manifests,
and restored-content checks answered the relevant structural and runtime
questions. A graph refresh was not attempted because it would not strengthen
the live authority, sandbox, backup, or recovery evidence; no graph evidence
was relied upon.
