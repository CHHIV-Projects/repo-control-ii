## 2. Implemented Commands & Interface

A dedicated module `src/repoctl/workflow/coder_interface.py` was implemented and wired directly into the main CLI entry point in `src/repoctl/cli.py`.

### 2.1 Context and Status Retrieval

| Command | Purpose | Formats |
|---|---|---|
| `repoctl coder-context` | Retrieves authoritative active milestone prompt, lifecycle authorization check, standing document references, and open conditions. | `--format text` (human-readable), `--format json` (machine-readable) |
| `repoctl coder-status` | Lightweight read-only report of active milestone lifecycle, blockers, lock-ins, and event counts without embedding prompt text. | `--format text` (human-readable), `--format json` (machine-readable) |

**Key Capabilities:**
- **Deterministic External Pointer Resolution:** Resolves active milestone selection strictly from `~/.local/share/repoctl/<repo_id>/milestones/selection.json`. Does not guess from Git commit logs or file timestamps.
- **Repository Registry Integration:** Resolves repository name and relative document paths from `ops/repositories.toml` when present, with safe fallback to single-repository defaults.
- **Standing Document References:** Outputs repository-relative paths to `coding_agent_rules.md`, `project_workflow.md`, and `project_architecture.md` instead of embedding large repetitive documents into the prompt stream.
- **Git Mutation Warning Notice:** Explicitly reminds the Coder that Git mutation (staging, commit, push, switch, rebase, clean, etc.) is strictly prohibited.

### 2.2 Bounded Coder Event Submission

The Coder CLI exposes exactly four bounded write commands corresponding to Model B:

1. `repoctl coder-question "<summary>" [--blocking] [--category clarification|decision|blocker|other]`
   - Maps to `question_submitted`.
   - Non-blocking: stays in `IN_PROGRESS`, records question in open conditions.
   - Blocking (`--blocking`): pauses implementation and transitions milestone from `IN_PROGRESS` to `WAITING`.
   - Requires `IN_PROGRESS` phase; rejected in all other phases.
2. `repoctl coder-bug "<summary>"`
   - Maps to `bug_discovered`.
   - Records discovery of a defect during work without granting classification authority.
   - Valid in `IN_PROGRESS` and `WAITING`.
3. `repoctl coder-test "<summary>" --source "<cmd>" --result "<outcome>"`
   - Maps to `test_result_recorded`.
   - Records test execution outcome; explicitly labeled in sidecar as reported evidence.
   - Valid in `IN_PROGRESS`, `WAITING`, and `REVIEW`.
4. `repoctl coder-closeout [--summary "<summary>"]`
   - Maps to `closeout_submitted`.
   - Verifies the matching milestone closeout artifact exists on disk before submission.
   - Transitions milestone from `IN_PROGRESS` to `REVIEW`.
   - Valid only in `IN_PROGRESS`.

## 3. Architecture and Invariant Preservation

- **No Coder MCP Network Surface:** Co-located in-process CLI execution was implemented; no network daemon, listening socket, or HTTP endpoint was added.
- **Model B Write Boundary Enforced:** Every Coder event hardcodes `actor_role="coder"` and `po_approved=False`.
- **No Generic Event Submission:** No `repoctl coder-event --type ...` or caller-selectable event mechanism exists.
- **No Product Owner Authority Usurpation:** The Coder CLI provides no mechanism to perform `prompt_approved`, `implementation_started`, `answer_recorded`, `decision_recorded`, `lock_in_approved`, `escalation_resolved`, `bug_classified`, `bug_fixed`, `implementation_resumed`, `correction_requested`, `acceptance_recorded`, or `milestone_closed`.
- **Git Mutation Prohibition:** Coding agents cannot execute Git mutations. Consequential Git actions remain strictly with the Product Owner.

### Repo Code Reused vs New Code

- **Reused:** Existing milestone discovery and external selection-pointer loading, lifecycle validation and event recording (`load_milestone_workflow()` / `record_milestone_event()`), shared sidecar ledger handling, and repository identity/registry helpers.
- **New:** `src/repoctl/workflow/coder_interface.py` implements Coder authorization/context/status and the four bounded submission functions; `src/repoctl/cli.py` adds six Coder subcommands and their output/error handling.
- The implementation delegates lifecycle transitions and sidecar persistence to the existing workflow engine rather than duplicating them.

## 4. Lifecycle Authorization Matrix

`get_authorization_status()` evaluates the active phase and returns deterministic authorization semantics:

| Lifecycle Phase | Authorized? | Can Preflight? | Status Code | Coder Authorization Policy |
|---|---|---|---|---|
| `PLANNING` | **NO** | False | `NOT_AUTHORIZED` | Prompt review and approval required before implementation. |
| `READY` | **NO** | True | `PREFLIGHT_ONLY` | Preflight permitted; implementation begins only after explicit lifecycle start. |
| `IN_PROGRESS` | **YES** | True | `AUTHORIZED` | Full implementation and validation authorized. |
| `IN_PROGRESS` (correction) | **YES** | True | `AUTHORIZED_CORRECTION` | Implementation authorized, strictly limited to requested bounded correction. |
| `WAITING` | **NO** | False | `NOT_AUTHORIZED` | Paused; resolution and Product Owner resume required. |
| `REVIEW` | **NO** | False | `NOT_AUTHORIZED` | Under review; no changes authorized unless correction requested. |
| `CLOSED` | **NO** | False | `NOT_AUTHORIZED` | Terminal; milestone complete. |

### 6.4 Milestone Tab Compatibility

The Coder CLI interacts with the milestone workflow sidecar exclusively through the shared `record_milestone_event()` and `load_milestone_workflow()` engine in `src/repoctl/workflow/lifecycle.py`:
- **Shared Storage and Locking:** Both the Milestone web tab and the Coder CLI acquire `STATE_ARTIFACT_LOCK` and parse/render the exact same markdown sidecar ledger format (`<milestone>_workflow.md`).
- **Immediate Bidirectional Visibility:** Any event recorded by the Coder CLI (such as a blocking question pausing the milestone to `WAITING`, a defect discovery, or closeout submission transitioning to `REVIEW`) is immediately reflected in the Milestone Tab upon page reload or query. Conversely, any event recorded in the Milestone Tab (such as Product Owner prompt approval to `READY`, lifecycle start to `IN_PROGRESS`, binding lock-in, answer recording, or resume) is immediately visible to `repoctl coder-status` and `repoctl coder-context`.
- **Identical State Reducer:** Both interfaces share the deterministic `_reduce_events()` function, ensuring zero divergence in phase transitions, waiting reasons, open questions, or open bugs.

### 6.5 Architect MCP Compatibility

The Coder CLI preserves 100% compatibility with the read-only Architect MCP adapter:
- **Zero Adapter Changes Required:** The Architect MCP adapter (`src/repoctl/mcp/architect_adapter.py`) queries Repo Control's read-only REST endpoints (`/api/architect/v1/status`, `/milestone`, `/workflow`, `/closeout`, `/evidence`, `/review`).
- **Seamless Evidence Exposure:** Because the Coder CLI writes standard `question_submitted`, `bug_discovered`, `test_result_recorded`, and `closeout_submitted` events to the sidecar:
  - `repo_milestone` instantly reflects Coder-initiated phase transitions (`IN_PROGRESS` → `WAITING` on blocking question, `IN_PROGRESS` → `REVIEW` on closeout submission).
  - `repo_workflow` immediately displays Coder questions and blockers to ChatGPT Architect.
  - `repo_evidence` immediately includes Coder test outcomes recorded with `coder-test` (correctly labeled as reported evidence).
  - `repo_closeout` serves the discovered closeout document once submitted via `coder-closeout`.
- **Architect Separation Maintained:** The Architect remains strictly read-only over the Secure MCP Tunnel, while the Coder remains strictly bounded to local in-process event submission.
