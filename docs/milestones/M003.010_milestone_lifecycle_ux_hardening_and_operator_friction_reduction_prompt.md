# 3. Live M003.009 Findings Driving This Milestone

The Product Owner and Architect observed the following during actual workflow use.

## 3.1 Stale Milestone UI State

Workflow changes made outside the browser, especially through the Coder CLI, were not reflected in the Milestone page until the browser was manually refreshed.

The server-side state was correct, but the displayed browser state lagged.

## 3.2 Generic Event Form Is Too Dense

The current “Record a meaningful workflow event” form exposes too many fields at once and requires the Product Owner to understand low-level event machinery.

The form should become:

```text
phase-aware
event-aware
context-aware
```

Show only the fields/actions relevant to the current lifecycle phase and selected action.

## 3.3 Repetitive Summary Entry

Many lifecycle actions already have an obvious deterministic meaning.

The Product Owner should not need to manually type repetitive summaries such as:

```text
Approve M003.010 prompt
Start M003.010 implementation
Resume M003.010 after question resolution
Accept M003.010
Close M003.010
```

Provide an editable prepopulated default where the system can safely derive one.

## 3.4 Human-Readable Question and Bug References

The workflow ledger should continue using UUID event IDs internally.

The Product Owner should not need to manually reason about or type UUIDs.

Present human-readable aliases such as:

```text
M003.010 Q1
M003.010 Q2
M003.010 B1
M003.010 B2
```

UI display should include the alias plus a concise summary.

The UUID remains the authoritative stored linkage.

## 3.5 Automatic Related-Item Selection

When an action requires a related open question or bug:

```text
if exactly one valid item exists
→ auto-select it

if multiple valid items exist
→ show a readable selector

if none exist
→ disable/reject the action clearly
```

The Product Owner should never have to manually paste an event UUID.

## 3.6 Intermittent First-Submission / Confirmation Failure

During M003.009 live acceptance, a Product Owner approval action initially failed with:

```text
invalid_workflow_event
Select Product Owner and explicitly confirm this approval action.
```

The visible form appeared to contain the required actor and checked confirmation state. A later attempt succeeded.

This milestone must investigate the behavior without assuming a cause. Do not overfit to one hypothesis.

# 4. Primary Scope

Implement the smallest safe UX improvements that address the observed issues.

## 4.1 Automatic or Lightweight State Refresh

Add a mechanism so the Milestone page reflects lifecycle changes made outside the browser without requiring a manual full-page refresh.

Preferred characteristics:

```text
lightweight
bounded
server-authoritative
low complexity
no websocket/event-bus requirement
no background service
no new persistence
```

A modest polling or targeted refresh approach is acceptable if it integrates cleanly with the current Flask application.

Requirements:
- external Coder events become visible within a reasonable short interval;
- current lifecycle phase updates;
- waiting/open-condition state updates;
- chronology/event count updates where displayed;
- actions available to the Product Owner reflect current state;
- stale browser state must not authorize an action that current server state rejects;
- avoid disruptive whole-page refresh if practical.

## 4.2 Phase-Aware Product Owner Action Surface

Reorganize the workflow event form around currently valid Product Owner actions.

Examples:

```text
PLANNING → Approve prompt
READY → Start implementation
IN_PROGRESS → Record answer/decision/lock-in as applicable
WAITING → Answer / decision / resolve → Resume only after valid resolution
REVIEW → Accept / Request bounded correction
CLOSED → no lifecycle action
```

Do not hide valid advanced workflow actions if they remain needed, but do not expose irrelevant fields by default.

## 4.3 Contextual Field Visibility

Fields should appear only when relevant to the selected action.

Examples:

```text
PO confirmation → only when required
related question selector → only when required
related bug selector → only when required
waiting category → only when applicable
binding / lock-in fields → only when applicable
evidence fields → only when applicable
```

Do not weaken server-side validation.

## 4.4 Editable Default Summaries

Provide deterministic default summaries for actions where a useful summary can be derived safely.

Rules:
- defaults are editable by the Product Owner;
- user override must be preserved;
- no AI generation is needed;
- do not fabricate substantive decisions;
- include Q/B alias where useful.

## 4.5 Human-Readable Event Aliases

Add presentation-layer aliases for:

```text
question_submitted → Q<n>
bug_discovered     → B<n>
```

Alias scope is milestone-local.

Expected form:

```text
M003.010 Q1
M003.010 B1
```

Requirements:
- deterministic from workflow chronology;
- no replacement of UUID persistence;
- historical sidecars remain valid;
- avoid sidecar schema migration if practical;
- selectors and visible chronology use aliases where helpful.

## 4.6 Auto-Select Single Related Item

For actions requiring related question/bug linkage:
- one eligible item → preselect;
- multiple → alias + concise summary selector;
- none → disable or clear message;
- persist UUID as `related_event_id`.

## 4.7 Investigate and Harden Product Owner Confirmation Handling

Inspect at minimum:

```text
form POST handling
actor-role field binding
PO confirmation checkbox parsing
redirect/refresh behavior
browser-visible state vs submitted state
validation error re-render behavior
```

Add regression coverage for the demonstrated failure mode if cause is identified.

If not reproducible, document what was inspected and do not claim a root cause.

# 6. Authority and Safety Invariants

Preserve all current authority boundaries.

Product Owner retains authority for prompt approval, implementation start, binding lock-ins, authoritative decisions, resume from WAITING, acceptance, milestone closure, and Git mutations.

Coder remains limited to `coder-context`, `coder-status`, question submission, bug discovery, test evidence, and closeout submission.

Architect remains read-only through MCP.

UI convenience must never become workflow authority. Server-side lifecycle validation remains authoritative.

---

# 7. Architecture Guidance

Prefer modifying the current Milestone route/template/JS behavior rather than creating a parallel UI.

Reuse existing lifecycle reducer, event validator, selection authority, sidecar persistence, open-condition derivation, event chronology, and Product Owner role checks.

Presentation aliases should preferably be derived from existing chronology rather than persisted as new authoritative identifiers.

Default summaries should preferably be derived in one deterministic helper rather than duplicated across template and route logic.

State refresh should query current server state rather than trusting cached browser state.

If current architecture makes these changes unexpectedly broad, stop and report before refactoring.
