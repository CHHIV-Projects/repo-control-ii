## 1. Freshness and source provenance

1. Establish and document the graph's *semantic freshness contract*. Identify every input that materially affects the supported structural graph: included/excluded supported source files and bytes, provider/extractor and schema versions, configuration/options, and any genuinely source-affecting factors. Preserve sufficient deterministic identity and audit provenance to detect relevant changes reliably.
2. Distinguish semantic graph input freshness from descriptive Git provenance (commit HEAD, branch, timestamps). A Git HEAD-only/documentation-only commit with identical graph-relevant inputs must not force an unnecessary structural graph rebuild or conceal an otherwise valid graph. Do not claim CURRENT if relevant source bytes or graph production inputs differ. If checkout or branch identity imposes a real trust or path boundary, model and justify it separately rather than assuming a HEAD mismatch means structural staleness.
3. Keep repository root/managed ID, safe path boundaries, provider compatibility, schema integrity, and source-input verification fail-closed. Never permit cross-repository graph reuse, silently trust stale unsupported inputs, or weaken response limits.
4. Support migration/compatibility with existing graph metadata: decide how older graph records without enough identity fields are classified. Prefer explicit unknown/incompatible/rebuild-required state to guessing that old evidence is CURRENT. Preserve old measurement data and explain any one-time rebuild.
5. Retain original Git HEAD/branch and build provenance as factual metadata, including when semantic freshness persists across a Git-only change. Do not rewrite historical build provenance to pretend a rebuild happened.
6. Keep the external derived-graph state and existing approved storage ownership; avoid a second graph store, unbounded indexes, new always-running service, or an unnecessary full graph engine redesign.
