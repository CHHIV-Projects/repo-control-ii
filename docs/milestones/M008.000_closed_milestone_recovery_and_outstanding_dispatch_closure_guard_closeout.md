# Milestone M008.000 — Closed Milestone Recovery and Outstanding-Dispatch Closure Guard

## 1. Scope Completed

Implemented append-only Product Owner reopening for CLOSED milestones and a deterministic guard against closing REVIEW milestones while approved applicable Architect guidance postdates the latest closeout.

The guard is enforced by the shared lifecycle action as well as the browser workflow route. The browser rejects direct `milestone_closed` submissions so they cannot bypass guarded **Accept & Close**.

## 2. Resulting Behavior

- The Product Owner can reopen a CLOSED milestone to `REVIEW` or `IN_PROGRESS` using a CSRF-protected browser form with a required reason and explicit confirmation.
- Reopen revalidates repository key/generation, selected milestone and prompt, CLOSED phase, and event count. It appends `milestone_reopened` to the existing workflow sidecar with `phase_before=CLOSED`, reported Product Owner actor, reason, and target phase.
- Reopen does not rewrite prior acceptance/closure events, prompt, closeout, selection, or Git history, and performs no Git operation. `REVIEW` remains unauthorized for Coder implementation; `IN_PROGRESS` uses the normal bounded milestone authorization and Coder context.
- **Accept & Close** detects approved `INSTRUCTION`/`RESPONSE` dispatches for the selected repository and milestone whose `approved_at` is strictly later than the latest `closeout_submitted`.
- When such dispatches exist, the first close submission displays dispatch ID, type, approval time, and a bounded excerpt without closing. A second explicit confirmation requires an acknowledgment, a reason, and the exact current dispatch ID list; the server revalidates that list before closure. The closure event durably records the override reason and dispatch IDs.
- A later closeout clears the guard when it postdates the dispatch approval. Pending/rejected dispatches, PROMPT dispatches, and other-repository or other-milestone dispatches do not trigger it.

## 4. Architecture / Integration Notes

- Reopen uses the existing tracked workflow sidecar, event reducer, atomic persistence, selected-milestone checks, and browser mutation/CSRF patterns; no parallel state store or replacement milestone was introduced.
- The additive `milestone_reopened` event is valid only from CLOSED and only with explicit reported Product Owner approval. It reconstructs directly to `REVIEW` or `IN_PROGRESS`; repeated close/reopen cycles preserve chronology.
- Outstanding-guidance comparison is centralized with Architect dispatch readback and reused by the browser display and the lifecycle action. The close action compares timezone-aware ISO-8601 timestamps and uses strict `approved_at > latest_closeout_submitted`.
- Override evidence is stored on `milestone_closed`, avoiding a separate authority event or state store.
