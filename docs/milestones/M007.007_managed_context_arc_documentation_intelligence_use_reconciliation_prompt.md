# PART F — REPOSITORY INTELLIGENCE DECISION RULE

## 10. Intent

Repository Intelligence remains optional evidence, not mandatory ceremony.

The Coder must not silently ignore it. For implementation milestones, the Coder must make and report an explicit disposition:

- `USED` — Repository Intelligence materially informed the work;
- `NOT USED` — it was available/current but not materially useful, with a brief reason;
- `NOT AVAILABLE` — it could not be relied on because state was MISSING, STALE, FAILED, INCOMPATIBLE, or otherwise unavailable, with the observed state/reason.

The purpose is to force an intentional decision point, not to force gratuitous graph calls.

## 11. Implementation Skill

Update the canonical `repo-control-implementation` Skill so that, during implementation preflight/planning, the Coder explicitly considers Repository Intelligence when the task may benefit from structural evidence, including:
- unfamiliar code/subsystems;
- cross-module impact;
- callers/callees;
- imports/references/dependencies;
- affected tests;
- structural blast radius;
- architecture/navigation questions that deterministic graph evidence can answer.

Required behavior:
- inspect Repository Intelligence freshness/status before relying on it;
- if CURRENT and materially useful, use targeted queries rather than broad graph dumps;
- if not used, consciously record why it was unnecessary;
- if unavailable/stale, do not rely on it as current evidence and record that state;
- absence of graph evidence must not be treated as proof that no runtime relationship exists;
- source/runtime inspection remains appropriate where graph coverage is insufficient.

Do not make Repository Intelligence mandatory for documentation-only, lifecycle-only, or trivially localized work.

## 12. Validation / closeout Skill

Update the canonical `repo-control-validation-closeout` Skill so every implementation milestone closeout contains a concise Repository Intelligence disposition.

Preferred forms:

`Repository Intelligence: USED — <question(s) it materially informed>.`

`Repository Intelligence: NOT USED — <brief reason it was not materially useful>.`

`Repository Intelligence: NOT AVAILABLE — <observed state/reason>; proceeded with <other evidence>.`

When USED:
- identify the operation/question at a useful level (for example impact, callers, tests, context);
- distinguish graph evidence from source/runtime proof;
- where the existing rating workflow is available, the consuming Coder should rate materially relied-on intelligence uses according to current Repo Control procedure.

Do not manufacture use or ratings merely to satisfy closeout formatting.

## 13. Shared workflow core

Repository Intelligence is an optional deterministic evidence source, but implementation milestones must explicitly disposition its use/non-use/unavailability in closeout.

Keep detailed procedure in the Skills rather than duplicating it in the workflow core.
