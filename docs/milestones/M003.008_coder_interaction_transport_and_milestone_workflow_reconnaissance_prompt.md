# 1. Purpose

M003.001–M003.007 established the core Workflow Orchestration architecture:

```text
milestone discovery / selection
six-state lifecycle
workflow sidecars and durable events
Coder and Architect handoff packets
read-only Architect API
ChatGPT Secure MCP Tunnel
live read-only Architect evidence retrieval
governing-document reconciliation
```

The major remaining Arc 3 gap is the **Coder interaction loop**.

The Product Owner still performs too much manual transport between:

```text
Architect
Coder
Repo Control
```

M003.008 should efficiently evaluate the full remaining interaction path as one bounded reconnaissance milestone rather than splitting it into separate prompt, question, and answer milestones.

The three transport problems to solve are:

```text
1. Prompt / current instructions → Coder
2. Coder question / blocker → Architect
3. Architect answer / Product Owner-approved decision → Coder
```

The Milestone tab must also be evaluated as the durable workflow surface supporting these exchanges.

This milestone is reconnaissance only. Do not implement transport integrations in M003.008.

---

# 2. Primary Objective

Produce a concrete, implementation-ready architecture for the smallest safe mechanism that allows a Coder to:

```text
discover the active milestone
read the authoritative prompt
read current workflow state
read approved lock-ins / decisions
submit or expose meaningful questions / blockers
receive approved answers / decisions
resume implementation
```

while preserving:

```text
Product Owner authority
Architect / Coder separation
read-only Git rule for Coder
durable workflow evidence
minimal copy/paste
provider neutrality where practical
simple local-server architecture
no unnecessary cloud coupling
```

The closeout must recommend exactly one preferred architecture for implementation in M003.009, with fallback(s) documented.

# 4. Problem Statement

## 4.1 Prompt → Coder

Today, the prompt exists in the repository and Repo Control knows which milestone is active, but the Product Owner still has to point the Coder toward it or provide a packet.

Target:

```text
Product Owner selects / approves milestone
→ Coder deterministically discovers active milestone and current instructions
```

without manual prompt copy/paste.

## 4.2 Coder Question → Architect

Today:

```text
Coder asks question in VS Code chat
→ Product Owner copies question
→ Product Owner pastes question into Architect chat
```

Target:

```text
Coder raises meaningful question / blocker
→ question becomes durable milestone workflow state
→ Architect retrieves it through existing read-only MCP
```

## 4.3 Architect Answer → Coder

Today:

```text
Architect answers
→ Product Owner copies answer
→ Product Owner pastes answer into Coder chat
```

Target:

```text
Architect provides recommendation
→ Product Owner approves when required
→ answer / decision becomes durable milestone workflow state
→ Coder retrieves it
```

The Product Owner remains the approval boundary where the answer is binding.


# 6. Candidate Mechanisms to Evaluate

Evaluate at least:

## 6.1 Direct Filesystem Convention

Coder reads the active prompt, workflow sidecar, and governing rules directly, perhaps assisted by a small deterministic locator.

Assess simplicity, freshness, discoverability, multi-repo behavior, stale/wrong milestone risk, and provider portability.

## 6.2 Repo Control Read-Only CLI for Coder

Possible conceptual interface:

```text
repoctl coder-status
repoctl coder-context
repoctl coder-prompt
repoctl coder-workflow
```

or one bounded command:

```text
repoctl coder-context
```

Potential output:

```text
repository
selected milestone
phase
prompt path/content
approved lock-ins
open blocker
next authorized action
relevant standing rules / references
```

Assess whether this is the best fit because the Coder already runs locally on `henderson-server1`.

## 6.3 Generated Coder Context File / Packet

Evaluate a generated local derived artifact such as:

```text
.repo-control/coder-context.md
```

Assess freshness, generation trigger, staleness, tracked/untracked status, accidental-authority risk, and Product Owner friction.

## 6.4 Local Read-Only HTTP/API Access

Evaluate reusing the loopback Architect API or adding Coder-specific read shaping.

Assess whether a second API is actually necessary.

## 6.5 Coder MCP

Evaluate direct MCP only as a candidate. Compare standard tool ergonomics against provider coupling, configuration burden, permission expansion, and unnecessary infrastructure for a same-host Coder.

Do not prefer MCP merely because Architect MCP exists.

## 6.6 Coding-Agent Native Mechanisms

Evaluate current agent/workspace support for files, commands, tasks, instructions, skills, and MCP. Separate provider-neutral capabilities from vendor-specific ones.

# 7. Prompt → Coder Requirements

The preferred mechanism must let the Coder determine without guessing:

```text
repository identity
active milestone ID
active prompt
lifecycle phase
whether implementation is authorized
approved lock-ins
open blocking condition
next authorized action
standing Coder rules
```

The Coder must not infer active milestone from numeric order, newest filename, mtime, latest Git commit, or closeout presence.

Lifecycle behavior must be explicit:

```text
PLANNING  → do not implement
READY     → preflight / start allowed
WAITING   → stop until resolved
REVIEW    → bounded correction only if explicitly requested
CLOSED    → no new implementation under that milestone
```

---

Distinguish:

```text

escalation
```

```text

```

For a blocking question, preserve:

```text

→ question_submitted
→ WAITING
```

Compare these models:

```text
A. Product Owner records the event in Milestone tab.
B. Coder submits a narrow bounded workflow event directly.
C. Coder creates a pending event proposal requiring Product Owner approval.
D. Coder writes a structured local request artifact that Repo Control ingests.
```

Recommend one.

# 10. Product Owner Approval Boundary

Classify answer handling:

```text
Routine answer
→ clarification preserving prompt
→ answer_recorded when durability matters

Durable decision
→ resolves blocker / chooses permitted path
→ decision_recorded

Binding lock-in
→ materially refines or supersedes prompt detail
→ explicit Product Owner approval
→ lock_in_approved

Material scope change
→ objective / architecture / authority / risk / persistence /
  product behavior / validation burden changes
```

The transport must not blur these categories.

# 13. Coder Resume Model

A Coder in WAITING should deterministically know when it may resume.

Target:

```text
Coder checks current milestone state
→ sees WAITING + unresolved question
→ stops

later:

Coder checks current milestone state
→ sees answer / approved decision
→ sees implementation_resumed / IN_PROGRESS
→ resumes
```

Evaluate whether the Coder should manually query at the start of work/resume, receive a generated update, or use another simple mechanism.

Prefer explicit checks over background polling unless evidence justifies more complexity.

---

# 14. Coder Write Boundary

Recommend one model:

## Model A — Read-Only Coder Interface

Coder reads prompt/workflow/lock-ins/next action. Product Owner records workflow events.

## Model B — Narrow Direct Coder Submission

Coder may submit only bounded event types such as:

```text
question_submitted
bug_discovered
test_result_recorded
closeout_submitted
```

Coder may not approve prompts, approve lock-ins, record Product Owner decisions, resume implementation, accept/close milestone, or mutate Git.

## Model C — Staged Submission

Coder submits a pending proposal; Product Owner approves/rejects before durable workflow mutation or lifecycle transition.

Compare safety, friction, and implementation complexity and select one.

# 15. Security and Authority Analysis

For each candidate assess:

```text
who can read
who can write
what can be written
whether lifecycle can change
whether Git can change
whether paths are caller-controlled
whether shell execution exists
whether arbitrary HTTP exists
whether one repo can affect another
whether stale selection can cause wrong-project action
how Product Owner authority is preserved
```

Reject designs requiring arbitrary shell, filesystem writes, Git commands, public service exposure, broad cloud-agent machine access, silent lifecycle transitions, or silent Product Owner approval.
