## 2. Resulting Behavior

`resolve_repository_entry()` validates the requested worktree, loads the
central registry relative to the canonical Repo Control II package
installation, and requires exactly one managed entry whose canonical path
matches. It returns that entry's identity, milestone root, and document map.
Unmanaged paths, unavailable or invalid central configuration, ambiguous
mappings, missing milestone roots, invalid Git paths, and mismatched
`--milestone-root` assertions fail clearly; no synthetic `default` entry is
created.

Repository IDs and external selection/workflow/dispatch state scoping remain
unchanged. The browser service's systemd command explicitly uses
`/home/chuck/projects/repo-control-ii/ops/repositories.toml`; the Coder
resolver reads the same file from the canonical package root. Normal startup
uses:

```bash
/home/chuck/projects/repo-control-ii/.venv/bin/python -m repoctl.cli coder-context
```

The existing `--milestone-root` option remains for compatibility, but only as
an assertion that must equal the managed configuration.

## 4. Architecture / Integration Notes

registry format or project-local installation is introduced. Resolution is
shared by Coder read and bounded-write operations. All five governing-document
role mappings are returned from the central registry; the context text output
shows their references without copying document contents.

The documented absolute Python invocation avoids selecting an executable by
shell `PATH` and works from both registered worktrees. No daemon, transport,
Coder MCP, lifecycle redesign, registry mutation, or Vocab product change was
introduced.
