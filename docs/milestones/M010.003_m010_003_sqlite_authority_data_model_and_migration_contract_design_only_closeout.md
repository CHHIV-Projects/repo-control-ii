### Recommended authority model

Use one database at `<state_root>/workflow.sqlite3` (default state root `~/.local/share/repoctl`) for workflow events and their derived projections across registered repositories. Keep the repository registry, prompts, closeouts, other human-readable project documents, Git state, and the active milestone selection pointer outside the database in their existing authorities. Keep Architect dispatch metadata in its existing separate state-root ledger; do not copy it into workflow tables.

| Artifact or decision | Before cutover | During migration | After a separately approved cutover |
|---|---|---|---|
| Repository registry, prompts, closeouts, documentation, Git operations | Existing registry and Git working tree/repository | Unchanged; migration reads prompt and sidecar sources | Unchanged; SQLite does not acquire Git authority |
| Selected milestone | Existing external `selection.json` pointer | Remains the selector; verify it before and during cutover | Remains external and authoritative for selection |
| Workflow events and lifecycle projection | v1 sidecar is the sole authority | v1 remains authoritative; imported database is an offline comparison fixture only | SQLite is the sole read/write authority |
| Architect dispatches | Existing external `architect_dispatches.json` ledger | Unchanged and read-only during import | Remains separate; closure checks still consult current approved dispatches |
| Existing `*_workflow.md` files | Current v1 event ledgers | Read-only migration sources | Immutable archival evidence, explicitly non-authoritative |
| Future Markdown export | None required | None | Optional, explicit, one-way archival export with source revision/hash and a prominent non-authoritative label; never overwrite an active sidecar path or import an export back into SQLite |
| Historical custom-v2 artifacts | Non-authoritative | Excluded from automatic import | Retained as historical evidence only |

This moves current workflow events out of ordinary Git versioning. The database backup and restore path therefore becomes an operational responsibility; a future Product Owner must explicitly accept this tradeoff and decide whether optional archival exports are useful. Git remains authoritative for Git operations and repository documents, not for the future live workflow ledger.

### Minimal schema and store contract

Use standard-library `sqlite3`, SQLite `TEXT` for UTF-8 JSON and ISO-8601 UTC timestamps, `INTEGER` for sequence/revision/counters, and lowercase SHA-256 hex strings. Store the complete event object as canonical JSON; indexed columns duplicate only fields needed for identity, ordering, and lookup. Keep the schema small:

| Table | Minimum contents and constraints |
|---|---|
| `repository` | `repository_id` primary key; canonical registered root; creation time. The registered root and `make_repository_id` remain the identity authorities, not caller-supplied paths. |
| `milestone` | Composite primary key `(repository_id, milestone_id)`; repository foreign key; prompt path and current prompt SHA-256; `revision`, `event_count`, and reducer-derived `projection_json`; optional migration source sidecar path/hash and prompt-hash provenance. `revision` counts committed store transactions; it is distinct from per-event sequence and event count. |
| `workflow_event` | Composite primary key `(repository_id, milestone_id, sequence)`; unique `(repository_id, milestone_id, event_id)`; event ID, event type, original timestamp, transaction ID, full event JSON, and payload hash; foreign keys to milestone and transaction receipt. Sequences are contiguous per milestone and preserve source sidecar order. |
| `transaction_receipt` | Composite primary key `(repository_id, milestone_id, transaction_id)`; request hash, resulting revision, first/last sequence, canonical result JSON, and creation time. Store the exact result needed to answer a retry without appending again. |

The event primary key supports ordered paging; add only `(repository_id, milestone_id, event_type, sequence)` if measured query needs justify it. Use `PRAGMA application_id` and `user_version` for database/schema identity. Migrations are explicit, sequential, transactional, and performed by an operator command; service startup must reject an unknown/newer schema rather than silently initialize or downgrade it. The store exposes no event update/delete operation. A local hash/audit detects inconsistency but is not a tamper-proof external completeness anchor.

Small interface, implemented behind a lifecycle/service facade:

```text
load_snapshot(identity) -> projection, revision, event_count, compatible event view
append(identity, expected_revision, transaction_id, request_hash, events) -> receipt + snapshot
page_history(identity, snapshot_revision, after_sequence, limit <= 100) -> ordered page + cursor
audit(identity) -> SQLite checks + event validation/replay + projection comparison
backup(destination) -> standalone, verified snapshot
restore(verified_backup) -> explicit offline/operator procedure, never an automatic fallback
```

For `append`, begin with `BEGIN IMMEDIATE`; validate the exact repository/selection/milestone/prompt identity, current prompt SHA-256, expected revision, event shape, lifecycle transition, and external dispatch guard as applicable. Check an existing transaction receipt **before** rejecting a stale expected revision: the same transaction ID and same canonical request hash returns the saved receipt; the same ID with different content fails explicitly. For a new request, insert receipt and ordered events and update projection/revision/event count in one SQL transaction. Reuse the v1 reducer before commit; do not reimplement lifecycle transitions or approvals in SQL. A stale prompt, selection, or revision rejects the append with no write.

The cursor binds repository, milestone, snapshot revision/event boundary, and last sequence. Pages are ordered by sequence; invalid, stale, or mismatched cursors fail explicitly and are never silently restarted. The browser's hidden submission token must survive HTTP retry. CLI writes accept the same transaction ID for caller-requested retry; an invocation may generate one for ordinary use, but a later retry after an ambiguous result must use the original ID. No separate outbox or retry journal is introduced.

Keep the existing lifecycle reducer responsible for all 21 event types, six phases, before/after states, waiting category/reason, question and bug linkage, escalation, closeout, acceptance, closure, and reopening. The database stores actor role, `po_approved`, binding flags, and all other original fields without treating them as authenticated identities. Product Owner approval remains an explicit browser action and domain validation; atomicity is not approval. Preserve these specific rules:

- `prompt_approved`, binding lock-ins, acceptance, closure, and reopen require the existing explicit Product Owner confirmation contract.
- Resolve & Resume must resolve the active blocking question/escalation/bug condition, not an unrelated open item.
- Accept & Close and other multi-event actions validate all constituent events and persist them atomically.
- Closure still consults current approved applicable Architect dispatches; explicit override IDs and reason remain in the closure event.
- Reopen appends to history with required reason and target `REVIEW` or `IN_PROGRESS`; it never erases prior acceptance or closure.
- Context verification remains audit-only and never grants authority.

The v1 sidecar records `prompt_path` but not a historical prompt-content hash or transaction boundaries. Migration must preserve each full event object, ID, timestamp, order, and linkage, and record a hash of each source sidecar. It must not invent historical transaction boundaries. Import each sidecar's event list as one migration transaction. A prompt hash computed during import is explicitly labeled migration-observed, not a recovered event-time hash; reject missing/ambiguous sources or mark historical provenance honestly. Never claim information that v1 did not persist.

Test with the approved fixed runtime. Fail closed on missing, malformed, duplicate, or mismatched sources. No managed-state write or deployment.
4. **M010.007 — Separately approved live cutover:** only after independent acceptance and an explicit Product Owner prompt, take a complete pre-cutover backup, quiesce browser and CLI writers, inventory/hash all authoritative sidecars, import and audit all selected historical ledgers, verify the external selection pointer and current prompt identity, then switch all consumers once. Re-enable writes only after read parity and explicit operator approval. At no point may both stores accept writes.
5. **Post-cutover recovery:** before the first SQLite write, a failed cutover can return to v1 because v1 remains unchanged. After SQLite has accepted writes, never silently switch to a stale sidecar. Prefer recovery from a verified SQLite snapshot. If returning to v1 is ever necessary, it requires a separately approved, audited DB-to-v1 conversion that preserves all post-cutover events; otherwise a restore must identify the chosen snapshot and disclose likely lost activity to the Product Owner before proceeding. No automatic fallback or custom WAL repair.
6. Preserve v1 sidecars as immutable archival evidence after cutover. Retain historical custom-v2 data separately and exclude it from automatic migration.

### Runtime and operations

- Place the database on the local Linux host's local SSD, outside the repository, under a state-root directory owned by the service/CLI user (`chuck` in the current systemd unit). Restrict the directory to mode `0700` and database files to owner-only access; ensure transient `-wal` and `-shm` files inherit safe permissions. Do not place the live WAL database on NAS/network storage.
- Require the actual linked SQLite library reported by `sqlite3.sqlite_version_info` to be at least **3.51.3**. The [M010.002 closeout](./M010.002_disposable_sqlite_workflow_persistence_proof_of_concept_two_stage_gated_evaluation_closeout.md) records that the WAL-reset concurrency bug affects versions through 3.51.2 and is fixed in 3.51.3, with backports including 3.50.7 and 3.44.6. Use 3.51.3 as the conservative minimum rather than trying to infer backport status. The measured current runtime (Python 3.12.3 / SQLite 3.45.1) is below this gate and is **not eligible** for production SQLite writes. No upgrade or install is part of M010.003; later work must use an already available supported runtime or obtain separate operator approval for one.
- Pin the explicit Python interpreter/environment used by both systemd and the local CLI; at startup/report time capture `sys.executable`, Python version, and `sqlite3.sqlite_version`. Test that exact runtime. Do not assume the Python package version identifies the linked SQLite library. Fail startup before writes if the runtime is below the gate.
- Use WAL, `synchronous=FULL`, foreign keys, and a finite 10,000 ms busy timeout as the initial conservative configuration, based on the disposable POC. Keep retries bounded and reuse the exact transaction ID/request hash; after exhaustion return an explicit busy error, never a success-shaped fallback. SQLite remains a single-writer database.
- On startup verify database path/ownership, application/schema IDs, `PRAGMA quick_check`, and `foreign_key_check`. Run full store audit by explicit operator command and before/after backup or restore. If the DB is missing, corrupt, incompatible, or unexpectedly newer, fail closed; never create a blank authority or fall back to v1.
- Create backups with Python's SQLite Online Backup API into a temporary local destination, then close, run SQLite checks plus full event/projection replay, and atomically publish the standalone verified snapshot. Do not copy the live main DB, WAL, and SHM files independently. The [canonical parking lot](../context/canonical_parking_lot.md) identifies operational-state backup/restore as deferred; no workflow-specific database backup procedure is currently established. If the host's existing server/NAS backup covers the state root, use it to copy verified standalone snapshots, not the live WAL set. Confirm coverage operationally before relying on it.
- Restore only from a named verified snapshot while writers are quiesced. Recheck runtime/schema/integrity/replay, preserve the pre-restore files for diagnosis, and obtain explicit Product Owner acknowledgment of the snapshot date and possible loss of newer events. Do not treat `integrity_check` as proof that no committed history was omitted; M010.002's deliberate WAL-header-corruption result remains **FAIL, B1** and is not repaired or reclassified by this design.
- Backup cadence, retention, numeric RPO/RTO, and restore-loss acceptance remain later Product Owner choices. No mandatory NAS integration, replication, custom recovery engine, or independent external event-completeness ledger is proposed.

### Decision rationale and open Product Owner decisions

SQLite is the preferred candidate for this single-user, single-Linux-host installation: standard-library `sqlite3` provides atomic multi-row event/receipt/projection transactions, uniqueness constraints, WAL, and snapshot backup without a database service. It should reduce custom full-sidecar rewrite and persistence bookkeeping, but still requires lifecycle integration, importer, audit, history access, and operational procedures; no numeric code or maintenance savings are claimed.

Keeping improved v1 is the lowest-migration-risk fallback and preserves human-readable Git history, but retains full-ledger parsing/replacement, fixed size/event ceilings, and file-lock/write mechanics. PostgreSQL adds a server and administration burden not justified by this local single-user target. M010.002 is experimental evidence only: its parity, 10,000-event, eight-writer, paging, audit, and active-WAL backup tests do not establish production readiness. Its deliberate corrupt-WAL FAIL/B1 remains a real residual risk.

The later Product Owner must separately authorize implementation and cutover, accept the move of live workflow history outside normal Git history, approve any runtime/host change needed to meet SQLite 3.51.3, and choose backup cadence/retention/RPO/RTO and restore-loss policy. These are not blockers to this design milestone and do not authorize any future work.
