## 4. Architecture / Integration Notes

### 4.1 Observed v1 contract and failure model

- The canonical artifact is the Markdown file paired with the prompt:
  `<stem>_workflow.md`. It contains exactly one
  `repoctl-workflow-ledger:v1` marker and a fenced JSON object with
  `schema_version`, `repository_id`, `milestone_id`, `prompt_path`, and the
  ordered `events` array. The ledger binds the prompt path, not its content
  hash. The JSON event objects carry stable event IDs, timestamps, actor
  attribution, approval/binding fields, phase-before/after, and event-specific
  data.
- `lifecycle.py` bounds the complete sidecar to 5,000,000 bytes and 2,000
  events. A load reads the whole file, validates its identity and every event,
  then reduces the entire chronology to derive phase and waiting state.
  `_reduce_events` passes a growing prefix to transition validation; question
  and bug helpers also scan prior history. The effective replay cost can
  therefore be quadratic in event count for some event mixes.
- A write reads and validates the whole old ledger, constructs the complete
  next history, reduces it, renders the full Markdown/JSON sidecar, writes a
  same-directory temporary file, fsyncs that file, and atomically replaces the
  canonical path. It does not fsync the containing directory after replace.
  Multi-event browser actions are validated before the one replacement.
- All workflow read/modify/write paths use the process-local
  `STATE_ARTIFACT_LOCK` (`threading.RLock`) but do not use
  `state_artifact_lock(state_root)`, which adds cross-process `flock`.
  Independent processes can read the same old version and each atomically
  replace it; atomic replacement alone does not serialize the read/modify/write.
- A disposable nested-lock experiment also showed that simply wrapping the
  workflow path in the current `state_artifact_lock` is unsafe: nested
  acquisition in the same process blocked until a 3-second external timeout.
  The helper uses a reentrant thread lock but opens/flocks the lock directory
  again on each entry. A future fix must not introduce this deadlock through
  closure's nested dispatch inspection.
- A fresh barrier-controlled isolated fixture started with two events and
  launched two independent processes to append one decision each. It finished
  with three events and retained one of the two appends. This is a reproduced
  software defect, not evidence that production events were lost.
- `load_milestone_workflow` exposes the full `event_history` in memory.
  Browser workflow actions and close/reopen logic depend on the full sequence;
  Coder status/context derives binding lock-ins, verification and open
  conditions from it; handoff packets select decisions, blockers, corrections,
  tests, and closeouts; Architect HTTP/MCP views derive current state and event
  summaries; procedure-remap and authority/context-verification paths also
  inspect history. Some consumers independently read the canonical sidecar
  as one file with a 5 MB bound. A v2 reader therefore must replace, not
  bypass, those whole-file assumptions.
- Existing `_contained_file`/milestone identity checks and symlink rejection
  are required invariants. `state_artifact_lock` serializes other state
  artifacts across processes; any future workflow lock design must also
  specify lock ordering and nested calls (notably closeout's dispatch
  inspection) and prove that the fix does not deadlock.

### 4.2 Design comparison and selected direction

| Design | Benefits | Failure/performance properties | Decision |
|---|---|---|---|
| Increase/configure v1 count and byte caps | Smallest format and reader change; preserves today's single-file tooling. | Every read still loads and replays all events; every append rewrites all old bytes. The event-reduction path has growing-prefix scans. Any finite cap merely moves the cliff, and it does not fix concurrent lost updates or missing directory fsync. | Not a durable WF-01 solution. Keep current limits until a versioned reader/writer is separately authorized. |
| Immutable event segments plus a versioned canonical anchor/manifest | Bounded append writes, independently bounded pages, preserved event IDs, explicit completeness metadata, and a stable migration boundary. | Requires coordinated changes to all history consumers, a cross-process transaction protocol, integrity/recovery behavior, v1 compatibility, and a separately approved live cutover. Full audit/replay remains O(total history), which is necessary to independently verify the complete chronology. | Recommended design for M009.021.002, not authorized or implemented here. |
| Governed lossless archival | Could separate hot and cold storage while retaining historical retrieval. | Does not itself make appends or authority reconstruction bounded. Adds archive indexing, authentication/provenance, restoration, and old-reader semantics; risks a hidden second source of truth. No current archive contract exists. | Do not introduce as the initial implementation. Reconsider only with a separate Product Owner decision and concrete need. |

### 4.3 Proposed v2 storage and authority contract

This is the recommended design baseline for Product Owner review in
M009.021.002; it is not an implemented schema.

1. **Canonical anchor.** Keep `<stem>_workflow.md` as the sole authoritative
   pointer. Its versioned marker is `repoctl-workflow-ledger:v2`; its bounded
   manifest binds schema version, repository ID, milestone ID, prompt path and
   SHA-256, generation, total event count, segment count, last sequence/event
   ID, latest lifecycle checkpoint, terminal segment hash, and the fixed set
   of segment-catalog and projection-index root hashes. The manifest is a
   fixed-size record (target maximum 256 KiB), not a copy of event history or
   variable-size identity sets. Prompt edits or identity changes invalidate
   the binding and fail closed; an explicit approved migration/rebind is
   required.
2. **Immutable segments.** Store event files under the paired
   `<stem>_workflow_segments/` directory, named by monotonically increasing,
   zero-padded segment index. Each JSON segment binds repository/milestone/
   prompt identity, schema version, segment index, first/last global sequence,
   event count, exact serialized byte length, predecessor segment SHA-256,
   and the unchanged event objects with their original IDs and order. The
   manifest records the contiguous expected segment count and terminal hash.
   Missing, duplicate, reordered, oversized, malformed, identity-mismatched,
   or hash-mismatched segments are errors, never an empty ledger or a
   successful partial read.
3. **Per-segment bounds.** Proposed hard limits are 64 events and 256 KiB per
   segment, whichever is reached first; a valid single event must fit within
   the byte cap. Pages have a 256 KiB serialized response ceiling and return
   whole events only. These are engineering targets, to be measured with
   maximum valid event payloads before implementation. They are per-operation
   bounds, not a total-history or disk-growth cap.
4. **Ordering, complete projection, and transition equivalence.** Global
   sequence, not timestamp sorting, is authoritative; timestamps remain
   nondecreasing validated event data. V1 event records, fields, IDs and order
   are preserved without semantic rewriting. The manifest keeps a bounded
   lifecycle checkpoint and fixed-size roots for the persistent projection
   indexes. It does not embed variable-size question, bug, decision or closeout
   histories. The minimum transition dependencies observed in
   [`lifecycle.py`](../../src/repoctl/workflow/lifecycle.py#L161) are:

   | Event(s) | Existing transition/history dependency | Minimum incremental projection and exact provenance |
   |---|---|---|
   | Every event | Shape/type and field limits; unique ID; nondecreasing timestamp; `phase_before` and all derived-after fields must match the preceding prefix. | `generation`, contiguous `event_count`/last global sequence, last event ID/type/timestamp, phase/waiting category/reason; a global event-ID index with `(event_id, sequence, type, segment hash, record offset)` for duplicate detection and lookup. The event index preserves each original ID and exact segment/record location. |
   | `prompt_approved`, `implementation_started`, `review_requested`, `correction_requested` | Phase transition only; approval additionally requires reported Product Owner role/approval. | Lifecycle checkpoint. Keep the event ID in the general and decision index. A reported approval is not authenticated identity. |
   | `question_submitted`, `answer_recorded` | Questions are added while `IN_PROGRESS`; an answer is allowed only in active/waiting phase and must reference a currently open `question_submitted`. | Persistent open-question index keyed by the exact submission event ID, with its sequence and segment/record reference. Add on submission; on answer, resolve only that ID and retain the answer's `related_event_id` and answer event ID in immutable history and the relation index. |
   | `bug_discovered`, `bug_classified`, `bug_fixed` | Discovery is allowed while active/waiting; classification must point to an unclassified discovery; fix must point to a classified `in_scope`, not-yet-fixed discovery. `needs_escalation` additionally requires active phase and a reason and enters `WAITING`. | Bug-status index keyed by discovery event ID; store discovery sequence/ref, classification event ID/scope/ref if present, and fix event ID/ref if present. Maintain query indexes for unclassified discoveries and classified-in-scope/unfixed bugs. Each relation points to the exact event IDs; no classification/fix removes the source events. |
   | `escalation_opened`, `escalation_resolved`, `implementation_resumed`; waiting `question_submitted` and `bug_classified` | Opening enters `WAITING`; escalation resolution requires current escalation waiting state; resume requires a qualifying event after the most recent transition into `WAITING`. The combined action identifies that latest boundary and, for a question boundary, requires its question still be open. | Current wait boundary `(entry_event_id, sequence, event_type, category, reason)`; a `has_qualifying_resolution` bit and the first qualifying resolution `(event_id, sequence, type)` after it. Qualifiers are exactly `answer_recorded`, `decision_recorded`, `lock_in_approved`, `escalation_resolved`, and `bug_fixed`. On resume, consume/reset the current wait projection but retain the boundary/resolution relation in history. Read the open-question index when the boundary is a question. |
   | `decision_recorded`, `lock_in_approved`, `acceptance_recorded`, `prompt_approved` | Decisions/lock-ins/acceptance have phase and binding constraints; resume may use a decision or lock-in after the current wait boundary. Consumers also expose binding and recent decision history. | Ordered decision/approval index keyed by global sequence, with exact event ID/type and segment/record ref; keep a compact pointer to the most recent `po_approved` event among `prompt_approved`, `lock_in_approved`, and `acceptance_recorded`, matching `latest_authoritative_decision`. Store reported fields exactly; they do not prove actor identity. |
   | `closeout_submitted`, `milestone_closed`, `milestone_reopened` | Closeout requires `IN_PROGRESS` and an evidence path; ledger reads require every closeout reference to match the extant canonical closeout path. Closure requires `REVIEW`, binding PO fields, and an immediately preceding `acceptance_recorded`; guarded closure also inspects applicable approved dispatches after the latest closeout. Reopen requires `CLOSED`, PO fields, and a valid target/reason. | Ordered closeout index with every closeout event ID/path/sequence/ref. Keep last acceptance ID/type/sequence so closure can check adjacency in O(1); record derived `(acceptance_event_id, closure_event_id)` and `(closure_event_id, reopen_event_id)` pairs in a relation index without changing v1 events. The closeout event continues to carry the supplied dispatch IDs/reason. |
   | `test_result_recorded`, `git_disposition_recorded`, `context_verification_recorded` | Phase and event-shape checks; test source/result are required. Verification also validates its bounded payload and any expected phase/count/prompt identity supplied by its caller. | General event index and lifecycle checkpoint; verification's optimistic precondition compares generation/count and prompt hash under the writer lock. Preserve evidence fields and IDs in the source event. |

   These rows cover all currently supported event types in
   [`_EVENT_TYPES`](../../src/repoctl/workflow/lifecycle.py#L31). Event
   validation also checks the event-specific limits, closure override shape,
   actor-role fields, and v1 closeout-path binding. No projection substitutes
   an inferred event or changes the existing rule.

   **Projection representation and validation.** Store each ordered index as
   an immutable, content-addressed B+ tree with a maximum 64 KiB serialized
   page under the sibling `<stem>_workflow_indexes/` directory. The fixed-size
   v2 anchor (target maximum 256 KiB) stores only a
   constant set of roots: segment catalog, all-event-ID, open questions, bug
   status, decisions/approvals, closeouts/relations, plus lifecycle/generation
   scalars and the last full-audit generation. Tree entries contain bounded
   IDs, sequences, types, hashes and offsets, not event summaries or arbitrary
   history text. Splits add pages and tree levels, not anchor fields or a
   limit on the number of legitimate questions, bugs, decisions or closeouts.
   The manifest commits every root by SHA-256; each page commits its children
   and is checked along the lookup path. Segment membership is proved through
   a persistent segment-catalog tree keyed by index, in addition to the
   segment predecessor hash. An index reference is consumed only after its
   page proof, catalog proof, segment hash, event ID/type and exact sequence
   are checked. These hashes bind bytes to the anchor; they are not signatures
   or authenticated actor provenance.

   Under the writer lock, a transaction validates the old bounded anchor,
   relevant index paths and source-event references, checks the expected
   generation/identity, then applies each bounded new event to the checkpoint
   and copy-on-write index paths. It writes the new event segment(s), catalog
   pages and projection pages before atomically committing their roots in the
   anchor. A page split or legitimate set growth has no total-item cap. If a
   single bounded entry cannot fit a page, a page exceeds its byte limit, disk
   or an OS resource is exhausted, or any proof/reference disagrees, the
   transaction aborts before anchor replacement, reports an explicit
   fail-closed error, preserves uncommitted artifacts, and does not drop an
   unresolved ID or advance state. No arbitrary fixed upper bound on
   governance-history cardinality is introduced.

   A normal append does **not** revalidate all earlier events against the
   projection. It relies on the prior committed roots and verifies every
   page/reference it reads plus each new event and index delta. An independent
   streaming full auditor pins one manifest generation, streams the complete
   segment/catalog chain, checks count, sequence, timestamps, IDs, hashes,
   binding and every transition, rebuilds the projection into a shadow tree,
   then compares every rebuilt root with that generation's committed roots.
   It may process a bounded event batch per invocation; until the pinned
   generation completes, it reports `history_verified=false`. A matching
   audit records that exact generation and anchor hash. Consumers must
   distinguish `manifest_complete`/page integrity from `history_verified`;
   only a completed matching audit can report full-history verification. A
   page reports its generation, total count, sequence range, `has_more`, and
   page proof status. Full navigation must detect gaps/duplicates and end at
   the snapshot count; a changed anchor yields an explicit stale-cursor
   response.

   If a reader, append, or auditor finds a missing/corrupt page, mismatched
   root, gap, duplicate, or disagreement between checkpoint and replay, it
   marks that generation inconsistent and blocks authority-dependent writes
   and success-shaped reads. It preserves all files and evidence; it does not
   silently rebuild, adopt or prune. An operator investigates the exact
   anchor, roots, event/page proofs and reproducible replay, then uses an
   explicitly approved recovery to reconstruct from a fully validated event
   stream or keep the ledger blocked. Periodic/bounded-batch audit detects
   disagreement without making every ordinary append O(history). Full audit
   remains O(total events and bytes); normal transition decisions process
   only bounded new events, with O(log N) authenticated index lookups/updates
   per referenced identity—not O(1) and not a replay of all history.
5. **Explicit read completeness.** Event pages bind their opaque cursor to
   repository ID, milestone ID, prompt hash, manifest generation/hash,
   segment index, and intra-segment offset. A changed anchor yields a stale
   cursor response requiring restart. Pages include snapshot event/segment
   totals, returned sequence range, `has_more`, and a completeness/integrity
   status. A page verifies the segment it returns; it must not claim full
   history verification. Only a full audit reports `history_verified=true`.
   Missing files, sequence gaps, digest errors, or incomplete audits are
   surfaced as errors/status, never success-shaped fallbacks.
6. **Integrity claims.** SHA-256 values detect inconsistency against the
   committed anchor, catalog and index roots; they are not signatures and do
   not authenticate a user or protect against an actor who can rewrite the
   entire repository and recompute every digest. Repo Control's existing
   reported actor attribution remains unauthenticated. Any future claim of
   adversarial tamper resistance requires a separately approved external
   trust anchor.
7. **Resource behavior.** Normal append reads the fixed manifest and bounded
   current tail/projection, writes only new immutable segment(s) and
   copy-on-write index/catalog paths, and never reads or rewrites every
   historical event. A full audit/replay is O(total events and bytes); paged
   retrieval is bounded by a cursor's page ceiling plus O(log N) index
   access. Streaming limits open file descriptors to a small constant and
   avoids loading the entire archive. Total disk use grows with retained
   events and indexes; there is no pruning, rollover deletion, or automatic
   retention. ENOSPC, page-size and lock-timeout errors are explicit failures.
8. **Consumer contract.** Keep scalar workflow status and bounded recent
   events available through existing APIs, but include ledger version,
   snapshot generation/count, projection status, and explicit
   completeness/verification state. Add a bounded event-page operation and
   bounded/paged open-condition and decision history where required. No
   consumer may infer that the anchor Markdown alone contains the full
   history. Browser, Architect HTTP/MCP, Coder context/status/bootstrap,
   handoff, closeout, verification, and procedure-remap callers must be
   audited for whole-history assumptions. Preserve existing role/CSRF checks,
   active-versus-historical authority, exact event IDs, transition semantics,
   context byte bounds, and truthful omission reporting.

### 4.4 Append, recovery, migration, and rollback protocol

**Source-backed entry-point and lock map.** Current workflow reads funnel
through `load_milestone_workflow` / `_load_milestone_workflow_locked`
([`lifecycle.py`](../../src/repoctl/workflow/lifecycle.py#L616)); they currently
take only `STATE_ARTIFACT_LOCK`, revalidate selection and load the complete
sidecar. Browser milestone pages and the Architect HTTP/MCP
([`architect_contract.py`](../../src/repoctl/web/architect_contract.py#L173)),
Coder status/context, handoff
([`handoff_packets.py`](../../src/repoctl/workflow/handoff_packets.py#L149))
and procedure-remap readers consume that result or derive a bounded view from
it. These are read-only with respect to the workflow ledger. V2 readers pin
one manifest generation under the state lock, then verify immutable
pages/segments outside the lock; a complete audit names the exact pinned
generation.

Current writers are:

| Entry point | Current path/locks | Required v2 transaction behavior |
|---|---|---|
| Individual workflow event, including question/answer, bug discovery/classification/fix, test, closeout, context verification and Coder evidence | Browser event route ([`app.py`](../../src/repoctl/web/app.py#L2674)) or Coder interface ([`coder_interface.py`](../../src/repoctl/workflow/coder_interface.py#L544)) -> [`record_milestone_event`](../../src/repoctl/workflow/lifecycle.py#L1149) -> `_record_milestone_event_locked`; current lifecycle uses the process-local `STATE_ARTIFACT_LOCK`. CLI Coder commands reach the same helpers. | One transaction owner obtains the shared external state lock, rechecks selection, repository/milestone/prompt identity and expected generation, validates/appends, commits and returns only after durable anchor commit. |
| Combined Product Owner `approve_and_start`, `resolve_and_resume`, `accept_and_close` | Browser route -> [`record_milestone_action`](../../src/repoctl/workflow/lifecycle.py#L1059); current path re-enters `STATE_ARTIFACT_LOCK`. Retain the state lock across the dispatch snapshot and workflow commit; nested calls reuse the same OS lock descriptor and depth, never open/flock a second descriptor. Expected generation and current dispatch IDs are rechecked before commit. |
| Reopen / correction | Browser reopen route -> [`record_milestone_reopen`](../../src/repoctl/workflow/lifecycle.py#L1115); direct `correction_requested` uses the individual event path. | Selection and prompt identity | [`load_milestone_selection`](../../src/repoctl/workflow/milestones.py#L241) and [`save_milestone_selection`](../../src/repoctl/workflow/milestones.py#L320); current code uses `STATE_ARTIFACT_LOCK` but not the external `flock`. Web registry generation remains protected by `repository_action_lock`; validate the selected repository, milestone ID, prompt path and prompt-content hash again inside the workflow transaction. |
| Dispatch state used by closure, and other scanner/state artifacts | `workflow/architect_dispatches.py` uses `state_artifact_lock` for dispatch read/write; [`scanner/core.py`](../../src/repoctl/scanner/core.py#L26) currently takes `STATE_ARTIFACT_LOCK` then `flock`s an opened state-directory descriptor. State-artifact code may call workflow readers only in the documented forward order; it may not acquire the web lock while holding the external state lock. |
| Read-only HTTP/MCP/API/CLI views | Web/Architect contracts, handoff, Coder status/context and CLI reads ultimately load workflow state; they do not independently append lifecycle events in the inspected source. | Return manifest/projection/page completeness explicitly; no full-history claim from a bounded snapshot. Keep the same locking and snapshot-generation contract. |

The web `repository_action_lock` is an application-local `threading.RLock`,
not cross-process protection. It protects repository-registry selection and
orders web mutations. `STATE_ARTIFACT_LOCK` is also process-local. The current
`state_artifact_lock` takes that RLock and then `flock`s a directory fd; each
nested call opens another fd and attempts another `flock`. The isolated
three-second timeout reproduced why blindly nesting that helper is unsafe.
The inspected closeout path is exactly such a future nesting hazard. These
locks and `os.replace` alone do not serialize separate processes.
The source crosscheck found the web event/reopen routes acquire
`repository_action_lock` before `STATE_ARTIFACT_LOCK`; the lifecycle and
dispatch helpers do not acquire the web lock. No reverse-order acquisition
was observed in these paths. The selected hierarchy preserves that observed
order and explicitly forbids introducing the reverse edge.

**Selected lock owner and total order.** Use one exclusive per-canonical-
`state_root` external lock as the single transaction owner for workflow,
selection and state-artifact writes; do not add a competing per-milestone
flock. This deliberately serializes different milestones and scanner/dispatch
mutations sharing the same state root; same-root parallel writer throughput
is not promised. It is the simplest correct coordination with the existing
dispatch/state-artifact lock domain and avoids a cross-domain cycle.

The sole acquisition order is:

1. Web `repository_action_lock`, if the caller is a web mutation (never
   acquired from lifecycle/state-artifact code).
2. Process-local `STATE_ARTIFACT_LOCK` RLock.
3. External OS `flock(LOCK_EX)` on the canonical state-root lock file.

The external state lock remains held through selection/identity and expected
generation checks, full validation of the old v1 ledger or bounded v2
manifest/projection paths, transition validation, segment/index writes,
durability sync, anchor commit, and reconciliation of the committed result.
Closeout's dispatch-guidance read is inside this same transaction. Release is
the exact reverse order. No path may acquire the web lock after the state
RLock/flock, or acquire a workflow-specific lock (none is introduced) before
the state-root lock. Nested same-thread acquisition for the same canonical
state root reuses the already-held file descriptor and increments a
thread-local depth; it must not open another fd and call `flock` again.
Nested acquisition for a different state root is forbidden; any future
multi-root operation must acquire all canonical state roots in sorted path
order before entering a transaction. Cross-thread operations serialize on
the RLock; cross-process operations serialize on the external flock. The web
lock is never treated as cross-process protection.

Replace the current parent-directory `flock` in
[`state_artifact_lock`](../../src/repoctl/scanner/core.py#L26) with one
implementation of this lock; do not retain or acquire both lock domains.
The lock file lives at `<canonical-state-root>/.locks/state-artifacts.lock`,
where the resolved state root must be outside the repository. Create and
open each `.locks` path component relative to a verified directory fd with
no-follow semantics and mode 0700; open the file relative to that fd with
`O_CREAT|O_CLOEXEC|O_NOFOLLOW` and mode 0600, then `fstat` and reject
non-regular files, symlinks, wrong ownership or unsafe permissions. All Repo
Control processes using that canonical state root use the same inode. Never
rename or unlink the lock file during operation or cleanup.
Acquire nonblocking with a fixed 10-second deadline; on timeout, return an
explicit busy/lock-timeout error (HTTP 503 or nonzero CLI result), with no
event reported committed. The file remains after release; OS `flock` is
released by explicit unlock/close and automatically on process exit/abort.

After lock acquisition, re-read identity and manifest generation; expected
generation/count/prompt-hash mismatch is a stale-write error, never a
last-writer-wins retry. Use a stable transaction ID and event IDs across
uncertain retries: if the committed anchor includes that transaction, return
its committed result; if it does not and the previous generation remains,
retry only the same transaction; if the outcome cannot be proven from the
anchor and bounded transaction tail, block and require audit/manual
reconciliation. Lock timeout, stale generation, fsync failure and process
abort are explicit outcomes. A process abort releases the flock, but does
not prove whether an anchor replacement was durable.

**Commit protocol.**

1. Under the shared external lock, open the canonical anchor safely, validate
   its identity/generation and bounded manifest, and build the transition
   from its committed checkpoint and verified index paths. Preserve a stable
   transaction ID for retry reconciliation.
2. Create new event segment(s), segment-catalog pages and projection-index
   pages with exclusive/no-follow semantics. Validate exact event order,
   bounds, event/index references and hashes; fsync each file and its
   directory. Existing committed names are immutable and may not be
   overwritten.
3. Write the bounded anchor with the new generation, contiguous totals,
   last event identity, checkpoint and all new catalog/index roots to a
   same-directory temporary file; flush and fsync it, atomically replace the
   canonical anchor, then fsync the containing directory. The durable anchor
   replacement is the commit point. If the operation fails after replace but
   before directory fsync, outcome is uncertain; reconcile the stable
   transaction ID instead of retrying with new event IDs.
4. Return only after commit durability is established. If the process crashes
   before anchor commit, the prior anchor remains authority and staged
   segments/index pages remain visible as uncommitted artifacts. They are
   retained, not deleted or silently adopted. Detect and report orphans;
   block subsequent writes until explicit safe recovery/retry.

| Failure point | Authority after restart | Required behavior |
|---|---|---|
| Before any segment write | Old anchor and old history | Retry is safe; no event was committed. |
| Partial segment/index/temp write | Old anchor; incomplete artifact is not authority | Retain and report; never parse as committed state or silently delete. |
| Segment/index file fsync or directory fsync fails | Old anchor; new artifact durability is unknown | Do not advance anchor; preserve the artifact and require explicit reconciliation. |
| New segment/index pages durable, anchor not replaced | Old anchor; new artifacts are orphans | Preserve; fail closed for further writes until transaction is reconciled. |
| Anchor file fsync fails or atomic replace fails | Old anchor; temp is uncommitted | Preserve/report temp; do not advance state; retry only with transaction identity. |
| Anchor replaced, directory fsync succeeds | New anchor and all referenced durable segments/index pages | New transaction is committed and must be visible exactly once. |
| Anchor replaced, directory fsync fails or process dies before confirmation | Old or new name may survive depending on filesystem | Report uncertain outcome; inspect anchor/transaction ID and segment chain; no blind duplicate append. |
| Missing/corrupt/mismatched/reordered segment or altered binding | No trustworthy complete ledger | Fail closed; preserve evidence; require controlled recovery. |

Recovery never prunes. A contiguous, fully validated orphan may be presented
for explicit operator reconciliation, but must not be automatically committed
or discarded. A transaction ID permits a retry to identify an already
committed append; if its commit status cannot be established from the bounded
tail/manifest, an exceptional full scan is acceptable. Recovery paths and
failure injection are required tests.

**V1 compatibility and migration.**

- V1 remains byte-for-byte untouched until a separate PO-approved cutover.
  V1 readers keep their existing behavior and reject unknown v2 markers or
  schemas; they may not interpret v2 as an empty or truncated v1 ledger.
  V2 readers retain a strict v1 reader. Runtime capability negotiation must
  prove that the live consumer understands v2 before a writer can create a
  v2 anchor.
- Migrate only disposable fixtures in coder tests. Read and fully validate
  v1, preserve every event ID/order/field, write the v1 source image and its
  digest into the immutable v2 storage area, write/fsync all v2 segments and
  metadata, then atomically replace the canonical anchor as the final commit.
  Before that replace, v1 is authoritative; after it, v2 is authoritative.
  Interrupted pre-commit migration leaves v1 intact and v2 artifacts as
  retained orphans. Do not migrate the active M009.021.001 ledger or closed
  milestone data during implementation.
- Pre-commit rollback uses the unchanged v1 anchor. Post-commit, never
  silently switch back to an old reader. Reverse conversion is permitted only
  after a complete v2 verification and lossless projection that fits v1
  schema and size/count limits, with explicit PO approval and retained v2
  source. Once v2 contains more than v1 can represent, rollback is forward
  repair or a compatible v2 reader, not a truncated v1 restore.
- A live migration requires a separate PO operational plan: verified backup,
  dry-run inventory, reader-version check, explicit cutover approval,
  service/restart coordination by the PO if necessary, post-cutover full
  verification, rollback decision tree, and retained source. Coder performs
  none of these operations.
