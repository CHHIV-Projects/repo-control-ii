## Part A — Canonical managed-repository documentation contract

Define the **mandatory canonical current authority paths** for new Repo Control-managed work:
`docs/context/project_context.md`
`docs/context/project_architecture.md`
`docs/context/project_workflow.md`
`docs/context/coding_agent_rules.md`
`docs/context/canonical_parking_lot.md`
and `docs/milestones/` for new managed milestone prompt, workflow and closeout artifacts. Version metadata belongs INSIDE canonical documents and Git, not as suffixes in active filenames.

Define responsibilities, authority hierarchy and project-specific preservation, not just rename instructions:
- Context = present product/project state, outcomes and constraints;
- Architecture = current architectural boundaries and invariants;
- Workflow = project-specific operating rules distinct from canonical generic procedure;
- Coding agent rules = **focused repo-specific overlay** conforming to the shared overlay contract (not a 71 KB duplicate generic SOP);
- Parking lot = future/deferred items only.
Generic safe-start, lifecycle, Coder/Git boundary, verification and shared Skills belong to one canonical procedure source, not five independently diverging copies. The project-specific rules (e.g. Photo Organizer immutable Vault, Source/provenance identity, development/test/production separation, user/PO authority, NAS safety) must remain explicit, discoverable and authoritative.

Specify migration of existing version-suffixed/legacy current files to these names as a **reviewed content and reference reconciliation**: inventory existing authority and sections, map each substantive rule to the appropriate canonical document, identify contradictions/duplication, preserve original text as necessary in a historical/provenance location, repair all current incoming links and registry roles, and independently validate semantic coverage. Never silently discard, compress away or overwrite user-approved project-specific invariants. A successful filename change alone is not sufficient.

## Part B — Historical milestones and folder-structure contract

Define and document a project-agnostic onboarding inventory that finds and classifies:
- existing legacy milestone identifiers (including Photo Organizer's 12.64–12.66 application history and any deployment/housekeeping milestones), current active managed milestones, accepted prompts, closeouts, evidence/notes, archived project contexts and retained historical indices;
- current-vs-historical authority and whether items need to be moved, indexed, linked, or left untouched;
- working documentation, active prompts/sidecars/closeouts, `docs/history/**` archives, legacy directories, duplicate filenames and link dependencies.

**Preserve historical milestone IDs and provenance.** Never renumber 12.xx to `M001.xxx`, manufacture retrospective Repo Control lifecycle approval, or interpret historical documents as current authority. New Photo Organizer Repo Control milestones use `M001.xxx`. Preserve old content and traceability in a documented archive/index arrangement. Do not require new detailed milestone-history maintenance merely to onboard; an index is sufficient when useful.

Canonical folder expectations are:
`docs/context/` (the five current canonical documents),
`docs/milestones/` (new active/managed milestone artifacts),
`docs/history/` (preserved non-current milestone/document evidence when archival migration is chosen),
`.github/` (Copilot bootstrap),
repo-root `AGENTS.md` (Codex bootstrap if host evidence supports it),
`.agents/skills/` (shared procedure Skills),
`.repo-control/` (workflow core/release lock/controlled metadata).
Other application/runtime/storage/backup folders remain project-specific; do not reorganize application code or durable media/NAS paths to satisfy an administrative convention.

Respect existing `repo_history_search` / `repo_history_document` scope: configured milestone root plus supported historical archive under `docs/history/`. If legacy material is outside those scopes, produce a traceable archive/index plan with explicit migration evidence; do not silently widen arbitrary filesystem browsing or allow historical documents to override current governing authority. Validate history discovery for representative preserved legacy prompt and closeout artifacts, current/noncurrent rejection boundaries, and read-only behavior.

## Part C — Auditable onboarding stages and validation

Design the smallest supportable onboarding sequence:
1. Registry/identity verification and read-only baseline snapshot;
2. Full current-document, existing-folder, historical-artifact and reference inventory with classification and potential collisions;
3. Reviewable canonical migration plan: exact source→target mapping, completeness/authority matrix, semantic coverage, old/new path inventory, changes to Git-tracked files and central registry roles, archival/index handling, conflicts and rollback;
4. PO-approved repository-local migration performed only in a **separate authorized target-repository milestone**, with PO ownership of Git mutations and any central registry or service changes;
5. Target repository procedure status / overlay validation, separately PO-confirmed Apply, version/lock verification;
6. Cold-session Codex and Copilot bootstrap and `coder-context`/`coder-verify` audit;
7. Final repository structure, links, history access and lifecycle/Git isolation acceptance.

Specify an explicit **read-only preflight/checklist/report** that can be performed against fixtures or one registered repository as evidence, and a post-migration acceptance checklist. Implement a **bounded, deterministic, non-mutating validator/assessment utility** only if reuse of existing registry, docs/status and history contracts does not already cover these checks. No general document rewriting engine, bulk folder mover, auto migration of managed repositories, or automatic stale-history conversion. When an unsafe migration cannot be resolved deterministically, the plan must stop for PO decision.

Include explicit safety coverage for existing canonical target collisions, stale registry mapping, referential integrity, symlink and path traversal, dirty Git state, archived duplicates, preservation of unchanged original bytes or auditable diffs, and interrupted migration/recovery. Do not treat read-only assessment as authorization to relocate files.
