**Objective:** Make Repo Control discoverable and safe from a fresh agent/chat session without relying on prior conversation, while giving the Product Owner a first-class reviewable way to propagate **versioned shared-procedure releases** into managed repositories without ever overwriting repository-owned governing documents.

## 1. Product problem and acceptance intent

The Product Owner observed a fresh Vocab App chat receiving only **"Prompt ready."** without understanding Repo Control; after explicitly directing it to retrieve Coder context, it discovered the existing workflow. The Product Owner wants the equivalent of a dependable "BIOS" entrypoint for new sessions. Separately, when generic canonical procedure changes (bootstrap, workflow, Skills), the Product Owner needs to know **what changed and how each managed repository gets the approved update**, rather than running bespoke reconciliation milestones or guessing that a central edit automatically propagates.

These are related but **not identical trust/host boundaries**:

- **Host bootstrap/discovery:** An agent can consume Repo Control only if its host has loaded instructions/tools and knows the intended workspace/repository. Repo-resident `.github/copilot-instructions.md` covers supported VS Code Copilot workspace sessions when actually loaded; it does NOT automatically inject itself into new ChatGPT/other-vendor chats. M007.006 previously validated fresh/resumed **Coder** sessions in Repo Control II and Vocab using the canonical `coder-context` path. It did not prove the separate Product Owner-observed fresh-chat phrase-only behavior in every chat host.
- **Canonical generic shared procedure:** Repo Control II owns `shared/procedure/` sources and manifest/release/hash metadata. Each registered repository pins physical generated files and `.repo-control/shared-procedure.lock.toml`. Canonical release publishing **does not automatically change any managed worktree**.
- **Repository-owned governing documents:** `docs/context/project_context.md`, `project_architecture.md`, `project_workflow.md`, `coding_agent_rules.md`, `canonical_parking_lot.md` describe that repository's truth. These are NOT generic synchronized materialization outputs. `coding_agent_rules.md` remains the local overlay; no central procedure publish may replace it. A separate proposal/approval/milestone path remains appropriate for substantive updates.
- **Git boundary:** Product Owner performs all Git mutations separately. A reviewed Product Owner UI procedure Apply operation may write only explicitly approved generated procedure paths, **never stage/commit/push**, and does not grant Coders such write access.

This milestone promotes the relevant **WORKFLOW-006** parking-lot objective into authorized scope, limited to supported status/preview/review/apply/verify behavior. It does NOT automatically promote **DOC-001** into a generic governing-document editor, and does not reactivate deferred fallback-packet optimization (**WORKFLOW-002**) or Coder MCP integration (**WORKFLOW-003**).

**Target end state:**
1. The user has one compact, truthful startup/handoff recipe usable in VS Code Coder, a fresh ChatGPT Architect chat, and documented non-Copilot hosts—no claim of host-agnostic automatic injection.
2. A fresh session first establishes which Repo Control role it serves (Architect vs Coder), what managed repository/worktree is selected, and which actual tool/entrypoint it may use, then reads current authoritative context; `Prompt ready.` remains a *handoff notification*, never authorization.
3. Repo Control UI shows versioned shared-procedure CURRENT/drift for registered repositories, and a selected repository has a **Preview Update → PO Approve/Apply → Verify CURRENT → ordinary Git Review** workflow.
4. All generated files have provenance; repository-local project docs and overlays are protected, and releases never silently propagate.
5. Cross-repository production state remains untouched by implementation/tests unless the Product Owner separately performs an actual PO UI Apply after review.
