## Mandatory Git Review case — design and experiments
- Trace browser selection, server validation, staging preparation, index/worktree snapshot, token/path-byte budgets, execution and postverification, then commit preview/preparation/execution. The UI currently hardcodes data-max-paths=256, JS disables actions above it, git_actions.py uses MAX_ACTION_PATHS=256, MAX_COMMIT_PATHS=256 and MAX_ACTION_PATH_BYTES=32 KiB. Determine where a >256-path operation fails even after files are staged and how diff/timeout limits affect review. Demonstrate on 256/257, 1,103, and ideally 5,000 synthetic-path fixtures including long paths, 549 rename-like moves, deletion/new-file mixtures, dirty files and errors. Distinguish Git's native capability from Repo Control's design.
- Compare (a) a safely raised tested ceiling, (b) multiple transparent bounded operations, and (c) a single explicit PO-approved logical action with internally bounded stages and trustworthy atomicity/partial-failure semantics. Prefer a usable UI that clearly shows progress/completeness and never silently stages unrelated paths. Destructive restore must retain stronger explicit confirmation. Do not bypass exact-image integrity or misrepresent multi-command sequences as atomic. Show how committing an already reviewed large staged set will work.
- Proposed acceptance: a 1,103-path approved change set can be staged, completely reviewed and committed through Repo Control, without hidden truncation, disabling the workflow, unbounded memory/time or needing terminal Git, after separately approved implementation and tests.

## Mandatory large-document/evidence case — design and experiments
