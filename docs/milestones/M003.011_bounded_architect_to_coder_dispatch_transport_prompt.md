# 1. Purpose

Repo Control II now has a working bounded Coder → Repo Control → Architect path:

```text
Coder
→ bounded CLI event
→ Repo Control workflow state
→ Architect read-only MCP retrieval
```

The reverse direction remains incomplete.

Today, Architect → Coder communication still requires the Product Owner to act as the transport layer:

```text
Architect writes milestone prompt
→ Product Owner downloads/copies it
→ Product Owner transfers it into repository

Architect writes bounded correction or follow-up
→ Product Owner copies it
→ Product Owner pastes it to Coder

Architect reviews Coder evidence and responds
→ Product Owner manually relays the response
→ Coder continues
```

This is unnecessary operator friction.

M003.011 shall establish a bounded Repo Control transport path so the Architect may submit **proposed dispatches**, the Product Owner may review and authorize them, and the Coder may retrieve approved dispatches through the existing local Repo Control interface.

The Product Owner must remain the authority for consequences.

The architectural principle is:

```text
Architect may propose.
Product Owner authorizes.
Repo Control transports.
Coder consumes.
```

Repo Control must not give the Architect general repository-write, lifecycle, shell, or Git authority.

```text

                          │

                          │

                          │
                    coder-context
                          │
```

The initial supported Architect dispatch types shall be:

```text
PROMPT
→ proposed full milestone prompt

INSTRUCTION
→ bounded implementation follow-up, correction, clarification, or review instruction

RESPONSE
→ bounded Architect response/guidance associated with an active milestone,
  including guidance arising from Coder questions or evidence review
```

These are transport classifications.

They must not silently acquire lifecycle authority.

# 3. Authority Boundary

## 3.1 Architect May

The Architect may use narrowly scoped MCP submission tools to create pending Repo Control dispatch records.

Candidate tool surface:

```text
architect_submit_prompt_draft
architect_submit_instruction_draft
architect_submit_response_draft
```

Exact names may vary if implementation reality strongly favors another clear naming scheme, but separate narrowly typed operations are preferred over a caller-selectable generic write tool.

The Architect may also use a bounded read interface to inspect dispatch status if needed.

A read tool such as:

```text
repo_dispatches
```

is acceptable if useful.

## 3.2 Architect Must Not

Architect dispatch capability must not permit the Architect to:

```text
write arbitrary repository files
choose arbitrary filesystem paths
modify governing documents directly
modify source code
modify workflow sidecars directly
record lifecycle events as Product Owner
approve its own dispatch
select a milestone
approve a milestone prompt
start implementation
resume implementation
accept a milestone
close a milestone
run shell commands
stage Git changes
commit
push
tag
merge
rebase
reset
stash
clean
switch/checkout branches
create/delete branches
modify remotes
```

The existing read-only Architect evidence tools remain read-only.

M003.011 adds a separate **bounded proposal channel**. It does not convert the Architect MCP interface into a general write API.

# 4. Product Owner Authority

Every Architect dispatch begins as:

```text
PENDING
```

A pending dispatch has no authority over the Coder.

The Product Owner must explicitly approve it through Repo Control before it becomes available as an authorized Coder instruction.

Required conceptual states are:

```text
PENDING
APPROVED
REJECTED
```

Additional states should not be added unless implementation reality demonstrates a concrete need.

The UI should clearly distinguish:

```text
dispatch approval
```

from:

```text
milestone prompt approval
workflow lifecycle approval
```

Approving an Architect dispatch is authorization to deliver/persist that proposed content.

It must not automatically perform unrelated lifecycle transitions.

---

# 5. Dispatch Persistence

Architect submission must not directly write repository files.

Pending dispatches should be stored as Repo Control operational state outside the repository unless reconnaissance demonstrates a stronger existing mechanism.

Requirements:

- deterministic per-repository scoping;
- milestone association where applicable;
- durable enough to survive service restart;
- bounded record size;
- safe concurrent update behavior;
- atomic persistence;
- no caller-controlled arbitrary filesystem path;
- no secret material in repository artifacts;
- clear source/actor metadata;
- timestamps;
- dispatch type;
- status;
- full proposed body;
- target milestone where applicable.

Avoid introducing a database solely for this milestone.

Prefer a small, explicit operational-state mechanism consistent with existing Repo Control patterns.

# 6. PROMPT Dispatch Semantics

A `PROMPT` dispatch proposes a new milestone prompt.

Architect submission creates only a pending dispatch.

It must not immediately create or modify a file under `docs/milestones/`.

The pending prompt should contain enough validated metadata to identify:

```text
milestone ID
title
proposed prompt content
canonical destination
```

The destination must be constrained to the configured milestone documentation root.

The Architect must not supply an arbitrary filesystem path.

Preferred behavior:

```text
Architect submits prompt draft
→ Repo Control validates bounded metadata
→ pending PROMPT appears in Product Owner UI
→ Product Owner reviews
→ Product Owner chooses Approve & Save Prompt
→ Repo Control atomically creates the canonical prompt artifact
```

The resulting prompt must be constrained to a canonical form such as:

```text
docs/milestones/M003.012_<canonical_slug>_prompt.md
```

Implementation may derive the filename from validated milestone metadata or strictly validate a proposed canonical filename.

Either approach is acceptable if path containment and naming safety are deterministic.

Prompt approval must not:

```text
select the milestone
record prompt_approved
start implementation
stage the file
commit the file
push the file
```

Those remain separate current workflow operations.

M003.012 may later compress some Product Owner lifecycle actions.

---

# 7. INSTRUCTION Dispatch Semantics

An `INSTRUCTION` dispatch is bounded guidance for an already active milestone.

Examples include:

```text
update only the closeout
correct this factual statement
investigate this bounded defect
run this additional validation
adjust this implementation within approved scope
respond to Architect review findings
```

It must be associated with a repository and active milestone.

After Product Owner approval, it becomes available to the Coder through the local Repo Control interface.

It must not itself modify:

```text
workflow phase
lifecycle event ledger
repository files
Git state
```

The Coder decides how to execute the approved instruction subject to normal milestone authority and coding-agent rules.

---

# 8. RESPONSE Dispatch Semantics

A `RESPONSE` dispatch carries Architect guidance back toward the Coder.

It may optionally reference a relevant workflow event such as a Coder question.

Example:

```text
Coder question
→ Repo Control
→ Architect reads question
→ Architect submits RESPONSE draft
→ Product Owner reviews/approves
→ Coder receives approved response
```

For M003.011, dispatch approval does **not** need to automatically record `answer_recorded`, `lock_in_approved`, or `implementation_resumed`.

Those lifecycle interactions remain under the existing Product Owner workflow.

M003.012 will address human-action compression.

Do not expand M003.011 into lifecycle redesign.

# 17. Security / Containment Requirements

Architect-submitted content is untrusted input until Product Owner approval.

Validate at boundaries.

Required protections include:

- bounded request/body sizes;
- repository identity preconditions;
- milestone identity validation where applicable;
- canonical milestone-root containment for prompt materialization;
- no `..` traversal;
- no absolute caller paths;
- no symlink escape;
- no arbitrary extension;
- atomic prompt creation;
- collision handling;
- no silent overwrite of an existing prompt;
- no arbitrary shell execution;
- no Git invocation;
- no lifecycle mutation from Architect submission;
- no Product Owner impersonation;
- no generic caller-selected event injection.

A prompt materialization collision must stop safely and report clearly.

Do not overwrite an existing milestone prompt silently.

---

# 18. Concurrency / Staleness

Use existing repository/milestone precondition patterns where practical.

At minimum prevent obvious stale approval problems such as:

```text
pending prompt approved after target file already appeared
instruction approved for the wrong repository
active milestone changed before a milestone-bound dispatch is approved
duplicate approval causing duplicate side effects
```

Approval operations should be idempotent or safely reject repeated submission.

Do not build a generalized distributed transaction system.

---

# 19. Storage Bounds

Choose conservative explicit limits.

The exact values may follow existing Repo Control conventions.

At minimum bound:

```text
dispatch body size
number of retained dispatches per repository
display/retrieval result count
```

If retention cleanup is needed, use a simple deterministic policy.

Do not silently discard pending dispatches.

# 20. Tests

Add focused automated tests for at least:

### Architect submission

- valid PROMPT draft becomes PENDING;
- valid INSTRUCTION draft becomes PENDING;
- valid RESPONSE draft becomes PENDING;
- submission does not modify repository files;
- submission does not modify lifecycle state;
- invalid repository/milestone rejected;
- size bounds enforced.

### Prompt containment

- canonical prompt destination accepted;
- traversal rejected;
- absolute path rejected if caller paths are exposed at all;
- wrong extension rejected;
- symlink escape rejected where applicable;
- existing prompt collision rejected;
- Product Owner approval atomically materializes expected prompt only.

### Product Owner approval

- PENDING → APPROVED;
- PENDING → REJECTED;
- repeated approval is safe;
- rejected dispatch cannot later be silently materialized;
- dispatch approval does not trigger lifecycle transitions.

### Coder consumption

- only APPROVED applicable dispatches appear in `coder-context`;
- PENDING does not appear as authorized instruction;
- REJECTED does not appear as authorized instruction;
- repository/milestone scoping is respected.

### Architect readback

- pending/approved/rejected status available through bounded read interface;
- result limits enforced.

### Regression

- existing Architect read tools remain unchanged;
- existing Coder bounded commands remain valid;
- lifecycle tests pass;
- Git-control tests pass;
- full suite passes.

```text
.venv/bin/python -m pytest <focused tests> -q
.venv/bin/python -m pytest
git diff --check
```

# 24. Stop / Escalation Conditions

Stop and report before broadening scope if any of the following is discovered:

- the existing MCP adapter cannot support narrowly typed submission tools without materially changing the transport architecture;
- ChatGPT MCP integration cannot expose the tools without a fundamentally different service model;
- secure prompt materialization requires arbitrary filesystem authority;
- dispatch persistence requires a database or major persistence redesign;
- Product Owner approval cannot be separated from Architect submission;
- Coder consumption would require Coder MCP despite local CLI availability;
- implementation would grant Architect lifecycle or Git authority;
- existing governing architecture materially contradicts this plan in a way not resolvable by bounded documentation reconciliation;
- unexplained working-tree changes exist outside expected active milestone operational state.

Do not solve around an authority-boundary problem silently.
