## 3. Implemented Diagnosis Model

The existing read-only Git Review service now returns a concise diagnosis for a selected changed path:

- Observed human-readable status and comparison basis.
- A bounded line-count summary for each available staged/unstaged diff.
- Git-derived facts, advisory comparison signals, and explicitly unknown intent.
- A contextual question tied to the selected path and its current state.
- An explicit statement when no machine-readable active milestone/file-scope association is available.

Diagnosis does not infer authorship, intent, harmlessness, or safety. Diff line counts are evidence summaries, not semantic interpretations.

## 4. Git Facts vs Repo Control Derivations vs Unknowns

**Git facts** include the porcelain status, HEAD OID, staged index-vs-HEAD patch, unstaged worktree-vs-index patch, and bounded worktree-vs-HEAD comparison.

**Deterministic Repo Control derivations** include status explanations, added/removed text-line counts from complete bounded patches, the result of the explicit Git whitespace-ignore comparison, and action-layer consequences derived from the comparison source.

**Unknowns** remain why the path changed, who intended it, whether it is harmless, and whether the Product Owner wants to keep it. The UI states these explicitly rather than treating a signal as a verdict.

## 5. Milestone / Scope Evidence Available

The existing stage workflow stores machine-readable candidate paths in operation plans, and commit workflow stores operation evidence. These records identify Git-operation scope but have no machine-readable association with an active milestone or its approved file scope.

The application has no active-milestone/file-scope adapter or record linking those artifacts to the selected path. Git Review therefore reports scope ownership as unknown. It does not infer scope from filenames, directory names, timestamps, commit subjects, or closeout prose. No new persistence or scope parser was added.

## 6. Selected-File Diagnosis UX

The existing selected-file pane now shows:

1. File identity and Git status.
2. Diagnosis: comparison basis, HEAD, what changed, known facts, advisory signals, unavailable scope evidence, and unknown intent.
3. One contextual question based on the state (for example, whether to preserve staged content while reviewing later worktree edits).
4. Applicable preview-only choices.
5. The existing staged/unstaged diff evidence.

The accepted wide layout and navigation remain unchanged. Preview cards repeat repository, branch, HEAD source, and selected path for decision context.

## 7. Whitespace / Similarity Signal Behavior

For each complete, available text diff, Repo Control separately runs `git diff --ignore-all-space` with the same staged or unstaged comparison basis. If that comparison has no output, the UI reports that under Git's `--ignore-all-space` comparison no text difference remains. If output remains, it reports that a difference remains.

This is a narrowly defined advisory signal. It is not semantic equivalence, proof the change is only whitespace in every possible file attribute/mode sense, proof of harmlessness, or a recommendation to discard. Incomplete, undecodable, and binary ordinary diffs do not receive an equivalence conclusion.

## 8. Guided Question Behavior

The selected-file diagnosis presents one concise contextual question:

- General tracked change: whether the Product Owner intended to keep it.
- Staged plus unstaged: whether to preserve the staged version while reviewing additional worktree edits.
- Untracked file: whether it was intended to be kept for later review.
- Conflict: which conflict-resolution result is intended.

Questions are informational only. No answer is collected or persisted, and no answer triggers a Git operation.

## 9. Unstage Preview Semantics

For a supported staged path with complete diff evidence, **Preview: Unstage** explains that a future unstage would restore the index from HEAD for that path, while leaving the worktree untouched. The staged index-vs-HEAD patch shows the staged state that would cease to be staged.

The preview calls out staged-addition and staged-deletion outcomes: an addition with a present worktree path would become untracked; a staged deletion with its worktree path still absent would become an unstaged deletion. If later unstaged edits exist, the intermediate staged version may no longer remain in the worktree. This is a preview only; no unstage command is run.

## 10. Restore-Unstaged Preview Semantics

For supported tracked paths with unstaged changes, **Preview: Restore unstaged changes** explains that a future restore from the current index would affect the worktree only and preserve the index, including staged content. The current worktree-vs-index diff represents the change that could be discarded. A tracked deletion is represented by its bounded deletion patch.

No restore command is run.

## 11. Restore-to-HEAD Preview Semantics

For supported tracked paths, **Preview: Restore to HEAD** identifies the current HEAD OID and explains that a future restore-to-HEAD operation would update both index and worktree. The index-vs-HEAD patch represents staged index differences; a separately bounded worktree-vs-HEAD patch represents what the current worktree differs from the selected HEAD source by.

Possible content loss is called out. An unavailable or incomplete required comparison prevents the choice from being linked as a fully reviewable preview; direct requests also mark the preview unavailable/incomplete. No restore command is run.

## 12. Conflict / Untracked Behavior

- **Conflicted/unmerged:** Only “Leave unchanged” is offered. The page explains that ordinary two-way patches are incomplete for conflict stages and conflict recovery is limited.
- **Untracked:** The page offers “Leave unchanged” and “Keep for later review.” It does not offer unstage or tracked restore-to-HEAD semantics; no delete or `git clean` behavior is present.
- **Rename/copy:** The page does not offer ordinary single-path recovery previews because source/destination semantics are not implemented here.
- **Binary, undecodable, and unsupported/incomplete evidence:** Relevant action previews are withheld or marked unavailable; no preview is represented as fully reviewed.

## 13. Evidence Bounds / Incomplete-State Behavior

The implementation reuses R002.02 limits and applies the per-diff limit to the additional comparisons:

- Status inventory: **1 MiB**, fail closed on overflow.
- Each ordinary, whitespace-ignore, or worktree-vs-HEAD diff: **128 KiB** stdout.
- Untracked text preview: **64 KiB**.
- Git stderr: **16 KiB**.
- Git command timeout: **10 seconds**.

When a required comparison is truncated, undecodable, binary, or otherwise unavailable, the action preview is not available as a complete review. The UI labels the limitation and does not turn missing evidence into a clean/equivalent result.

## 18. Deviations from Prompt

- No scope adapter was added because inspection found no machine-readable association between active milestone identity and recorded stage/commit operation scopes. Scope ownership is explicitly reported as unknown, as required.
- Rename/copy and conflict paths receive only limited non-mutating choices rather than previews with ambiguous path/layer semantics.
- Preview routes use query parameters on the existing GET-only Git Review endpoint; they do not persist a preview plan.
- No other scope deviation.

## 19. Known Limitations

- Product Owner manual browser review of the new diagnosis and preview pane is still required; automated route/template tests do not replace that review.
- Stage/commit operation plans are not active milestone-scope evidence and are not associated with files in diagnosis.
- The whitespace signal follows Git's `--ignore-all-space` comparison and does not establish semantic equivalence.
- Binary, conflict, rename/copy, and incomplete evidence intentionally restrict choices.
- Existing application startup behavior and the deferred manual server/SSH-forward access model are unchanged.
- Preview evidence is point-in-time and must not be treated as authorization for any later action; future mutation work needs fresh state validation and its own approval contract.
