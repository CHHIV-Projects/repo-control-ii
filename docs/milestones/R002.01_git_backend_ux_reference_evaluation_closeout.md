# R002.01 — Git Backend / UX Reference Evaluation Closeout

**Status:** Evaluation complete; architecture recommendation prepared for Product Owner / Architect review  
**Mode:** Integration / tool evaluation; no implementation authorized  
**Evidence checked:** 2026-10-07; repository and installed Git 2.43.0 inspected read-only; public product documentation, source and licenses reviewed without installing software

## 1. Executive Recommendation

Retain the R002.00 direction: **Repo Control should be a browser control plane on Linux, with standard Git CLI as the repository-fact and operation authority.** Do not adopt a Git library or embed a desktop Git client now.

Use the existing subprocess approach, but keep it behind a small typed Repo Control Git-service/adapter boundary. Prefer Git's stable machine-oriented formats (`status --porcelain=v2`, NUL-delimited plumbing output, explicit `--format` for logs) over parsing human-oriented output. Keep UI and workflow policy out of Git command construction. Git state is authoritative; Repo Control adds milestone-aware explanation, decision support, approval, precondition checks, and evidence.

Implement in evidence-first steps. **R002.02 should be read-only Git inspection and change review**: show current branch/HEAD, staged and unstaged/untracked/conflicted changes, and bounded per-file diffs, with binary/large/unsupported states called out. It should not add restore, stage, commit, remote, or branch mutations. Validate the inspection and diff evidence before enabling corrective actions in a later milestone.

Use mature products as references, not dependencies:

- **GitUI** demonstrates a capable keyboard-driven Git workflow in a Linux terminal over SSH; it does not solve the browser UI or Repo Control workflow problem.
- **SourceGit**, SmartGit, and GitKraken demonstrate useful visual status/diff/history/staging interactions. GitKraken's native Linux desktop client could operate on the authoritative repository if a graphical Linux session or remote-display mechanism were provided, but that differs from the current headless-server / Windows-browser operating model.
- GitButler contributes useful change-set, branch-lane, and undo-timeline concepts, but its virtual-workspace model remains a poor fit for mixed writes with Repo Control's ordinary index-based services.
- **Looset Trace** informs guided diagnosis only. The Product Owner clarified the intended concept; no stable canonical implementation/demo was independently verified. No architecture depends on the product.

Do not attempt to infer why a file changed from Git status alone. Git can establish current content/state and history; attribution to an agent, milestone, or accidental edit requires explicit Repo Control activity evidence or a qualified human-facing explanation. A whitespace-equivalent diff is a signal, not proof of harmlessness. Restoring even one path can destroy user work, so first release must only explain and preview options.

Git is the backend for repository facts and primitives. `--porcelain`/plumbing forms are preferred for application parsing; ordinary log/graph/diff output is primarily for people and can be affected by configuration, attributes, drivers, text conversion, and Git version.

Git status is the best starting point for current facts; history, line-level review, “why”, milestone ownership, and safe-action policy are different questions.

## 4. Existing Repo Control Git Wrapper Assessment

The implementation already wraps Git CLI using argument arrays and `git -C`, rather than embedding Git internals or invoking shell strings. It validates a worktree, gets HEAD/current branch, reads tracked paths and parses porcelain v2. `workflow/git_state.py` derives classifications and reads local ahead/behind headers without fetching. Stage planning uses Git raw diff and path/filter checks, creates a deterministic plan, and stage execution revalidates scope/state. Commit planning fingerprints the staged delta; commit execution revalidates and verifies a local commit.

**Reuse:** the CLI authority, porcelain-v2 status parser, Git-state classifications, immutable plan/execution split, explicit approval, exact candidate-path verification, revalidation and evidence record.

**Gaps:** no general changed-file diff reader or history/branch browser; no Repo Control selective staging UI; stage currently selects all eligible candidates; commit planning remains coupled to full scans/snapshot matching; no diagnosis, milestone-scope association, or human explanation layer. A UI review currently names scope but does not render the full associated diff.

**Boundary recommendation:** keep a Git service/adapter that accepts a validated repository root and typed request, constructs fixed argument vectors, parses stable machine output, enforces bounds, and returns typed Git facts/diffs/errors. Application routes should call this service and add milestone policy; HTML must never formulate arbitrary Git arguments. Preserve normal Git errors and unavailable states explicitly. Avoid adding a Git library just to reorganize these existing calls.

## 5. Missing Product-Level Capability

Git already reports files, tree/index differences, refs, objects, and operation outcomes. It does not know Repo Control's active milestone, the coder's approved file scope, whether a user intended a change, or what consequences matter to this Product Owner.

Repo Control's distinct product layer should add:

- **Milestone/work scope:** compare current changes against explicit approved scope or recorded operation evidence. A path outside scope is a review prompt, not proof the edit is accidental.
- **Change diagnosis:** state observable evidence first (path/status/diff/HEAD/time if independently recorded); explain what Git does and does not establish; ask a contextual question where intent is unknown.
- **Decision support:** present bounded choices and consequences, including “leave untouched”; distinguish safe-to-inspect from safe-to-mutate; do not label a restore as safe based solely on whitespace or file age.
- **Approval:** prepare exact immutable plans; require the PO's direct confirmation before index, worktree, ref, history, or remote mutations.
- **Milestone and agent workflow:** connect approved prompt, worktree baseline, validation and closeout to changed-file evidence without treating filenames or commit subjects as authoritative ownership metadata.
- **Evidence:** record observed repository/HEAD, operation plan, reviewed scope, freshness, explicit decision, result and verification.
- **Accessible control plane:** let the PO inspect the authoritative Linux repository from a Windows browser while Git remains on the server.
- **Optional explanation:** AI may summarize evidence and propose questions/options, clearly marked as advisory, with links back to actual Git facts; it must not invent authorship or decide/execute an operation.

Do not duplicate ordinary Git buttons unless they participate in one of these workflow/evidence functions.

## 6. SmartGit UX Reference

SmartGit is a mature desktop Git client and a useful reference for **separating working-tree changes from the index**, showing diffs in context, navigating a history/branch graph, and surfacing operation-specific controls such as conflict solving, continue/abort, stash and remote actions. Its UI treats Git operations as workflows with visible state, rather than a list of command buttons.

Its graph-centered interaction, staging/review sequence, conflict solver and operation abort/undo affordances are useful inspiration. It remains a desktop application that opens a local working tree; no supported browser-hosted control surface for Repo Control's remote checkout was established here. SmartGit is commercial software with gated non-commercial eligibility/registration; use product documentation as UX reference, not a bundled dependency or copied implementation.

## 7. SourceGit UX Reference

SourceGit's current public README advertises a cross-platform desktop GUI with a visual commit graph, branch/remotes/tags/stashes/worktrees, file and revision diffs, branch comparison, file history/blame, image diff, interactive rebase, merge/rebase/reset/revert/cherry-pick, Git LFS, command logs, and forge PR creation. It requires Git 2.25.1 or later. Its Linux note says Linux is tested on Debian 12 under X11 and Wayland; this is evidence of Linux desktop support, not a server-hosted browser mode.

Useful patterns: keep graph/history and changed-file review linked; make staged/unstaged state visible; expose a file's history/blame from the file view; provide context for branch diff and image changes; display executed command/evidence. The breadth illustrates why Repo Control should not reproduce advanced operations.

The repository's license is MIT, so it is modifiable under the usual notice conditions. That does not make its Avalonia desktop UI a ready-made component for the existing Flask application, nor solve the authoritative remote repository/browser interaction. A later local-desktop tool trial could study it, but R002.01 neither installs nor selects it.

## 8. GitKraken UX Reference

GitKraken has a fully supported native Linux Desktop client and is a polished commercial reference for a graph-first navigation model: branch/commit visibility, selecting a commit to inspect its patch, inline/split diff modes, hunk/line staging, conflict tooling, remote/forge context, and undo/discard actions. It demonstrates how graph navigation can keep branch identity, commit contents and action context adjacent, and how destructive actions can be surfaced at file/hunk granularity.

In principle, that Linux client could operate directly on the authoritative repository if `henderson-server1` had a graphical Linux session or a remote-display mechanism. That is technically compatible with the repository location, but does not match the current operating model: a headless Linux server controlled from a Windows browser. GitKraken On-Premise Self-Hosted Server does not change this: it hosts GitKraken authentication, licensing, and version-management infrastructure; the full Git GUI remains the GitKraken Desktop client, not a browser-served GUI on the repository host.

The current pricing page describes the Community offer as local repositories/public remotes and a paid Pro tier for private repository remotes; additional integrations and organization features have higher tiers. Terms and entitlements may change, so no particular plan or price is assumed here. GitKraken is proprietary commercial software, not an open component or backend dependency. It remains a strong UX/functionality reference and a possible future specialist client if the operator chooses to provide graphical Linux access, but it is not currently a drop-in replacement for Repo Control's browser-served Git control surface.

Borrow interaction ideas only; do not depend on its proprietary UI, licensing service, cloud integrations, or AI features.

## 9. GitUI Server-Native Reference

GitUI is the strongest fit among the named tools for proving an SSH-accessible Linux host can provide rich Git interaction without a desktop session. Its terminal UI documents keyboard-only navigation with contextual help, status/diff, file/hunk/line stage/unstage/revert/reset, commit/amend and hooks, stash operations, branch listing and management, remote push/fetch, log search and commit-diff browsing. Its README provides Linux release binaries and describes a responsive terminal experience; its current license file is MIT.

It is a **TUI specialist tool**, not a browser frontend or Repo Control API. GitUI describes itself as beta and lists limitations, including no Git LFS/sparse repository support and interactive rebase/visual branching structure as roadmap items in the README version reviewed. Credential-helper setup is an operator concern. It should be available as an optional manual tool only if the PO separately approves installing/trying it; do not let it and Repo Control concurrently write the same index/worktree.

**Operational answer:** yes, a headless Linux server can support a meaningful Git control experience over SSH without a desktop, including much finer staging than Repo Control currently offers. That establishes an optional terminal workflow, not a replacement for the desired Windows-browser-to-Linux control plane. GitUI also validates the concept of contextual help and commands grouped around a selected file/hunk rather than exposing raw command syntax.

Sources: [GitUI official repository / README](https://github.com/gitui-org/gitui), [MIT license](https://github.com/gitui-org/gitui/blob/master/LICENSE.md).

## 11. Looset Trace Decision-Support Reference

The Product Owner clarified that **Looset Trace is not Looset Diagram**. The intended reference is the newer interactive visual Git knowledge/troubleshooting concept described as beginning with a problem or intent, asking situational questions, exposing prerequisite concepts, branching based on answers, and helping prevent unsafe or inappropriate commands.

Use only this decision-support sequence as a UX reference:

```text
observed Git state or user intent
→ contextual questions
→ explanation of relevant Git concepts
→ consequence / safety guidance
→ bounded action choices
→ Product Owner decision
```

The canonical product/implementation/demo could not be independently verified from public sources reviewed. The interaction description above comes from the Product Owner's clarification, not an independently verified product implementation. R002.01 evaluates the pattern, not undocumented features, a Git backend, a Git GUI, repository intelligence engine, or an integration dependency.

Repo Control should adopt the guided-diagnosis *principle* only where it reduces risk: show the observed state and evidence, identify missing context, ask one material question, explain consequences, offer limited options, and leave the decision to the PO. Do not add a generic questionnaire/knowledge graph before a concrete troubleshooting flow justifies it. An uncertain answer should result in “unknown / inspect more,” not a command recommendation.

## 15. Recommended Git Backend Architecture

Recommended shape:

```text
Windows browser
    ↓ SSH tunnel / approved local-only access
Repo Control web UI on henderson-server1
    ↓ typed, policy-aware service requests
Repo Control Git adapter (fixed argv, parsers, bounds, explicit errors)
    ↓ standard Git CLI
authoritative worktree / index / refs / objects on Linux
```

| Layer | Authority | Responsibility | Data crossing boundary | Replaceability |
| --- | --- | --- | --- | --- |
| Browser | No Git authority | Show facts/diffs, collect PO questions and explicit decisions | Repository-scoped requests; rendered Git facts and bounded diff | Replaceable UI, not a Git engine |
| Repo Control workflow/policy | Authority over Repo Control milestone/process state only | Scope, explanations, approvals, plans, warnings, audit evidence | Approved milestone identity/scope, reviewed facts, explicit operator decision | Replaceable/iterable; cannot override actual Git facts |
| Git adapter/service on Linux | No independent repository truth | Validate root, run fixed Git operations, parse machine output, bound output and report errors | Typed requests/results, paths, OIDs, patches/status | Replaceable implementation behind service contract |
| Standard Git + repository | **Authority for local repository state** | Index, worktree, refs, commits, local remote-tracking refs | Git repository data and CLI process I/O | Not replaced by Repo Control |
| GitHub / configured remote | Authority for hosted remote state | PRs, remote refs/status, collaboration | Explicit API/network responses with freshness/source | Separate optional connector; no implied freshness from local Git |
| Specialist client | User-operated tool, only when selected | Advanced visualization and complex Git workflows | Direct repo access; results re-read from Git afterward | Optional; never concurrent writer without an explicit boundary |
| AI explanation | No authority | Summarize evidence or ask useful context questions | Selected, provenance-bearing facts/diffs | Optional and removable; never decides/executes mutation |

The Linux process remains the only Repo Control process touching the authoritative repository. Use fixed executable/argument lists, no shell interpolation, explicit repository root, stable formats, output/time limits, and path-safe parsing. A later writer must revalidate against live Git immediately before executing and report the exact effect. Remote network operations are separate from local facts.

## 16. Git CLI vs Git Library Recommendation

**Decision: A/C mixed model — standard Git CLI for repository operations, with small Repo Control parsers/adapters; no Git library dependency now.** This is “mixed” only in the sense that Repo Control interprets output and adds workflow policy; it does not delegate different Git operations to competing engines.

- **Maturity and coverage:** use the installed canonical Git 2.43 behavior and machine formats; each of GitPython, pygit2/libgit2, and Dulwich would add an API but also a second operation/compatibility surface.
- **Semantic mismatch risk:** native CLI behavior, attributes, hooks, config, filters, and user expectations already center on Git itself. Reimplementing state/mutation semantics or relying on a library that may differ in Git edge cases risks contradictory state.
- **Maintenance:** existing code already uses direct subprocess calls; preserve that with shared typed helpers rather than introduce a wrapper dependency such as GitPython.
- **Performance:** Git subprocess startup is reasonable for bounded interactive requests and can be measured later. No current evidence says it is a bottleneck; history queries should be bounded. Optimize only against measured workload.
- **Advanced capability:** the CLI exposes the full installed Git command set. A library could offer structured object access but would not replace Repo Control's milestone and authority logic.
- **Dependency/licensing:** GitPython is BSD-licensed but still wraps/depends on Git and documents long-running-process resource limitations; pygit2 binds libgit2 and has a GPLv2 license with linking exception; Dulwich is a pure-Python Git implementation under Apache-2.0 OR GPL-2.0-or-later. None is justified as a new dependency for this application.

Reconsider a library only if a demonstrated feature cannot be provided safely/performance-acceptably by the CLI adapter and the candidate passes compatibility tests against Git behavior. Do not add one for convenience or because a GUI uses one internally.

Sources: [GitPython overview](https://gitpython.readthedocs.io/en/stable/intro.html), [pygit2 docs/license](https://www.pygit2.org/), [Dulwich docs](https://www.dulwich.io/docs/).

## 17. Repo Control Value Above Git

Repo Control should own the **decision context and accountable workflow**, not Git's mechanics:

1. Show trustworthy state from Git with repository, HEAD, branch, staged/unstaged and freshness clearly identified.
2. Associate approved work with milestones using explicit scope and activity records.
3. Explain evidence and unknowns in plain language, including questions that resolve intent.
4. Preview the exact consequences of candidate operations and isolate unrelated work.
5. Require Product Owner approval at the correct risk boundary.
6. Record what evidence was reviewed, what decision was made, and what operation/verification followed.
7. Bridge the same repository evidence into Product Owner / Architect / Coder handoffs and closeouts.

Repo Control should not offer “stage” or “restore” solely as an alternative spelling of a Git command. It should make an action safer by explaining its scope, impact, and relationship to the active work. If it cannot establish context, it should say so and request a decision rather than invent an answer.

## 21. Risks / Open Questions

- The official web app must remain local-only/SSH-forwarded under the current single-PO model; diff content can expose sensitive repository data to anyone with access to the UI.
- `git remote -v` may expose embedded credentials; redact before rendering or recording.

- Git can show the state but cannot prove why a working-tree edit exists, whether it is accidental, or whether it belongs to a milestone. Those answers need workflow records or an explicit PO decision.

- Product-specific Looset Trace claims remain unverified beyond the PO-provided description; this does not block the UX-pattern recommendation.
- SmartGit / GitKraken licensing and feature entitlements can change; recheck official current terms if ever considered for adoption.
- A separate terminal specialist (especially GitUI) must not become a concurrent Repo Control writer without an explicit mutual-exclusion/refresh contract.
