## 2. Resulting Behavior

### DISP-02 — Architect dispatch readback

`architect_dispatches.py` creates dispatches with a 64 KiB body ceiling and
stores a schema-v1 repository ledger outside the repository. Writes preserve
existing records, enforce 500 records and 40 MiB per repository, and replace a
same-directory temporary file after flushing and syncing it.

`list_dispatch_page` retains the 1–5 count ceiling and adds a 400,000-byte
serialized-record budget. Its opaque cursor binds repository identity, ledger
snapshot, filters, and newest-first offset. Pages expose total/returned counts,
`has_more`, `complete`, and a next cursor; append or status mutation invalidates
continuation. Exact-ID reads remain unchanged. HTTP and MCP expose the same
page fields and cursor; HTTP returns a conflict for a stale cursor. The Owner
page renders one byte- and count-bounded page at a time and offers continuation.

Coder context still lists every applicable approved dispatch by exact ID, but
embeds at most 64 KiB of bodies. Remaining bodies are explicitly referenced
with `coder-read-dispatch`, which rechecks active-milestone approval before
returning exact content. Copilot's 20,000-byte hook envelope retains four
references and reports the omitted count; its instruction directs the Coder
to the full context command to enumerate all IDs.

**Corrected completeness defect:** `list_outstanding_guidance` scans all
validated approved dispatches independently of display paging, so older
created records approved after closeout remain discoverable. Regression
fixtures cover 6, 100, and 500 records.

### WF-01 — Durable workflow ledger

`lifecycle.py` stores a schema-v1 complete event list in one milestone
sidecar. Reads reject unsafe/non-regular paths, missing or duplicate markers,
invalid JSON, repository/milestone/prompt mismatch, more than 2,000 events,
or a sidecar larger than 5,000,000 bytes. Accepted events are fully
shape-checked, checked for unique IDs and chronological/lifecycle consistency,
and reduced to reconstruct the current phase. Missing sidecars retain the
existing empty-ledger meaning.

Writes validate the entire prior history and proposed event(s), enforce both
caps, render the full sidecar, write and `fsync` a same-directory temporary
file, then `os.replace` it while holding the shared state-artifact lock. The
lock combines a process-local lock and `flock` on the state-root parent
directory. The containing directory is not explicitly synced after replace.
Event IDs and original payloads remain in the sidecar; no event hash chain or
multi-file manifest exists today.

All lifecycle decisions, question/bug state, closure/reopen and correction
validations depend on full-history replay. The browser workflow page renders
the latest 8 events and total event count. Coder status/context exposes the
latest 5 and total count. Architect HTTP/MCP workflow responses return up to
30 events and include total, returned, and omitted counts. Handoff packets
summarize the latest 30 and state how many earlier events were omitted. The
complete sidecar remains the durable chronology; no dedicated paginated
workflow-event API was found in the inspected surfaces.

### GIT-02 — Local Git history and branches

`git_history.py` preserves its 10-second subprocess timeout, 16 KiB stderr
cap, 1 MiB history output cap, 256 KiB local-branch inventory output cap, and
128 KiB commit/branch diff caps. Commit and per-file views fetch one extra
record beyond their bounded page, use `--skip` against a captured HEAD object,
and report `has_more`, truthful `complete`, and snapshot-bound cursors.
Stale/malformed continuations fail explicitly; byte truncation yields an
incomplete response with unknown `has_more`, rather than false completeness.
File history still validates encoded paths and uses `--follow` with a literal
pathspec.

Local branch inventory reads all local `refs/heads/` within the byte cap and
pages 20 refs at a time. Ancestry/upstream metrics are computed for only the
display page and selected branch. The selected branch's ahead/main-only commit
lists are also cursor-paginated. The browser Git Review UI exposes all of these
continuations. No Git-history MCP/API surface was added; reads remain local
only, with no fetch or remote refresh.

### Design comparisons and recommendations

**A — DISP-02 readback**

- **Recommended:** bounded cursor pagination over a stable ledger snapshot.
  Bind the cursor to repository identity, normalized filters, ledger revision,
  and deterministic record order. Return page count, snapshot total, `has_more`,
  and an explicit completion state. Any append or status mutation makes the
  snapshot cursor stale and returns an explicit restart/conflict response;
  this avoids duplicates, skipped status matches, or a stale total. Preserve
  exact-ID lookup and HTTP/MCP/UI parity. Change outstanding-guidance logic to
  operate on the full validated matching set, not a display page.
- **Alternative:** a one-shot complete-history endpoint is simpler but would
  return up to tens of MiB, conflict with the 512,000-byte response ceiling,
  and amplify the already-unbounded Owner/Coder full reads. Not recommended.
- Keep page byte limits and the existing 500/40 MiB write safeguards until a
  separate DISP-01 decision. Do not silently drop terminal records.

**B — WF-01 no-loss capacity**

- **Option 1, budget increase/configuration:** smallest migration, but
  full-ledger validation, replay, serialization, and rewrite remain
  proportional to all history, and any finite cap can still block later
  writes. Not sufficient for the prompt's durable, bounded-operation goal.
- **Option 2, versioned append-only segments:** preferred architecture
  direction, but not a safe M009.021 quick change. Preserve v1 sidecars as
  immutable legacy history; define a versioned manifest and immutable ordered
  segments with event ID/range and integrity metadata; make manifest commit
  the append commit point under the existing cross-process lock; sync files
  and containing directories; explicitly recover or fail closed on orphaned,
  missing, corrupt, or mismatched segments. Preserve every original event and
  ID, support full historical enumeration and replay without loading or
  rewriting the entire archive on each append, and never report old-reader
  partial data as complete. Specify migration rollback and service-restart
  behavior before implementation.
- **Option 3, rollover/archive:** acceptable only as governed immutable
  archival with verified references, full replay, and explicit retrieval.
  Treating archive as deletable cache or pruning event history is rejected.
- **Recommendation:** split WF-01 into a separately authorized sequential
  milestone (proposed M009.022) for detailed protocol/migration design and
  implementation. Cross-file atomicity, old-reader behavior, migration,
  corruption recovery, and complete replay require dedicated acceptance tests;
  no WF-01 migration is authorized in this phase.

**C — GIT-02 history navigation**

- **Recommended:** preserve current per-command output/time bounds and add
  stable continuation. Use a snapshot bound to repository identity, HEAD/ref
  OIDs, filter/path, and deterministic commit/ref order. Fetch one extra
  record to distinguish an exact 30-item page from exhausted history. A
  changed HEAD, branch inventory, or relevant ref returns a stale-cursor
  error. Keep local-only behavior and exact-ref/path validation.
- Page branch inventory separately and compute expensive ancestry/upstream
  metrics only for the selected branch or requested page. Preserve clear
  behavior for refs changing during navigation; do not fetch remote refs.
- Update Git Review UI and any future read API consistently. There is no
  current history-specific MCP tool to align; do not invent one without
  product approval.

**D — explicit related-risk disposition required**

- **DISP-01:** current limits are 500 records, 40 MiB, and 64 KiB/body. Keep
  refusal/no-deletion behavior unless the Product Owner separately approves
  a governed capacity/archive design. Recommend deferring that design to
  M009.022, owner Product Owner, with 500/501-record, byte-boundary,
  restart/read-integrity, and large full-read/output tests.
- **PROC-02:** observed source behavior prunes terminal transaction history
  at the 10-directory threshold; this contradicts the M009.019 statement
  that history capacity refuses new records rather than discarding. Recommend
  no code change in M009.021 and a Product Owner-owned M009.022 decision on
  whether bounded terminal retention is intentional or must become preserved,
  governed archival. Tests must prove exact retention, recovery-image
  integrity, and any approved archive/rollback semantics.
- These are recommendations only. Product Owner approval is required for
  either deferral or separately enumerated implementation.
