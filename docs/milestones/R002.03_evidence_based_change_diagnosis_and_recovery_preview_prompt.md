# 1. Product Goal

Build the next layer of the Git Review experience so the Product Owner can select a changed file and understand:

```text
What Git proves
What Repo Control can derive deterministically
What remains unknown
What action choices are relevant
What each action would change
What content could be lost
```

The desired interaction pattern is:

```text
Observed Git state
        ↓
Deterministic evidence
        ↓
Plain-language explanation
        ↓
Known vs unknown
        ↓
Relevant action choices
        ↓
Consequence preview
        ↓
Product Owner decision
```

# Part I — Diagnosis Model

## 7. Facts, Derivations, and Unknowns

The UI must explicitly distinguish three classes of information.

### A. Git Facts

Examples:

```text
file is untracked
file is modified
file has staged changes
file has unstaged changes
file is conflicted
file differs from HEAD
file differs from index
current HEAD OID
branch name
diff content
```

These are authoritative Git-derived facts.

### B. Deterministic Repo Control Derivations

Examples:

```text
diff appears whitespace-equivalent under a specific comparison
file contains only additions/removals visible in the bounded diff
path appears in explicitly recorded milestone scope
selected recovery action would replace worktree content with HEAD content
unstage would preserve worktree content but change index state
```

These must be explainable from explicit evidence.

### C. Unknown / Human-Intent Questions

Examples:

```text
why the file changed
who intended the change
whether it is accidental
whether it is harmless
whether the Product Owner still wants it
whether a whitespace-only change is safe to discard
```

These must remain explicitly unknown unless supported by actual recorded workflow evidence.

Do not collapse B or C into A.

---

## 8. Diagnosis Summary for Selected File

Extend the selected-file Git Review detail with a compact diagnosis area.

For a selected changed file, show a summary such as:

```text
Observed state
Comparison basis
What changed
What Repo Control can establish
What Repo Control cannot establish
Relevant next choices
```

Exact wording may vary.

The UI should not become a verbose report generator.

Prefer concise, high-value interpretation near the existing diff evidence.

---

## 9. Example Diagnosis Behavior

For a tracked unstaged file with only whitespace-equivalent differences, an acceptable presentation is conceptually:

```text
Observed:
Modified / unstaged

Git evidence:
Working tree differs from index.

Additional signal:
Ignoring whitespace, no remaining text difference was detected.

Known:
The current worktree content differs from the index only in whitespace under this comparison.

Unknown:
Repo Control cannot determine whether the change was intentional or safe to discard.
```

Do not say:

```text
This is accidental.
This is harmless.
You should restore it.
```

unless future explicit evidence supports such a conclusion.

# Part III — Guided Decision Support

## 13. Contextual Questions

Where intent is unknowable from repository evidence, Repo Control may present one concise contextual question.

Examples:

```text
Did you intend to keep this change?

Was this file supposed to be part of the current milestone?

Do you want the staged version preserved while removing only later unstaged edits?
```

Do not create a generic questionnaire engine.

The question must be tied to the selected file and current Git state.

No answer should cause an automatic Git mutation.

---

## 14. Looset-Trace-Inspired Interaction Principle

Use only the previously accepted decision-support concept:

```text
observed state

→ explanation

```

Do not implement:

```text
a knowledge graph
a generic Git tutor
an AI chat agent

```

R002.03 should use this pattern only where it makes the selected-file decision safer and clearer.

# Part IV — Recovery / Action Preview

## 15. Preview-Only Action Model

For applicable selected files, show relevant possible future actions.

Possible preview choices include:

```text
Leave unchanged
Unstage
Restore unstaged worktree content
Restore file to HEAD
```

Not every action applies to every Git state.

Only show choices whose semantics are understood and can be previewed accurately.

These controls must be clearly labeled as:

```text
Preview
```

not:

```text
Execute
Apply
Confirm
Restore
Unstage
```

No action may mutate Git in R002.03.

---

## 16. Leave Unchanged

Always allow the conceptual choice:

```text
Leave unchanged
```

This requires no Git operation.

The interface should not pressure the Product Owner toward cleanup merely because a file is dirty.

---

## 17. Unstage Preview

For staged content, provide a read-only preview of what a future unstage operation would mean.

The preview must explain:

```text
- index content would change;
- working-tree content would remain;
- the file would become unstaged or partially unstaged depending on later selected scope;
- no content is being changed now.
```

Where feasible, show the exact staged diff that would cease to be staged.

Do not execute:

```text
git restore --staged
git reset
```

---

## 18. Restore Unstaged Changes Preview

For a tracked file with unstaged changes, preview the consequence of restoring the working tree from the current index.

Conceptually:

```text
working tree
→ would be replaced by index content
```

The preview must make clear:

```text
which current unstaged content would be lost
whether staged content would remain
whether the file also has staged changes
```

Do not execute:

```text
git restore <path>
```

---

## 19. Restore to HEAD Preview

For a tracked file, preview the consequence of replacing the selected file with its HEAD version.

The preview must explicitly identify:

```text
HEAD OID used as source
current staged state
current unstaged state
content that would be lost from index
content that would be lost from worktree
```

If a future restore-to-HEAD action would require separate index and worktree changes, explain that accurately.

Do not oversimplify Git semantics.

Do not execute any restore command.

---

## 20. Conflicted / Unmerged Paths

Do not offer misleading ordinary restore/unstage previews for unresolved conflicts unless semantics are unambiguous and explicitly supported.

Prefer:

```text
Conflict detected.
Recovery preview is limited in this milestone.
Use conflict-specific workflow later.
```

Conflict resolution remains out of scope.

---

## 21. Untracked Files

For untracked files, avoid presenting tracked-file restore semantics.

Possible choices may be:

```text
Leave unchanged
Keep for later review
```

Do not implement delete/clean previews in this milestone unless there is a compelling existing requirement.

`git clean` is explicitly out of scope.

---

# Part V — Consequence Evidence

## 22. Exact Evidence Before Future Destructive Actions

The purpose of R002.03 is to establish the evidence contract needed before future mutations.

A recovery preview must show enough evidence that a Product Owner could later make an informed decision.

At minimum identify:

```text
repository
branch
HEAD
selected path
current Git state
comparison/source used
affected layer:
  - worktree
  - index
  - both
whether content loss would occur
which diff represents that loss
whether evidence is complete or bounded
```

---

## 23. Bounded Evidence

Reuse R002.02 bounds where appropriate.

Do not introduce unbounded diff generation.

If a preview cannot show the full consequence because evidence exceeds configured limits:

```text
mark it incomplete
do not label the action fully reviewed
```

A partial preview must never be represented as complete enough for later automatic approval.

# 42. Definition of Done

R002.03 is complete when:

```text
- selected changed files receive an evidence-based diagnosis;
- Git facts are distinguished from Repo Control derivations and unknown intent;
- whitespace-equivalent or similar signals are advisory only;
- existing explicit milestone/work-scope evidence is used only where trustworthy;
- missing scope evidence is reported as unknown rather than inferred;
- applicable future actions can be previewed without execution;
- unstage preview semantics are accurate;
- restore-unstaged preview semantics are accurate;
- restore-to-HEAD preview semantics are accurate;
- possible content loss is visible;
- conflicted/untracked cases fail closed or show appropriately limited options;
- evidence bounds remain explicit;
- no Git mutation occurs;
- no workflow-state mutation occurs from diagnosis/preview requests;
- automated tests prove read-only behavior;
- full regression suite passes;
- no Git library or external Git client is added;
- startup/access work remains deferred;
- one closeout exists under the exact required filename;
- the Product Owner has a concrete browser workflow to evaluate before any destructive action is authorized in a later milestone.
```

The core principle is:

```text
Git establishes facts
→ Repo Control explains consequences
→ Product Owner decides
→ execution remains future work
```
