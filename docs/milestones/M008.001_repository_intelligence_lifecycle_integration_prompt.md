# M008.001 — Repository Intelligence Lifecycle Integration

**Project:** Repo Control II  
**Repository:** `/home/chuck/projects/repo-control-ii`  
**Target branch:** `main` (verify live)  
**Milestone mode:** Bounded workflow/intelligence integration implementation  
**Objective:** Make a CURRENT Repository Intelligence graph the normal automatic starting baseline for an authorized milestone, permit a Coder to refresh only the same configured derived graph during authorized work when useful, simplify the manual Product Owner graph control, and publish the corresponding central shared-procedure update.

## 1. Background and product intent

M004.002 established bounded, replaceable-provider Graphify-backed structural intelligence, source-identity/freshness checks, shared Architect/Coder queries, external graph generations, and value reporting. It intentionally did **not** give Coders build/refresh authority. The current implementation Skill expressly says never to refresh without Product Owner authority.

Recent Vocab M002.001–M002.003 closeouts show three valid patterns:
- graph used early, then became STALE after source edits and potentially useful follow-up intelligence was unavailable;
- graph became STALE but direct evidence already answered the remaining questions, so refresh was not needed;
- CURRENT targeted intelligence contributed useful impact evidence, supplemented by source/browser validation.

The Product Owner has decided that graph maintenance should not require repeated approval interrupts. A graph is **derived repository-intelligence state**, not source/Git/lifecycle/project authority. A Coder should be able to restore the *existing configured* derived graph during an authorized milestone without being allowed to change the intelligence producer or configuration.

Desired routine:
```text
Product Owner: Approve & Start
→ Repo Control establishes/verifies a CURRENT graph for a graph-enabled repo
→ implementation begins with current structural evidence available
→ authorized source edits may make graph STALE
→ Coder determines whether more structural evidence would materially help
→ if yes: bounded same-configuration refresh, then targeted query and source verification
→ if no: continue with direct evidence, explain why refresh was unnecessary
→ closeout reports use and refresh decisions
```
**No extra checkbox** in the ordinary lifecycle or graph-build workflow. The manual **Build / Refresh Graph** button remains available.

## 2. Binding scope/authority decisions

1. **Automatic baseline:** Integrate an intelligence freshness check and, when necessary, an ordinary fixed-configuration build/refresh into Product Owner **Approve & Start**, so configured, operational graph-enabled repositories enter implementation with a verified CURRENT graph. If already CURRENT for the exact source identity, do not rebuild ceremonially.
2. **Manual control:** Retain the existing Product Owner manual Build / Refresh Graph action on the Intelligence Value page, but remove its redundant separate PO-approval checkbox. The deliberate button remains an authorization action protected by CSRF, repository identity/generation, selection revalidation, and appropriate server validation.
3. **Coder capability:** Add the smallest **bounded, explicit Coder refresh operation**, preferably through the existing co-located local CLI/service architecture. Only for the currently resolved managed repository and an authorized `IN_PROGRESS` milestone; never while PLANNING, READY, WAITING, REVIEW, or CLOSED. It may only rebuild the *existing configured* graph with existing provider/runtime/schema/source inclusion and exclusion policy/bounds. It cannot supply arbitrary paths, targets, provider options, shell commands, configuration, or repo selection.
4. **Coder judgment:** Refresh only when the graph is STALE/MISSING/FAILED or otherwise non-CURRENT **and** further structural evidence would materially help the remaining authorized work. Do not rebuild every time a file changes. If CURRENT, the command must be a non-destructive no-op or a clearly reported CURRENT result; no unnecessary rebuild.
5. **No new authority:** Neither automatic initialization nor Coder refresh grants Coder/Architect Git, lifecycle, config, repository-registration, provider-version, graph-schema, model, or source mutation authority. It may write only ordinary, external, bounded **derived intelligence state** using the existing publisher. The existing Product Owner's authority over graph configuration and runtime changes remains intact.
6. **Provenance/evidence:** Return and record a bounded receipt for each attempted actual refresh, including actor path (PO lifecycle, PO manual, or authorized Coder), selected repository ID, active milestone where applicable, triggering freshness, action/no-op, new generation/source identity, final freshness, elapsed/error outcome, and whether it completed. Do not record raw source text, query bodies, secrets, or misleading token-savings claims. Reuse current intelligence measurement/event mechanisms where suitable rather than inventing new canonical state.
7. **Closeout disposition:** Shared procedure must tell the Coder to report Repository Intelligence as USED / NOT USED / NOT AVAILABLE, whether a graph refresh was attempted, whether it was needed, outcome, and why it was/wasn't performed. Structural query usefulness and refresh maintenance should be distinguishable; do not count refreshes as evidence queries.
8. **Canonical procedure:** Generic refresh policy belongs under Repo Control II `shared/procedure/`, not solely in Vocab or Repo Control II's local overlay. Implement the real capability first/alongside the instructions; publish the next appropriately versioned release with correct hashes and guarded local materialization. Managed repositories reconcile individually under later explicit Product Owner authorization; no Vocab file or lifecycle mutation in this milestone.

## 4. Automatic graph-current baseline at Approve & Start

Implement on the existing Product Owner lifecycle start boundary, not in a background scheduler and not on every page view, status poll, Architect query, or Coder context read.

Requirements:
- Reuse the registered, fixed provider and existing freshness/source identity/build path; do not create a parallel graph store or custom scanner.
- For graph-enabled supported repositories, test CURRENT first; rebuild only when necessary; verify resulting CURRENT against the same selected repository and current source identity before authorizing implementation start.
- Preserve distinct ordered `prompt_approved` and `implementation_started` events and existing atomic sidecar rules. Avoid a state where a partial lifecycle start is incorrectly reported as successful. **If a required build fails or returns non-CURRENT, report a bounded actionable error and do not partially advance PLANNING/READY into IN_PROGRESS.** An external derived graph generation may have been attempted, but that is not an authorized lifecycle transition.
- Revalidate repository key/generation, selected milestone, prompt identity, expected lifecycle phase/event count, source identity, and any relevant concurrency preconditions at the correct boundaries. Reuse existing build locks, timeouts, staging/publication safety, and bounds; do not hold a lifecycle lock in a way that deadlocks intelligence.
- Repositories where intelligence is genuinely not configured/supported must preserve the normal lifecycle start path and clearly report NOT AVAILABLE rather than pretending CURRENT or requiring an unrelated tool installation. Distinguish those from a configured provider's failed build. Do not introduce a general “skip current graph” checkbox; if an exceptional override seems necessary, STOP and ask instead of silently bypassing the policy.
- Existing READY → Start implementation should have consistent graph preparation where appropriate. Do not change other lifecycle transitions or automatically rebuild at resume/closeout.
- Do not rebuild solely because tracked documentation or workflow sidecar changed when the existing source-identity scope excludes them.

## 5. Bounded Coder refresh

Prefer a focused operation such as `repoctl coder-intelligence-refresh` (final name based on existing CLI conventions) rather than granting arbitrary build options or the existing Product Owner endpoint unchanged.

- Only the same centrally registered repository identity that the Coder workspace resolves; bind to active milestone selection and verify `IN_PROGRESS` authorization and no unresolved blocking condition immediately before build and publication. Do not let a stale authorization or repository switch publish under an unintended identity.
- Fixed configured graph only. No caller-controlled graph producer, version, model, options, include/exclude, source root, output path, target repository, or limits.
- Reuse the existing provider, source-scope snapshot checks, generation lock, atomic publication, current/previous generation retention, failure states, and bounded worker/environment/network safeguards.
- Bounded, synchronous status/receipt; handle contention, already-CURRENT, source changing during rebuild, provider failure, timeouts, and interrupted builds explicitly. No automatic unbounded retry loop.
- Refuse unauthorized phases, unregistered/cross-selected repository, incorrect working directory, or missing relevant prerequisites. Refusal must not alter Git, lifecycle or source files.
- After refresh, Coder must still use source/runtime verification when graph coverage is insufficient, especially Flask/templates/browser behavior. CURRENT means source-matched static graph, not guaranteed runtime truth.
- Refresh can happen more than once in a long authorized milestone **when justified**; it is not a standing permission to alter graph configuration or perform repetitive speculative builds.
