### 4.3 Recommendation and reversal conditions

**Recommend SQLite as the next disposable evaluation target, not as the already-approved production answer.** It is the best fit to evaluate first for one Linux host, one user, local SSD, several local processes, and a preference for fewer moving parts. It provides relational uniqueness, transactions, indexed reads and a standard backup API without a separate database daemon. WAL mode allows readers alongside a writer, but still has one writer at a time and requires all processes to be on the same host. The current v1 lock already serializes writes, so a SQLite single-writer constraint is not, by itself, evidence of unacceptable capacity.

Do not adopt SQLite until a fixture-only proof of concept demonstrates exact event/projection parity, crash-safe idempotency, multi-process behavior, snapshot pagination, and successful backup/restore under an agreed operating envelope. If it does not meet PO-selected latency, resource, or restore objectives, keep v1 authoritative while comparing alternatives. Retain v1 as the preferred fallback if actual growth never approaches its caps and the PO values Git-visible ledger simplicity over database features. Reconsider PostgreSQL only if measured local concurrency or operational requirements justify another service or if a new multi-user/cross-host requirement is explicitly approved. Do not revive custom v2 merely as a fallback; its known partial-write defect and maintenance burden require a separate decision and a complete repair/validation case.

### 4.4 Conceptual SQLite model (not a schema migration)

Use one local database per Repo Control installation, keyed by `repository_id`, rather than one database per milestone. The proposed location is beneath the existing external state root on local SSD; exact path, permissions and backup ownership require PO approval.

- `repository`: stable repository ID, configured root/key, and a database-instance identity.
- `milestone`: repository ID, milestone ID, prompt path and current prompt SHA-256; current revision, phase, waiting state, and projection hash. A repository/milestone pair is unique.
- `workflow_event`: repository ID, milestone ID, contiguous sequence, immutable source `event_id`, original timestamp, event type, exact structured payload JSON, payload SHA-256, source/provenance metadata, and unique transaction ID. Enforce unique `(repository_id, milestone_id, sequence)`, unique `(repository_id, event_id)`, and appropriate transaction uniqueness. Do not rewrite imported IDs, timestamps, event types, or payload fields.
- `workflow_transaction`: idempotency/transaction ID, request hash, expected prior revision, resulting revision, ordered event-ID range, and stored result needed to answer a retry after an ambiguous commit. Reusing an ID with a different request hash is a hard conflict.
- `milestone_projection`: transactionally maintained current derived fields and revision. It is a cache, not independent authority; rebuild it from `workflow_event` and compare at audit.
- Indexes: `(repository_id, milestone_id, sequence)` for paging/replay; `(repository_id, event_id)` for identity; `(repository_id, milestone_id, event_type, sequence)` for history filters; and `(repository_id, milestone_id, related_event_id, event_type)` for questions, bugs, decisions and escalation linkage.
- Optional `active_selection`: repository ID, milestone ID, prompt hash and selection generation. If adopted, move selection authority into the database in the same cutover; do not leave two writers or treat a pointer file and DB row as competing truth. Keeping an external bootstrap pointer is also possible, but its exact authority must be decided before implementation.

Within one `BEGIN IMMEDIATE` transaction, check current selection/prompt identity and expected revision; verify/insert the idempotency record; validate the full incoming domain transition; insert the exact events in order; update the projection and revision; then commit. A retry with an unknown commit outcome looks up the same transaction ID and returns the stored result. Bounded `SQLITE_BUSY` handling must return a visible error; it must not silently skip an event or fall back to v1. SQL uniqueness and triggers are defense-in-depth, not a replacement for the existing versioned lifecycle reducer.

### 4.5 Audit, Markdown, and source-of-truth boundary

Before any cutover, v1 remains the only writable/current workflow authority. A future database must not be dual-written with v1. A migration rehearsal preserves source event IDs, order, timestamps, JSON content, prompt identity and a SHA-256 of each original sidecar; current v1 has no per-event hashes, so migration must identify which hashes are newly computed and which provenance hashes cover the original source file.

For the DB-backed mode, the complete audit independently replays all source events, verifies event IDs/sequences/payload hashes and transaction boundaries, checks the repository/milestone/prompt identity, recomputes the projection, and compares it with the stored projection and a snapshot hash. `PRAGMA integrity_check` is an additional physical consistency check, not a substitute for application replay or source provenance. A local hash chain can detect accidental reordering/corruption; without an externally protected checkpoint or signature, it cannot prove that a privileged local operator did not rewrite both data and hashes.

Prompts and closeouts remain human-authored, Git-visible contract/report documents. If the PO approves a database as the source of workflow truth, the workflow Markdown becomes a **generated, read-only audit export**, not a second writable ledger. Include database-instance ID, repository/milestone/prompt identity, revision and event sequence range, event/payload hashes, projection hash and export timestamp. Repo Control readers write only to the DB; export verification compares the document against the DB. Historical v1 sidecars remain preserved as migration provenance, not as a second current event source. Existing Git-visible review remains useful while having an unambiguous authority label.

### 4.6 Failure model and backup/recovery outline

| Failure | Required future behavior |
|---|---|
| Process interruption before transaction commit | SQLite rollback leaves the prior revision. On reopen, audit reports the old revision; no partial event/projection rows. |
| Commit succeeds but response is lost | Retry with the identical transaction ID/request hash returns the stored prior result and does not duplicate events. |
| Concurrent writers or stale browser/CLI | Check expected revision and prompt hash inside the write transaction. Serialize SQLite writers; after a bounded busy wait, return an explicit retryable error. Stale revision returns conflict without mutation. |
| Power loss / storage errors | Select and verify WAL/synchronous settings on the target local filesystem; test process kill and controlled I/O failure. Do not promise power-loss durability beyond what the OS, filesystem, device cache, and fsync behavior provide. |
| Missing/corrupt WAL, malformed DB, or failed integrity check | Fail closed; preserve the DB and any WAL/SHM evidence for diagnosis. Do not unlink WAL files, create an empty DB, or silently fall back to sidecar writes. Restore a verified backup or perform an explicitly approved forward repair. |
| Disk full, permission failure, busy timeout, or DB unavailable | Surface a specific error and leave source events/projection consistent. Never report success with missing writes. |
| Backup/restore | Use SQLite's Online Backup API (or an equivalent database-aware snapshot) to a temporary local destination. Verify the closed snapshot, hash it, then copy to Synology and verify the copy. Never copy a live WAL-mode `.db` file alone. Restore to a disposable local directory; run integrity check and full event/projection replay before accepting it. Set cadence, retention, RPO/RTO and restore drill interval by PO decision. |
| Cross-version cutover | Gate DB schema/event writer compatibility for both service and local CLI. If versions disagree or DB state is inconsistent with the approved cutover generation, fail closed. No auto-select between DB and sidecars. |

The active database must remain on the host's local SSD, not on Synology, SMB or NFS. Synology is a backup destination only. A copy to NAS is not a backup until a restore drill passes. The host can still be unavailable after a failure; PO must choose the acceptable RPO/RTO and number of retained, verified generations. Keep backups private and do not expose a DB port externally.

SQLite references consulted: [WAL mode and constraints](https://sqlite.org/wal.html), [transactions](https://sqlite.org/lang_transaction.html), [online backup API](https://sqlite.org/backup.html), and [PRAGMA documentation](https://sqlite.org/pragma.html#pragma_synchronous). PostgreSQL references: [concurrency control](https://www.postgresql.org/docs/current/mvcc.html) and [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html).

### 4.7 Authority transition outline

1. M010.002, if separately approved, tests only disposable fixtures and a temporary local database. No managed workflow path, selected sidecar, live service, or production state is read for writes.
2. A later PO-approved migration milestone creates an offline importer and independent parity audit. It preserves all v1 source payloads, event IDs, timestamps, sequence/order, prompt hashes, closeout paths, PO-reported binding fields, unresolved conditions and source file hashes. It does not reinterpret actor attribution as authenticated identity.
3. Before cutover, quiesce all old service/CLI writers, create and verify a restorable backup of the v1 source, capture the exact registry/selection/prompt identities, import once, and compare event and projection results. The transition has one writer authority at a time; no dual-write period.
4. Switch all consumers in a reviewed release: browser lifecycle, Coder CLI/context/status/tests/closeout, handoff packets, Architect read APIs/MCP, history, close/reopen guards, context verification, and operational tooling. Version mismatches, missing DB, stale selection, and parity failures stop writes and reads that claim current authority.
5. After the first DB-authoritative event, do not roll back by simply reactivating stale v1 sidecars. Either forward-repair from verified DB history or perform a separately approved reverse export that preserves every new event and proves parity. Git staging, service restart/deployment, live migration, rollback, and final acceptance remain Product Owner/operator actions under their own authorization.

## 10. Recommended Next Milestone

### Candidate M010.002 — Disposable SQLite proof of concept (proposal only)

**Status: proposed, not selected, approved, or authorized.** The Product Owner must create/approve the exact milestone prompt and start it separately before any POC work.

**Objective:** test whether SQLite can preserve exact v1 event and projection semantics while safely supporting histories beyond the current 2,000-event/5,000,000-byte limits, concurrent local processes, idempotent retries, stable paging, and recoverable backups.

**Scope and boundaries:**

- Use only temporary fixture directories and a disposable SQLite database outside all selected/managed repositories and state roots.
- Replay a frozen set of v1 fixtures containing every event type and lifecycle edge, then add separate fixtures of 2,001 events and more than 5,000,000 serialized source bytes.
- Include a 10,000-event fixture with fixed IDs, payloads, order, timestamps, and batch/transaction shape. Compare with historical v2 measurements only if the historical fixture and transaction shape are shown equivalent; otherwise mark the comparison non-equivalent and make no head-to-head performance claim.
- Run concurrent writer processes against the same disposable database; a proposed characterization workload is eight processes submitting 250 one-event transactions each. Also characterize the 10,000-event fixture using a separately fixed batched-import pattern.
- Test keyset pages of 100 events while new writes occur, transaction interruption at each commit boundary, same-ID retry after ambiguous commit, stale-revision rejection, audit/projection reconstruction, corruption detection, and database-aware backup/restore while the source remains active.
- Measure database, WAL and SHM bytes; transaction and page p50/p95/max latency; busy wait/errors; RSS; file descriptors; total elapsed time; and backup/restore duration. State workload and transaction shape with every number.
- Do not touch production state, current v1 sidecars, service deployments, or external database services. Do not repair or adopt custom v2.

**Exact functional acceptance criteria proposed:**

1. Zero event-ID, timestamp, type, field-content, order, prompt-identity, phase, waiting-state, question/bug/escalation-linkage, or binding-decision parity mismatches across every fixture.
2. Zero lost or duplicate events in the eight-process workload. Each acknowledged transaction is present once; any request rejected after the bounded busy policy is an explicit error and is not reported as success.
3. At every injected pre-commit interruption, the result is exactly the old revision; at every post-commit/before-response interruption, the result is exactly the complete new revision. No partial event batch or projection is observable.
4. Retrying the same transaction ID and same request hash adds zero events and returns the same saved result. Reusing the transaction ID with a different hash is rejected without mutation.
5. A stale expected revision or prompt hash is rejected with zero database changes.
6. For 100-event keyset pages, the fixed snapshot contains every expected event exactly once. Snapshot invalidation is an explicit result, not a silently changing page sequence.
7. Full replay produces the expected projection and matches the stored projection. A deliberately modified payload, sequence, hash, transaction boundary, or projection is detected and reported invalid.
8. A concurrent database-aware backup restores to a disposable database for which SQLite integrity checking succeeds and complete event/projection audit matches the snapshot revision and hashes.
9. No test creates a listener on a non-loopback/external interface or writes to a managed workflow state path.

**Thresholds that require a PO decision before claiming operational acceptance:** maximum p95 and worst-case append latency under the agreed transaction shape; acceptable busy wait and retry count; maximum database/WAL bytes, RSS and file descriptors; backup cadence, retention and restore interval; RPO/RTO; and the maximum expected concurrent writer count. M010.002 may report measurements before these limits are chosen, but must label operational acceptance **undetermined** rather than inventing thresholds.
