## Goal

Decide the appropriate Git Control architecture for Repo Control II.

Specifically determine whether Repo Control II should use:

```text
A. a custom Repo Control Git UI based on the inherited Flask shell;

B. GitButler as the primary graphical Git UI with Repo Control integrating around it;

C. a split/hybrid model in which Repo Control owns selected workflow/control-plane functions while GitButler or another mature Git UI owns advanced Git visualization/manipulation;

D. another clearly superior option discovered during evaluation.
```

Also define the intended Product Owner mutation-authority contract for Git actions performed through Repo Control.

The closeout must end with one recommended direction, not merely a feature comparison.

---

## Background

R001.00 established that the inherited Repo Control implementation is not the Repo Control II architecture, but it contains useful Git-control foundations.

R001.00 found the following strong salvage candidates:

```text
- deterministic Git state parsing;
- staged / unstaged / untracked / conflicted classification;
- immutable stage and commit plans;
- exact-scope operation planning;
- explicit approval before execution;
- precondition revalidation;
- execution verification;
- audit/evidence artifacts;
- strong Git regression tests.
```

R001.00 also found important limitations:

```text
- Git status is coupled to the inherited scanner/snapshot machinery;
- commit preparation is snapshot-gated;
- staging is currently --all rather than Product Owner-selected paths;
- the UI does not provide file-level diff review;
- the UI lacks branch/history visualization;
- there is no general remote/GitHub awareness;
- browser POST routes can execute stage and commit actions;
- the inherited README incorrectly states those browser routes do not mutate Git;
- the current local UI relies on loopback access + CSRF rather than a distinct Product Owner identity;
- Flask is not an architecturally locked framework choice.
```

R001.00 recommended evaluating the Git UI/tool fit and authority model before substantive custom Git UI coding.

That recommendation is the basis of R002.00.

# Part II — Mutation Authority Model

## 3. Define Product Owner Git Authority

The Repo Control II architecture requires the Product Owner to own consequential Git mutations.

Determine what this should mean in practice for graphical Git control.

Evaluate at least these actions:

```text
stage
unstage
commit
branch create
branch switch
merge
rebase
tag
push
pull
fetch
reset
stash
clean
conflict resolution
```

For each meaningful action, classify:

```text
read-only information
safe direct Product Owner action
requires explicit confirmation
requires preview/review evidence
should remain outside Repo Control initially
should never be delegated to a coding agent
```

The key distinction is:

```text
Product Owner clicking an explicit approved action in Repo Control
≠
coding agent independently deciding to mutate Git
```

Do not treat all browser-triggered Git mutation as inherently prohibited.

The issue is authority, visibility, scope, and safety.

## 8. Evaluate Option C — Hybrid / Split Architecture

```text
Repo Control owns:
- project/workflow state
- milestone state
- selected Git facts
- Product Owner action orchestration
- integration with Architect/Coder
- review package assembly
- policy/authority boundaries

GitButler or another mature Git tool owns:
- advanced branch visualization
- history graph
- complex branch manipulation
```

```text

```
