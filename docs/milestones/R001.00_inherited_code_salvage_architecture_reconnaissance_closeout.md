## 1. Executive Conclusion

The inherited implementation contains a useful, well-tested Git status and guarded local stage/commit foundation, but it is not a Repo Control II architecture. The strongest salvage candidates are deterministic Git-state collection, explicit immutable operation plans, precondition revalidation, exact-path staging, and execution evidence. Keep these capabilities, but decouple them from the inherited scanner/snapshot model and make the UI's review surface adequate for informed Product Owner decisions.

The current Flask application does expose POST approval routes that execute stage and commit plans. These routes are evidence of inherited behavior, not automatic authorization for the Repo Control II product. Their plan/review/approval flow has meaningful safeguards and is conceptually compatible with Product Owner-controlled Git actions, but it lacks a file-level diff review surface and uses loopback access plus a CSRF session rather than a distinct Product Owner identity. Preserve the workflow engine for evaluation; do not expand its write surface before the next milestone resolves the desired UI/tool strategy and review contract.

The README's statement that browser routes do not stage or commit is inaccurate for the current source. The relevant tests include both an approval-flow test for each mutation and a separate GET-only test whose name suggests a broader non-mutation guarantee. This discrepancy is recorded as an explicit finding below; neither the implementation nor README is treated as Repo Control II architecture.

Recommended foundation:

- **KEEP:** deterministic Git state parsing and guarded local stage/commit service logic, subject to the boundaries below.
- **REFACTOR:** Git status and plan generation away from mandatory full scans/snapshot matching; make the Git UI's review and authority behavior explicit.
- **REFACTOR:** bounded context assembly as an adapter/query layer over a future repository-intelligence engine, if evaluation confirms a need.
- **RETIRE:** inherited Python-only repository analysis, snapshot/comparison machinery, and local-model interpretation as standalone product features after replacement/transition decisions are approved.
- **Next milestone:** a bounded Git UI/tool-fit and mutation-authority evaluation before committing to a larger custom UI or external Git UI integration.

No implementation files were changed. The required automated test suite passed.

## 4. Current Implementation Map

The package is `repoctl`, exposed as the `repoctl` CLI entry point. Its main components are:

- `scanner/`: Git worktree inspection, tracked-file inventory, file metadata, Python AST parsing, test discovery, internal relationships, and scan artifact publication.
- `context/`: deterministic lexical seed ranking, bounded one-hop relationship/test selection, and Markdown/JSON context packs.
- `snapshot/` and `compare/`: content-addressed scan snapshots and deterministic directional structural comparisons.
- `analysis/`: bounded comparison packet construction, local Ollama/GPT-OSS requests, output validation, and advisory reports.
- `workflow/`: Git status projection, immutable stage/commit plans, explicit execution, and audit/evidence artifacts.
- `web/`: Flask app, HTML views/templates, status/context/snapshot/comparison/analysis/workflow pages.
- `cli.py`: `scan`, `context`, `snapshot`, `compare`, `analyze`, `web`, and `milestone` status/stage/commit commands.

The primary dependency direction is CLI/web → workflow and feature managers → scanner/Git helpers → filesystem artifacts. The current workflow-status and commit-planning path also invokes the full scanner and uses snapshot artifacts, coupling Git control to inherited repository-analysis concepts.

## 5. Git Capability Assessment

### Read-only state

[`scanner/git_ops.py`](../../src/repoctl/scanner/git_ops.py) validates a worktree and reads HEAD, branch, tracked paths, and Git porcelain-v2 status. It distinguishes ordinary, rename/copy, unmerged, and untracked entries and sorts paths deterministically.

[`workflow/git_state.py`](../../src/repoctl/workflow/git_state.py) derives staged, unstaged, untracked, and unmerged path sets; clean/staged-only/unstaged-only/staged-and-unstaged/conflicted states; detached HEAD; active operation markers; and local-ref upstream ahead/behind. It does not fetch, so divergence can be stale relative to GitHub.

This state collection is deterministic, tested, and read-only toward the target Git repository. It does **not** provide file diffs, commit history, branch listing/graph, remote discovery, tag listing as a general capability, or GitHub awareness. The UI shows the current HEAD subject and tags at HEAD, not a history or branch browser.

### Stage and commit plans/execution

[`workflow/stage_plan.py`](../../src/repoctl/workflow/stage_plan.py) prepares immutable `--all` plans over eligible exact paths. It rejects an existing staged index, conflicts, active operations, and unsupported path types/filters. [`workflow/stage_execution.py`](../../src/repoctl/workflow/stage_execution.py) requires explicit approval, verifies the plan and current state, stages only the planned paths, verifies the result, and records execution evidence.

[`workflow/commit_plan.py`](../../src/repoctl/workflow/commit_plan.py) requires staged changes and a clean remainder, attached HEAD, no conflicts/active operation, and a matching snapshot before creating a deterministic plan. [`workflow/commit_execution.py`](../../src/repoctl/workflow/commit_execution.py) requires explicit approval; validates plan integrity, repository/branch/state fingerprints, Git identity, and hook constraints; performs a local commit; verifies it; and records execution/audit evidence. Neither execution path pushes or refreshes remote state.

The plan/execute split, explicit approval, exact path plan, revalidation, blocked unsupported conditions, and audit artifacts are sound reuse candidates. The enforced snapshot prerequisite is an unnecessary dependency on the legacy scanner/snapshot subsystem and should be reconsidered: the immutable stage/commit plans already fingerprint the Git state they act on. Stage preparation supports `--all` only, not Product Owner selection of a subset. The UI presents paths and commit message but not a diff, weakening review quality.

### Browser mutation boundary finding

The supplied Product Owner lock-in resolves the conflict as follows: source is evidence of current inherited behavior; the README and source are both non-authoritative for Repo Control II design; no route is changed in R001.00.

- [`web/app.py`](../../src/repoctl/web/app.py) exposes POST `/workflow/stage/approve` and `/workflow/commit/approve`; each requires a CSRF token and calls the corresponding execution service with `approve=True`.
- The app rejects non-loopback host binding. The review forms in [`workflow_plan_review.html`](../../src/repoctl/web/templates/workflow_plan_review.html) show exact planned paths or staged paths, branch/HEAD, plan ID, and an explicit “Approve Stage” or “Approve Commit” button. The workflow page offers plan preparation separately from approval.
- The local service does not establish an authenticated Product Owner identity; authority is effectively the local operator with access to the loopback UI/session. This may be acceptable for a single-operator local tool, but must be an explicit product assumption.
- The README's M009 statement at [`README.md`](../../README.md#browser-ui-milestone-009) says browser routes do not stage or commit and execution is CLI-only. That description is stale/inaccurate against the source.
- [`test_workflow_stage_review_and_approve_flow`](../../tests/test_web.py#L602) and [`test_workflow_commit_review_and_approve_flow`](../../tests/test_web.py#L637) exercise the web plan/review/approval flows in temporary repositories. The separate `test_forbidden_git_mutation_services_not_invoked_by_web_actions` at [`test_web.py`](../../tests/test_web.py#L730) tests GET-page behavior and does not establish that POST approval routes cannot mutate Git.

The current staged/commit web actions are not inherently incompatible with Repo Control II: the architecture intends a graphical Git control surface and reserves important Git mutations to the Product Owner. The execution model is directionally suitable if approval is a deliberate Product Owner action and the reviewed scope/evidence are adequate. It should be refactored to make those guarantees and assumptions explicit and to provide diff-level review before approval.

## 7. Repository Scanner / Static Analysis Assessment

`scanner/core.py` scans **tracked** files and publishes repository metadata, per-file size/hash/line counts, requirements declarations, Python symbols/imports, tests, and a summary. It reads current tracked contents, reports worktree state separately, and writes outputs under `~/.local/share/repoctl/<repository_id>/`.

`scanner/python_scan.py` uses Python `ast` to parse top-level functions/classes/imports and test structure. `scanner/relationships.py` resolves conservative internal module/imported-symbol edges, static calls, and test-to-symbol references, with ambiguity/rebinding/parse diagnostics. It is deterministic and well covered, but Python-only and limited to static heuristics; it does not resolve environments/dependencies or establish runtime call behavior.

Some concepts remain useful: deterministic facts, explicit unresolved/ambiguous diagnostics, query-oriented neighborhoods, bounded outputs, and test-to-symbol navigation. The parser/relationship engine itself is likely to duplicate a future Graphify/DevLens engine. A Repo Control adapter/query and bounded-context layer may remain valuable if the selected engine does not expose the required evidence contract. Defer adoption and any benchmark until a separate approved evaluation; no external repository-intelligence tool was installed or benchmarked.

## 8. Snapshot / Comparison Assessment

Snapshots store the six scan artifacts plus a manifest containing repository identity/path, branch, HEAD, working-tree state, artifact hashes, and tracked-file coverage. IDs derive from scan artifact bytes; snapshots live outside the target repository and validate hashes/content on reuse. The snapshot is not a complete source backup and structural scope is tracked files; untracked paths make coverage explicitly partial.

Comparisons are directional and report added/removed/changed file metadata, requirements, symbols, module/import/call/test relationships, diagnostics, and aggregate counts. File body changes are represented by hashes/sizes/line counts rather than a source diff. Both are deterministic and tested, but no independent Repo Control II requirement currently needs this persistence model. They overlap with Git history/diffs and the future repository-intelligence baseline/current view. Commit preparation's matching-snapshot gate also couples Git control to this feature.

**Recommendation:** RETIRE the inherited snapshot and comparison products after decoupling stage/commit plans from snapshot matching. Preserve the baseline/current structural-delta use case as a future repository-intelligence requirement, not as a reason to retain this storage engine.

## 9. Context / AI Functionality Assessment

Context generation uses lexical matching over file/module/symbol/source evidence to choose bounded seeds, files, symbols, relationships, and test references, then writes `context.json` and `context.md`. It is deterministic, capped, and explicitly navigation evidence rather than source authority. It is not a general prompt or milestone generator.

The analysis path consumes immutable comparison data, sends bounded structural metadata (not source bodies) to a local Ollama endpoint for `gpt-oss:20b`, validates structured responses and evidence IDs, and stores advisory output with model/request provenance. There is no cloud fallback. The safety/grounding choices are defensible, but having a local model interpret repository changes is not a current Repo Control II requirement and overlaps the Architect role and later Model Gateway arc.

**Recommendation:** REFACTOR context generation into a thin adapter/query layer only if needed over the eventual repository-intelligence engine. RETIRE the standalone lexical/AST context engine and local analysis feature after migration decisions; preserve the bounded-evidence and advisory/non-authoritative principles, not necessarily these implementations.

## 10. Workflow / Project-State Assessment

The inherited “milestone” workflow is Git workflow visibility and controlled staging/commit preparation/execution, not milestone orchestration. It has no project registry, active milestone state, prompt/addendum tracking, Q&A/decision/event trail, Architect review state, or closeout lifecycle.

Repository identity is a slug plus a hash of the canonical absolute path. Repository selection is supplied as a path through CLI/web arguments; there is no durable multi-project registry. `workflow/status.py` writes a replaceable current-state projection and derives its snapshot candidate by running the full scanner. Plans and execution records are content-addressed/local artifacts, but they are not human project milestone state.

**Recommendation:** Keep the Git-specific plan/execution semantics as a starting point. Refactor away the legacy “milestone” naming and scanner/snapshot prerequisites as the new orchestration model is designed. Build real workflow/milestone state from tracked human-readable artifacts and lightweight operational state only when an approved milestone defines its transitions.

## 11. Persistence / Dependency Assessment

There is no SQLite/database state. Derived artifacts and plans are stored outside target repositories under `~/.local/share/repoctl/<repository_id>/`, grouped into scanner output, contexts, snapshots, comparisons, analyses, and workflow status/plans/executions/audits. Most are recomputable; plan/execution evidence is useful operational audit state. This cleanly avoids writing application data into a target repository, but the single repository-ID namespace currently mixes unrelated legacy features and current Git operations.

Direct declared runtime dependency: Flask (`flask>=3.0,<4`). Python stdlib supplies AST, filesystem, JSON, hashing, subprocess, and HTTP client support. Runtime assumptions include Python >=3.11, Git CLI, and Flask for the web UI. Local analysis additionally assumes an independently running loopback Ollama service/model; it is not a declared Python package dependency. Pytest is available in the existing venv but is not declared in `pyproject.toml`.

**Recommendation:** Retain external-to-target storage and deterministic structured artifacts for operational plans/evidence; refactor namespace/authority around selected projects and milestones. Do not add a database during salvage. Flask remains conditional on the UI/tool evaluation; no dependency changes were made.

## 14. Minimum Viable Repo Control II Foundation

**KEEP**

- Git-derived repository identity/state facts and deterministic status classification.
- Immutable, exact-scope stage/commit plan mechanics, precondition checks, explicit operator approval, verification, and audit evidence—after decoupling from snapshots and confirming the intended local Product Owner boundary.
- Existing Git tests as regression gates.

**REFACTOR**

- Separate Git status/plan creation from full repository scan and snapshot creation.
- Keep the UI as a thin Git/workflow shell only if the tool evaluation supports that choice; provide diff-based review and make local approval assumptions explicit.
- Treat context assembly as a query adapter over a future specialized repository-intelligence engine.
- Represent milestone/workflow state separately from Git state and derived scan artifacts.

**RETIRE / quarantine until approved transition**

- Python-only scanner and relationship graph as the product's repository-intelligence engine.
- Standalone scan snapshots/comparison persistence and its commit-plan prerequisite.
- Local GPT-OSS comparison interpretation.
- Legacy context/snapshot/comparison/analysis UI pages if no longer needed by the chosen architecture.

No database, external engine, model gateway, new Git mutation, or UI redesign is needed to establish this foundation.
