---

## 2. Product Owner intent

Repo Control must support both new and mature repositories without requiring prior chat history.

For a mature project such as Vocab App, the Architect needs two distinct kinds of context:

1. **Current authoritative state**
   - active managed repository;
   - selected milestone;
   - lifecycle/authorization;
   - governing documents;
   - current Git/test evidence;
   - approved applicable dispatches.

2. **Historical planning evidence**
   - prior milestone prompts/closeouts;
   - accepted/rejected architectural paths;
   - prior experiments and their conclusions;
   - historical decisions needed to understand why the current product looks the way it does.

The Coder likewise must deterministically reach the same managed-repository identity/configuration as the browser and Architect.

The target design principle is:

```text
Current governing documents + Repo Control lifecycle
→ define current authority

Historical milestone/document evidence
→ informs planning but never silently becomes current authority

Chat history
→ optional convenience, never required bootstrap state
```

- active prompt/workflow/closeout;

## 8. Design candidate bounded repository-document read capability

Recommend a narrow read-only mechanism for explicitly selected repository documentation/text artifacts.

Evaluate:

- whether to extend `repo_document` versus add a separate fixed tool/API;
- repository-relative path validation;
- server-selected active repository only;
- permitted file types/locations;
- tracked **and uncommitted** file support;
- maximum bytes / truncation behavior;
- symlink/path traversal protection;
- binary-file rejection;
- source metadata/provenance;
- whether content should be limited to documentation roots or an allowlisted text-file policy;
- whether directory listing/discovery is needed or should remain separate;
- auditability and predictable failure modes.

The capability must not grant:

- arbitrary filesystem access;
- arbitrary shell execution;
- Git mutation;
- lifecycle mutation;
- Product Owner authority;
- write/edit capability.

## 9. Formalize the missing mature-project use case

Use Vocab App as a concrete evidence case without modifying it.

Document why current governing documents alone may be insufficient for planning future arcs in a mature repository. Examples include needing to recover:

- why an architecture was chosen;
- what alternatives were tested;
- why a model/path was rejected;
- what partial milestone work remains;
- which Product Owner decisions shaped the current baseline;
- what earlier work is historical only versus still relevant.

Preserve the distinction:

```text
history informs planning
current governing documents + current Repo Control lifecycle define authority
```

## 10. Inventory existing historical sources and discovery behavior

Determine what historical material Repo Control can currently discover/read and through which interfaces.

Consider at minimum:

- milestone prompts;
- workflow sidecars;
- closeouts;
- historical milestone roots/corpora;
- `docs/history/**`;
- other Markdown/text planning artifacts;
- explicit current milestone selection versus historical artifacts outside active discovery.

Identify whether existing recursive milestone discovery intentionally excludes archived/historical roots and ensure any future history capability does not accidentally make historical artifacts active candidates.

## 11. Design bounded historical discovery/retrieval

Recommend a progressive-disclosure model suitable for Architect planning.

Evaluate candidate operations such as:

```text
historical artifact search
historical artifact listing/filtering
read one selected historical artifact
search by milestone ID
search by artifact type
bounded text/term search
optional compact arc/history index
```

Do not assume those exact tool names.

The design should:

- keep current authority separate from historical evidence;
- permit selective retrieval instead of loading the full corpus;
- return explicit source paths/types;
- support mature repositories with many milestones;
- avoid recursive active-milestone pollution;
- work even when historical artifacts have been moved under `docs/history/`;
- use bounded output and deterministic limits;
- be repository-scoped and read-only;
- not depend on prior ChatGPT memory.

Assess whether `INTEGRATION-002` and `INTEGRATION-003` should share one lower-level bounded repository text/document service with distinct higher-level interfaces.

## 13. Authority and security boundaries

Preserve all accepted boundaries:

- Product Owner owns consequential lifecycle and Git mutation.
- Coder performs no Git mutation.
- Architect proposals require PO approval.
- Architect evidence access is read-only.
- Historical evidence never overrides current governing documents/lifecycle.
- Repository paths are server-selected/allowlisted.
- No arbitrary filesystem traversal.
- No arbitrary command execution.
- No network expansion unless separately justified.
- No hidden automatic refresh/build/mutation as a side effect of reading context.

Explicitly identify new threat surfaces introduced by any proposed document/history read capability.
