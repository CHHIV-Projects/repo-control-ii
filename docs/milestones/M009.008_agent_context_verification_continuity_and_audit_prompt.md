# M009.008 — Agent Context Verification, Continuity, and Audit

## Objective and authority
Implement a shared, auditable contract so that a new Coder or Architect context verifies current Repo Control authority without a Product Owner reminder; a warm context does not repeat full bootstrap ceremonially; a Coder handoff reconciles authoritative work state; and milestone review distinguishes verified evidence from mere agent claims. This is an implementation milestone in Repo Control II only. The proposal is not implementation authorization: begin only after the Product Owner creates/selects M009.008, approves its prompt, and puts the lifecycle into authorized IN_PROGRESS.

Repository: repo-control-ii at /home/chuck/projects/repo-control-ii. M009.007 is CLOSED and its central Copilot/Codex adapters, read-only coder-bootstrap-preview, fail-closed identity binding, and guide are the baseline. The Vocab M002.007 pilot does not have full provider-native host receipts; do not represent that pilot as PASS or require its original hook-receipt acceptance as a precondition for this work.

## Required behavior
1. Define formal trigger semantics in the canonical shared procedure: NEW = fresh agent context/new independent session, or lost/cleared governing context; WARM = same agent context with still-valid previously established instructions; HANDOFF = a distinct Coder taking over existing work; AUTHORITY TRANSITION = selected repository/milestone, prompt/approved instruction, lifecycle/authorization, or applicable procedure changed. A model switch with intact context and an ordinary follow-up message do not independently force full bootstrap. On uncertain validity, resolve live context rather than assume continuity.
2. NEW: run a canonical fresh lookup before consequential work. Validate managed repository key/ID/root, selected milestone/prompt path/hash, current lifecycle/authorization and open blocking conditions, governing shared procedure + local overlay, and Product Owner Git boundary. Agents cannot infer authority from chat, hooks, files, packets, or a handoff phrase alone. Wrong identity or unavailable/incoherent authority stops work.
3. WARM: preserve verified governing instructions and do not reread entire context/project documents or record identical bootstrap events on every interaction. Before acting on a material transition, perform a focused fresh authoritative lookup of changed values. In particular WAITING to IN_PROGRESS, changed prompt/approved response, repository or milestone switch, or suspected context loss requires revalidation. Never treat historic authorization as permanent.
4. HANDOFF: fresh bootstrap plus targeted reconciliation of active prompt, approved decisions, recorded questions/blockers, tests/closeout/workflow evidence as relevant, and read-only working tree/HEAD/uncommitted changes. Do not require the Product Owner to copy transcripts or create ceremonial handoff packages if canonical evidence suffices. If ownership of dirty files or unfinished work is ambiguous, STOP and escalate.
5. Both Coders and the ChatGPT Architect follow the same trigger/authority policy but use their supported canonical interfaces. Coder: Repo Control coder-context and applicable procedure-status/status/other bounded CLI. Architect: connected read-only repo_status, repo_workflow, repo_prompt and additional bounded evidence where needed. Do not instruct ChatGPT Architect to execute local coder-context or assume host hooks are accessible to it. Handoff notices such as 'Prompt ready.' are signals only, never approvals.

## Durable shared instructions / delivery

Update canonical shared/procedure sources (always-loaded bootstrap, workflow core, and only relevant existing Skills) with concise normative instructions including trigger matrix, exact lookup strategy, stopping rules, and evidence duty. Avoid copying the full process into every repository-specific docs/context/project_workflow.md or milestone prompt. Preserve local overlays and the accepted separation between canonical shared release and per-repository installed/pinned versions.
7. Publish through the existing canonical shared-procedure release and preview/versioning mechanism. Regenerate/reconcile only Repo Control II's own installed generated artifacts if within authorized scope and deterministically verified. Do not silently update other repositories; each target adopts a new release under its own separate Product Owner authorization. Document deployment/reconciliation steps and version-drift semantics.
8. Preserve existing provider-specific SessionStart adapters/registrations as optional delivery mechanisms; the normative agent-side verification fallback must work without proof of host hook execution. Do not bypass trust, edit global host config, or claim hook execution/delivery from discovery, preview, or agent statements alone.

## Auditable evidence and review
9. Inspect existing CLI, event/sidecar schemas, review surfaces and tests before choosing the smallest implementation. Prefer the existing event chronology/sidecar and current review interface over new tables, services, process daemons, or a generic session-monitoring platform.
10. Provide a bounded deterministic path for recording a verification outcome at a REQUIRED trigger, with the actual checked authority snapshot and source. Separate authoritative server-observed lookup values from agent-reported claims and from provider-native host evidence. Never label untrusted agent identity/session claims 'authenticated', and never claim independent host delivery without a correlated host receipt. If a provider offers no trustworthy session ID, use explicit 'session identity unverified' classification instead of inventing one.
11. Record at minimum: repository key/ID/root; milestone; prompt identity/hash; lifecycle and authorization; open conditions; procedure release/overlay identity; Git boundary acknowledgement; trigger (NEW, HANDOFF, AUTHORITY_TRANSITION, RECOVERY); lookup time/source; result (VERIFIED, BLOCKED, PARTIAL/UNVERIFIED as appropriate); and provenance/evidence strength. Minimize secrets/PII and do not store prompt bodies or conversation transcripts. Verification failures must not grant authority or mutate lifecycle.
12. Audit surface: expose bounded read-only milestone-level verification coverage via an existing review/status surface (and operator-facing documentation as needed). Report which required, *observed* triggers have corresponding valid verification and whether newer material authority changes render prior verification stale. Distinguish missing record, invalid or stale record, agent-reported vs server-observed outcome, and provider hook delivery unverified. A missing event is NOT proof that no new chat started; do not claim completeness for unobservable sessions. If a host/session boundary is not observable, explicitly report the coverage limitation.
13. Reduce overhead: normal warm interactions generate no redundant record; avoid unconditional re-reading of all governing docs and duplicate noisy sidecar writes. Never replace authorization checks at consequential boundaries with an outdated cached snapshot. Avoid adding a required Product Owner manual step.

## Scope boundaries

Focused and full relevant unit tests, compile/syntax, docs and shared-procedure preview/release checks, git diff --check, final read-only Git. No live provider-host receipt is needed for acceptance; instead state precisely what was proven and what requires a future platform-specific validation.
