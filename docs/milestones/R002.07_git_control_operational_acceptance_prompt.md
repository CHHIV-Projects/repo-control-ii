## Multi-Repository Operational Requirement

Repo Control's long-term role is to manage multiple repositories from one control plane.

R002.07 must not unnecessarily hard-code the always-on service to:

    /home/chuck/projects/repo-control-ii

The authoritative Repo Control repository remains the required acceptance target,
but the operational architecture should preserve or establish a path to selecting
among multiple known repositories without starting a separate service instance for
each repository.

Perform reconnaissance on the current repository-selection model.

Preferred end state for R002.07, if achievable without materially broadening scope:

    one always-on Repo Control service
    ↓
    server-controlled repository registry / known repository list
    ↓
    Product Owner selects active repository in the browser
    ↓
    existing Git inspection/mutation safeguards operate against that selected repo

Requirements:

- repository paths must come from server-controlled configuration or discovery;
- arbitrary browser-supplied filesystem paths must not become Git execution targets;
- switching active repository must not itself mutate Git state;
- current active repository must remain clearly visible;
- prepared actions must remain repository-bound and become invalid if repository
  selection changes;
- no separate daemon/process per repository should be required for normal use.

If the current architecture cannot support this cleanly within R002.07 without
becoming a substantial new feature project, stop and report the architectural gap
and recommend the smallest follow-on milestone rather than hard-coding the service
permanently to one repository.





R002.07 Windows Access Addendum — Portable Launcher Package

The Product Owner prefers to preserve the current loopback-only + SSH access model,
but wants the Windows-side experience to behave like an easily accessible local
program.

Replace/extend the current single PowerShell helper with a small portable,
credential-free Windows launcher package.

Preferred tracked structure:

    ops/windows/RepoControlLauncher/
        RepoControl.cmd
        open-repo-control.ps1
        install-startup-task.ps1
        remove-startup-task.ps1
        README.txt

Goals:

1. RepoControl.cmd
   - primary double-click entry point;
   - invokes the PowerShell helper without requiring the Product Owner to type
     PowerShell commands;
   - ensures Repo Control access is available;
   - opens the Repo Control browser UI.

2. open-repo-control.ps1
   - retain the accepted behavior already tested:
       * reuse an existing healthy Repo Control tunnel;
       * refuse a foreign/stale listener rather than overwrite it;
       * otherwise start an SSH tunnel using normal Windows OpenSSH authentication;
       * use ExitOnForwardFailure and reasonable keepalive options;
       * wait for the Repo Control health endpoint;
       * open the browser;
       * print the tunnel PID / stop command when it creates a tunnel;
   - add a bounded switch such as:

         -TunnelOnly

     which ensures the tunnel is available but does not open the browser.

3. install-startup-task.ps1
   - optional convenience installer;
   - creates a per-user Windows Task Scheduler task triggered at user logon;
   - invokes open-repo-control.ps1 -TunnelOnly;
   - must not require administrator rights if Windows permits the intended
     per-user task;
   - must not embed credentials or weaken SSH host-key handling;
   - should be idempotent or clearly replace/update the same named task.

4. remove-startup-task.ps1
   - removes only the Repo Control startup task created by this package;
   - must not change unrelated scheduled tasks or SSH configuration.

5. README.txt
   - concise Windows instructions:
       * copy the RepoControlLauncher folder anywhere on the PC;
       * double-click RepoControl.cmd for on-demand use;
       * optionally run install-startup-task.ps1 once to keep the tunnel
         available after Windows login;
       * run remove-startup-task.ps1 to remove startup behavior;
       * requirements: Windows OpenSSH client, network access to
         henderson-server1, and valid SSH authentication;
       * no passwords or private keys are included in the package.

Design requirements:

- The launcher folder should be portable and safe to copy to another Windows PC.
- Do not package credentials, private keys, passwords, host-key exceptions, or
  machine-specific secrets.
- Do not build or require a compiled .exe for R002.07.
- Do not create a Windows service.
- Do not introduce third-party dependencies or external modules.
- Preserve the Linux service's loopback-only bind.
- Preserve the existing foreign/stale-local-port refusal behavior.
- Prefer configuration constants near the top of the PowerShell script so this
  launcher pattern can later be reused for other server-hosted applications.

Acceptance:

- Double-clicking RepoControl.cmd from a copied local folder opens Repo Control.
- If a healthy tunnel already exists, it is reused.
- If no tunnel exists, one is started securely.
- A stale/foreign port listener still fails clearly.
- -TunnelOnly establishes/reuses access without opening a browser.
- install-startup-task.ps1 creates a working per-user logon task.
- after Windows logon, the tunnel can be available without manually launching
  Repo Control.
- RepoControl.cmd still opens the browser on demand.
- remove-startup-task.ps1 cleanly removes only that startup task.

Keep this within R002.07 operationalization. Do not broaden into a generic launcher
framework or another application yet. The goal is to establish the pattern with
Repo Control first.
