# R003.00 — Workflow Orchestration Architecture Reconnaissance Closeout

**Status:** PASS — architecture direction and staged roadmap recommended
**Mode:** Architecture reconnaissance / design only
**Date:** 2026-10-11

## 1. Executive Result

R003.00 reconnaissance is complete. The current codebase has useful
repository-scoped Git state, immutable Git-action plans, execution evidence,
and a multi-repository web shell, but it does not implement milestone
orchestration. Its existing `workflow_state` is strictly a derived Git
working-tree state.

Recommended direction:

- Keep tracked Markdown prompts, decisions/lock-ins, and closeouts as the
  durable human-readable authority.
- Add a small, repository-scoped operational record for the explicitly
  selected milestone; do not infer the active milestone from recency.
- Derive artifact presence and current Git/test facts from their sources.
  Treat workflow phase as an explicit, minimal lifecycle rather than as a
  synonym for Git state.
- Record meaningful questions, decisions, bugs, and review outcomes as events
  in a milestone's durable record, without requiring a new formal document
  for every exchange.
- Keep Product Owner approval explicit for binding decisions, material scope
  changes, acceptance, Git mutations, and closure.
- Start with an agent-neutral, read-only milestone view and generated handoff
  packet; defer direct Architect/Coder integrations until their security and
  authority contracts are defined.

No blocking architecture conflict or prerequisite database decision was found.
The prompt's reconnaissance-only boundary was maintained; no application code,
configuration, tests, or Git history were changed.

1. Architect and Product Owner shape and approve a bounded prompt.
2. Coder reads the prompt, performs preflight, and may ask questions, report

3. Architect answers technical questions within approved intent; Product
   Owner carries/approves binding decisions and material lock-ins.
4. Coder implements iteratively, validates, and prepares a closeout.
5. Architect reviews evidence; Product Owner accepts, requests bounded
   correction, or directs separate work.
6. Product Owner retains Git mutation authority and closes the milestone.

Repo Control does not yet discover or expose this milestone lifecycle, so the
Product Owner still manually transports prompts, questions, answers, and
closeouts. The live browser navigation exposes Dashboard and Git Review. A
read-only legacy `/workflow` route remains but is not milestone orchestration.

## 4. Deterministic vs Explicit State Matrix

| Fact | Classification | Source / boundary |
|---|---|---|
| Configured repository identity and worktree root | **DERIVED** | Validated server-side from `ops/repositories.toml`; never accept an arbitrary browser path. |
| Current HEAD, branch, index/worktree state, active Git operation, locally known upstream divergence | **DERIVED** | Git is authoritative; divergence is local-ref based and may be stale. |
| Prompt, addendum, decision record, and closeout file presence and paths | **DERIVED** | Repository inventory. Presence does not prove approval, completeness, or acceptance. |
| Prompt/closeout content and recorded evidence | **DERIVED** | Read from identified tracked artifacts; do not infer semantic status from file timestamps. |
| Which milestone is selected for current work | **EXPLICIT** | Product Owner selects a specific milestone ID/artifact for each repository. Never pick “latest” or the only file missing a closeout without confirmation. |
| Prompt approval and authoritative lock-in | **AUTHORITATIVE DECISION** | Record the decision and actor; Product Owner approval is required before it becomes binding. |
| Current lifecycle phase and reason for waiting | **EXPLICIT** | Record a small phase plus a typed reason/owner where waiting. Do not derive from Git dirty/clean state. |
| Coder question, answer, bug discovery/classification, test result, resume, review request | **EVENT** | Preserve meaningful chronology and references in a durable milestone record. An event need not create a new phase. |
| Whether a question/answer changes requirements or scope | **AUTHORITATIVE DECISION** | Ordinary technical clarification can be recorded as an event; binding lock-in is explicitly attributed/approved. |
| Test command and exit/result evidence | **DERIVED or EVENT** | Machine-run evidence may be imported with command/result/source; a coder-reported result remains explicitly reported, not silently treated as verified. |
| Closeout exists | **DERIVED** | File presence only; does not mean Architect review or Product Owner acceptance. |
| Final acceptance, material re-scope, or milestone closure | **PRODUCT OWNER APPROVAL** | Explicit action and durable record; must not be inferred from closeout language, clean Git state, or a pushed commit. |
| Stage, commit, push, branch/remote mutation | **PRODUCT OWNER APPROVAL** | Preserve existing Git confirmation and verification safeguards; workflow orchestration does not authorize these automatically. |

## 5. Recommended Minimal Workflow State Model

Use six coarse lifecycle phases:

```text
PLANNING
READY
IN_PROGRESS
WAITING
REVIEW
CLOSED
```

Suggested meanings:

- **PLANNING** — a milestone is selected for preparation; prompt/approval may
  not yet be complete.
- **READY** — authoritative prompt and required approvals are recorded; work
  may be handed to a Coder.
- **IN_PROGRESS** — implementation or validation is active.
- **WAITING** — work is paused for clarification, decision, blocker, or
  escalation. Store `waiting_for` and `reason`; do not create a unique phase
  for each type.
- **REVIEW** — closeout/evidence is available for Architect and Product Owner
  review. Review requests and bounded corrections are events; the phase may
  remain REVIEW or return to IN_PROGRESS.
- **CLOSED** — Product Owner accepted the outcome and recorded Git disposition
  (completed or explicitly deferred as authorized by project policy).

The selected milestone ID is a pointer, not a lifecycle phase. Git readiness
is a separate, freshly derived view of branch/index/worktree/upstream facts.
Do not introduce separate phases for every question, test, bug, or approval.
Do not mark a milestone closed solely because a closeout exists or Git is
clean.

Transitions should generally be explicit events. Automatic derivation may
suggest `REVIEW` when a closeout appears, but it must not silently accept or
close the milestone.

## 6. Recommended Event Model

Keep a small event vocabulary and do not turn every conversational exchange
into workflow state:

| Event | Typical effect |
|---|---|
| `prompt_approved` / `prompt_superseded` | Authoritative decision; may move PLANNING to READY or require re-review. |
| `question_submitted` / `answer_recorded` | Durable event; WAITING can return to IN_PROGRESS when the authorized answer is available. |
| `decision_recorded` / `lock_in_approved` | Authoritative decision; binding changes require Product Owner approval and may update a tracked addendum. |
| `escalation_opened` / `escalation_resolved` | Sets/clears WAITING reason; material scope changes remain unresolved until explicit approval. |
| `bug_discovered` / `bug_classified` / `bug_fixed` | Usually events only; a material bug may put work in WAITING. Record fix and validation in the milestone record. |
| `test_result_recorded` | Evidence event; record command, result, source, and whether independently executed or reported. |
| `implementation_resumed` | Clears waiting state after a valid response/decision. |
| `closeout_submitted` / `review_requested` / `correction_requested` | Usually moves into or remains in REVIEW; a bounded correction resumes IN_PROGRESS. |
| `acceptance_recorded` / `milestone_closed` | Explicit Product Owner action; final phase CLOSED. |
| `git_disposition_recorded` | Records relevant accepted Git outcome or explicit deferral; does not itself grant Git authority. |

An event record should include event type, stable event ID, timestamp, actor/role
when known, milestone ID, repository identity, short description, and links to
supporting artifacts/evidence. Never infer actor identity from browser access
alone.

## 7. Clarification / Addendum Rule

- **Routine conversation:** No formal addendum for a transient explanation or
  wording choice that does not affect future implementation. Keep normal
  collaboration lightweight.
- **Durable decision event:** Record a question/answer when it changes coder
  behavior, resolves a blocker, establishes an assumption, or needs to survive
  chat loss. Add it to one milestone decision/Q&A record rather than creating a
  standalone file per exchange.
- **Formal addendum / lock-in:** Required when a clarification supersedes or
  materially refines a prompt requirement while preserving the approved
  objective. Attribute the decision and Product Owner approval; update the
  authoritative prompt/addendum record.
- **Re-scope / new milestone:** Stop implementation when objective,
  architecture, authority, risk, or validation burden materially changes.
  Record the escalation and wait for Architect/Product Owner direction. Do not
  silently expand the current milestone.

The three-level model in the prompt is sufficient. The useful refinement is
that durability depends on whether guidance affects future action, not on
whether a conversation is labelled a “question.”

## 8. Bug Handling Rule

Keep a bug inside the active milestone when it is directly related to the
changed behavior, the fix is bounded, approved objective/architecture/
authority/risk remain unchanged, and the coder records discovery, classification,
fix, and focused validation. A new formal milestone is not required for every
such correction.

Pause and escalate if the defect suggests a cross-project safety issue,
material security/authority risk, broad architecture change, unrelated
subsystem work, or materially different validation burden. Product Owner
approval is required to re-scope; otherwise capture a follow-up milestone.

This is consistent with the current
[`coding_agent_rules.md`](../context/coding_agent_rules.md) bug-boundary rule.

## 9. Active Milestone Identification

Require explicit Product Owner selection of a milestone within the already
selected, server-configured repository. A future inventory may discover
candidate prompt artifacts by a validated naming convention, but it must
display candidates and ambiguity and require selection. Do not use “latest
file,” modification time, highest number, missing closeout, or inferred status
as an automatic selector.

For the first implementation, store the selected milestone ID and canonical
prompt path in a small atomic JSON record under the existing external state
root, keyed by `repository_id`. Treat this as an operational pointer only, not
as the authoritative milestone record. If the record is absent, stale, or
invalid, require explicit re-selection rather than guessing. Verify the
resolved artifact remains inside the selected repository and is a valid
milestone prompt.

The service's current repository selection is process-wide; milestone
selection/state must nevertheless be repository-scoped. Every request should
resolve repository and milestone together and apply the existing stale-
repository-selection protections. Restart may return the repository selector
to its configured default, but must not silently transfer one repository's
milestone selection to another.

## 10. Persistence Recommendation

Recommend a **hybrid**, without introducing SQLite or a workflow database in
the first slice:

1. **Tracked Markdown remains authoritative** for approved prompts,
   addenda/lock-ins, durable decisions, coder closeouts, review outcomes, and
   acceptance. It is transparent, reviewable, recoverable with Git, and shared
   with future agents.
2. **Small per-repository operational JSON** stores only the active milestone
   pointer and UI/runtime conveniences. It is external to the target repository,
   keyed by `repository_id`, atomically written, schema-versioned, and
   reconstructible through explicit selection.
3. **Derived views** may cache artifact inventories and Git/test evidence, but
   must be reproducible and clearly distinguish reported from machine-verified
   evidence.

Do not store secrets, credentials, or the authoritative decision trail only
in local state or chat history. Consider SQLite only if demonstrated
concurrent event writes, query needs, or transactional requirements exceed the
simple file model. Before direct multi-agent writes, define locking,
idempotency, actor authentication, and conflict handling.

## 11. Transport Reduction Roadmap

Use this incremental progression:

1. **Discover and display** candidate milestone artifacts for the selected
   repository; require explicit Product Owner selection and show prompt,
   decisions, closeout, current phase, and next action.
2. **Record decisions and events** in a single durable milestone record with
   clear authority labels; do not create one file per question.
3. **Generate handoff packets** from source artifacts and current deterministic
   facts. Provide copy/export for Coder and Architect without duplicating
   editable source-of-truth content.
4. **Establish a file-based Coder contract**: identify repository and selected
   milestone, read prompt/addenda/standing rules, perform preflight, submit
   questions/events/closeout through a defined channel, and never assume Git
   authority.
5. **Expose controlled Architect queries** for selected milestone, prompt,
   decisions, open questions, closeout, tests, and Git state. Prefer read-only
   tools first.
6. **Add bounded Coder submission tools** only after caller authentication,
   project/milestone scoping, event attribution, idempotency, and approval
   boundaries are defined. Keep these tools agent/provider-neutral.
7. **Assemble review evidence** from closeout, changed files, test evidence,
   and Git state; preserve Product Owner acceptance and Git actions as explicit
   separate steps.

One-click copy/export is a low-risk transitional convenience. Direct
ChatGPT-to-server tools are not required for the first useful slice.

## 12. Product Owner Approval Matrix

| Action / transition | Approval rule |
|---|---|
| Select active milestone | Explicit Product Owner selection; repository must be server-configured. |
| Mark prompt authoritative / ready for Coder | Product Owner approval of the prompt and applicable lock-ins. |
| Record routine technical answer | Architect may answer within approved intent; record if it changes implementation or clears a blocker. |
| Make answer binding or supersede prompt | Product Owner approval; record the decision and addendum/lock-in. |
| Classify bounded bug as in-scope | Coder may propose; record rationale and tests. Product Owner/Architect review is needed if objective boundary is uncertain. |
| Re-scope or change architecture/authority/risk | Stop and require explicit Architect recommendation and Product Owner decision. |
| Submit closeout / report tests | Coder may submit; submission is not acceptance. Label test evidence by source. |
| Request evidence or bounded correction | Architect may recommend; record request. Product Owner controls material re-scope. |
| Accept implementation / close milestone | Product Owner explicit approval after review; do not infer from files, CI/test text, or Git status. |
| Stage, commit, push, or other Git mutation | Product Owner explicit action through existing prepared/revalidated Git workflow or authorized manual Git. |

Transitions that are purely deterministic (artifact presence, Git state,
validated test-process output, current selected repository) may be displayed
automatically but must not manufacture approval.

## 13. UI Recommendation

Add a small, explicitly named **Milestone / Workflow** view rather than
rebranding Git `workflow_state`. The first useful view should show:

- configured project/repository identity;
- explicitly selected milestone ID and prompt path;
- lifecycle phase and, if waiting, reason/owner;
- prompt/addenda/decision/closeout presence and links;
- open questions and latest durable decisions;
- test evidence with source and verification status;
- current Git branch/HEAD/working-tree summary and a clear note that it is
  independently derived;
- next action and the actor authorized to take it.

Start read-only except for a Product Owner-controlled milestone selector and
small lifecycle actions when their persistence/audit rules are implemented.
Do not add broad chat, IDE, code-editing, AI-writing, or autonomous project-
manager surfaces in R003.01.

## 14. Proposed R003 Implementation Milestones

Recommended sequence; each remains subject to Product Owner review:

- **R003.01 — Milestone Artifact Discovery and Explicit Selection:** validated
  artifact inventory, repository-scoped active pointer, safe re-selection,
  minimal read-only Workflow view, and tests for ambiguous/malformed/cross-
  repository paths.
- **R003.02 — Minimal Lifecycle and Durable Decisions:** phase transitions,
  one milestone decision/event record, Q&A/lock-in/escalation and bounded bug
  recording, with explicit Product Owner authority checks.
- **R003.03 — Coder and Architect Handoff Packets:** deterministic assembly
  from prompt, standing rules, decisions, closeout and current evidence;
  copy/export only, no duplicate source of truth.
- **R003.04 — Architect Read-Only Workflow Contract:** stable, bounded,
  repository/milestone-scoped query contract for status, prompt, decisions,
  questions, closeout and evidence; evaluate tool transport and authentication
  separately before exposure.
- **R003.05 — Coder Submission Contract:** authenticated, attributable
  question/event/closeout submission with idempotency and explicit approval
  boundaries; no autonomous scope changes or Git mutations.
- **R003.06 — Review Evidence and Acceptance Surface:** consolidate closeout,
  test and Git evidence; record Architect recommendation and explicit Product
  Owner acceptance/closure.

Do not make R003.04 a prerequisite for R003.01–R003.03. Do not select an MCP,
database, or AI provider in R003.00.

## 15. Risks / Open Questions

No open issue blocks an initial implementation prompt. Resolve these at the
relevant later boundary:

- Whether the active pointer should eventually become tracked/shareable or
  remain operational local state. The first-slice local pointer is
  reconstructible; decide before multi-host workflows depend on it.
- The exact prompt filename grammar and optional metadata schema. Existing
  files provide naming conventions but no consistent front matter contract;
  malformed or duplicate candidates must fail visibly.
- How to authenticate Architect, Coder, and Product Owner roles. The current
  loopback Flask UI and CSRF protection do not establish distinct caller
  identities; network/tool integrations require a separate security design.
- How to serialize concurrent updates and avoid duplicate event submissions
  before enabling multi-agent write tools.
- Whether machine-run tests can be securely invoked/collected by Repo Control
  or whether initial test evidence remains Coder-reported.
- How long external operational state is backed up and retained; tracked
  decisions must remain recoverable independently.

No direct AI/Coder integration is required before a useful first slice.
Repository selection is already allowlisted; the key architectural condition
is strict per-repository scoping and stale-selection validation.
