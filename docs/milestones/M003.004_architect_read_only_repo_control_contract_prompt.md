# 1. Purpose

M003.004 should establish the smallest safe **read-only Architect query contract** between Repo Control II and an external Architect client.

The immediate objective is not yet to build full ChatGPT integration.

The objective is to define and implement a bounded, provider-neutral way for an Architect client to retrieve current project evidence from Repo Control II without requiring the Product Owner to manually assemble or copy a large Architect Review Packet.

M003.003 proved that Repo Control can already assemble relevant evidence deterministically.

M003.004 should expose that evidence through a stable read-only contract suitable for future controlled tool integration.

---

# 2. Desired End State

Repo Control II should expose a small read-only Architect surface that can answer bounded queries such as:

```text
What repository is active?

What milestone is selected?

What is the current lifecycle phase?

What is the authoritative prompt?

What Product Owner-approved binding lock-ins exist?

What unresolved questions / blockers / escalations / bugs exist?

Is there a closeout?

What is the current deterministic Git state?

What test evidence has been recorded?

What governing project documents are configured?

Can I retrieve a bounded Architect review view?
```

The response should be:

```text
deterministic
repository-scoped
milestone-scoped
bounded
read-only
source-labeled
safe to consume by an Architect
provider-neutral
```

---

# 3. Architecture Principle

Repo Control II remains the control plane.

The Architect contract should expose trusted project evidence, not autonomous decisions.

Conceptually:

```text
Architect client
      │
      │ read-only request
      ▼
Repo Control II
      │
      ├── repository registry
      ├── active milestone selection
      ├── milestone prompt
      ├── workflow sidecar
      ├── closeout
      ├── governing documents
      ├── Git state
      └── recorded test evidence
      │
      ▼
bounded structured response
```

Do not make ChatGPT or any other model the authority for repository state.

# 6. Transport Decision

Evaluate the smallest safe transport that fits the current Flask/server architecture.

Preferred direction:

```text
local HTTP JSON API
```

or another equally small read-only interface if repository evidence strongly favors it.

The interface should remain:

```text
loopback-bound
non-mutating
server-controlled
explicitly versioned or versionable
```

Do not expose the service directly to the LAN or public Internet.

The current accepted network boundary remains:

```text
127.0.0.1:8765
```

If a separate read-only endpoint/route is added, it should remain under the same loopback-only service unless a stronger reason exists.

# 7. Contract Shape

Prefer a small set of explicit read-only endpoints rather than one giant opaque endpoint.

A reasonable shape might be:

```text
GET /api/architect/v1/status

GET /api/architect/v1/milestone

GET /api/architect/v1/prompt

GET /api/architect/v1/workflow

GET /api/architect/v1/closeout

GET /api/architect/v1/git

GET /api/architect/v1/evidence

GET /api/architect/v1/review
```

Exact route names are not prescribed.

The key requirement is a stable bounded contract.

Avoid returning arbitrary filesystem contents.

# 10. Prompt Contract

The Architect must be able to retrieve the current authoritative prompt.

Response should include:

```text
milestone ID
prompt path
prompt content

```

Prompt content may be returned in full up to the documented source-size limit.

Do not silently truncate.

If too large:

```text

do not provide partial misleading content
```

# 11. Workflow Contract

At minimum:



# 12. Closeout Contract

Expose:

```text

```

Do not infer acceptance merely because a closeout exists.

# 13. Git Contract

Expose a bounded deterministic summary such as:


Do not include full diffs by default.

Do not run fetch as part of read-only status.

Do not contact a remote unless a future milestone explicitly authorizes it.

# 17. Read-Only Invariant

Every Architect endpoint/query must be read-only.

It must not:

```text
append workflow events
change lifecycle
change selected milestone
create/update/delete prompt
create/update/delete closeout
create/update/delete workflow sidecar
change governing documents
stage
unstage
restore
commit
push
fetch
switch branch
create branch
delete branch
alter Git refs
write repository files
write external operational state
```

If any request would require mutation, reject it.

Do not use POST merely for convenience if GET can safely represent the request.

Do not add state-changing actions under the Architect namespace.

# 31. Stop / Escalation Conditions

Stop and ask the Product Owner before proceeding if:

- safe read-only exposure requires binding Repo Control beyond loopback;
- caller authentication is mandatory for even local read-only use and cannot be bounded simply;
- implementation requires arbitrary caller-supplied filesystem paths;
- implementation requires a new database;
- implementation requires workflow or Git mutation;
- direct ChatGPT/OpenAI integration becomes necessary;
- MCP becomes a materially different architectural commitment rather than a thin transport choice;
- source validation would need to be duplicated inconsistently;
- repository isolation cannot be guaranteed;
- contract responses cannot remain bounded;
- scope expands into general remote administration or full API redesign.

Do not silently broaden the milestone.
