## 3. Current-State Findings (The 3 Transport Gaps)

While M003.001–M003.007 established deterministic Git control, workflow sidecars, a six-state lifecycle engine, handoff packets, loopback Architect API, and a live Secure MCP Tunnel for ChatGPT, the Coder interaction loop remains heavily dependent on manual Product Owner transport across three distinct phases:

### Gap 1: Prompt / Instructions → Coder
- **Current Reality:** The approved milestone prompt exists in `docs/milestones/`. Repo Control records active milestone selection in an external operational file (`~/.local/share/repoctl/<repo_id>/milestones/selection.json`).
- **Friction:** The Coder running in VS Code Remote SSH on `henderson-server1` has no deterministic in-repo file indicating which milestone is selected. The Product Owner must either manually instruct the Coder in chat ("see docs/milestones/M003.xxx_prompt.md") or generate a monolithic Coder Handoff Packet in the browser and paste it into VS Code.
- **Packet Inefficiency:** The Coder Handoff Packet bundles the full prompt, full `coding_agent_rules.md` (1,270 lines), and full `project_workflow.md` (1,500 lines), resulting in a ~100 KB payload that consumes significant AI context on every initialization.

### Gap 2: Coder Question / Blocker → Architect
- **Current Reality:** When a coding agent encounters a blocker, conflict, or clarifying question during implementation, it writes the question as chat output in VS Code.
- **Friction:** The Product Owner must copy the text from VS Code, switch to the Repo Control Milestone tab, manually fill out the 8-field universal event form to record `question_submitted` (or manually copy the question into ChatGPT). Only after the event is recorded can the Architect inspect it via MCP `repo_workflow`.

### Gap 3: Architect Answer / Decision → Coder
- **Current Reality:** The Architect answers the question in ChatGPT.
- **Friction:** The Product Owner must copy the answer, navigate to Repo Control UI, record `answer_recorded` or `lock_in_approved`, optionally record `implementation_resumed`, and then copy/paste the answer back into VS Code chat to direct the Coder to resume.

## 4. Milestone Tab Assessment

The current Milestone tab (`src/repoctl/web/views.py` and `app.py`) serves as the Product Owner's primary workflow control surface.

### Current Strengths:
- Accurately discovers milestone candidates recursively beneath the server-configured `milestone_root` (`docs/milestones`).
- Supports explicit Product Owner milestone selection, persisted safely outside the repository in `~/.local/share/repoctl/<repo_id>/milestones/selection.json`.
- Displays authoritative lifecycle phase, prompt presence, closeout presence, binding lock-in, and open conditions.
- Reconstructs chronological workflow history from the tracked Markdown sidecar (`*_workflow.md`).
- Enforces strict transition validation and actor authorization (e.g. `po_approved=True` for binding events).

### Limitations & Target Role:
- **Not a Chat Application:** The Milestone tab is designed as an authoritative control surface and audit ledger, not a conversational UI. It should not be transformed into a live chat window.
- **Form Ergonomics:** The universal "Record a meaningful workflow event" form exposes all 19 event types and multiple optional fields in a single dense block. While functionally complete, it imposes unnecessary cognitive friction for routine events.
- **Target Role:** The Milestone tab should remain the authoritative interface for **governing decisions** (prompt approval, binding lock-ins, review acceptance, milestone closure) while routine, non-authoritative operational events (coder questions, bug reports, test records) are submitted directly by the Coder via CLI.

## 5. Candidate Mechanisms Evaluation

Six candidate mechanisms were evaluated against the technical requirements of Repo Control II:

### 5.1 Direct Filesystem Convention
- **Concept:** Coder reads local files directly in the repository workspace.
- **Pros:** Zero new tools or daemons; universally supported by any coding agent or IDE; transparent.
- **Cons:** Selection state is intentionally and strictly external (`~/.local/share/repoctl/...`); Repo Control explicitly forbids storing selection state inside the repository. The Coder cannot reliably deduce the selected milestone without guessing or inspecting untracked host paths.
- **Verdict:** Insufficient on its own for discovery, though essential for reading static repository files once identified.

### 5.2 Repo Control Read-Only CLI (`repoctl coder-context` / `repoctl coder-status`)
- **Concept:** Dedicated CLI subcommands in `repoctl` that inspect repository state, selection pointer, and workflow sidecar in-process.
- **Pros:**
  - **Co-location:** The Coder already executes in the repository environment on `henderson-server1` via VS Code Remote SSH.
  - **In-Process Access:** Direct access to `load_milestone_selection()`, `load_milestone_workflow()`, and `inspect_git_state()` without network roundtrips.
  - **Provider Neutrality:** Works identically across GitHub Copilot, Codex, Claude Code, Cline, Aider, OpenCode, Goose, or plain bash.
  - **Safety & Isolation:** Strictly read-only; respects multi-repository registry and external state directory.
  - **Context Efficiency:** Can return a clean, layered summary rather than embedding thousands of lines of standing rules.
- **Cons:** Requires CLI invocation by the coding agent (standard behavior during agent preflight).
- **Verdict:** **Strongest Candidate for Prompt → Coder.**

### 5.3 Generated Local Context File (`.repo-control/coder-context.md`)
- **Concept:** Repo Control background service writes an untracked, gitignored context file into the repo workspace upon selection or state change.
- **Pros:** Coding agent can read a file without running a shell command.
- **Cons:** Creates cache synchronization and staleness risks; introduces filesystem mutation side-effects to read-only API/web paths; risks accidental commits if `.gitignore` fails; creates a secondary source of truth.
- **Verdict:** Rejected due to staleness and synchronization risks.

### 5.4 Local Read-Only HTTP/API Access (`curl http://127.0.0.1:8765/api/...`)
- **Concept:** Coding agent queries the existing loopback Architect API.
- **Pros:** Reuses existing `/api/architect/v1/*` endpoints.
- **Cons:** Returns raw JSON requiring agent parsing; requires knowing server port and host; more brittle than a native Python CLI subcommand.
- **Verdict:** Viable as a transport layer, but inferior to a purpose-built CLI command.

### 5.5 Coder MCP (Model Context Protocol)
- **Concept:** Configure a local MCP server for VS Code Copilot or other agents exposing Coder tools.
- **Pros:** Structured tool invocation within modern agent chat interfaces.
- **Cons:**
  - **Configuration Overhead:** Requires per-client configuration (`.vscode/mcp.json`, agent settings, runtime paths) that varies across tools.
  - **Unnecessary Machinery:** For local processes on `henderson-server1`, standard CLI execution is faster, more reliable, and requires zero client configuration.
  - **Architect vs. Coder Asymmetry:** Architect needed MCP because ChatGPT runs in the OpenAI cloud; Coder runs locally on the server where the code and CLI already reside.
- **Verdict:** Over-engineered for local Coder on `henderson-server1`. Rejected for M003.009.

### 5.6 Coding-Agent Native Mechanisms (Tasks, Skills, Custom Instructions)
- **Concept:** Leverage VS Code Tasks or Agent Skills to run preflight commands automatically.
- **Pros:** Enhances agent ergonomics.
- **Cons:** Dependent on specific IDE/agent features; secondary to having a robust CLI foundation.
- **Verdict:** Complementary to CLI; planned for R004 (Agent Skills), but requires the CLI foundation first.

## 7. Recommended Prompt → Coder Architecture

### Selected Mechanism: `repoctl coder-context`
A new CLI subcommand in `src/repoctl/cli.py` backed by `src/repoctl/workflow/coder_interface.py`:

```bash
repoctl coder-context [--repository <path>] [--format text|json]
```

### Output Content (Layered Presentation):
1. **Repository Identity:** Verified repository key, path, and registry generation.
2. **Active Milestone:** Selected milestone ID and relative prompt path.
3. **Lifecycle Phase & Authorization:**
   - Current phase (`PLANNING`, `READY`, `IN_PROGRESS`, `WAITING`, `REVIEW`, `CLOSED`).
   - Explicit authorization statement (e.g. `IN_PROGRESS: implementation authorized`).
   - Next authorized action.
4. **Authoritative Prompt:**
   - Prompt path, title, and full prompt text (or section outline if requested).
5. **Durable Milestone Context:**
   - Latest Product Owner-approved binding lock-ins.
   - Active open conditions, blockers, and waiting reason.
   - Bounded recent workflow chronology (last 5 events).
6. **Standing Rules References:**
   - Links to `docs/context/coding_agent_rules.md`, `project_architecture.md`, and `project_workflow.md`.
   - Explicit Git mutation prohibition notice.

### Coder Operational Preflight:
In `docs/context/coding_agent_rules.md`, Step 1 of preflight becomes:
```bash
repoctl coder-context
```
The Coder immediately obtains authoritative instructions and boundary constraints without prompt copy/paste.

## 8. Recommended Coder Question → Architect Architecture

### Selected Mechanism: Narrow Direct Coder Submission (`repoctl coder-question`)
A dedicated, bounded CLI command allowing the Coder to record questions directly into the tracked sidecar:

```bash
repoctl coder-question "<summary>" [--blocking] [--category clarification|decision|blocker] [--scope <component>]
```

### Behavioral Invariants:
- **Actor Role Locked:** Automatically sets `actor_role="coder"`.
- **Non-Binding:** Strictly enforces `po_approved=False`.
- **Sidecar Persistence:** Invokes `record_milestone_event()` directly with `event_type="question_submitted"`.
- **Lifecycle Transition:**
  - If `--blocking`: Automatically transitions milestone lifecycle from `IN_PROGRESS → WAITING` with `waiting_category` and `waiting_reason`.
  - If non-blocking: Records question as open condition while remaining `IN_PROGRESS`.
- **Architect Visibility:** The question immediately appears in the sidecar and is retrievable by ChatGPT Architect via the existing live MCP tool:
  `repo_workflow` or `repo_milestone`.
- **Zero PO Clerical Overhead:** The Product Owner no longer copies text between VS Code and the Milestone tab. The PO simply prompts the Architect in ChatGPT: *"Review current Coder blocker"*.

## 9. Recommended Architect Answer → Coder Architecture

### Flow:
1. **Architect Review:** Architect calls `repo_workflow`, reads the Coder's open question and context, and provides an analysis and recommended answer/decision in ChatGPT.
2. **Product Owner Authorization:**
   - **For Non-Binding Clarifications:** Product Owner records `answer_recorded` in Repo Control UI (resolving the open question).
   - **For Binding Lock-Ins / Decisions:** Product Owner records `lock_in_approved` with explicit approval checkbox and clicks `[Resume Implementation]` (`implementation_resumed`), advancing lifecycle from `WAITING → IN_PROGRESS`.
3. **Coder Retrieval:**
   - The Coder runs `repoctl coder-context` (or `repoctl coder-status`).
   - The command outputs the resolved question, latest approved lock-in, and confirmed `IN_PROGRESS` phase.
   - The Coder resumes implementation with zero ambiguity.

## 10. Product Owner Authority Model

The recommended architecture strictly preserves Product Owner authority boundaries:

| Workflow Action | Authorized Role | Enforcement Mechanism |
|---|---|---|
| **Select Active Milestone** | Product Owner Only | Browser UI (`/milestones/select`) writing to external pointer |
| **Approve Prompt (`PLANNING → READY`)** | Product Owner Only | Sidecar validator requires `po_approved=True` |
| **Start Implementation (`READY → IN_PROGRESS`)** | Product Owner / Coder | Sidecar event `implementation_started` |
| **Submit Question / Blocker** | Coder / Product Owner | CLI `coder-question` (sets `actor="coder"`, `po_approved=False`) |
| **Approve Binding Lock-In** | Product Owner Only | Milestone tab requires explicit checkbox (`po_approved=True`) |
| **Resume Implementation (`WAITING → IN_PROGRESS`)** | Product Owner Only | Milestone tab event `implementation_resumed` |
| **Submit Closeout (`IN_PROGRESS → REVIEW`)** | Coder / Product Owner | CLI `coder-closeout` (requires closeout file present) |
| **Accept Milestone (`REVIEW → CLOSED`)** | Product Owner Only | Milestone tab event `acceptance_recorded` + `milestone_closed` |
| **Git Staging / Commit / Push** | Product Owner Only | Guarded UI actions; Coder strictly prohibited from Git mutations |

## 11. Coder Write Boundary Recommendation

### Selection: Model B — Narrow Direct Coder Submission
- **Model A (Read-Only):** Rejected because it forces the Product Owner to continue manually retyping or copying Coder questions into the UI.
- **Model C (Staged Proposal):** Rejected because queueing proposals adds substantial state machinery without meaningful security gain.
- **Model B (Selected):** The Coder is permitted to append only **four bounded, non-authoritative event types**:
  1. `question_submitted`: Open a question or blocker (can pause to `WAITING`).
  2. `bug_discovered`: Record an observed issue or defect.
  3. `test_result_recorded`: Record automated test run results (labeled as reported).
  4. `closeout_submitted`: Signal that closeout report is written and request `REVIEW`.

**Prohibited Coder Events:**
The CLI strictly forbids the Coder from submitting `prompt_approved`, `lock_in_approved`, `decision_recorded`, `implementation_resumed`, `acceptance_recorded`, or `milestone_closed`. Any attempt returns an error and rejects the write.

## 15. Security & Isolation Analysis

- **Filesystem Isolation:** The CLI operates strictly within the resolved repository root and respects `milestone_root`.
- **Locking & Concurrency:** All sidecar writes use the existing `STATE_ARTIFACT_LOCK` and atomic rename pattern (`.tmp` -> replace), preventing file corruption.
- **No Ingress / Public Ports:** The CLI is local-only; no new network ports or daemons are created.
- **No Git Access:** The CLI contains zero Git mutation operations.
- **Process Isolation:** Runs as the local user `chuck` under existing Linux permissions.
