# 1. Purpose

R003.00 established the Workflow Orchestration architecture direction.

R003.01 is the first implementation milestone in that arc.

The objective is to give Repo Control a deterministic, repository-scoped way to:

```text
discover milestone artifacts
+
show candidate milestones
+
require explicit Product Owner selection
+
persist the selected milestone operationally
+
display the selected milestone safely in a minimal read-only Workflow view
```

This milestone should not implement the full lifecycle, event model, handoff packets, direct Architect integration, direct Coder integration, acceptance workflow, or autonomous milestone progression.

The first slice is deliberately narrow:

```text
discover
→ validate
→ select
→ persist pointer
→ display
```

The purpose is to establish a trustworthy active-milestone boundary on top of the already accepted repository-selection and Git foundations.

# 2. Governing Architecture From R003.00

Treat the following R003.00 decisions as controlling for this milestone.

## 2.1 Tracked Markdown Remains Authoritative

Approved milestone prompts, future addenda/lock-ins, decisions, closeouts, review outcomes, and acceptance remain durable human-readable project evidence.

The operational selected-milestone record must not become a competing source of milestone truth.

## 2.2 Active Milestone Must Be Explicitly Selected

Do not infer the active milestone from:

```text
latest file
highest milestone number
modification time
creation time
only prompt without closeout
Git history recency
directory ordering
```

Repo Control may discover candidates, but the Product Owner must explicitly select the milestone.

## 2.3 Operational Pointer Only

The first implementation should store:

```text
selected milestone ID
canonical prompt path
repository identity
schema/version metadata as needed
```

in a small atomic repository-scoped operational record under the existing external Repo Control state model.

The record is a pointer only.

It does not itself establish:

```text
approval
phase
acceptance
closure
scope
requirements
```

## 2.4 Repository Scoping Is Mandatory

Milestone selection must be scoped to the currently selected server-configured repository.

A milestone selected for one repository must never be silently surfaced or used for another repository.

## 2.5 No Guessing on Invalid State

If the operational milestone pointer is:

```text
missing
stale
invalid
malformed
outside repository boundary
points to missing prompt
ambiguous
```

Repo Control must visibly require re-selection.

It must not silently choose another milestone.

# 4. Artifact Discovery Requirements

## 4.1 Discovery Root

Milestone discovery must operate only within the selected repository's configured milestone/documentation area.

Use the existing project/repository configuration where available.

For Repo Control II, current milestone documents are under:

```text
docs/milestones/
```

Do not search arbitrary filesystem locations.

## 4.2 Initial Artifact Types

At minimum discover:

```text
milestone prompt files
milestone closeout files
```

If the current repository already contains recognizable addenda or related milestone documents, inventory them only if doing so is safe and useful.

Do not broaden this milestone into full semantic artifact classification unless needed to avoid ambiguity.

## 4.3 Candidate Milestone Identification

Use a validated naming convention based on current repository evidence.

The implementation should be able to identify a milestone ID from a valid prompt filename.

Examples may include:

```text
R003.00_..._prompt.md
R003.01_..._prompt.md
```

The exact parser should be based on observed repository naming, not invented assumptions.

The implementation must reject or visibly flag malformed candidates rather than silently coercing them.

## 4.4 Prompt Is Selection Anchor

For the first slice, the selected milestone should be anchored to a validated prompt artifact.

A closeout without a corresponding valid prompt should not automatically become a selectable active milestone.

If existing repository history contains irregular artifacts, handle them visibly and safely rather than forcing all historical files into a new naming contract.

## 4.5 Canonicalization

Selected prompt paths must be:

```text
repository-relative or otherwise safely normalized
resolved inside the selected repository
validated against traversal / escape
checked for existence
checked for expected file type
```

Do not allow traversal, arbitrary absolute paths, symlink escape, cross-repository selection, or browser-supplied repository roots to defeat the configured repository boundary.

# 5. Selection Requirements

## 5.1 Explicit Product Owner Action

The Product Owner must explicitly select a candidate milestone.

Do not auto-select a milestone merely because there is only one candidate, it has the highest number, it is newest, it lacks a closeout, or it appears related to current branch state.

## 5.2 Selection Confirmation

The selection operation should clearly identify:

```text
repository
milestone ID
prompt path
```

before persistence.

Use the same safety philosophy as the existing prepared/revalidated Git actions where appropriate, but do not over-engineer a full prepared-action subsystem if the selection risk can be bounded more simply.

## 5.3 Reselection

The Product Owner must be able to select a different valid milestone for the same repository.

Reselection should:

```text
replace the operational pointer atomically
not mutate Git
not modify the prompt
not modify other milestone artifacts
not affect another repository's selection
```

# 6. Persistence Requirements

## 6.1 Storage Location

Use the existing Repo Control external per-repository state model if appropriate.

R003.00 identified:

```text
~/.local/share/repoctl/<repository_id>/
```

as the existing pattern for repository-scoped operational state.

Prefer integration with existing abstractions over inventing a parallel state root.

## 6.2 Record Shape

Keep the record intentionally small.

A conceptual example:

```json
{
  "schema_version": 1,
  "repository_id": "repo-control-ii",
  "milestone_id": "R003.01",
  "prompt_path": "docs/milestones/R003.01_milestone_artifact_discovery_and_explicit_selection_prompt.md"
}
```

This is illustrative, not a mandatory exact schema.

Do not store derived Git facts or duplicate prompt content in this record.

## 6.3 Atomicity

Write/update the operational pointer atomically.

A partial or interrupted write must not leave a misleading valid-looking selection.

## 6.4 Schema Validation

On read:

```text
validate schema/version
validate repository identity
validate milestone ID
validate prompt path
re-resolve prompt inside selected repository
verify file still exists
```

If validation fails, return an explicit invalid/stale state and require Product Owner re-selection.

## 6.5 Restart Behavior

The selected milestone should survive Repo Control service restart for that repository.

Repository selection may still return to the configured default on service restart.

The implementation must ensure that the default repository after restart loads only that repository's milestone pointer and never carries over another repository's active milestone.

# 2. Product Owner Lock-In â€” Canonical Milestone Artifact Standard

## 2.1 Canonical Milestone Root

Repo Control-managed milestone artifacts must live beneath a configured **milestones root** for that repository.

Examples of acceptable configured roots include:

```text
docs/milestones/
milestones/
```

For new projects, prefer:

```text

```

For existing/historical projects, the configured root may point to the project's existing milestone directory if that is the practical migration path.

The important rule is:

```text
one configured milestone root per repository
```

Repo Control must not scan the whole repository looking for milestone artifacts.

---

## 2.2 Folder-Agnostic Beneath the Milestone Root

Discovery should be recursive beneath the configured milestone root.

Human-readable subfolders are optional.

Examples that should be equivalent for machine discovery:

```text
docs/milestones/M003.001_example_prompt.md

docs/milestones/arc_003/M003.001_example_prompt.md

docs/milestones/workflow_orchestration/M003.001_example_prompt.md

```

Folder names are for human organization only.

They must not define:

```text
process type
arc ID
milestone ID
artifact type
workflow state
```

Machine identity comes from the canonical filename.

All resolved files must remain inside the configured milestone root and repository boundary.

Symlink/traversal protections remain mandatory.

# 3. Canonical Filename Grammar

The forward-looking filename contract is:

```text
<process_code><arc_id>.<sequence>[.<subsequence>...]_<name>_<artifact_type>.md
```

For the current milestone process:

```text
process_code = M
```

Meaning:

```text
M = Milestone
```

Only explicitly defined process codes are valid.

Do not invent additional codes in this milestone.

Future process types may use other leading alpha characters if explicitly defined later.

---

## 3.1 Numeric Components

Each numeric component is exactly three digits.

Examples:

```text
M003.001
M003.002
M003.010
M003.010.001
M003.010.002
M004.001
```

Meaning:

```text
M
â†’ process type: Milestone

003
â†’ arc ID

001
â†’ sequential milestone number within arc 003

.001
â†’ optional sub-milestone level

additional .NNN
â†’ optional deeper bounded sub-milestone levels if ever needed
```

The default should remain simple:

```text
M003.001
M003.002
M003.003
```

Sub-milestones are optional and should not be required for ordinary question, clarification, bug, or event handling.

---

## 3.2 Human-Readable Name

The `<name>` portion should remain a lowercase human-readable snake_case slug.

Example:

```text
milestone_artifact_discovery_and_explicit_selection
```

The name is descriptive but is not the machine identity.

The canonical milestone identity is the process code plus numeric hierarchy.

---

```text
closeout
```

Examples:

# 4. Prompt / Closeout Pairing

- recursive discovery creates an unbounded performance or security concern;
- current Repo Control historical compatibility cannot be preserved without a large compatibility subsystem;
- canonical and legacy IDs cannot be distinguished safely;
- the change would require renaming/moving historical artifacts;
- the scope would expand beyond artifact discovery/selection;
- existing Product Owner Git authority or repository isolation would be weakened.
