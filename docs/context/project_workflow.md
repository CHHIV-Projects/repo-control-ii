# Repo Control II operating workflow

**Baseline:** As of accepted M011.004 and the M011.005 documentation reconciliation. The operating agreement applies across milestones. Live Repo Control determines the selected repository, scope and lifecycle.

[Roles](#roles-and-authority) · [Normal cycle](#normal-milestone-cycle) · [Startup](#cold-start-handoff-and-warm-continuation) · [Evidence and closeout](#validation-and-closeout) · [Operator boundaries](#shared-procedure-operator-boundaries)

## Roles and authority

| Role | Working agreement |
|---|---|
| Product Owner (PO) | Owns outcomes, priority, repository and milestone selection, approvals, scope changes, lock-ins, blocking resolutions, correction, acceptance/closure, deployment and consequence-bearing operations. Owns all Git mutation, including stage, commit, push, tag and merge. |
| Architect | Reads bounded connected evidence, reasons about scope/architecture, submits typed pending PROMPT/INSTRUCTION/RESPONSE drafts, answers questions through the approval path, reviews actual evidence and recommends acceptance or correction. Evidence tools are read-only. Typed proposals do not grant authority to execute commands, set lifecycle, approve, write files or mutate Git. |
| Coder | Uses the local canonical CLI, verifies worktree and authority, reads targeted evidence, follows applicable Skills and works within the approved prompt/correction. Records bounded questions, bug discoveries, actual test outcomes and one closeout. Git use is read-only throughout. |
| Repo Control | Resolves registered identities, enforces transitions and transactional write boundaries, and projects deterministic observed facts. Browser lifecycle actions use reported PO attribution and deliberate action buttons. This single-user boundary does not authenticate the human's identity cryptographically. |

Standing roles are `context`, `architecture`, `workflow`, `coding_agent_rules` and `parking_lot` from the server registry. [Context](project_context.md) records product purpose and the dated baseline. [Architecture](project_architecture.md) owns system/data/security boundaries. This workflow describes human/agent actions. The [Coder overlay](coding_agent_rules.md) adds repository constraints and the [parking lot](canonical_parking_lot.md) holds future options. The generated [bootstrap](../../AGENTS.md) and [workflow core](../../.repo-control/workflow_core.md) carry generic procedure. They do not override PO authority or the active prompt. Stop on material conflicts between governing rules, approved scope and observed facts.

## Normal milestone cycle

1. **Define and propose.** PO and Architect agree on outcome, mode, correct repository, scope, excluded action surfaces, required evidence, stop conditions and closeout. Modes include reconnaissance-only, implementation after reconnaissance, direct low-risk, validation-only, documentation-only, bounded repair, integration/tool evaluation and operational validation. Treat changes to architecture, authority, risk, persistence or substantive acceptance criteria as re-scope decisions. Record meaningful clarifications while leaving routine prose decisions in conversation.
2. **Approve transport and select.** Architect submits a typed pending draft. PO reviews actual bytes in Architect Dispatches and approves or rejects. **Approve & Save Prompt** authorizes storing the prompt in the configured authority, separate from selecting or starting it. Subsequent INSTRUCTION/RESPONSE approvals are durable scope-bound guidance. Applicable approved text is already available to the Coder, so the PO need not retype it as a second summary. Approval of dispatch transport alone emits no lifecycle transition. Coder excludes pending, rejected and other-milestone drafts.
3. **Approve and start the exact prompt.** PO selects the registered repository and milestone deliberately. Newest filenames, Git history and the absence of a closeout are irrelevant. Use **Approve & Start** when offered. The selected managed prompt's exact approved revision is durable in SQLite. A Git commit of that prompt is not a prerequisite in managed mode. A worktree draft or materialized-prompt case proceeds only under the exact managed/file authority and dirty-path protections described below.
4. **Verify and work.** The Coder resolves local context and preflight, records or escalates only material issues, then works within approved scope. Use accepted reconnaissance rather than repeating it. A question, clarification or defect need not start a new milestone when it remains within the approved objective.
5. **Validate and submit.** Reuse accepted evidence at its actual scope, record new actual results and submit one exact closeout through the canonical Coder workflow. In REVIEW, the Architect examines exact closeout, binding decisions, tests, current Git and open conditions before a recommendation. A requested correction returns to IN_PROGRESS for the bounded correction only, with an updated revision and proportional validation.
6. **PO acceptance, Git disposition and closure.** PO judges the evidence and accepts or requests correction. Review the exact local file set before any PO stage, inspect staged state before commit and distinguish local commit from remote verification. Manage accepted artifact publication and other Git disposition through the reviewed PO action or document deliberate deferral. **Accept & Close** records acceptance then closure. Git and lifecycle are independent operations; coordinate their order with the particular publication prerequisites.

## Lifecycle and conditions

| Phase | Authority and transitions |
|---|---|
| PLANNING | Selected proposal under review. Work begins only after PO approval and start. |
| READY | Prompt approved, awaiting explicit start. **Approve & Start** records `prompt_approved` then `implementation_started` as distinct ordered events. The contextual Start action applies to an already READY milestone. |
| IN_PROGRESS | Authorized bounded work or correction. `coder-question --blocking` or a qualifying escalation can move the milestone to WAITING. Submit a matching verified closeout to request REVIEW. |
| WAITING | Stop implementation. Record the active question answer or escalation resolution, optional separate binding lock-in, then `implementation_resumed`. **Resolve & Resume** combines those steps. A previously recorded resolution can permit explicit Resume. Answering an unrelated question does not resolve the active blocker. |
| REVIEW | Coder authority ends. Review evidence, request a bounded correction or accept. Closing requires PO direction and admissible open-condition state. |
| CLOSED | Acceptance and closure recorded. A reasoned PO reopen appends an event targeting REVIEW or IN_PROGRESS and preserves historical decisions. A reopen to REVIEW permits reconsideration without editing; an IN_PROGRESS reopen bounds continuation to the authorized scope. |

The lifecycle is a validated projection of state and ordered events. Selection, health, approvals, implementation authority and event chronology are separate facts. Combined lifecycle actions validate all constituent transitions atomically. Neither passing tests nor Git status, file presence, local commits or pushes advance lifecycle on their own. Before Accept & Close, a newly approved applicable INSTRUCTION/RESPONSE after the latest closeout requires an amended closeout or a deliberate second PO confirmation recording the reason and affected dispatch IDs. A valid preceding acceptance can be reused. Browser status polling refreshes untouched forms and preserves edited input while blocking stale submissions. Legacy extended live polling coverage was limited.

A Coder records a defect using `coder-bug`. PO classification distinguishes `in_scope` from `needs_escalation`. A real in-scope fix and its verification may be recorded via `coder-bug-fixed` and `coder-test` within applicable authority. The platform has no general `bug_deferred` transition. A PO-approved deferral can remain visible/open even after a scoped CLOSED evaluation. Generic `decision_recorded` evidence does not close a bug. A later fix in a different milestone may leave the original status open; link accepted evidence rather than reopening or manufacturing an event solely to clear a counter. Imported CLOSED history has no current implementation authority. [Accepted M011.004 dispositions](../milestones/M011.004_cross_repository_authority_historical_evidence_and_onboarding_reliability_reconciliation_closeout.md#6-questions--decisions-incorporated) · [Cross-milestone gap](canonical_parking_lot.md#workflow-009--cross-milestone-bug-resolution-tracking)

A **hard blocker** stops current authorized work or a required safety/acceptance action. **Deferred** is a recorded PO scope decision. **Unverified** identifies missing proof. **Functional-evaluation ready** supports the approved evaluation criteria. **Production-release ready** requires separate approved operator evidence for the exact installed version and recovery surface.

## Cold start, handoff and warm continuation

`Prompt ready.`, `Instruction ready.` and `Correction ready.` are notifications. Never infer authority from the message, filename, packet or chat. The Coder opens the intended registered worktree and runs:

```bash
/home/chuck/.venvs/repo-control-python-3.12.16-sqlite-3.51.3/bin/python -m repoctl.cli coder-context
```

On NEW, HANDOFF, AUTHORITY_TRANSITION or RECOVERY, use the generated [bootstrap](../../AGENTS.md) to run bound `coder-verify` with expected key, repository ID/root, milestone and Git-boundary acknowledgement. For managed mode also match exact selection ID/revision and prompt document ID/revision/SHA-256. Read repository/generation, selected prompt, lifecycle, authorization, applicable approved dispatches/lock-ins, procedure and overlay. On HANDOFF, reconcile open questions/bugs, evidence, closeout and read-only branch/HEAD/status. Stop if identity does not match, state is unavailable, authority is unclear, dirty ownership is unexplained, or verification is BLOCKED/PARTIAL_UNVERIFIED. RELEASE_PREPARATION authorizes only the marked release procedure. Correction authorizes only stated work. A warm interaction with intact authority does not require a duplicate audit. Refresh affected authority before a consequential transition.

The PO selects repositories via registered browser keys. Coder resolves local root against the same central registry. Architect binds reads and proposals to current key/generation and selected milestone where required. A stale request or different repository must fail closed and be refreshed; neither agent silently changes global selection. See the [authority map](project_architecture.md#authority-and-state).

Use read-only Git branch, status, recent history and relevant diff. An exact materialized prompt permission requires the same approved prompt path/bytes. Exact dirty snapshots, where applicable under current instructions, bind every declared path and SHA-256; they do not cover staged, conflicted, mismatched or unrelated work. File/ledger mode retains its narrow active-sidecar exception. No generic dirty-tree bypass applies and no prompt needs a premature Git commit merely to satisfy a ritual. If ownership is uncertain, preserve the files and escalate.

Native Codex/Copilot SessionStart uses the qualified interpreter and canonical context. Treat delivered startup text as stale when its version or binding disagrees. Fetch current context and verify before work. Inspect independent evidence of real native delivery and review trust for the exact changed Codex hook via its UI. A VERIFIED context-verification observation binds a snapshot and records agent-reported trigger, with unverified session identity and provider delivery. It is not a provider attestation. Read [host evidence and limits](project_architecture.md#hooks-procedure-and-operator-execution) and the [continuity contract](../guides/coder_session_continuity_contract.md). Use the explicit implementation, blocker/bug and validation-closeout Skills for their applicable work; they carry procedure without authority.

## Managed artifacts and legacy files

| Artifact | Managed practice |
|---|---|
| Prompt | Use the selected exact approved SQLite revision. Review exact text/metadata before approval. File-backed mode uses the explicit registered prompt under the milestone root and applicable exact-byte checks. |
| Workflow | SQLite preserves state, append-only events, conditions and approvals. In explicitly configured legacy mode the canonical `*_workflow.md` sidecar holds the file-backed event history. The sidecar never selects a milestone on its own. |
| Closeout | The draft is a human-readable work artifact. Managed submission binds an immutable revision to the selected workflow; PO acceptance and an explicit Git publication action govern export of an accepted revision. A Git file using the same basename can differ from the event-time version. Keep prior revisions and their provenance. |
| Packet | Coder Handoff and Architect Review Packets are derived read-only fallback exports. Their repository, milestone and observation time matter. During a disconnect, use a packet for bounded evidence and confirm authority before consequential work. Packets confer no new scope or transition. |

New exported prompt/closeout names follow `M<arc>.<sequence>[.<subsequence>...]_<snake_case_name>_{prompt,closeout}.md` under the registry milestone root. Numeric components each use three digits. A matching legacy sidecar uses the same basename plus `_workflow.md`. Subfolders organize files but do not define identity. Preserve old names and exact revision references. Keep one closeout. Consolidate transient narrative into that closeout after verifying rationale, test evidence and outstanding obligations are retrievable. Separately authorized executable evidence, machine-readable results or durable operator references may have independent value. ## Validation and closeout

Run checks proportional to scope and risk. Prefer prior immutable accepted observations where unchanged. Use source, fixture, native host and live evidence only for what each tested. Report failures/skips and uncertain outcomes honestly. Before more probes, ask what material decision would change. Stop repeated patches or retests when confidence decreases; preserve the baseline/evidence and ask for the smallest explicit PO choice.

Use the same qualified interpreter with these bounded CLI commands:

| Command | Purpose |
|---|---|
| `coder-status`, `coder-context` | Read authoritative selected state, current blockers, prompt and approved guidance. |
| `coder-question "<summary>" [--blocking]` | Record precise question and context. Use blocking only when work cannot continue safely. |
| `coder-bug "<summary>"` | Record a discovered defect with impact and evidence. |
| `coder-bug-fixed --bug-event-id <id> "<summary>"` | Record a real, verified fix for the classified in-scope discovery in the current milestone. |
| `coder-test "<summary>" --source "<procedure>" --result "<outcome>"` | Record actual outcomes as reported evidence, distinguish independent confirmation. |
| `coder-closeout --draft-file <canonical-path> --content-sha256 <exact-sha256> --summary "<scope>"` | Submit the selected managed draft via exact contents, or use exact `--document-id`, `--revision-id` and `--content-sha256` for an existing managed revision. Confirm REVIEW and stop. Use the applicable legacy path only under file/ledger authority. |

The normal closeout sections are Scope Completed, Resulting Behavior, Files Changed, Architecture / Integration Notes, Validation Performed, Questions / Decisions Incorporated, Deviations from Prompt, Known Limitations, Deferred / Follow-Up Work, Recommended Next Milestone and Git Status. Record SHA/provenance for applicable evidence and report read-only Git branch, HEAD, changed paths and limits at preparation. Evolving status remains live in Git. Do not claim acceptance from the draft or a Coder submission.

Repository Intelligence is optional evidence when material. Use bounded current queries, verify source for dynamic/cross-layer behavior, and record USED, NOT USED or NOT AVAILABLE with the cause. STALE by itself is not NOT AVAILABLE. Keep graph refresh receipts distinct from evidence use and optional consumer feedback. PO Approve & Start may establish the required CURRENT baseline for supported repositories; unsupported configurations report NOT AVAILABLE. An authorized IN_PROGRESS Coder may refresh only when noncurrent graph evidence materially helps; no query silently rebuilds. [Intelligence guide](../guides/intelligence_value_tutorial.md)

## Shared procedure operator boundaries

- Canonical shared procedure 1.5.0 and Repo Control II CURRENT were observed at the baseline. Each registered repository pins its own manifest and hashes. Release 1.4.0 added optional root `AGENTS.md` rendering to the historical 1.3.0 target set. Protect a preexisting `AGENTS.md` without matching lock provenance even when its text matches. Publishing a canonical release alone may produce expected version drift and does not apply it anywhere.
- Inspect `coder-procedure-status` and deterministic `coder-procedure-preview`. In Procedure Updates, use Review Update then separate CSRF-protected PO Confirm Apply for one registered repository. Confirm seals a reviewed request and the supported executor revalidates scope. Independently verify the full generated set as CURRENT and use ordinary PO Git Review. Status, preview and GET are read-only. The internal materializer is not a Coder command. Recover requires its own exact-image review/confirmation; unknown images, unsafe paths and corrupt journals stop. Apply/Recover cannot silently switch selection, modify local project overlays or Git, update other repositories or certify provider delivery. [Executor architecture](project_architecture.md#hooks-procedure-and-operator-execution)
- A separately reviewed first-time overlay initialization is available for an existing safely mapped UTF-8 rules file that fails the structural contract. Reject missing/unsafe/ambiguous or oversized content. PO reviews repository, bytes, complete diff, hashes and candidate contract; the old text remains a byte-identical suffix and role mapping stays fixed. Separate CSRF-protected confirmation and exact-image transaction apply only that mapped file. Then separately review ordinary Apply, verify CURRENT and run the correct bound verification. Neither step starts a milestone. Photo Organizer needs current mapping/activation and native proof before applying any historical runbook. [Onboarding guide](../guides/repository_onboarding_and_integration_guide.md) · [Photo Organizer checks](../milestones/M011.004_operator_acceptance_preflight.md#photo-organizer-document-cleanup-proposal)
- The separately authorized M009.017 role remap uses `coder-procedure-remap-preview` with all five exact paths, `coder-procedure-remap-stage --plan-sha256 <reviewed-hash> --confirm`, then an operator restart/target selection and `coder-procedure-remap-status` and `coder-procedure-remap-activate --operation-id <id> --confirm`. Preview requires the registered target selection and a nonstale central registry. Review old/new role map, references, hashes, registry, Git, milestone and restart/rollback prerequisites before staging. The registry is written last. Activation verifies the new runtime, exact map, milestone, document hashes and CURRENT result. On a failed activation, reviewed out-of-band `coder-procedure-remap-recover --operation-id <id> --confirm` restores only known before-images, followed by restart and rollback verification. This is not atomic across files and restart. Neither agent edits role files, lock or runtime to bypass blocked state. [Remap contract and exact prerequisites](../milestones/M009.017_po_controlled_governing_role_remap_and_overlay_rebinding_closeout.md)
- Canonical release preparation requires the current manifest digest, a higher candidate and explicit scoped marker, strict read-only preview and revalidated publication. The v2 marker can bind the specific authorized root AGENTS artifact map addition with repository/milestone identity. Publication is separate from rollout and only the exact authorized release scope is eligible. [Release procedure](../guides/runtime-compatibility-and-procedure-release.md)

## Git and live operations

Coder uses read-only Git. Stage/unstage, commit, push, tag, merge, rebase, reset, restore, checkout/switch, stash, clean, branch creation/deletion and remote mutation belong to the PO. Inspect exact intended files and keep unrelated work out of the logical commit. Tracking refs alone do not prove current remote state. [Prepared actions and security](project_architecture.md#runtime-and-security)

Production database changes, NAS operations, backup/restore, service/timer/systemd changes, trust changes, code cutover and rollback require separate PO/operator authorization and reviewed exact identities. Cross-repository edits require approved scope in that repository. Code rollback uses the prior verified release and effective configuration with compatible state. Database restore has its own authority and integrity checks. Avoid treating a live checkout, service PID, backup exit code, historical restore or a functional acceptance as a release receipt. [Recovery boundaries](project_architecture.md#recovery-and-operational-assurance) · [Deferred rollout and smoke matrix](../milestones/M011.004_operator_acceptance_preflight.md#operator-sequence-and-smoke-matrix)

## How a future Architect starts

1. Use connected `repo_status`, `repo_workflow` and `repo_prompt` for exact selected identity, phase, prompt and approved guidance. Use `repo_review`, `repo_git`, `repo_evidence` and `repo_closeout` as needed. Never run local Coder commands or assume provider-hook delivery.
2. Read the four project governing documents and the mapped Coder overlay when relevant, the latest accepted closeout, and the present open conditions. Compare only the portions of historical evidence that bear on the decision. If live tools are unavailable, a current bounded review packet is an evidence fallback.
3. Recommend acceptance, bounded correction, a PO decision, or deferral against agreed evidence. For a real blocker record the conflict, observed facts, affected scope, smallest safe options and pending work. Send through the typed draft/PO review path. Avoid redundant confirmations, re-testing proven functionality, and new work whose evidence cannot affect the PO decision.
