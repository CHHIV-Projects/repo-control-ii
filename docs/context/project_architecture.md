## Authority and state

```text
Product Owner → loopback browser → Repo Control service → managed SQLite InformationStore
                                  ↘ prepared Git operations → registered local Git → GitHub
Architect → Secure MCP Tunnel → bounded Architect API → current / historical evidence
                                                     ↘ pending typed dispatches
Coder + native SessionStart → local canonical CLI → managed context and bounded events
Repository roots → role-mapped Markdown, shared-procedure copies, Git and worktree providers
Qualified runtime → service / CLI / hook paths and backup publisher / monitor
```

| State or boundary | Authority | Mutations and readers |
|---|---|---|
| Eligible repositories and governing role paths | Server-controlled [registry](../../ops/repositories.toml) | PO controls configuration and role remap. Browser and API resolve keys and assert repository/generation server-side. Clients cannot inject paths or synthesize repositories. |
| Which repository is selected | Live service selection and registry generation; managed selection is persisted and validated against the bound registry | PO selects. Requests carrying the wrong key or stale generation fail closed. Service startup reconciles its own selection/registry context, so stale clients refresh. |
| Which milestone and approved prompt govern | R8 SQLite managed selection and exact revision/approval, with the required compatibility selection file at the accepted baseline | PO selects/approves/starts. Browser and qualified CLI must agree on the resolved repository, milestone, selection revision and prompt binding. A compatibility file is an operational prerequisite in this baseline. It must never grant authority on its own. |
| Lifecycle and decisions | Managed workflow state, chronological events, exact document approval/link records and applicable approved dispatches | PO approves consequential transitions. Coder appends only bounded questions, discovered bugs, reported tests, verification and closeout events. Architect can submit pending typed proposals. |
| Source, index, branch/HEAD, history and reviewed exports | Local Git for local facts, GitHub for actual remote tips | PO owns mutations. Observed ahead/behind uses local tracking refs unless explicitly refreshed. Historical/working-tree document reads identify provider and revision. |
| Durable document content | Role-mapped working-tree Markdown for standing project context. Managed documents and immutable revisions for selected approved prompt and submitted/accepted closeout | Canonical context decides which revision is executable. A local draft or later Git export does not replace it. Historical authorities and provenance are retained. |
| Procedure and host delivery | Versioned shared sources, repository-local hashes, and each provider's actual hook definition and persisted delivery evidence | PO installs/rolls back per target and controls exact provider trust. Version/integrity, verified context and provider delivery are three distinct facts. |
| Derived evidence | Git/status summaries, packets, scanner cache and graph store | Bounded readers and scoped producers. Each carries provenance/freshness. Derived results cannot become a competing authority. |
| Recovery | R8 managed DB and exact verified manifests, payload and receipt linkage, plus separate procedure journal state | PO/operator owns live backup policy and restore. Guarded writes require coverage bound to the managed database and authority. |

## Runtime and security

- The observed Flask/systemd web service runs as `chuck` at `127.0.0.1:8765` on `henderson-server1`. The tracked base unit and effective installed drop-ins differ. Inspect effective configuration and import locations before a release. Earlier reports observed multi-second health latency under polling. Windows uses a per-user scheduled SSH local forward and a [launcher](../../ops/windows/RepoControlLauncher/) fallback. Reuse a healthy tunnel, reject an unrelated listener, preserve SSH host-key verification, avoid embedded credentials and keep startup unattended without a console or Windows service. [Web unit](../../ops/systemd/repo-control.service) · [Effective M011.004 observations](../milestones/M011.004_operator_acceptance_preflight.md#effective-service-and-release-identity)
- The Architect tunnel is outbound, terminates on the loopback API and uses a dedicated `repo-control-architect-tunnel.service` and fixed stdio adapter. Its API key/tunnel ID belong outside Git in private configuration (historically `~/.config/repo-control/tunnel.env`, mode 0600). It supplies bounded evidence GETs and fixed typed proposal POSTs. It exposes neither a general shell nor arbitrary filesystem/Git access. Local tool inventory and remote ChatGPT catalog visibility require separate checks when tools change. [Architect adapter](../../src/repoctl/mcp/architect_adapter.py)
- The accepted browser Git surface includes status/diff/history, exact-path stage/unstage/restore, staged commit, clean branch switching, safe local branch create/delete, fetch, non-force push, first publish with upstream, and fast-forward-only update. Merge/conflict resolution, rebase, cherry-pick, reset/stash/reflog, worktrees/submodules, force push, arbitrary refs/refspecs, remote deletion/config edits, tags and PR/CI operations are outside that baseline. The PO may use manual Git for advanced operations. Prepare binds the action to repository, selection and exact state. Confirmation tokens are short-lived, single-use and revalidated. Verify the resulting authoritative state, including the actual remote tip for Push. [Git actions](../../src/repoctl/workflow/git_actions.py)
- Remote Git is noninteractive: no terminal prompts, askpass, or stdin. Use SSH BatchMode and normal strict host-key checks. Repo Control II's dedicated alias is `github-repo-control-ii`, with remote `git@github-repo-control-ii:CHHIV-Projects/repo-control-ii.git`. The repository-scoped, filesystem-protected deploy key is outside the checkout. Its passphrase-free unattended use is an accepted tradeoff. Separate project identities and keep secrets, service credentials and environment contents out of agent context.
- Managed authority requires SQLite at least 3.51.3. Qualified host Python is 3.12.16 with SQLite 3.51.3. The checkout's older 3.45.1 runtime returned exit 2. At the M011.004 service observation the qualified venv still imported from the editable tree, including web, scheduled backup, monitor and on-demand procedure execution. Source edits can therefore affect the next process. The existing web process's already loaded revision was unproven. Forward source archive and qualified binaries need their own provenance. ## Document and history contracts

The [document library](../../src/repoctl/document_library.py), [Architect API contract](../../src/repoctl/web/architect_contract.py), [browser](../../src/repoctl/web/app.py) and [MCP adapter](../../src/repoctl/mcp/architect_adapter.py) expose complementary reads. `repo_document` reads the five registered governing roles. `repo_read_document` requires an explicit repository-relative text-document path, expected repository key and generation. It is bounded to supported text under allowed documentation roots, root README and Skill files. Symlinks, traversal, source/secrets, arbitrary roots and history paths do not qualify. It reads the working tree, including modified/untracked allowed documents, with a 128,000-byte response bound and 5,000,000-byte file limit.

Historical search is repository-local and ties candidates to the configured milestone root and supported `docs/history/` convention with Git-worktree and managed SQLite provenance. Use search then repeat the advertised path, `document_id` and `revision_id` for exact reads. A single-match path-only read remains compatible. An ambiguous path returns `ambiguous_historical_revision` (409). The selected milestone is excluded by default. Explicit `include_selected_closed=true` belongs on both search and exact read, and only applies to a selected CLOSED milestone. Conditions from CLOSED imports may be visible as historical/nonblocking evidence with no synthetic resolution or executable authority. Unverified closeout provenance remains structured and inspectable without supplying current bytes as the historical submission. Provider warnings stay within the selected repository.

History limits protect the service and avoid deceptive complete results. Broad inventory requires a milestone or paired category/type filters, pages default to 10 with a maximum of 20 results, and incomplete candidate discovery reports `historical_discovery_incomplete` (503). Search returns provenance and match metadata rather than source excerpts. Use the returned signed continuation and repeat the same query, filters and limit. Changed inventory can return `stale_history_cursor` (409), and malformed or wrong-query cursors return `invalid_history_cursor` (400). Restart invalidates open cursors where the service signing key is in memory. Oversize, unsafe and invalid text fail explicitly. [Operator contract](../guides/repo_control_user_guide.md#architect-reads-of-historical-project-evidence)

M011.004 prepared shared provenance, isolated provider diagnostics and exact selectors, validated by 231 focused regressions (`3a50c42f985e4bfaa4cc00c1babb6b80`). The old service returned 400 for the added selected-CLOSED option and 409 `stale_repository_selection` for a nonselected Photo Organizer request. This shows the old guard and the forward deployment gap. Acceptance on the changed browser/API/MCP surfaces and correct Photo Organizer selection remains outstanding. ## Recovery and operational assurance

| Component | Recorded design and evidence |
|---|---|
| Backup publisher | R8 backup every 15 minutes. Managed DB snapshot, integrity checks, fsynced/staged outputs, ordered payload/manifest publication and local verified recovery receipt. The separate procedure journal is outside SQLite backup coverage. |
| Verification and write eligibility | Verify manifest SHA-256 using canonical JSON with `manifest_sha256` removed. Raw file bytes contain the embedded digest and final LF. ## Architecture decision baseline

**Decision status:** Open for Product Owner choice following the M011.004 evaluation. These are alternatives and evidence thresholds. Scope and release acceptance are later decisions.

| Alternative | Benefit | Costs and risks | Evidence that favors or rules it out |
|---|---|---|---|
| Retain and repair | Keep known managed data, browser/CLI/hook contracts and operational investment. A narrow fix can close discrete launch and packaging gaps. | Coupling among compatibility pointers, runtime packages, guard checks and operator steps remains. Local fixes can start new defect loops. | Favor if one bounded scope can show scheduled reliability, frozen imports and rollback with the current store and tolerable routine operator effort. Reconsider if failures recur across unrelated paths or verification expands again. |
| Simplify/refactor | Preserve working data/authority while reducing redundant state, catalog work, release configuration or operator handoffs. M010.031 and M011.004 identify candidate seams. | Indirection can move elsewhere. Changing selection or recovery policy risks stale authority, reduced integrity coverage and compatibility failures. | Favor if a concrete subsystem redesign eliminates a whole maintenance/approval burden and can be compared to the existing store/contracts in isolated fixtures with reversible rollout. Require explicit guard/integrity tradeoffs and preserved provenance. |
| Rebuild | Design for the actual single operator with only proven high-value capabilities and an explicit migration path. Reuse proven boundaries and tools. | Highest migration, validation and operational transition burden. Risk of losing historical IDs, exact permissions or event order and reintroducing already fixed failures. | Favor only if a credible end-to-end slice preserves the five pillars and data/provenance through import and tested rollback, and combined migration/operation cost is justified by recurring effort avoided. A smaller codebase alone does not establish that case. |
| Defer | Preserve working functional evidence and avoid more speculative work. | Existing release gaps and failure exposure remain. A release decision still needs evidence. | Favor if the owner does not need cutover or the value of new work cannot justify its total effort. Revisit on a concrete use, recovery or maintenance constraint. |

Evaluate each option on correctness in the five pillars, authority/implementation complexity, operator steps and time, restore and rollback behavior, I/O plus memory proportionality, state and provenance preservation, deployment reproducibility and accepted single-user risk. Set a small timeboxed decision scope before any candidate work. Prefer exact observed failure/evidence and expected reduction in operating effort over a new framework or another full proof cycle. Invariants are PO Git/approval ownership, fail-closed repository isolation, explicit lifecycle, durable exact approval/closeout history, bounded secret-free evidence and recoverability.
