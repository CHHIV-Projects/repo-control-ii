What is and is not synchronized

Only the versioned generic procedure bundle may be materialized through an explicitly authorized future workflow. These five repository-owned governing documents and overlays are never generic synchronization targets:

  • Project context — docs/context/project_context.md
  • Project architecture — docs/context/project_architecture.md
  • Project workflow — docs/context/project_workflow.md
  • Repository-specific Coder rules overlay — docs/context/coding_agent_rules.md
  • Canonical parking lot — docs/context/canonical_parking_lot.md

Milestone prompts, decisions, workflow sidecars, and closeouts follow their own repository and lifecycle authority. Host-level project instructions and tool settings are controlled by the user/PO in that host; Repo Control cannot install them.

Apply journals and recovery images are stored in the service user's private transaction sibling directory, outside managed worktrees and scanner-replaced state. Interrupted transactions block new Apply. Recover is an explicit, separate PO confirmation and restores only the verified original state; changed files that match neither known image require manual escalation. The journal provides crash detection and recovery, not simultaneous six-file visibility or a guarantee against non-cooperating external writers.

Fresh-session startup check

  1. Did the host load Repo Control instructions and expose the required tool?
  2. Is the intended managed repository explicit and the service-selected key correct?
  3. Is a milestone selected, and what lifecycle phase does current Repo Control state report?
  4. Does that current state authorize this role and action? A handoff phrase is not approval.

If any answer is unknown, stop and use the operator fallback and copy-ready host guidance in the Repo Control User Guide. The repository cannot guarantee that a new ChatGPT or other-vendor chat consumed project instructions.
